## Q1-01. 문자열 상수와 문자열 변수의 차이는? `★`

> 원 질문: `char* arr1 = "ABC";` 와 `char arr2[4] = "ABC";` 는 뭐가 다른가?

**30초 답변**
> `char* arr1 = "ABC"`는 읽기 전용 메모리에 있는 **문자열 리터럴의 주소**를 포인터가 가리키는 것이라, `arr1[0] = 'B'` 같은 수정은 정의되지 않은 동작이고 대부분 런타임에 크래시가 납니다. 반면 `char arr2[4] = "ABC"`는 리터럴의 **내용을 스택 배열에 복사**한 것이라 독립된 변수이고 자유롭게 수정할 수 있습니다. 핵심은 "포인터가 상수 영역을 가리키느냐" vs "배열이 값을 복사해 갖느냐"입니다.

**상세 설명**
- `char* arr1 = "ABC";` — 문자열 리터럴 `"ABC"`는 컴파일 시점에 실행 파일의 **읽기 전용 데이터 영역(.rodata)**에 박힌다. `arr1`은 그 시작 주소를 담은 포인터일 뿐이다. 포인터 자체(4/8바이트)는 스택에 있지만, 가리키는 대상은 상수 영역이다.
- `char arr2[4] = "ABC";` — 스택에 4바이트 배열을 잡고, 리터럴의 내용을 `strcpy`처럼 **복사**해 넣는다. `arr2`는 그 배열 자체다.
- 그래서 같은 리터럴을 두 번 써도 `char* a = "ABC"; char* b = "ABC";` 는 컴파일러가 같은 주소를 재사용할 수 있어 `a == b`가 참일 수 있다. 반면 배열 두 개는 항상 다른 주소다.
- C++11부터는 `char* p = "ABC";` 자체가 컴파일 에러다(문자열 리터럴 타입이 `const char[N]`이라 `const`를 떼는 변환이 금지됨). 반드시 `const char* p = "ABC";`로 써야 한다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 9번 — `char*` 수동 메모리관리를 `std::string`으로 전환한 실습. "왜 `std::string`을 쓰는가"의 출발점이 바로 이 문제다.
- `c_핵심정리.md` 4번(1차원 배열 & 문자열 직접 처리), 5번(포인터 기초).

**꼬리질문**
- **Q.** `sizeof(arr1)`과 `sizeof(arr2)`는 각각 얼마인가?
  **A.** `arr1`은 포인터라서 포인터 크기(64비트 환경에서 8). `arr2`는 배열이라서 `4`(널 문자 포함). 이게 "배열은 포인터가 아니다"의 대표적 증거다 → Q1-15 참고.
- **Q.** `arr2`의 크기를 왜 4로 잡았나?
  **A.** `'A' 'B' 'C'` 3글자 + 문자열 끝을 나타내는 널 문자 `'\0'` 1바이트. C 문자열은 길이를 따로 저장하지 않고 널 문자로 끝을 판단하기 때문에 반드시 +1이 필요하다.
- **Q.** 함수 인자로 배열을 넘기면 어떻게 되나?
  **A.** 배열은 함수 인자로 전달될 때 **첫 원소의 포인터로 붕괴(decay)**한다. 그래서 함수 안에서 `sizeof`를 찍으면 배열 전체 크기가 아니라 포인터 크기가 나온다. 크기가 필요하면 별도 인자로 넘겨야 한다.

**함정**
"문자열 상수는 상수 영역에 있다"까지만 말하고 끝내면 약하다. **"그래서 수정하면 크래시가 난다"**는 실제 결과까지 붙여야 이해한 것으로 들린다.

## Q1-02. `malloc`/`free`와 `new`/`delete`의 차이는? `★`

**30초 답변**
> `malloc`/`free`는 C 표준 **라이브러리 함수**고 `new`/`delete`는 C++ **연산자**입니다. 가장 중요한 실질적 차이는 `new`가 메모리 할당에 더해 **생성자를 호출**하고 `delete`가 **소멸자를 호출**한다는 점입니다. 또 `malloc`은 `void*`를 반환해서 캐스팅과 `sizeof` 계산이 필요하지만 `new`는 타입을 알기 때문에 크기 계산과 캐스팅이 필요 없고, 실패 시 `malloc`은 `NULL`을 반환하는 반면 `new`는 `std::bad_alloc` 예외를 던집니다.

**상세 설명**

| 항목 | `malloc`/`free` | `new`/`delete` |
|---|---|---|
| 정체 | 라이브러리 함수 | 언어 차원의 연산자 |
| 생성자/소멸자 | **호출 안 함** | **호출함** |
| 반환 타입 | `void*` (캐스팅 필요) | 해당 타입 포인터 |
| 크기 지정 | `sizeof` 직접 계산 | 자동 |
| 실패 시 | `NULL` 반환 | `std::bad_alloc` 예외 |
| 재할당 | `realloc` 가능 | 불가 |
| 오버로딩 | 불가 | 클래스별 `operator new` 오버로딩 가능 |

```cpp
int* a = (int*)malloc(sizeof(int) * 10);   // 캐스팅 + 크기 계산 필요
free(a);

int* b = new int[10];                       // 타입만 알려주면 끝
delete[] b;                                 // 배열은 반드시 delete[]
```

**꼬리질문**
- **Q.** `delete`와 `delete[]`를 섞어 쓰면 어떻게 되나?
  **A.** 정의되지 않은 동작이다. `new[]`로 만든 배열을 `delete`로 지우면 첫 원소의 소멸자만 호출되고 나머지는 소멸자가 안 불려서 자원 누수가 생기며, 힙 관리 정보가 깨져 크래시가 나기도 한다. **`new[]`↔`delete[]`, `new`↔`delete`는 반드시 짝을 맞춰야 한다.**
- **Q.** `malloc`으로 할당한 걸 `delete`로 해제해도 되나?
  **A.** 안 된다. 서로 다른 메모리 관리 체계를 쓸 수 있어서 정의되지 않은 동작이다. 반드시 `malloc`↔`free`, `new`↔`delete`로 짝을 맞춘다.
- **Q.** 클래스 객체를 `malloc`으로 만들면 무슨 일이 생기나?
  **A.** 메모리만 잡히고 **생성자가 안 불려서** 멤버가 초기화되지 않은 쓰레기 값 상태가 된다. 가상 함수가 있는 클래스라면 vtable 포인터도 세팅되지 않아 가상 함수 호출 시 크래시가 난다 → Q1-08 참고.
- **Q.** `new`가 실패했는지 `NULL` 체크로 확인하면 되나?
  **A.** 안 된다. 기본 `new`는 실패 시 `NULL`을 반환하지 않고 `std::bad_alloc`을 던지므로 `try/catch`로 잡아야 한다. `NULL` 반환을 원하면 `new(std::nothrow) int;`를 쓴다.

**함정**
"`new`는 생성자를 호출한다"가 이 질문의 **핵심 득점 포인트**다. 캐스팅/크기 얘기만 하면 C 지식만 보여주는 셈이다.

## Q1-03. 얕은 복사와 깊은 복사의 차이는? `★`

**30초 답변**
> 얕은 복사는 멤버 값을 그대로 복사하기 때문에 포인터 멤버가 있으면 **두 객체가 같은 메모리를 가리키게** 됩니다. 이 상태에서 두 객체가 소멸하면 같은 메모리를 두 번 `delete` 하게 되어(이중 해제) 크래시가 납니다. 깊은 복사는 복사 생성자에서 **새로 메모리를 할당하고 내용을 복사**해서 각 객체가 독립된 자원을 갖게 합니다. C++ 기본 복사 생성자는 얕은 복사이므로, 포인터 멤버가 있으면 직접 구현해야 합니다.

**상세 설명**
```cpp
class Buf {
    char* data;
public:
    Buf(const char* s) { data = new char[strlen(s)+1]; strcpy(data, s); }
    ~Buf() { delete[] data; }

    // 깊은 복사 — 이걸 안 만들면 컴파일러가 얕은 복사본을 만들어준다
    Buf(const Buf& o) {
        data = new char[strlen(o.data)+1];   // 새 메모리 확보가 핵심
        strcpy(data, o.data);
    }
};
```
얕은 복사에서 생기는 문제 3종:
1. **이중 해제(double free)** — 두 소멸자가 같은 주소를 `delete`
2. **댕글링 포인터** — 한쪽이 먼저 소멸하면 다른 쪽 포인터가 죽은 메모리를 가리킴
3. **의도치 않은 값 공유** — 한쪽을 수정하면 다른 쪽도 바뀜

**내 프로젝트 연결**
- `cpp_핵심정리.md` 3번 — 깊은 복사와 **Rule of Three/Five/Zero**를 정리한 항목. 여기까지 답하면 확실히 앞서간다.
- `cpp_핵심정리.md` 9번 — `char*` 수동 관리를 `std::string`으로 바꾼 실습(그러면 깊은 복사를 직접 안 짜도 된다).

**꼬리질문**
- **Q.** Rule of Three가 뭔가?
  **A.** 소멸자, 복사 생성자, 복사 대입 연산자 **셋 중 하나라도 직접 구현해야 한다면 나머지 둘도 구현해야 한다**는 규칙. 자원을 직접 관리하는 클래스라는 신호이기 때문이다. C++11부터는 이동 생성자/이동 대입까지 더해 **Rule of Five**, 아예 `std::string`·스마트 포인터를 써서 하나도 안 짜는 게 최선이라는 **Rule of Zero**로 확장됐다.
- **Q.** 복사 대입 연산자에서 주의할 점은?
  **A.** **자기 대입 가드**가 필요하다. `a = a;`일 때 기존 자원을 먼저 `delete`해버리면 복사할 원본까지 날아간다. `if (this == &other) return *this;`를 앞에 둔다.
- **Q.** 복사를 아예 막고 싶으면?
  **A.** `Buf(const Buf&) = delete;` 로 삭제 선언한다(C++11). 예전엔 `private`에 선언만 하고 정의하지 않는 방식을 썼다.

**함정**
> 실제 내 코드에서 이 문제를 겪었다 — `cpp_핵심정리.md` 하단 "고쳐볼 만한 부분"에 **`mystring::operator=`에 자기 대입 가드가 없다**는 이슈를 직접 기록해뒀다. 면접에서 "직접 짜보다 발견한 문제"로 말하면 설득력이 크게 오른다.

## Q1-04. 오버로딩이란? `★`

**30초 답변**
> 같은 이름의 함수를 **매개변수의 타입이나 개수를 다르게** 해서 여러 개 정의하는 것입니다. 컴파일러가 호출 시점의 인자를 보고 어느 함수를 부를지 **컴파일 타임에** 결정합니다. 정적 바인딩의 대표적인 예입니다.

**상세 설명**
```cpp
int  Add(int a, int b)          { return a + b; }
double Add(double a, double b)  { return a + b; }   // 타입 다름 - OK
int  Add(int a, int b, int c)   { return a+b+c; }   // 개수 다름 - OK
// double Add(int a, int b);                        // 반환형만 다름 - 컴파일 에러
```
- 구분 기준: **매개변수의 타입 / 개수 / 순서**. **반환 타입만 다른 것은 오버로딩이 아니다.**
- C++는 내부적으로 **네임 맹글링(Name Mangling)**으로 함수 이름에 파라미터 타입 정보를 붙여 서로 다른 심볼로 만들기 때문에 가능하다. C는 맹글링이 없어서 오버로딩을 지원하지 않는다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 1번 — 함수 오버로딩 실습.
- `unity_핵심정리.md` 12-8 — C# 쪽에서 `params` 키워드로 배열 종류별 `ArrDisplay`를 오버로딩한 사례.

**꼬리질문**
- **Q.** C에서는 왜 오버로딩이 안 되나?
  **A.** C 컴파일러는 함수 이름을 그대로 심볼로 쓴다(맹글링 없음). 같은 이름이면 링크 단계에서 중복 심볼 에러가 난다. 그래서 C++에서 C 함수를 쓸 때 `extern "C"`를 붙여 맹글링을 끄는 것이다.
- **Q.** `extern "C"`를 실제로 써본 적 있나?
  **A.** 있다 — `unity_핵심정리.md` 12-1번, Unity에서 C++ 네이티브 DLL을 P/Invoke로 부를 때 C# 쪽 `DllImport`가 심볼을 찾을 수 있도록 C++ 함수에 `extern "C"`를 붙였다.

## Q1-05. 오버라이딩이란? `★`

**30초 답변**
> 부모 클래스의 `virtual` 함수를 자식 클래스에서 **같은 시그니처로 재정의**하는 것입니다. 부모 타입 포인터로 자식 객체를 가리켜도 **실행 시점에 자식의 함수가 호출**되는데, 이게 다형성의 핵심이고 동적 바인딩으로 동작합니다.

**상세 설명**
```cpp
class Base   { public: virtual void Hi() { cout << "Base"; } virtual ~Base() {} };
class Derived: public Base { public: void Hi() override { cout << "Derived"; } };

Base* p = new Derived();
p->Hi();      // "Derived"  <- virtual 덕분에 자식 것이 불림
delete p;     // 가상 소멸자 덕분에 Derived 소멸자도 불림
```
- `virtual`이 **없으면** `p->Hi()`는 "Base"를 출력한다. 이건 오버라이딩이 아니라 **이름 가리기(name hiding)**다.
- `override` 키워드(C++11)를 붙이면 "정말 부모에 이 시그니처의 가상 함수가 있는지" 컴파일러가 검사해준다. 오타로 인한 조용한 버그를 막아준다.

**오버로딩 vs 오버라이딩 한 줄 비교**

| | 오버로딩(Overloading) | 오버라이딩(Overriding) |
|---|---|---|
| 관계 | 같은 클래스 안 | 상속 관계(부모↔자식) |
| 시그니처 | **달라야** 함 | **같아야** 함 |
| 결정 시점 | 컴파일 타임(정적) | 런타임(동적) |
| 목적 | 편의성 | 다형성 |

**내 프로젝트 연결**
- `cpp_핵심정리.md` 6번(다형성/순수가상함수), 5번(상속과 protected).
- `unity_핵심정리.md` 5-12 — C#의 `virtual`/`override` 다형성 실습.
- `unity_핵심정리.md` 11-1 — XR Toolkit에서 부모의 `OnSelectEntered`를 오버라이드하며 구/신 API 버전이 나란히 남아있는 실사례.

**꼬리질문**
- **Q.** C#에서는 오버라이딩 문법이 어떻게 다른가?
  **A.** C#은 자식에서도 명시적으로 `override` 키워드를 **반드시** 써야 한다(C++는 선택). 또 일부러 가리려면 `new` 키워드를 붙여야 경고가 사라진다. 실수 방지를 언어 차원에서 강제한 셈이다.
- **Q.** 왜 `cpp_핵심정리`에서 `override` 미사용을 이슈로 적었나?
  **A.** 내 `OOP` 프로젝트 코드에서 재정의는 했는데 `override`를 안 붙인 곳들이 있었다. 컴파일은 되지만 시그니처가 살짝 어긋나면 오버라이딩이 아니라 새 함수가 되어버리는데 컴파일러가 잡아주지 못한다. 그래서 개선점으로 기록해뒀다.

## Q1-06. 순수 가상 함수와 추상 클래스란? `★`

**30초 답변**
> 순수 가상 함수는 `virtual int GetPay() = 0;` 처럼 **선언만 있고 본문이 없는** 가상 함수입니다. 순수 가상 함수를 하나라도 가진 클래스는 **추상 클래스**가 되어 그 자체로는 객체를 만들 수 없고, 상속받은 자식이 전부 구현해야 비로소 객체를 만들 수 있습니다. "이 인터페이스는 반드시 구현하라"고 강제하는 장치입니다.

**상세 설명**
```cpp
class Shape {
public:
    virtual double Area() = 0;      // 순수 가상 함수 -> Shape는 추상 클래스
    virtual ~Shape() {}             // 추상 클래스일수록 가상 소멸자 필수
};
// Shape s;                          // 컴파일 에러: 추상 클래스는 인스턴스화 불가
class Circle : public Shape {
public:
    double Area() override { return 3.14 * r * r; }   // 구현해야 객체 생성 가능
private: double r = 1.0;
};
```
- 순수 가상 함수도 **본문을 가질 수 있다**(기본 동작 제공). 다만 여전히 자식이 재정의해야 한다.
- 모든 멤버가 순수 가상 함수이고 데이터 멤버가 없으면 사실상 **인터페이스** 역할을 한다. C++엔 `interface` 키워드가 없어서 이렇게 표현한다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 6번 — 다형성과 순수가상함수/추상클래스.
- `unity_핵심정리.md` 5-11 — C#에서 추상 클래스 vs 인터페이스를 비교 정리한 항목.

**꼬리질문**
- **Q.** 추상 클래스와 인터페이스의 차이는? (매우 자주 나옴)
  **A.** 추상 클래스는 **구현된 멤버와 필드를 가질 수 있고** 공통 상태/기본 동작을 물려주는 게 목적이라 "is-a" 관계에 쓴다. 인터페이스는 **구현 없이 규약만** 정의하고 다중 구현이 가능해서, 상속 계층이 전혀 다른 클래스들에 같은 기능을 붙일 때("can-do" 관계) 쓴다. C++은 다중 상속이 되므로 순수 가상 클래스로 둘 다 표현하지만, C#/Java는 클래스 다중 상속이 안 되기 때문에 이 구분이 훨씬 중요하다.
- **Q.** 그럼 언제 추상 클래스를 쓰고 언제 인터페이스를 쓰나?
  **A.** 자식들이 **공유할 코드나 상태가 있으면** 추상 클래스, 서로 무관한 타입에 **동일한 능력만 부여**하고 싶으면 인터페이스. 실무에선 "추상 클래스로 기본 구현 + 인터페이스로 규약"을 같이 쓰는 경우도 많다.

## Q1-07. 가상 소멸자는 왜 필요한가?

**30초 답변**
> 부모 타입 포인터로 자식 객체를 `delete` 할 때, 소멸자가 `virtual`이 아니면 **부모 소멸자만 호출되고 자식 소멸자는 호출되지 않습니다.** 자식이 동적 할당한 자원이 있다면 그대로 누수됩니다. 그래서 **다형적으로 사용될 기반 클래스의 소멸자는 반드시 `virtual`로 선언**해야 합니다.

**상세 설명**
```cpp
class Base    { public: ~Base()  { cout << "~Base"; } };            // virtual 없음!
class Derived : public Base {
    int* buf;
public: Derived() { buf = new int[100]; }
        ~Derived() { delete[] buf; cout << "~Derived"; }
};
Base* p = new Derived();
delete p;   // "~Base"만 출력 -> buf 100개 int 누수 + 정의되지 않은 동작
```
`~Base()`에 `virtual`을 붙이면 `~Derived()` → `~Base()` 순서로 정상 호출된다.

**내 프로젝트 연결**
> 이건 내가 **직접 코드 리뷰하다 발견한 실제 이슈**다. `cpp_핵심정리.md` 7번 항목이 통째로 이 주제이고, 하단 "고쳐볼 만한 부분"에도 기록해뒀다 — `OOP` 프로젝트의 `Account` 클래스에 가상 소멸자가 없는데 `Container<T>`가 **기반 클래스 포인터로 `delete`를 하고 있었다.** 정확히 이 시나리오다.

**꼬리질문**
- **Q.** 그럼 모든 클래스에 가상 소멸자를 붙이면 되나?
  **A.** 아니다. `virtual`을 붙이면 vtable 포인터(8바이트)가 객체마다 추가되어 크기가 커지고, 작은 값 타입 클래스에는 부담이 된다. **"이 클래스가 상속되어 기반 포인터로 삭제될 가능성이 있는가"**가 기준이다. 상속을 의도하지 않으면 `final`을 붙이는 것도 방법이다.
- **Q.** 소멸자를 순수 가상으로 만들 수 있나?
  **A.** 가능하지만 **반드시 본문을 정의해야 한다**(`virtual ~Base() = 0;` + `Base::~Base() {}`). 자식 소멸자가 항상 부모 소멸자를 호출하기 때문이다. 다른 순수 가상 함수가 없는데 추상 클래스로 만들고 싶을 때 쓰는 기법이다.
- **Q.** C#에도 같은 문제가 있나?
  **A.** 없다. C#은 GC가 실제 타입을 알고 정리하므로 이 문제가 발생하지 않는다. 대신 `IDisposable`/`Dispose` 패턴에서 비슷한 "자원 해제 책임" 이슈를 다루며, `cpp_핵심정리` 21번의 RAII 락과 C#의 `using` 블록이 같은 발상이다.

## Q1-08. 가상 함수 테이블(vtable)은 어떻게 동작하나?

**30초 답변**
> 가상 함수를 가진 클래스는 컴파일러가 **함수 포인터 배열인 vtable**을 클래스마다 하나씩 만들고, 각 객체에는 그 테이블을 가리키는 **vptr(가상 함수 테이블 포인터)**을 숨겨서 넣습니다. 가상 함수를 호출하면 객체의 vptr을 따라가 테이블에서 실제 함수 주소를 찾아 호출하기 때문에, 어떤 타입의 객체냐에 따라 런타임에 다른 함수가 불립니다. 대신 한 단계 간접 참조 비용이 생깁니다.

**상세 설명**
```
Derived 객체 메모리
┌─────────────┐        Derived vtable
│ vptr        │──────► [0] Derived::Hi
│ 멤버 변수들 │        [1] Derived::~Derived
└─────────────┘
```
- vtable은 **클래스당 1개**(객체마다가 아님). 객체는 vptr 하나(보통 8바이트)만 더 갖는다.
- 그래서 가상 함수가 하나라도 있으면 `sizeof(클래스)`가 포인터 크기만큼 늘어난다. 면접에서 종종 `sizeof`로 물어본다.
- 생성자에서 가상 함수를 호출하면 **자식 버전이 아니라 현재 생성 중인 클래스 버전**이 불린다. 생성 순서상 부모 생성자 시점엔 vptr이 아직 부모 것을 가리키기 때문이다. → 자주 나오는 함정 질문.

**꼬리질문**
- **Q.** 가상 함수 호출이 일반 함수보다 느린 이유는?
  **A.** ① vptr → vtable → 함수 주소로 **두 번의 메모리 간접 참조**가 필요하고, ② 호출 대상이 런타임에 정해져서 **컴파일러가 인라인 최적화를 못 한다.** 다만 요즘 CPU는 분기 예측이 좋아서 실측 차이는 크지 않은 경우가 많다. 게임에선 매 프레임 수만 번 호출되는 타이트 루프에서만 실제로 문제가 된다.
- **Q.** 생성자/소멸자에서 가상 함수를 호출하면 왜 위험한가?
  **A.** 생성자에서는 자식 부분이 아직 초기화되지 않았고 vptr도 부모를 가리키므로 **자식 오버라이드가 불리지 않는다.** 소멸자도 마찬가지로 자식이 이미 소멸된 상태다. 초기화 로직을 가상 함수로 빼는 설계는 피해야 한다.
- **Q.** `malloc`으로 만든 객체에서 가상 함수를 부르면?
  **A.** 생성자가 안 불려서 **vptr이 세팅되지 않은 쓰레기 값**이다. 호출 즉시 크래시 → Q1-02와 연결되는 질문.

## Q1-09. 정적 바인딩과 동적 바인딩의 차이는? `★`

**30초 답변**
> 정적 바인딩은 **컴파일 타임에** 어떤 함수를 호출할지 결정되는 것이고, 동적 바인딩은 **런타임에** 객체의 실제 타입을 보고 결정되는 것입니다. C++에서는 `virtual`을 붙인 함수만 동적 바인딩되고 나머지는 전부 정적 바인딩입니다. 다형성은 동적 바인딩 덕분에 성립합니다.

**상세 설명**
- **정적(이른) 바인딩**: 일반 함수 호출, 함수 오버로딩, 템플릿 인스턴스화. 빠르고 인라인 최적화가 가능하다.
- **동적(늦은) 바인딩**: `virtual` 함수 호출. vtable을 경유한다(Q1-08).
```cpp
Base* p = GetSomething();   // 어떤 자식이 올지 컴파일러는 모른다
p->Hi();                    // virtual이면 런타임 결정, 아니면 무조건 Base::Hi
```
- 자바는 기본이 동적 바인딩(모든 메서드가 가상)이고, C++/C#은 **기본이 정적**이라 명시적으로 `virtual`을 붙여야 한다. "성능을 기본값으로 삼는" 언어 철학의 차이다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 6번(다형성), 8번(템플릿 — 이쪽은 정적 다형성).

**꼬리질문**
- **Q.** 템플릿도 다형성인가?
  **A.** 맞다. **컴파일 타임 다형성(정적 다형성)**이라고 부른다. 런타임 비용이 없다는 장점이 있지만 코드가 타입마다 복제되어 바이너리가 커진다. 반대로 가상 함수는 **런타임 다형성**이다.
- **Q.** 어느 쪽이 더 좋은가?
  **A.** 상황에 따라 다르다. 타입이 컴파일 시점에 정해지고 성능이 중요하면 템플릿, 런타임에 어떤 타입이 올지 모르고 하나의 컨테이너에 여러 타입을 담아야 하면 가상 함수를 쓴다.

## Q1-10. 객체지향의 4대 특성은?

**30초 답변**
> **추상화, 캡슐화, 상속, 다형성**입니다. 추상화는 복잡한 대상에서 필요한 특징만 뽑아내는 것, 캡슐화는 데이터와 그 데이터를 다루는 함수를 묶고 내부 구현을 숨기는 것, 상속은 기존 클래스의 특성을 물려받아 재사용하는 것, 다형성은 같은 인터페이스로 서로 다른 동작을 하게 하는 것입니다.

**상세 설명**

| 특성 | 핵심 | 내 코드 예시 |
|---|---|---|
| **추상화** | 필요한 속성/기능만 정의 | `Shape::Area()` 순수 가상 함수 |
| **캡슐화** | 데이터 은닉 + 접근자 제공 | `private` 필드 + 프로퍼티(`unity_핵심정리` 5-6) |
| **상속** | 코드 재사용 + 계층 표현 | `Item` → `Equipment` → `Weapon` (`unity_핵심정리` 5-22) |
| **다형성** | 같은 호출, 다른 동작 | `virtual`/`override` (`unity_핵심정리` 5-12) |

- **캡슐화 ≠ 정보 은닉**을 구분하면 좋다. 캡슐화는 "묶는 것", 정보 은닉은 "감추는 것"으로, 캡슐화의 결과로 은닉이 가능해진다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 12번 — 종합 대표 예제인 OOP 계좌관리 시스템(`Account` 상속 계층 + `Container<T>` 템플릿 + `AccManager`)이 4대 특성을 한 번에 보여준다. 면접에서 예시로 이걸 들면 좋다.

**꼬리질문**
- **Q.** 상속보다 컴포지션을 선호하라는 말이 있는데 왜인가?
  **A.** 상속은 부모-자식이 강하게 결합되어 부모 변경이 자식 전부에 파급되고(취약한 기반 클래스 문제), 계층이 깊어지면 이해하기 어려워진다. 컴포지션은 필요한 기능을 객체로 **가지고 있기만** 해서 결합도가 낮고 런타임 교체도 가능하다. Unity의 **컴포넌트 패턴이 정확히 이 철학**이다 — 상속 계층 대신 `GameObject`에 필요한 `MonoBehaviour`를 붙인다.
  → `cpp_핵심정리.md` 10번(컴포지션 기반 책임 분리 설계)에 직접 실습한 내용이 있다.

## Q1-11. 객체지향 설계 5원칙(SOLID)은?

**30초 답변**
> **SRP(단일 책임)**, **OCP(개방-폐쇄)**, **LSP(리스코프 치환)**, **ISP(인터페이스 분리)**, **DIP(의존 역전)** 입니다. 한 클래스는 하나의 책임만 갖고, 확장에는 열려 있되 수정에는 닫혀 있어야 하며, 자식은 부모를 대체할 수 있어야 하고, 인터페이스는 잘게 나누며, 구체 클래스가 아니라 추상에 의존하라는 원칙입니다.

**상세 설명**

| 원칙 | 의미 | 위반하면 |
|---|---|---|
| **S**RP | 클래스는 변경 이유가 하나여야 | 한 곳 고치면 무관한 기능이 깨짐 |
| **O**CP | 확장은 열고 수정은 닫고 | 기능 추가할 때마다 기존 코드 수정 |
| **L**SP | 자식은 부모 자리에 들어갈 수 있어야 | 다형성이 깨지고 타입 체크 분기 남발 |
| **I**SP | 안 쓰는 메서드를 강요하지 말 것 | 빈 구현이 잔뜩 생김 |
| **D**IP | 추상에 의존, 구체에 의존 X | 모듈 교체 불가, 테스트 어려움 |

**내 프로젝트 연결**
- **SRP** — `winapi_핵심정리.md` 10번(엔진/윈도우 책임 분리 설계), `unity_핵심정리.md` 13-3(FSM에서 상태 판단과 애니메이션 재생 책임 분리).
- **OCP** — `unity_핵심정리.md` 13-1, FSM을 `if/else` 절차형에서 State 패턴으로 바꾼 것이 정확히 OCP 개선이다. 새 상태를 추가할 때 기존 코드를 안 건드려도 된다.
- **DIP** — `unity_핵심정리.md` 5-10(인터페이스 실습).

**꼬리질문**
- **Q.** 5개 중 실제 프로젝트에 적용해본 걸 하나만 설명해보라.
  **A.** OCP. FSM 프로젝트에서 적을 `if (state == Idle) ... else if (state == Patrol) ...` 식으로 짰다가, 상태가 늘어날 때마다 이 분기문을 계속 고쳐야 하는 게 문제였다. State 패턴으로 각 상태를 클래스로 분리하니 새 상태는 클래스만 추가하면 되고 기존 코드는 안 건드려도 됐다. 나중에 Unity `StateMachineBehaviour`로 한 번 더 바꿔서 세 가지 방식을 비교해봤다.

## Q1-12. 객체지향과 절차지향의 차이와 장단점은?

**30초 답변**
> 절차지향은 데이터와 함수가 분리된 상태로 **순서대로 실행되는 흐름 중심** 설계이고, 객체지향은 데이터와 그 데이터를 다루는 함수를 **객체 단위로 묶어** 객체 간 상호작용으로 문제를 푸는 설계입니다. 절차지향은 단순하고 실행이 빠르지만 규모가 커지면 결합도가 높아져 수정이 어렵고, 객체지향은 재사용성과 유지보수성이 좋지만 설계 부담과 약간의 런타임 오버헤드가 있습니다.

**상세 설명**

| | 절차지향 | 객체지향 |
|---|---|---|
| 중심 | 함수(프로시저)와 실행 순서 | 객체와 메시지 |
| 데이터 | 함수 밖에 노출 | 객체 안에 은닉 |
| 장점 | 단순, 빠름, 작은 프로그램에 적합 | 재사용/확장/유지보수 유리 |
| 단점 | 결합도 높음, 규모 커지면 수정 지옥 | 설계 비용, 가상 함수 오버헤드 |
| 대표 언어 | C, 포트란 | C++, C#, Java |

**내 프로젝트 연결**
> 이 질문은 내 학습 경로 자체로 답할 수 있다. `c_핵심정리.md` 12번의 미로찾기는 전역 배열 + 함수들로 짠 **전형적인 절차지향**이었고, `cpp_핵심정리.md` 12번의 계좌관리 시스템은 같은 규모를 **객체 단위로 재설계**한 것이다. 특히 `unity_핵심정리.md` 13-1(FSM 3단계 진화)은 **같은 문제를 절차형 → 객체지향 State 패턴으로 직접 다시 짠 비교 사례**라 이 질문의 실증 자료가 된다.

**꼬리질문**
- **Q.** 객체지향이 항상 좋은가?
  **A.** 아니다. 게임 클라이언트에서 매 프레임 수천 개 오브젝트를 순회하는 코드는 객체마다 흩어진 메모리를 따라다니느라 **캐시 미스**가 심해진다. 그래서 요즘은 데이터를 배열로 모아 순차 처리하는 **DOD(데이터 지향 설계)**가 주목받고, Unity의 **DOTS/ECS**가 그 방향이다. "OOP는 유지보수, DOD는 성능"이라는 트레이드오프로 답하면 좋다.
- **Q.** 대표적인 절차지향/객체지향 언어는?
  **A.** 절차지향은 C, 객체지향은 C++·C#·Java. 다만 C++는 절차지향도 가능한 **멀티 패러다임 언어**이고, C#도 함수형 요소(LINQ, 람다)를 많이 흡수했다.

## Q1-13. 클래스와 객체(오브젝트)의 차이는?

**30초 답변**
> 클래스는 객체를 만들기 위한 **설계도(틀)**이고, 객체는 그 설계도로 실제 메모리에 만들어진 **실체(인스턴스)**입니다. 붕어빵 틀이 클래스, 구워진 붕어빵이 객체입니다. 클래스는 컴파일 타임의 개념이고 객체는 런타임에 메모리를 차지합니다.

**상세 설명**
- 클래스: 어떤 데이터(멤버 변수)와 어떤 기능(멤버 함수)을 가질지 정의만 한다. 메모리를 차지하지 않는다(정적 멤버 제외).
- 객체/인스턴스: 클래스를 바탕으로 실제 메모리가 할당된 것. 같은 클래스로 만든 객체 100개는 **각자 다른 멤버 변수 값**을 갖는다.
- **인스턴스**와 **객체**는 거의 같은 말이지만, "A는 B 클래스의 인스턴스다"처럼 **관계를 강조할 때 인스턴스**를 쓴다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-7 — **`MonoBehaviour`를 `new`로 생성하면 안 되는 이유**를 직접 실험한 코드. "클래스가 있다고 아무렇게나 객체를 만들 수 있는 게 아니다"는 걸 보여주는 좋은 사례라서 이 질문의 꼬리질문으로 자연스럽게 이어붙일 수 있다.

**꼬리질문**
- **Q.** Unity에서 `MonoBehaviour`를 `new`로 만들면 왜 안 되나?
  **A.** `MonoBehaviour`는 C# 객체이면서 동시에 엔진 내부의 네이티브 객체와 짝을 이루고 있다. `new`로 만들면 C# 쪽 껍데기만 생기고 네이티브 쪽이 없어서 `transform` 접근 등이 실패하고, `Awake`/`Start`/`Update` 같은 생명주기 콜백도 전혀 불리지 않는다. 반드시 `AddComponent<T>()`나 `Instantiate`로 만들어야 한다. → `unity_핵심정리.md` 5-7에서 직접 실험해봤다.
- **Q.** 정적(static) 멤버는 어디에 속하나?
  **A.** 객체가 아니라 **클래스에 속한다.** 객체를 몇 개 만들든 하나만 존재하고 데이터 영역에 할당된다 → Q1-18, Q1-20 참고.

## Q1-14. C++에서 `struct`와 `class`의 차이는?

**30초 답변**
> C++에서는 **기본 접근 지정자만 다릅니다.** `struct`는 기본이 `public`, `class`는 기본이 `private`이고, 상속할 때의 기본 접근 지정자도 각각 `public`/`private`입니다. 그 외 멤버 함수, 생성자, 상속, 다형성 전부 동일하게 쓸 수 있습니다. 관례적으로 단순 데이터 묶음에는 `struct`, 캡슐화된 객체에는 `class`를 씁니다.

**상세 설명**
```cpp
struct S { int x; };          // x는 public
class  C { int x; };          // x는 private
```
- C에서의 `struct`는 **함수를 가질 수 없는 순수 데이터 묶음**이지만, C++의 `struct`는 클래스와 기능이 같다. C 호환성 때문에 남아있는 것.
- **C#은 완전히 다르다.** C#의 `struct`는 **값 타입**(스택 할당, 복사 시 값 전체 복사), `class`는 **참조 타입**(힙 할당, 참조 복사)으로 근본이 다르다. 면접에서 "C++ 기준인가요, C# 기준인가요?"를 되물으면 오히려 좋은 인상을 준다. → `02_CSharp.md` Q2-02 참고.

**꼬리질문**
- **Q.** 그럼 언제 `struct`를 쓰나?
  **A.** C++에선 관례상 ① 공개 데이터만 있는 POD(Plain Old Data), ② 템플릿 메타프로그래밍의 타입 트레잇, ③ 콜백/함수 객체처럼 상태가 없는 작은 타입에 쓴다.
- **Q.** C#에서 `struct`를 쓰면 좋은 경우는?
  **A.** 크기가 작고(보통 16바이트 이하) 불변이며 수명이 짧은 값에 쓴다. Unity의 `Vector3`, `Quaternion`, `Color`가 전부 `struct`인데, **힙 할당을 피해서 GC 부담을 줄이기 위해서**다. 게임에서 매 프레임 수만 개씩 만들어지는 타입이라 이게 중요하다.

## Q1-15. 포인터와 배열의 차이는?

**30초 답변**
> 배열은 **연속된 메모리 블록 자체**이고, 포인터는 **주소를 담는 변수**입니다. 배열 이름은 대부분의 문맥에서 첫 원소의 주소로 붕괴(decay)해서 포인터처럼 쓸 수 있지만, `sizeof`를 찍어보면 배열은 전체 크기가 나오고 포인터는 주소 크기가 나옵니다. 또 배열 이름은 재대입할 수 없지만 포인터는 다른 곳을 가리키게 바꿀 수 있습니다.

**상세 설명**
```cpp
int arr[10];
int* p = arr;              // 배열 -> 포인터 붕괴 (암묵적)

sizeof(arr);               // 40 (int 10개)
sizeof(p);                 // 8  (64비트 포인터)
// arr = p;                // 컴파일 에러 - 배열 이름은 좌변에 못 옴
p = nullptr;               // OK
```
- `arr[i]`는 컴파일러가 `*(arr + i)`로 바꾼다. 그래서 `arr[i] == i[arr]`도 문법상 성립한다(면접 장난 문제로 나옴).
- **함수 인자로 넘어가면 배열은 무조건 포인터가 된다.** `void f(int a[10])`은 `void f(int* a)`와 완전히 같다. 크기 정보가 사라지므로 별도 인자로 길이를 넘겨야 한다.

**내 프로젝트 연결**
- `c_핵심정리.md` 6번(포인터와 배열의 관계), 7번(함수와 포인터, call by reference), 8번(2차원 배열).

**꼬리질문**
- **Q.** 2차원 배열 `int a[3][4]`와 이중 포인터 `int**`는 같은가?
  **A.** 전혀 다르다. `int a[3][4]`는 12개 `int`가 **한 덩어리로 연속**된 메모리이고, `int**`는 "포인터 배열을 가리키는 포인터"라 행마다 흩어져 있을 수 있다. 그래서 `int**`에 2차원 배열을 그냥 대입할 수 없다. 2차원 배열은 `int (*p)[4]` 형태의 배열 포인터로 받아야 한다.
- **Q.** 게임에서 왜 연속 메모리가 중요한가?
  **A.** **캐시 지역성** 때문이다. CPU는 메모리를 캐시 라인 단위로 통째로 읽어오므로, 연속된 배열을 순차 순회하면 캐시 히트율이 높아 훨씬 빠르다. 반대로 연결 리스트처럼 흩어진 구조는 캐시 미스가 잦다. 이게 Q1-28(vector vs list)에서 "실무에선 대부분 vector가 빠르다"고 하는 이유다.

## Q1-16. 참조자(`&`)와 포인터의 차이는?

**30초 답변**
> 참조자는 이미 존재하는 변수의 **별명**이라 선언과 동시에 반드시 초기화해야 하고, 한 번 묶이면 다른 대상을 가리키도록 바꿀 수 없으며 `null`이 될 수 없습니다. 포인터는 주소를 담는 독립된 변수라 초기화를 미룰 수 있고, 재대입도 되고, `nullptr`도 될 수 있으며 포인터 연산도 가능합니다. 안전성이 필요하면 참조자, 유연성이 필요하면 포인터를 씁니다.

**상세 설명**

| | 참조자 `T&` | 포인터 `T*` |
|---|---|---|
| 초기화 | **필수** | 선택 |
| 재대입 | 불가 | 가능 |
| null | 불가 | 가능 |
| 산술 연산 | 불가 | 가능 |
| 역참조 문법 | 그냥 사용 | `*`, `->` 필요 |
| 메모리 | 보통 별도 공간 없음(최적화됨) | 주소를 담는 실제 변수 |

```cpp
void SwapRef(int& a, int& b) { int t=a; a=b; b=t; }    // 호출: SwapRef(x, y)
void SwapPtr(int* a, int* b) { int t=*a; *a=*b; *b=t; } // 호출: SwapPtr(&x, &y)
```

**내 프로젝트 연결**
- `c_핵심정리.md` 7번 — C에는 참조자가 없어서 **포인터로 call by reference**를 구현한 실습. C++의 참조자가 이걸 문법적으로 편하게 만든 것이다.

**꼬리질문**
- **Q.** 함수 인자로 큰 객체를 넘길 때 어떻게 해야 하나?
  **A.** `const T&`(상수 참조)로 넘긴다. 값 복사 비용을 없애면서 함수가 원본을 수정하지 못하게 막을 수 있다. C++에서 가장 흔한 관용구다.
- **Q.** C#에도 참조자가 있나?
  **A.** C#의 `ref`/`out` 키워드가 비슷한 역할을 한다. 다만 C#은 클래스가 애초에 참조 타입이라 객체를 넘길 땐 이미 참조가 전달되고, `ref`는 주로 **값 타입(struct)을 참조로 넘기거나 참조 자체를 바꾸고 싶을 때** 쓴다.

## Q1-17. `const`는 붙는 위치에 따라 의미가 어떻게 달라지나?

**30초 답변**
> 포인터에서는 `*`을 기준으로 **왼쪽에 있으면 가리키는 대상이 상수**, **오른쪽에 있으면 포인터 자체가 상수**입니다. 멤버 함수 뒤에 붙으면 그 함수가 **멤버 변수를 수정하지 않겠다**는 약속이고, 이 약속 덕분에 `const` 객체에서도 호출할 수 있습니다.

**상세 설명**
```cpp
const int* p1;        // 가리키는 값이 const   -> *p1 = 5;  X   / p1 = &b;  O
int* const p2 = &a;   // 포인터가 const        -> *p2 = 5;  O   / p2 = &b;  X
const int* const p3;  // 둘 다 const

class A {
    int x;
public:
    int  Get() const { return x; }   // 멤버 수정 안 함을 보장
    void Set(int v)  { x = v; }      // const 객체로는 호출 불가
};
```
- 읽는 요령: **오른쪽에서 왼쪽으로** 읽는다. `int* const p2` → "p2는 const인 포인터, int를 가리키는".
- `const` 멤버 함수는 **`const` 객체에서 호출 가능한 유일한 멤버 함수**다. 그래서 게터에는 습관적으로 붙인다.

**꼬리질문**
- **Q.** `const`를 붙이면 성능이 좋아지나?
  **A.** 직접적인 성능 향상보다는 **컴파일러가 최적화할 여지를 준다**는 게 정확하다. 더 큰 가치는 "이 함수는 상태를 안 바꾼다"를 **컴파일 타임에 강제**해서 실수를 막는 것이다.
- **Q.** C#의 `const`와 `readonly`의 차이는?
  **A.** `const`는 컴파일 타임 상수라 선언 시점에 값이 정해져야 하고 호출하는 쪽 코드에 값이 **박제**된다(그래서 라이브러리에서 값을 바꿔도 재컴파일 안 하면 반영 안 됨). `readonly`는 런타임 상수로 생성자에서 값을 정할 수 있다. → `unity_핵심정리.md` 5-13에 `const` vs `static readonly` 비교가 정리돼 있다.

## Q1-18. `static` 키워드의 용도는?

**30초 답변**
> 크게 세 가지입니다. **전역/지역 변수에 붙으면** 프로그램 시작부터 종료까지 유지되는 정적 저장 기간을 갖고, **파일 스코프에서는** 다른 파일에서 접근 못 하는 내부 링크를 만들며, **클래스 멤버에 붙으면** 객체마다가 아니라 **클래스당 하나만 존재**하게 됩니다. 정적 멤버 함수는 `this`가 없어서 인스턴스 없이 호출할 수 있습니다.

**상세 설명**
```cpp
void Counter() {
    static int cnt = 0;   // 함수를 나가도 값이 유지됨. 최초 1회만 초기화
    cnt++;
}

class A {
    static int instanceCount;      // 모든 객체가 공유. 선언일 뿐
public:
    static void Print();           // this 없음 -> 정적 멤버만 접근 가능
};
int A::instanceCount = 0;          // 반드시 클래스 밖에서 정의(메모리 할당)
```
- 정적 멤버 변수는 **데이터 영역**에 할당된다(객체 안이 아님) → Q1-20.
- 정적 멤버 함수는 `this` 포인터가 없어서 **비정적 멤버에 접근할 수 없다.**

**내 프로젝트 연결**
- `cpp_핵심정리.md` 20번 — **싱글톤 패턴**이 정적 멤버의 대표적 활용. 정적 인스턴스 + 정적 접근 함수 구조다.
- `unity_핵심정리.md` 4-1(정적 인스턴스 기반 매니저), 5-8(순수 C# 싱글톤 vs MonoBehaviour 싱글톤), 5-16(제네릭 싱글톤 진화).

**꼬리질문**
- **Q.** 정적 변수의 초기화 순서 문제란?
  **A.** 서로 다른 번역 단위(.cpp 파일)에 있는 전역/정적 객체의 초기화 순서는 **표준이 보장하지 않는다**. A가 B에 의존하는데 B가 나중에 초기화되면 크래시다. 이를 **정적 초기화 순서 실패(SIOF)** 라 하고, 해결책이 함수 안의 지역 정적 변수를 쓰는 **Meyers 싱글톤**이다(첫 호출 시 초기화 보장). → `cpp_핵심정리.md` 22번(지연 초기화의 스레드 안전성)과 연결된다.
- **Q.** C#의 `static`은 C++과 뭐가 다른가?
  **A.** 개념은 비슷하지만 C#엔 정적 생성자(`static A() {}`)가 있어서 최초 접근 시 딱 한 번 실행되는 초기화를 언어가 보장해준다. 또 C#엔 `static class`가 있어서 인스턴스화 자체를 막을 수 있다. → `unity_핵심정리.md` 15-1에서 로컬라이제이션을 인스턴스 방식에서 **정적 클래스 방식**으로 바꾼 사례가 있다.

## Q1-19. `namespace`란 무엇인가?

**30초 답변**
> 이름이 충돌하지 않도록 **식별자를 담는 논리적 영역**을 만드는 기능입니다. 여러 라이브러리를 함께 쓰거나 여러 명이 협업할 때 같은 이름의 함수·클래스가 겹치는 걸 방지합니다. `std::vector`처럼 `::` 로 소속을 지정해 접근합니다.

**상세 설명**
```cpp
namespace Game { class Player {}; }
namespace UI   { class Player {}; }   // 이름은 같지만 소속이 달라 충돌 없음

Game::Player p;
using namespace Game;                  // 편하지만 헤더에서는 쓰지 말 것
```
- **헤더 파일에 `using namespace`를 쓰면 안 된다.** 그 헤더를 포함한 모든 곳에 오염이 전파되어 예상 못 한 충돌을 만든다. `.cpp` 안이나 함수 스코프에서만 쓴다.
- **익명 네임스페이스** `namespace { ... }`는 그 파일에서만 보이게 하는 용도로, C의 `static` 전역을 대체하는 현대적 방식이다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 9번(zombieStudy) — 폴더 위치와 무관하게 `namespace UnityStandardAssets.Effects`로 선언된 스크립트를 발견해 **"서드파티 코드다"라고 판별**한 실제 사례. 네임스페이스가 코드 출처를 식별하는 근거가 된 경우다.
- C#에서는 `unity_핵심정리.md` 전반에서 `using UnityEngine;`, `using UnityEditor;`로 사용.

**꼬리질문**
- **Q.** C#의 네임스페이스와 다른 점은?
  **A.** 개념은 같지만 C#은 `using UnityEditor;`를 파일 상단에 쓰는 게 표준이고 오염 문제가 C++만큼 심각하지 않다(C#엔 헤더 포함 개념이 없어서). 또 C#은 폴더 구조와 네임스페이스를 맞추는 관례가 있다.
- **Q.** Unity에서 에디터 전용 코드는 어떻게 구분하나?
  **A.** `using UnityEditor;`를 쓴 코드는 반드시 `Editor` 폴더에 넣거나 `#if UNITY_EDITOR`로 감싸야 한다. 안 그러면 빌드 시 `UnityEditor` 네임스페이스가 없어서 컴파일 에러가 난다. → `unity_핵심정리.md` 5-27, 22-3 참고. 실제로 `ItemManager`가 런타임 `MonoBehaviour`에서 에디터 전용 `AssetDatabase`를 쓰는 버그를 발견한 적이 있다.

## Q1-20. 메모리 4대 영역을 설명하라 `★`

**30초 답변**
> **코드(텍스트) 영역**에는 실행할 기계어가, **데이터 영역**에는 전역 변수와 정적 변수가, **힙**에는 런타임에 동적 할당한 메모리가, **스택**에는 지역 변수·매개변수·함수 호출 정보가 저장됩니다. 힙은 낮은 주소에서 위로, 스택은 높은 주소에서 아래로 자라며 서로 마주 보고 커집니다.

**상세 설명**
```
높은 주소
┌──────────────┐
│    스택      │  지역변수, 매개변수, 리턴주소   ↓ 아래로 성장
│      ↓       │
│              │
│      ↑       │
│     힙       │  malloc/new로 할당            ↑ 위로 성장
├──────────────┤
│ 데이터(BSS)  │  초기화 안 된 전역/정적
│ 데이터(Data) │  초기화된 전역/정적
├──────────────┤
│ 코드(Text)   │  기계어. 보통 읽기 전용
└──────────────┘
낮은 주소
```
- **문자열 리터럴**은 보통 데이터 영역 중 읽기 전용 구역(.rodata)에 놓인다 → Q1-01과 연결.
- 스택과 힙 사이 빈 공간을 서로 침범하면 **스택 오버플로**나 **힙 오버플로**가 난다.

**내 프로젝트 연결**
- `c_핵심정리.md` 5번(포인터 기초), 10번(구조체).
- `unity_핵심정리.md` 12-2 — Unity 네이티브 플러그인 실습에서 **DLL 전역 상태의 생명주기**를 다뤘는데, 이게 데이터 영역에 사는 변수가 DLL 로드/언로드에 따라 어떻게 되는지의 실전 사례다.

**꼬리질문**
- **Q.** 지역 변수와 멤버 변수 중 스택에 저장되는 건?
  **A.** **지역 변수**다. 멤버 변수는 그 객체가 어디에 있느냐를 따라간다 — 객체가 스택에 있으면 멤버도 스택에, `new`로 힙에 만들었으면 멤버도 힙에 있다.
- **Q.** 각각 언제 해제되나?
  **A.** 지역 변수는 **함수(스코프)를 벗어나는 순간** 자동 해제된다. 멤버 변수는 **객체가 소멸할 때** 함께 사라진다. 힙 메모리는 **명시적으로 `delete`/`free` 할 때까지** 살아있다(C++). C#/Unity에서는 참조가 끊긴 뒤 GC가 수거할 때.
- **Q.** 힙에 저장된 변수의 주소는 어디에 저장되나?
  **A.** 그 주소를 담은 **포인터 변수가 있는 곳**에 저장된다. 지역 포인터면 스택, 멤버 포인터면 객체가 있는 곳. "힙 객체 자체는 힙에, 그걸 가리키는 참조는 보통 스택에"가 표준적인 그림이다.

## Q1-21. 스택과 힙의 차이는? `★`

**30초 답변**
> 스택은 함수 호출과 함께 **자동으로 할당·해제**되는 LIFO 구조의 영역으로, 빠르지만 크기가 제한적이고 컴파일 타임에 크기가 정해져야 합니다. 힙은 **개발자가 직접 할당·해제**하는 영역으로, 크고 유연하며 런타임에 크기를 정할 수 있지만 느리고 관리 실수 시 누수나 단편화가 생깁니다.

**상세 설명**

| | 스택 | 힙 |
|---|---|---|
| 관리 | 컴파일러가 자동 | 개발자가 수동(또는 GC) |
| 속도 | 매우 빠름(포인터 이동만) | 느림(빈 공간 탐색 필요) |
| 크기 | 작음(보통 1~8MB) | 큼(가용 메모리만큼) |
| 크기 결정 | 컴파일 타임 | 런타임 |
| 수명 | 스코프 종료 시 | 명시적 해제까지 |
| 문제 | 스택 오버플로 | 메모리 누수, 단편화 |
| 캐시 | 지역성 좋음(빠름) | 흩어져 있어 미스 잦음 |

- 스택은 **스택 포인터를 증감시키는 것만으로** 할당이 끝나서 거의 공짜다. 힙은 free list를 뒤져 적당한 블록을 찾고 관리 정보를 갱신해야 한다.

**꼬리질문**
- **Q.** 스택 오버플로는 언제 나나?
  **A.** ① **재귀 깊이가 너무 깊을 때**, ② 지역 변수로 거대한 배열(`int arr[10000000]`)을 잡을 때.
  > 내 프로젝트에서 실제로 이걸 의식한 사례가 있다 — `unity_핵심정리.md` 18-5(A* 길찾기)에서 코드 주석에 **"재귀 함수 호출의 제한으로 인해 프로그램이 강제 종료될 수 있다"**고 적고 재귀 대신 코루틴 방식으로 구현했다.
- **Q.** 게임에서 힙 할당을 왜 줄이려 하나?
  **A.** ① 할당 자체가 느리고, ② C#/Unity에서는 힙 쓰레기가 쌓이면 **GC가 돌면서 프레임 스파이크**가 생기고, ③ 힙은 흩어져 있어 캐시 미스가 잦다. 그래서 오브젝트 풀링(`03_Unity.md` Q3-14)과 `struct` 활용(Q1-14)이 중요해진다.

## Q1-22. 왜 모든 데이터를 힙에 저장하지 않는가? `★`

**30초 답변**
> 힙은 할당과 해제 비용이 스택보다 훨씬 비싸기 때문입니다. 스택은 포인터를 옮기는 것만으로 할당이 끝나고 스코프를 벗어나면 자동으로 정리되지만, 힙은 빈 공간을 탐색하고 관리 정보를 갱신해야 하며 해제도 직접 해야 해서 누수 위험이 있습니다. 또 힙은 메모리가 흩어져 **캐시 지역성이 나빠 실제 접근 속도도 느립니다.** 수명이 짧고 크기가 정해진 데이터는 스택이 모든 면에서 유리합니다.

**상세 설명**
1. **속도** — 스택 할당은 `sub rsp, N` 명령 하나 수준. 힙은 할당자 알고리즘을 거친다.
2. **자동 정리** — 스택은 스코프 종료 시 자동. 힙은 누수/이중 해제 위험을 개발자가 진다.
3. **캐시 지역성** — 스택은 연속되어 캐시에 잘 올라가고, 힙은 파편화되어 캐시 미스가 잦다.
4. **단편화** — 힙은 할당/해제를 반복하면 빈 공간이 조각나서, 총량은 충분한데도 큰 블록을 못 잡는 상황이 생긴다.

**꼬리질문**
- **Q.** 메모리 단편화란?
  **A.** **외부 단편화**는 할당/해제 반복으로 빈 공간이 잘게 쪼개져 총합은 충분한데 연속된 큰 블록을 못 잡는 것. **내부 단편화**는 요청보다 큰 블록을 줘서 남는 부분이 낭비되는 것. 게임처럼 장시간 실행되는 프로그램에서 특히 문제가 되며, 그래서 **메모리 풀**을 미리 잡아두고 재사용하는 기법을 쓴다.
- **Q.** Unity에서 단편화가 문제 되나?
  **A.** 된다. Unity의 GC는 **Boehm 방식이라 힙을 압축(compaction)하지 않는다.** 그래서 오래 실행하면 단편화가 누적되어 힙이 계속 커지는 문제가 생긴다. 이게 오브젝트 풀링을 쓰는 또 하나의 이유다. → `02_CSharp.md` Q2-08, `03_Unity.md` Q3-16 참고.

## Q1-23. 구조체 패딩(메모리 정렬)이란? `★`

**30초 답변**
> CPU가 메모리를 효율적으로 읽으려면 데이터가 특정 크기의 경계에 맞춰 있어야 해서, 컴파일러가 구조체 멤버 사이에 **의미 없는 빈 바이트를 끼워 넣는 것**을 패딩이라고 합니다. 그래서 멤버 크기의 단순 합과 `sizeof` 결과가 다를 수 있고, **멤버를 크기 순으로 정렬하면 패딩을 줄여 메모리를 아낄 수 있습니다.**

**상세 설명**
```cpp
struct Bad  { char a; int b; char c; };   // sizeof == 12
// a(1) + 패딩(3) + b(4) + c(1) + 패딩(3)

struct Good { int b; char a; char c; };   // sizeof == 8
// b(4) + a(1) + c(1) + 패딩(2)
```
- 규칙: 각 멤버는 **자기 크기의 배수 주소**에 놓이고, 구조체 전체 크기는 **가장 큰 멤버 크기의 배수**가 된다.
- **큰 멤버부터 나열**하면 패딩이 최소화된다. 구조체를 수백만 개 만드는 게임에서는 실제로 유의미한 절약이다.
- `#pragma pack(1)`으로 패딩을 강제로 없앨 수 있지만, **네트워크 패킷이나 파일 포맷처럼 바이트 배치가 정확해야 할 때만** 쓴다. 성능은 떨어진다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 15번 — 구조체/클래스 메모리 정렬(Padding)과 `sizeof`를 직접 실습한 항목. 원본 엑셀에서는 이 내용이 "최적화 방법" 답변에 들어가 있었는데, **독립된 문항으로 분리하는 게 맞다.**

**꼬리질문**
- **Q.** 왜 CPU는 정렬된 주소를 좋아하나?
  **A.** CPU는 메모리를 워드 단위(보통 4/8바이트)로 읽는다. 정렬되지 않은 데이터는 **두 번 읽어서 붙여야** 해서 느리고, 일부 아키텍처(ARM 등)에서는 아예 하드웨어 예외가 발생하기도 한다.
- **Q.** 네트워크 패킷에 구조체를 그대로 보내면 안 되는 이유는?
  **A.** ① 컴파일러/플랫폼마다 **패딩이 달라서** 크기와 배치가 안 맞고, ② **엔디언(바이트 순서)**이 다를 수 있다. 그래서 명시적 직렬화를 하거나 `#pragma pack` + 엔디언 변환을 해야 한다. → `06_CS기본.md` 네트워크 파트 참고.

## Q1-24. C++의 캐스팅 4종을 설명하라

**30초 답변**
> `static_cast`는 컴파일 타임에 검사되는 일반적인 타입 변환, `dynamic_cast`는 **런타임에 상속 관계를 확인**하고 실패하면 `nullptr`/예외를 주는 안전한 다운캐스팅, `const_cast`는 `const`를 떼거나 붙이는 용도, `reinterpret_cast`는 비트 패턴을 그대로 다른 타입으로 재해석하는 가장 위험한 캐스팅입니다. C 스타일 캐스트보다 **의도가 드러나고 검색 가능해서** C++에서는 이 4종을 씁니다.

**상세 설명**

| 캐스트 | 용도 | 검사 시점 | 안전성 |
|---|---|---|---|
| `static_cast` | 논리적으로 연관된 타입 변환, 업캐스팅 | 컴파일 타임 | 보통 |
| `dynamic_cast` | 다형적 클래스의 **다운캐스팅** | **런타임(RTTI)** | 높음 |
| `const_cast` | `const`/`volatile` 제거·추가 | 컴파일 타임 | 위험 |
| `reinterpret_cast` | 무관한 타입 간 비트 재해석 | 없음 | 매우 위험 |

```cpp
Base* b = new Derived();
Derived* d1 = static_cast<Derived*>(b);    // 맞다고 내가 보장. 틀리면 UB
Derived* d2 = dynamic_cast<Derived*>(b);   // 아니면 nullptr 반환 -> 체크 가능
if (d2) { /* 안전 */ }
```
- `dynamic_cast`는 **가상 함수가 하나라도 있는 클래스**에만 쓸 수 있다(RTTI 정보가 vtable에 붙어야 하므로).
- `dynamic_cast`는 런타임 비용이 있어서, 성능이 중요한 루프에서는 가상 함수로 설계를 바꾸는 게 낫다.

**꼬리질문**
- **Q.** C 스타일 캐스트 `(int)x`를 왜 쓰지 말라고 하나?
  **A.** 상황에 따라 위 4가지 중 아무거나로 동작해서 **의도가 드러나지 않고**, 실수로 `const`를 떼거나 무관한 타입으로 재해석해도 컴파일러가 아무 말을 안 한다. 또 코드에서 "캐스팅하는 곳"을 검색으로 찾기도 어렵다.
- **Q.** C#의 캐스팅은?
  **A.** `(Derived)obj`는 실패 시 `InvalidCastException`을 던지고, `obj as Derived`는 실패 시 `null`을 반환한다(C++의 `dynamic_cast`와 비슷). `is` 연산자로 미리 검사할 수도 있고, C# 7부터는 `if (obj is Derived d)` 패턴 매칭이 표준이다.

## Q1-25. 스마트 포인터란?

**30초 답변**
> 원시 포인터를 감싸서 **소멸자가 자동으로 메모리를 해제해주는** 클래스 템플릿입니다. C++11부터 `unique_ptr`(단독 소유), `shared_ptr`(참조 카운팅 기반 공유 소유), `weak_ptr`(소유하지 않는 관찰자) 세 가지가 표준에 들어왔고, 이걸 쓰면 `delete`를 직접 부르지 않아도 되어 메모리 누수를 구조적으로 막을 수 있습니다.

**상세 설명**
```cpp
std::unique_ptr<A> p1 = std::make_unique<A>();   // 복사 불가, 이동만 가능
std::shared_ptr<A> p2 = std::make_shared<A>();   // 참조 카운트 관리
std::weak_ptr<A>   p3 = p2;                      // 카운트를 올리지 않음
```

| | `unique_ptr` | `shared_ptr` | `weak_ptr` |
|---|---|---|---|
| 소유권 | 단독 | 공유(참조 카운트) | 없음(관찰만) |
| 복사 | 불가(이동만) | 가능 | 가능 |
| 오버헤드 | 거의 없음 | 제어 블록 + 원자적 카운트 | 낮음 |

- **기본은 `unique_ptr`**. 성능 오버헤드가 사실상 없고 소유권이 명확해진다. 정말 공유가 필요할 때만 `shared_ptr`.
- `shared_ptr`의 참조 카운트 증감은 **원자적 연산**이라 멀티스레드에서 안전하지만 그만큼 비용이 있다.

**꼬리질문**
- **Q.** `shared_ptr`의 순환 참조 문제란?
  **A.** A가 B를, B가 A를 `shared_ptr`로 서로 가리키면 카운트가 절대 0이 되지 않아 **둘 다 영원히 해제되지 않는다.** 한쪽을 `weak_ptr`로 바꿔서 끊어야 한다. 부모→자식은 `shared_ptr`, 자식→부모는 `weak_ptr`이 전형적인 해법이다.
- **Q.** C#/Unity에도 이런 게 필요한가?
  **A.** C#은 GC가 있어서 메모리 누수 걱정은 적지만, **GC는 순환 참조를 처리할 수 있다**(도달 가능성 기준이라서). 다만 C#에서도 이벤트 구독을 해제 안 하면 참조가 남아 객체가 수거되지 않는 **논리적 누수**가 생긴다. → `unity_핵심정리.md` 5-4(이벤트 구독/해제와 MonoBehaviour 생명주기)에서 다룬 내용이 정확히 이것이다.

**최신 동향**
`auto_ptr`은 C++11에서 deprecated, C++17에서 완전히 제거됐다. 현대 C++에서는 **원시 포인터로 소유권을 표현하지 않는 것**이 기본 원칙(Rule of Zero)이다.

## Q1-26. L-value와 R-value, Move Semantics란?

**30초 답변**
> L-value는 **이름이 있고 주소를 얻을 수 있는** 값(변수), R-value는 **임시로 만들어졌다 사라지는** 값(리터럴, 함수 반환 임시 객체)입니다. Move Semantics는 어차피 사라질 R-value에서 자원을 **복사하는 대신 소유권만 훔쳐오는** 최적화로, C++11의 이동 생성자와 `std::move`가 이를 가능하게 합니다. 큰 객체를 반환하거나 컨테이너에 넣을 때 복사 비용을 없애줍니다.

**상세 설명**
```cpp
int a = 10;        // a는 L-value, 10은 R-value
int& lr = a;       // L-value 참조
int&& rr = 10;     // R-value 참조 (C++11)

class Buf {
    char* data;
public:
    Buf(const Buf& o)  { data = new char[...]; memcpy(...); }   // 복사: 새로 할당
    Buf(Buf&& o) noexcept {                                      // 이동: 훔쳐오기
        data = o.data;      // 포인터만 가져오고
        o.data = nullptr;   // 원본은 무력화 (소멸자가 delete 안 하도록)
    }
};
std::vector<Buf> v;
v.push_back(Buf());              // 임시 객체 -> 이동 생성자 호출 (복사 안 함)
v.push_back(std::move(existing)); // 명시적으로 이동시키겠다는 선언
```
- `std::move`는 **아무것도 옮기지 않는다.** 그냥 R-value 참조로 **캐스팅**할 뿐이고, 실제 이동은 이동 생성자/이동 대입이 한다. 이름이 오해를 부르는 대표 사례라 면접 단골이다.
- `std::move`를 한 객체는 **유효하지만 미지정 상태**가 된다. 이후 값을 읽으면 안 되고, 재대입만 안전하다.

**꼬리질문**
- **Q.** `std::move`를 쓰면 항상 빨라지나?
  **A.** 아니다. ① 이동 생성자가 없으면 **복사로 폴백**되고, ② `const` 객체에 `std::move`를 쓰면 이동 생성자를 못 골라 복사가 된다. ③ 반환값에 `return std::move(x);`를 쓰면 오히려 **RVO(반환값 최적화)를 방해**해서 느려질 수 있다 — 그냥 `return x;`가 낫다.
- **Q.** C#에도 Move Semantics가 있나?
  **A.** 없다. C#은 클래스가 참조 타입이라 애초에 대입 시 참조만 복사되어 이 문제가 크지 않다. 다만 큰 `struct`를 복사하는 비용은 있어서 `in`/`ref readonly` 매개변수로 복사를 피하는 기법이 있다.

## Q1-27. 템플릿의 장단점은?

**30초 답변**
> 장점은 **타입에 상관없이 동작하는 코드를 한 번만 작성**할 수 있어 중복이 사라지고, 컴파일 타임에 타입이 확정되므로 **런타임 오버헤드가 전혀 없다**는 점입니다. 단점은 타입마다 코드가 복제되어 **바이너리가 커지고 컴파일 시간이 늘어나며**, 에러 메시지가 매우 난해하고, 구현을 헤더에 둬야 해서 캡슐화가 약해진다는 점입니다.

**상세 설명**
```cpp
template<typename T>
class Stack {
    T data[100];
public:
    void Push(const T& v);
};
Stack<int> a;      // int 버전 코드 생성
Stack<float> b;    // float 버전 코드 별도 생성 (코드 부풀림)
```
- **코드 부풀림(code bloat)**: `Stack<int>`, `Stack<float>`, `Stack<Player*>`를 쓰면 실제로 3벌의 코드가 만들어진다.
- **구현을 헤더에** 둬야 하는 이유: 컴파일러가 인스턴스화 시점에 전체 정의를 봐야 하기 때문. 그래서 `.h`에 다 넣거나 `.hpp`/`.tpp`를 포함시킨다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 8번(템플릿 함수/클래스), 17번(템플릿 인자 추론의 모호성과 특수화), 18번(**배열 스택 → 클래스 스택 → 템플릿 스택** 진화), 19번(이중 연결 리스트 템플릿화).
> 특히 18번의 "같은 자료구조를 3단계로 발전시킨" 흐름은 "왜 템플릿이 필요한가"를 스스로 체감한 과정이라 면접에서 이야기하기 좋다.

**꼬리질문**
- **Q.** C++ 템플릿과 C# 제네릭의 차이는?
  **A.** C++ 템플릿은 **컴파일 타임에 타입별 코드를 실제로 생성**한다(코드 부풀림 발생, 대신 최적화 여지 큼). C# 제네릭은 **런타임에 CLR이 처리**하며 참조 타입들은 코드를 공유하고 값 타입만 특수화한다. 또 C# 제네릭은 `where T : IComparable` 같은 **제약(constraint)을 명시**해야 하지만 C++ 템플릿은 "쓸 수 있으면 되는" 덕 타이핑이라 에러가 사용 지점에서 터진다. C++20의 **Concepts**가 이 문제를 해결했다.
- **Q.** 제네릭 제약을 실제로 써봤나?
  **A.** 썼다 — `unity_핵심정리.md` 5-16의 제네릭 싱글톤에서 `where T : MonoSingleton3<T>` 라는 **자기 참조 제약(CRTP류 패턴)**을 사용했다. 자식 클래스가 자기 자신을 타입 인자로 넘기도록 강제하는 구조다.

## Q1-28. `vector`, `list`, `deque`의 차이는? `★`

**30초 답변**
> `vector`는 **연속된 메모리**에 저장해서 인덱스 임의 접근이 O(1)이고 순회가 빠르지만, 중간 삽입·삭제가 O(n)이고 확장 시 재할당 비용이 있습니다. `list`는 **이중 연결 리스트**라 위치만 알면 삽입·삭제가 O(1)이지만 임의 접근이 불가능하고 노드가 흩어져 순회가 느립니다. `deque`는 여러 개의 연속 블록을 묶은 구조라 **양쪽 끝 삽입·삭제가 O(1)**이면서 임의 접근도 가능합니다.

**상세 설명**

| 연산 | `vector` | `list` | `deque` |
|---|---|---|---|
| 임의 접근 `[i]` | **O(1)** | 불가 | O(1) |
| 끝에 삽입/삭제 | 평균 O(1) | O(1) | **O(1)** |
| 앞에 삽입/삭제 | O(n) | **O(1)** | **O(1)** |
| 중간 삽입/삭제 | O(n) | **O(1)** (위치 알 때) | O(n) |
| 메모리 연속성 | **연속** | 흩어짐 | 블록 단위 연속 |
| 캐시 효율 | **최고** | 나쁨 | 좋음 |

- **실무 결론: 웬만하면 `vector`.** 이론상 `list`가 삽입/삭제에 유리해도, 실제로는 캐시 지역성 때문에 `vector`가 훨씬 빠른 경우가 대부분이다. `list`는 "요소 주소가 절대 바뀌면 안 될 때"나 "중간 삽입/삭제가 압도적으로 많을 때"만 고려한다.
- `vector`의 확장: 공간이 부족하면 보통 **1.5~2배 크기로 새로 할당하고 전부 복사**한다. 그래서 크기를 알면 `reserve()`로 미리 잡아두는 게 좋다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 13번(STL 컨테이너 & 반복자), 18번(스택/원형 큐 직접 구현), 19번(**이중 연결 리스트를 센티넬 노드 패턴으로 직접 구현**).
> 원본 엑셀의 400번 문항이 "이중연결리스트를 직접 구현해보세요"였는데, 이건 `cpp_핵심정리.md` 19번에 실제 구현이 있다. 코딩 테스트로 나올 수 있으니 다시 짜보는 연습을 해두는 게 좋다.

**꼬리질문**
- **Q.** `vector`에서 요소를 지우면 반복자가 어떻게 되나?
  **A.** **반복자 무효화**가 일어난다. `erase` 이후의 반복자는 전부 무효가 되고, 재할당이 일어나면 **모든 반복자·포인터·참조가 무효**가 된다. 그래서 `erase`는 다음 유효 반복자를 반환하며, `for (auto it = v.begin(); it != v.end(); ) { it = v.erase(it); }` 식으로 써야 한다.
- **Q.** C#의 `List<T>`는 어느 쪽에 해당하나?
  **A.** 이름은 list지만 **내부는 배열 기반이라 C++의 `vector`에 해당한다.** C#에서 연결 리스트를 원하면 `LinkedList<T>`를 써야 한다. 헷갈리기 쉬운 부분이라 면접에서 자주 확인한다.

## Q1-29. `map`과 `unordered_map`의 차이는?

**30초 답변**
> `map`은 **레드-블랙 트리** 기반이라 키가 정렬된 상태로 유지되고 모든 연산이 O(log n)입니다. `unordered_map`은 **해시 테이블** 기반이라 평균 O(1)로 훨씬 빠르지만 순서가 보장되지 않고, 해시 충돌이 심하면 최악 O(n)까지 떨어집니다. 정렬이나 범위 검색이 필요하면 `map`, 단순 조회 성능이 중요하면 `unordered_map`을 씁니다.

**상세 설명**

| | `map` | `unordered_map` |
|---|---|---|
| 내부 구조 | 레드-블랙 트리(균형 이진 탐색 트리) | 해시 테이블 |
| 탐색/삽입/삭제 | O(log n) 보장 | 평균 O(1), 최악 O(n) |
| 순서 | **키 정렬 유지** | 없음 |
| 범위 검색 | 가능(`lower_bound` 등) | 불가 |
| 메모리 | 노드당 포인터 오버헤드 | 버킷 배열 + 여유 공간 |
| 키 요구사항 | `operator<` | 해시 함수 + `operator==` |

**꼬리질문**
- **Q.** 해시 충돌은 어떻게 해결하나?
  **A.** ① **체이닝** — 같은 버킷에 연결 리스트로 매달기(STL이 쓰는 방식), ② **개방 주소법** — 빈 버킷을 찾아 넣기(선형 탐사, 이차 탐사, 이중 해싱). 충돌이 많아지면 **재해싱(rehashing)**으로 버킷 수를 늘린다.
- **Q.** C#의 `Dictionary<K,V>`는?
  **A.** 해시 테이블 기반이라 `unordered_map`에 해당한다. 정렬된 게 필요하면 `SortedDictionary`(트리) 또는 `SortedList`를 쓴다.
- **Q.** Unity에서 `Dictionary`의 키로 `enum`을 쓰면 문제가 있다던데?
  **A.** 예전 Unity(Mono 구버전)에서는 `enum`을 키로 쓰면 기본 비교자가 `Equals`를 호출하며 **박싱이 발생**해 매 조회마다 가비지가 생기는 문제가 있었다. 해결책은 `IEqualityComparer<TEnum>`을 직접 구현해 넘기는 것이다. 최신 Unity에서는 상당 부분 개선됐지만, 게임 클라 면접에서 "박싱을 실제로 겪은 사례"로 자주 언급된다. → `02_CSharp.md` Q2-05 참고.

## Q1-30. RAII란 무엇인가?

**30초 답변**
> **Resource Acquisition Is Initialization** — 자원의 획득을 객체의 초기화 시점에, 해제를 소멸 시점에 묶는 C++의 핵심 관용구입니다. 스택 객체는 스코프를 벗어나면 소멸자가 **반드시** 호출되기 때문에, 예외가 발생하더라도 자원이 확실히 정리됩니다. 스마트 포인터, `lock_guard`, 파일 스트림이 전부 이 패턴입니다.

**상세 설명**
```cpp
void Foo() {
    std::lock_guard<std::mutex> lock(mtx);   // 생성 시 lock
    DoSomething();                            // 여기서 예외가 나도
}                                             // 소멸자가 반드시 unlock
```
- 수동 방식(`mtx.lock(); ... mtx.unlock();`)은 중간에 `return`하거나 예외가 나면 **unlock을 놓쳐 데드락**이 된다. RAII는 이를 구조적으로 불가능하게 만든다.
- **예외 안전성**의 기반이기도 하다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` 21번 — C++11 동시성에서 `mutex`/`lock_guard`/`unique_lock`을 **"RAII 락"**으로 명시해 정리한 항목. 직접 실습한 내용이다.
- `c_핵심정리.md` 13번 — C에서는 `CRITICAL_SECTION`을 수동으로 `Enter`/`Leave` 했는데, C++의 `lock_guard`가 이걸 어떻게 안전하게 만들었는지 대비된다.

**꼬리질문**
- **Q.** C#에는 RAII가 있나?
  **A.** 소멸자 타이밍이 GC에 달려있어서 C++식 RAII는 불가능하다. 대신 `IDisposable` + **`using` 블록**이 같은 역할을 한다 — 블록을 벗어날 때 `Dispose()`가 보장된다. 실제로 `unity_핵심정리.md` 5-21에서 `using (UnityWebRequest request = ...)` 로 네트워크 요청 객체를 감싼 사례가 있다.
- **Q.** C#에서 소멸자(finalizer)를 쓰면 안 되는 이유는?
  **A.** 언제 호출될지 보장되지 않고, finalizer가 있는 객체는 **GC를 두 번 거쳐야** 수거되어 오히려 부담이 커진다. → `unity_핵심정리.md` 5-11에 "C# 소멸자를 지양하는 이유"로 정리해뒀다.

## Q1-31. 메모리 누수와 댕글링 포인터란?

**30초 답변**
> 메모리 누수는 할당한 메모리를 **해제하지 않아 접근할 수도 없고 반환되지도 않은 채 남는** 것이고, 댕글링 포인터는 **이미 해제된 메모리를 여전히 가리키고 있는** 포인터입니다. 누수는 메모리가 서서히 차오르는 문제이고, 댕글링 포인터는 접근하는 순간 정의되지 않은 동작이라 크래시나 데이터 오염으로 이어집니다.

**상세 설명**
```cpp
int* p = new int(10);
p = new int(20);        // 누수! 첫 번째 10은 영원히 접근 불가

int* q = new int(5);
delete q;               // q는 이제 댕글링 포인터
// *q = 1;              // 정의되지 않은 동작
q = nullptr;            // 해제 후 즉시 null로 만드는 습관
```
- **이중 해제(double free)** 도 같은 계열 — 이미 해제된 걸 또 해제하면 힙 관리 구조가 깨진다. Q1-03의 얕은 복사 문제가 정확히 이 시나리오다.
- 근본 해결책은 **스마트 포인터**(Q1-25)와 **RAII**(Q1-30)다.

**꼬리질문**
- **Q.** Unity/C#에서도 메모리 누수가 생기나?
  **A.** GC가 있어도 생긴다. **참조가 살아있으면 GC가 수거하지 못하기 때문**이다. 대표적인 게 ① **이벤트 구독 해제 누락** — 구독자가 파괴돼도 이벤트가 참조를 붙들고 있어 수거 안 됨(`unity_핵심정리.md` 5-4), ② `static` 컬렉션에 계속 쌓기, ③ `DontDestroyOnLoad` 오브젝트가 씬 오브젝트를 참조.
- **Q.** Unity의 "Fake Null"이란?
  **A.** Unity 오브젝트는 `Destroy` 후에도 C# 객체는 남아있는데, Unity가 `==` 연산자를 오버로딩해서 **네이티브 객체가 죽었으면 `null`처럼 보이게** 만든다. 문제는 `?.`나 `??` 같은 null 조건 연산자는 이 오버로딩을 무시하고 실제 참조만 보기 때문에 **결과가 달라진다.** Unity 코드에서 `obj?.DoSomething()`을 쓰지 말라는 이유다. → `03_Unity.md` Q3-25 참고.

## Q1-32. C와 C++의 차이는?

**30초 답변**
> C는 절차지향 언어이고 C++은 여기에 **객체지향과 제네릭 프로그래밍을 더한 멀티 패러다임 언어**입니다. C++에는 클래스, 상속, 다형성, 템플릿, 예외 처리, 참조자, 함수 오버로딩, 네임스페이스, STL이 추가됐고, `new`/`delete` 연산자와 RAII 기반 자원 관리가 가능합니다. C++은 C와 거의 호환되지만 완전한 상위 집합은 아닙니다.

**상세 설명**

| 기능 | C | C++ |
|---|---|---|
| 패러다임 | 절차지향 | 멀티 패러다임 |
| 클래스/상속 | 없음(struct는 데이터만) | 있음 |
| 함수 오버로딩 | 불가(맹글링 없음) | 가능 |
| 참조자 `&` | 없음 | 있음 |
| 예외 처리 | 없음(반환값으로 처리) | `try/catch` |
| 템플릿/제네릭 | 없음(매크로로 흉내) | 템플릿 |
| 표준 라이브러리 | libc | STL 포함 |
| 메모리 | `malloc`/`free` | `new`/`delete` + 스마트 포인터 |

**내 프로젝트 연결**
> 내 학습 경로 자체가 이 답이다. `c_핵심정리.md` 12번에서 **스택을 배열로 직접 구현**했고, `cpp_핵심정리.md` 18번에서 같은 스택을 **클래스 → 템플릿**으로 발전시켰다. 또 `c_핵심정리.md` 11번의 **매크로 함수**가 `cpp_핵심정리.md` 8번의 **템플릿**으로 대체되는 흐름도 직접 겪었다.

**꼬리질문**
- **Q.** C++은 C의 완전한 상위 집합인가?
  **A.** 아니다. 유효한 C 코드가 C++에서 컴파일 안 되는 경우가 있다 — ① `void*`에서 다른 포인터로의 암묵 변환이 C++에선 금지, ② `class` 같은 C++ 키워드를 C에선 변수명으로 쓸 수 있음, ③ 문자열 리터럴 타입이 다름(Q1-01).
- **Q.** 그럼 게임에서는 왜 아직 C++을 쓰나?
  **A.** **성능을 직접 통제할 수 있으면서 추상화도 가능하기 때문**이다. GC로 인한 예측 불가능한 스파이크가 없고, 메모리 레이아웃을 개발자가 정할 수 있어 캐시 최적화가 가능하다. 언리얼 엔진과 대부분의 상용 엔진 코어가 C++인 이유다. 반면 Unity는 엔진 코어는 C++이고 게임 로직만 C#으로 짜는 구조다.
