## Q2-01. 값 타입과 참조 타입의 차이는? `★`

**30초 답변**
> 값 타입은 **변수 자체가 데이터를 직접 담고** 있어서 대입하면 값 전체가 복사되고, 주로 스택에 할당됩니다. 참조 타입은 **변수가 힙에 있는 객체의 주소를 담고** 있어서 대입하면 주소만 복사되고, 두 변수가 같은 객체를 가리키게 됩니다. `int`, `float`, `bool`, `struct`, `enum`이 값 타입이고 `class`, `string`, 배열, `delegate`, 인터페이스가 참조 타입입니다.

**상세 설명**
```csharp
struct PointS { public int x; }
class  PointC { public int x; }

PointS a = new PointS { x = 1 };
PointS b = a;      b.x = 99;   // a.x는 여전히 1  (값 복사)

PointC c = new PointC { x = 1 };
PointC d = c;      d.x = 99;   // c.x도 99!      (같은 객체를 가리킴)
```
- **"값 타입은 무조건 스택"은 정확하지 않다.** 클래스의 멤버로 들어간 `struct`는 그 객체를 따라 **힙에** 있고, 람다에 캡처된 지역 변수도 힙으로 올라간다. 정확히 말하면 **"값 타입은 자기가 선언된 곳에 그대로 저장된다"**가 맞다. 이걸 알고 답하면 확실히 앞서간다.
- 함수 인자로 넘길 때: 값 타입은 복사본이 넘어가고, 참조 타입은 **참조가 값으로** 넘어간다(= 객체 내용은 바꿀 수 있지만 참조 자체를 바꿔도 호출자에겐 반영 안 됨). 참조 자체를 바꾸려면 `ref`를 써야 한다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-9(`[System.Serializable]`로 커스텀 클래스를 인스펙터에 노출), 12-7(직렬화 규칙).
- Unity의 `Vector3`, `Quaternion`, `Color`가 전부 `struct`(값 타입)인 것이 대표 예시다.

**꼬리질문**
- **Q.** `string`은 참조 타입인데 왜 값 타입처럼 동작하나?
  **A.** `string`이 **불변(immutable)**이기 때문이다. 수정하는 것처럼 보이는 연산은 전부 새 `string` 객체를 만든다. 그래서 참조 타입이면서도 값처럼 안전하게 다룰 수 있다 → Q2-17.
- **Q.** `Vector3`는 왜 `struct`인가?
  **A.** 게임에서 좌표 계산은 매 프레임 수만 번 일어난다. `class`였다면 그때마다 **힙 할당 + GC 부담**이 생긴다. 작고 수명이 짧은 값이라 `struct`가 정답이다.
- **Q.** 그래서 `transform.position.x = 5;` 가 왜 컴파일 에러인가?
  **A.** `transform.position`은 프로퍼티라서 **`Vector3` 값의 복사본을 반환**한다. 그 복사본의 `x`를 바꿔봐야 원본엔 반영되지 않으므로 C# 컴파일러가 아예 막는다. 반드시 `transform.position = new Vector3(5, y, z);` 처럼 통째로 대입해야 한다. **값 타입 이해도를 확인하는 Unity 단골 질문이다.**

## Q2-02. C#에서 `struct`와 `class`의 차이는?

**30초 답변**
> C#에서는 C++과 달리 **근본적으로 다릅니다.** `struct`는 값 타입이라 스택(또는 소속된 곳)에 할당되고 대입 시 전체가 복사되며 상속이 불가능합니다. `class`는 참조 타입이라 힙에 할당되고 대입 시 참조만 복사되며 상속이 가능합니다. 크기가 작고 불변이며 수명이 짧은 데이터는 `struct`, 그 외에는 `class`가 기본입니다.

**상세 설명**

| | `struct` | `class` |
|---|---|---|
| 타입 | 값 타입 | 참조 타입 |
| 저장 | 선언된 위치(주로 스택) | 힙 |
| 대입 | 전체 복사 | 참조 복사 |
| 상속 | **불가**(인터페이스 구현만 가능) | 가능 |
| 기본값 | 모든 필드가 0/null인 인스턴스 | `null` |
| 매개변수 없는 생성자 | C# 10 이전 불가 | 가능 |
| GC 대상 | 아니오(박싱 안 되면) | 예 |

- **`struct` 권장 조건(MS 가이드라인)**: ① 크기가 16바이트 이하, ② 논리적으로 단일 값을 표현, ③ 불변(immutable), ④ 자주 박싱되지 않음.
- `struct`도 크면 복사 비용이 커서 오히려 손해다. 그래서 크기 기준이 있다.

**꼬리질문**
- **Q.** `struct`는 왜 상속이 안 되나?
  **A.** 값 타입은 크기가 컴파일 타임에 고정되어야 스택에 할당하고 복사할 수 있는데, 상속을 허용하면 자식이 필드를 추가해 크기가 달라진다. 또 vtable을 통한 다형성은 참조를 전제로 하기 때문에 값 복사와 맞지 않는다.
- **Q.** `struct`인데 인터페이스는 구현할 수 있다던데?
  **A.** 가능하다. 단, **인터페이스 타입으로 담는 순간 박싱이 일어난다**(인터페이스는 참조 타입이므로). 성능을 위해 `struct`를 썼는데 인터페이스로 다루면 이득이 사라지는 함정이다 → Q2-05.

## Q2-03. 박싱과 언박싱을 설명하라 `★★`

**30초 답변**
> 박싱은 **값 타입을 `object`나 인터페이스 같은 참조 타입으로 변환**하는 것으로, 스택에 있던 값을 힙에 새로 만든 객체에 복사하고 그 주소를 참조하게 됩니다. 언박싱은 반대로 힙에 포장된 값을 다시 값 타입으로 꺼내오는 것입니다. 박싱은 **힙 할당을 유발해 GC 부담**을 주기 때문에, 제네릭을 써서 피하는 것이 원칙입니다.

**상세 설명**
```csharp
int a = 100;
object o = a;        // 박싱   - 힙에 새 객체 생성 + 값 복사 (암시적)
int b = (int)o;      // 언박싱 - 힙에서 스택으로 값 복사 (명시적 캐스트 필요)
```
```
스택            힙
┌─────┐        ┌──────────────┐
│ a=100│        │ [헤더][100]  │  <- 박싱된 object
├─────┤        └──────────────┘
│  o  │───────────────▲
└─────┘
```
- **박싱은 암시적, 언박싱은 명시적.** 그래서 박싱은 코드에 안 보여서 더 위험하다.
- 언박싱은 **정확히 원래 타입으로만** 가능하다. `object o = 1;` 을 `(long)o`로 꺼내면 `InvalidCastException`이 난다(값이 아니라 타입이 기준).
- 비용: 박싱 = 힙 할당 + 복사 + 나중에 GC. 언박싱 = 타입 검사 + 복사.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-17(`var` 타입 추론과 무명 형식), 5-14(`List<T>` + `Predicate` 델리게이트) — 제네릭 컬렉션을 쓰는 게 박싱 회피와 직결된다.
- `unity_핵심정리.md` 12-8(C# 배열 문법 총정리).

**꼬리질문**
- **Q.** 박싱이 왜 성능에 나쁜가?
  **A.** 세 가지다. ① **힙 할당**이 스택 할당보다 훨씬 비싸고, ② 할당된 객체가 나중에 **GC 대상**이 되어 수집 비용을 유발하며, ③ 값이 힙에 흩어져 **캐시 미스**가 늘어난다. 게임처럼 매 프레임 반복되는 코드에서는 누적 효과가 크다.
- **Q.** `ArrayList`와 `List<T>`의 차이는?
  **A.** `ArrayList`는 내부적으로 `object[]`를 쓰기 때문에 값 타입을 넣을 때마다 **박싱**, 꺼낼 때마다 **언박싱**이 일어난다. `List<T>`는 제네릭이라 `T`가 `int`면 실제 `int[]`를 쓰므로 박싱이 없다. **제네릭이 도입된 가장 큰 이유가 이것**이다.
- **Q.** 박싱된 객체를 수정하면 원본이 바뀌나?
  **A.** 안 바뀐다. 박싱은 **값의 복사본**을 힙에 만드는 것이라 완전히 독립된 데이터다.

**함정**
원본 엑셀 답변에 "어떤 데이터든지 object를 상속받고 시작한다"고 되어 있는데, 이건 **"모든 타입이 `object`를 상속한다"**는 뜻으로는 맞지만 **"그래서 항상 힙에 할당된다"는 건 틀렸다.** 값 타입은 `object`를 상속하면서도 박싱되기 전까지는 힙에 가지 않는다. 이 구분을 정확히 해야 한다.

## Q2-04. 박싱을 피하려면 어떻게 해야 하나?

**30초 답변**
> 가장 기본은 **제네릭을 쓰는 것**입니다. `ArrayList` 대신 `List<T>`, `Hashtable` 대신 `Dictionary<K,V>`를 쓰면 박싱이 사라집니다. 그 외에 문자열 보간이나 `string.Format`에 값 타입을 넘길 때 `ToString()`을 미리 호출하고, `struct`에 인터페이스를 통해 접근하지 않으며, `Equals`/`GetHashCode`를 재정의해 기본 구현의 박싱을 피하는 방법이 있습니다.

**상세 설명**
```csharp
// 나쁨 - 박싱
ArrayList list = new ArrayList();
list.Add(10);                       // 박싱
int x = (int)list[0];               // 언박싱

// 좋음 - 박싱 없음
List<int> list2 = new List<int>();
list2.Add(10);
int y = list2[0];

// 나쁨 - int가 object 파라미터로 들어가며 박싱
Debug.Log("Score: " + score);
// 좋음
Debug.Log("Score: " + score.ToString());
```
- `struct`에서 `Equals`를 재정의하지 않으면 기본 `ValueType.Equals`가 **리플렉션 + 박싱**을 써서 매우 느리다. `IEquatable<T>`를 구현하는 게 정석이다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 18-8 — A* 프로젝트에서 **`PairNode`가 `IEquatable`을 구현**한 코드를 작성해뒀다(실제 사용은 안 했지만). 정확히 이 박싱 회피 목적의 인터페이스다.

**꼬리질문**
- **Q.** `IEquatable<T>`를 구현하면 왜 빨라지나?
  **A.** 기본 `object.Equals(object)`는 인자가 `object`라서 값 타입을 넘기면 **박싱**된다. `IEquatable<T>.Equals(T)`는 인자가 `T`라 박싱 없이 직접 비교한다. `Dictionary`/`List.Contains` 등이 이 인터페이스를 우선 사용한다.
- **Q.** `enum`을 `Dictionary` 키로 쓸 때 문제는?
  **A.** 구버전 Mono에서 `enum`의 기본 비교자가 박싱을 유발해 조회마다 가비지가 생겼다. `IEqualityComparer<TEnum>`을 직접 만들어 `Dictionary` 생성자에 넘기는 게 해법이다. Unity 게임 클라 면접에서 "실제 최적화 경험"으로 자주 언급되는 사례다.

## Q2-05. 실제로 박싱이 몰래 일어나는 경우는?

**30초 답변**
> 코드에 캐스팅이 안 보여도 박싱이 일어나는 대표 사례가 있습니다. **값 타입을 인터페이스로 다룰 때**, **`params object[]` 인자에 값 타입을 넘길 때**(`string.Format`, `Debug.Log`의 문자열 결합), **`struct`의 재정의 안 된 `Equals`/`GetHashCode` 호출 시**, **`foreach`로 비제네릭 컬렉션을 순회할 때**입니다. 게임에서 GC 스파이크를 추적하다 보면 대부분 이런 곳에서 나옵니다.

**상세 설명**
```csharp
// 1. struct를 인터페이스로 담을 때
IComparable c = 5;                      // 박싱

// 2. params object[] - 문자열 결합/포맷
string s = string.Format("{0}", 42);    // 42가 박싱
Debug.Log("HP: " + hp);                 // hp(int)가 object로 박싱

// 3. struct의 기본 Equals
myStruct1.Equals(myStruct2);            // ValueType.Equals -> 박싱 + 리플렉션

// 4. 비제네릭 컬렉션 순회
foreach (int i in arrayList) { }        // 매 반복마다 언박싱

// 5. 제네릭 메서드에서 T를 object로 취급하는 코드
```

**꼬리질문**
- **Q.** 그럼 `Debug.Log`는 어떻게 써야 하나?
  **A.** ① 값에 `.ToString()`을 명시적으로 붙이거나, ② 릴리즈 빌드에서는 로그 자체를 `#if UNITY_EDITOR`나 `[Conditional("DEVELOPMENT_BUILD")]`로 제거한다. 매 프레임 도는 `Update`에서의 로그는 문자열 할당까지 겹쳐서 심각한 가비지 소스다.
- **Q.** 어떻게 박싱을 찾아내나?
  **A.** Unity **Profiler의 GC Alloc 열**을 보면 어떤 함수가 프레임마다 얼마나 할당하는지 나온다. 매 프레임 0 B가 목표다. 더 정밀하게는 **Deep Profile**이나 Memory Profiler 패키지를 쓴다. → `03_Unity.md` Q3-18 참고.

## Q2-06. C#의 특징과 가비지 컬렉터를 설명하라 `★★`

**30초 답변**
> C#은 **.NET 런타임(CLR) 위에서 동작하는 관리형 객체지향 언어**로, 코드를 IL(중간 언어)로 컴파일한 뒤 실행 시점에 JIT으로 기계어로 바꿉니다. 가장 큰 특징이 **가비지 컬렉터에 의한 자동 메모리 관리**로, 개발자가 `delete`를 부르지 않아도 **더 이상 도달할 수 없는 객체**를 런타임이 찾아 회수합니다. 그 외에 타입 안전성, 제네릭, LINQ, `async`/`await` 같은 현대적 기능을 갖추고 있습니다.

**상세 설명**
- **GC의 판단 기준은 "참조 카운트"가 아니라 "도달 가능성(reachability)"이다.** 스택 변수, 정적 필드, CPU 레지스터 등 **루트(root)** 에서 출발해 참조를 따라가며 살아있는 객체를 표시(Mark)하고, 표시되지 않은 것을 회수(Sweep)한 뒤 살아남은 객체를 한쪽으로 몰아 단편화를 없앤다(Compact).
- 그래서 **순환 참조도 정상적으로 수거된다** — A↔B가 서로 참조해도 루트에서 도달 불가능하면 둘 다 쓰레기다. (참조 카운팅 방식인 C++ `shared_ptr`은 이걸 못 한다 → `01_C_CPP.md` Q1-25)
- GC가 도는 동안에는 **모든 스레드를 멈춘다(Stop-The-World).** 이게 게임에서 프레임 스파이크로 나타나는 원인이다.

**꼬리질문**
- **Q.** GC는 언제 실행되나?
  **A.** ① 힙에 새 객체를 할당하려는데 여유 공간이 부족할 때(가장 흔함), ② `GC.Collect()`를 명시적으로 호출할 때, ③ 시스템 메모리 압박이 감지될 때. **개발자가 시점을 통제할 수 없다는 점**이 실시간 게임에서 문제가 된다.
- **Q.** `GC.Collect()`를 직접 부르면 되나?
  **A.** 일반적으로는 **부르지 말아야 한다.** 전체 힙을 검사하는 비싼 작업이라 오히려 더 큰 멈춤을 만든다. 다만 게임에서는 예외적으로 **로딩 화면이나 씬 전환처럼 프레임 드랍이 보이지 않는 시점에 의도적으로 호출**하는 기법을 쓰기도 한다.
- **Q.** C++와 비교했을 때 GC의 장단점은?
  **A.** 장점은 메모리 누수/이중 해제/댕글링 포인터 같은 버그를 구조적으로 줄이고 생산성이 높다는 것. 단점은 **해제 시점을 예측할 수 없어** 실시간성이 중요한 게임에서 프레임 스파이크가 생기고, 메모리를 더 많이 쓰며, 오버헤드를 개발자가 직접 통제하기 어렵다는 것이다.

## Q2-07. 어떤 메모리가 GC에 의해 해제되는가? `★`

> 원본 엑셀에서 **답변이 비어있던 문항.**

**30초 답변**
> **관리 힙(managed heap)에 할당된 객체 중, 루트에서 참조로 도달할 수 없는 것**이 해제됩니다. 루트는 스택의 지역 변수, 정적 필드, CPU 레지스터, GC 핸들 등입니다. 반대로 스택에 있는 값 타입, 정적 필드가 붙들고 있는 객체, 그리고 **네이티브(비관리) 리소스는 GC가 건드리지 않습니다.**

**상세 설명**

| 대상 | GC가 해제? |
|---|---|
| 힙의 참조 타입 객체(도달 불가) | **O** |
| 박싱된 값 타입(도달 불가) | **O** |
| 스택의 지역 값 타입 | X (스코프 종료 시 자동) |
| `static` 필드가 참조하는 객체 | X (루트라서 항상 도달 가능) |
| 파일 핸들, 소켓, 네이티브 메모리 | **X** — `Dispose`로 직접 해제 |
| Unity의 텍스처·메시 등 네이티브 객체 | **X** — `Destroy`/`Resources.UnloadUnusedAssets` |

- **"참조가 끊어지면 즉시 해제"가 아니다.** 참조가 끊긴 순간 "수거 대상 후보"가 될 뿐이고, 실제 해제는 다음 GC가 돌 때 일어난다.

**꼬리질문**
- **Q.** 그럼 왜 메모리 누수가 여전히 생기나?
  **A.** **참조가 안 끊겼기 때문**이다. 대표 사례: ① **이벤트 구독을 해제하지 않아** 발행자가 구독자를 계속 참조, ② `static` 리스트에 계속 쌓기, ③ Unity에서 `DontDestroyOnLoad` 오브젝트가 씬 오브젝트를 붙들고 있기. GC가 있어도 "논리적 누수"는 개발자 책임이다.
- **Q.** 이벤트 누수를 실제로 다뤄봤나?
  **A.** 다뤘다 — `unity_핵심정리.md` 5-4가 **이벤트 구독/해제와 MonoBehaviour 생명주기**를 다룬 항목이다. `OnEnable`에서 구독하고 `OnDisable`에서 반드시 해제하는 패턴을 실습했다. `unity_핵심정리.md` 15-3의 언어 변경 이벤트도 같은 구조다.
- **Q.** Unity에서 텍스처를 `null`로 만들면 메모리가 비나?
  **A.** 안 빈다. Unity의 에셋은 **네이티브 메모리**에 있고 C# 참조는 껍데기다. `Resources.UnloadUnusedAssets()`를 호출하거나 `Destroy`로 명시적으로 해제해야 한다. 이게 Unity 메모리 관리가 순수 C#보다 까다로운 이유다.

## Q2-08. 세대별 GC(Generational GC)란?

**30초 답변**
> **"대부분의 객체는 금방 죽는다"**는 경험칙을 활용해, 힙을 Gen 0/1/2 세대로 나누고 **새로 만든 객체는 Gen 0에 두고 자주 검사**하는 방식입니다. Gen 0 수집에서 살아남으면 Gen 1로, 또 살아남으면 Gen 2로 승격됩니다. 전체 힙을 매번 훑지 않고 젊은 세대만 빠르게 훑기 때문에 평균 비용이 크게 줄어듭니다. **이건 .NET의 GC 얘기이고, Unity의 기본 GC는 세대별이 아닙니다.**

**상세 설명**

| 세대 | 대상 | 수집 빈도 | 비용 |
|---|---|---|---|
| **Gen 0** | 갓 생성된 객체 | 매우 잦음 | 매우 저렴 |
| **Gen 1** | Gen 0에서 살아남은 것 (버퍼 역할) | 보통 | 보통 |
| **Gen 2** | 오래 살아남은 것 + LOH | 드묾 | 비쌈(전체 수집) |

- Gen 2 수집을 **전체 수집(full GC)** 이라 부르며 가장 큰 멈춤을 유발한다.
- .NET GC는 SOH에서 **Mark-Sweep-Compact**를 수행한다. 압축(compact) 덕분에 단편화가 해소되고, 다음 할당이 포인터를 밀기만 하면 되어 매우 빠르다.

**꼬리질문**
- **Q.** 왜 이 가정("객체는 금방 죽는다")이 성립하나?
  **A.** 실측 통계다. 대부분의 객체는 지역 변수, 임시 문자열, 계산 중간 결과처럼 함수 하나의 수명만 갖는다. 반면 한 번 오래 산 객체(설정, 캐시, 매니저)는 계속 살 확률이 높다. 그래서 젊은 세대만 자주 보는 게 효율적이다.
- **Q.** Gen 2에 뭐가 쌓이면 위험한가?
  **A.** 짧게 쓸 큰 객체가 Gen 2/LOH에 올라가면 full GC를 자주 유발한다. 그래서 큰 배열은 재사용하거나 `ArrayPool`로 풀링하는 게 좋다.

## Q2-09. Unity의 GC는 .NET의 GC와 어떻게 다른가?

> **이 문항이 게임 클라 면접에서 결정적인 차별화 포인트다.** 대부분의 지원자가 .NET GC 설명(세대별)을 그대로 말하는데, Unity는 다르다.

**30초 답변**
> Unity는 .NET의 세대별 GC가 아니라 **Boehm-Demers-Weiser 방식의 보수적(conservative) GC**를 씁니다. 세대 구분이 없어서 수집할 때 **힙 전체를 훑고**, 힙을 **압축(compaction)하지 않기 때문에 단편화가 누적**됩니다. 또 한 번 늘어난 힙은 OS에 잘 반환되지 않습니다. Unity 2019부터 기본 활성화된 **증분(Incremental) GC**는 이 작업을 여러 프레임에 나눠 수행해 스파이크를 완화하는 것이지, 총 작업량을 줄이는 건 아닙니다.

**상세 설명**

| | .NET(CoreCLR) GC | **Unity(Boehm) GC** |
|---|---|---|
| 세대 구분 | Gen 0/1/2 | **없음 (전체 힙 스캔)** |
| 압축(Compaction) | 함 | **안 함 → 단편화 누적** |
| 정확도 | 정확한(precise) GC | **보수적(conservative)** |
| 힙 반환 | OS에 반환 | 잘 반환 안 함(계속 커짐) |
| 스파이크 완화 | 백그라운드/서버 GC | **증분 GC(여러 프레임에 분할)** |

- **보수적(conservative)** 이란: 스택의 어떤 값이 진짜 포인터인지 정수인지 확신할 수 없어서, **포인터처럼 보이면 살아있다고 간주**한다. 그래서 이미 죽은 객체가 우연히 살아남는 경우가 생긴다.
- **증분 GC의 트레이드오프**: 작업을 쪼개면 프레임당 부담은 줄지만, 쪼갠 사이에 참조가 바뀌는 걸 추적하는 **쓰기 장벽(write barrier)** 비용이 추가되어 전체 처리량은 오히려 약간 나빠질 수 있다.

**꼬리질문**
- **Q.** 그래서 Unity에서 오브젝트 풀링이 왜 그렇게 중요한가?
  **A.** ① 압축을 안 하니 할당/해제를 반복하면 **단편화가 쌓여 힙이 계속 커지고**, ② 전체 힙을 훑으니 힙이 커질수록 **GC 시간이 길어진다.** 풀링은 애초에 할당을 안 만들어서 두 문제를 동시에 피한다. → `03_Unity.md` Q3-14.
- **Q.** Mono와 IL2CPP는 GC가 다른가?
  **A.** 둘 다 Boehm GC를 쓴다. 차이는 스크립팅 백엔드(실행 방식)이지 GC가 아니다. Mono는 JIT, IL2CPP는 C++로 변환 후 AOT 컴파일이다. → `03_Unity.md` Q3-03.
- **Q.** 앞으로 바뀌나?
  **A.** 바뀐다. Unity는 **Mono 런타임을 CoreCLR로 교체하는 작업을 진행 중**이고, 로드맵상 Unity 6.8(2026년 예정)에서 Mono를 걷어낸다. CoreCLR로 가면 **현대적인 세대별 GC와 JIT, .NET 최신 BCL, 최신 C# 문법**을 쓸 수 있게 된다. "지금은 Boehm이지만 CoreCLR 전환이 예정되어 있다"까지 말하면 최신 동향을 따라가고 있다는 인상을 준다.

## Q2-10. LOH와 SOH란?

**30초 답변**
> .NET의 관리 힙은 **SOH(Small Object Heap)**와 **LOH(Large Object Heap)**로 나뉩니다. **85,000바이트 이상**의 객체는 LOH에 할당되는데, 큰 객체를 옮기는 복사 비용이 너무 커서 **LOH는 기본적으로 압축하지 않습니다.** 그래서 LOH는 단편화가 잘 생기고, LOH 수집은 Gen 2 전체 수집과 함께 일어나 비쌉니다.

**상세 설명**
- SOH: Gen 0/1/2로 관리되고 압축된다.
- LOH: 논리적으로 Gen 2에 속한다. 큰 배열(대략 `int` 20,000개 이상, `byte` 85,000개 이상)이 여기로 간다.
- LOH 단편화 대응: ① 큰 배열을 **재사용/풀링**한다(`ArrayPool<T>`), ② 필요하면 `GCSettings.LargeObjectHeapCompactionMode`로 1회성 압축을 요청한다.

**꼬리질문**
- **Q.** 게임에서 LOH를 신경 써야 하는 경우는?
  **A.** 텍스처 픽셀 데이터, 오디오 버퍼, 네트워크 수신 버퍼, 대용량 JSON 문자열처럼 **큰 배열을 매번 새로 만드는** 코드다. 매 프레임/매 패킷마다 새 버퍼를 만들면 LOH가 금방 지저분해진다. 버퍼를 미리 잡아두고 재사용하는 게 정석이다.
- **Q.** Unity에서도 LOH 개념이 있나?
  **A.** Unity의 Boehm GC는 .NET처럼 SOH/LOH를 명확히 나누지 않는다. 다만 **큰 할당이 단편화를 악화시킨다는 실질적 문제는 동일**하고, Unity는 압축 자체를 안 하기 때문에 오히려 더 조심해야 한다.

## Q2-11. GC 부하를 줄이는 방법은?

**30초 답변**
> 핵심은 **애초에 힙 할당을 만들지 않는 것**입니다. ① 오브젝트 풀링으로 생성·파괴를 재사용으로 바꾸고, ② 매 프레임 도는 코드에서 문자열 연결·`new`·LINQ·람다 캡처를 없애고, ③ 박싱을 유발하는 비제네릭 컬렉션을 제네릭으로 바꾸고, ④ 작은 데이터는 `struct`로 만들고, ⑤ `List`나 배열은 `Capacity`를 미리 잡아 재할당을 막습니다. 측정은 **Profiler의 GC Alloc 열**로 하고, 매 프레임 0 B를 목표로 합니다.

**상세 설명**
```csharp
// 나쁨 - 매 프레임 가비지
void Update() {
    scoreText.text = "Score: " + score;                  // 문자열 할당
    var enemies = FindObjectsOfType<Enemy>();            // 배열 할당 + 매우 느림
    foreach (var e in enemies.Where(x => x.hp > 0)) { }  // LINQ + 람다 할당
}

// 좋음
private StringBuilder sb = new StringBuilder(32);
private List<Enemy> cachedEnemies = new List<Enemy>(64);
void Update() {
    if (score != lastScore) {          // 바뀔 때만 갱신
        sb.Clear(); sb.Append("Score: ").Append(score);
        scoreText.SetText(sb);
        lastScore = score;
    }
}
```
| 흔한 원인 | 대안 |
|---|---|
| 문자열 연결/보간 | `StringBuilder`, 값이 바뀔 때만 갱신 |
| `Instantiate`/`Destroy` 반복 | 오브젝트 풀링 |
| LINQ, 람다 캡처 | 직접 `for` 루프, 캡처 없는 람다 |
| `foreach`(구버전 Unity의 일부 컬렉션) | `for` 인덱스 순회 |
| `FindObjectsOfType`, `GetComponent` 매 프레임 | `Awake`에서 캐싱 |
| `ArrayList`, `Hashtable` | `List<T>`, `Dictionary<K,V>` |
| 큰 배열 매번 생성 | 버퍼 재사용, `ArrayPool<T>` |

**내 프로젝트 연결**
- `unity_핵심정리.md` 1-5 — **`GetComponent` 캐싱 세 가지 접근법 비교**를 직접 실습했다.
- `unity_핵심정리.md` 4-2 — **오브젝트 풀링 직접 구현**(SpaceShooter).
- `unity_핵심정리.md` 9-3 — VR 프로젝트에서 오브젝트 재활용 패턴을 다시 구현.
- `unity_핵심정리.md` 7-7 — TempleRun `OnGUI`에서 **매 프레임 문자열 `Replace`가 불필요한 할당을 만든다**는 이슈를 직접 발견해 기록했다. 이 질문의 실제 경험 사례로 쓸 수 있다.

**꼬리질문**
- **Q.** `foreach`가 가비지를 만든다는 말은 사실인가?
  **A.** 조건부로 사실이다. 열거자가 `class`로 구현된 컬렉션은 `foreach`마다 힙 할당이 생긴다. `List<T>`나 배열은 열거자가 `struct`라 할당이 없다(단 `IEnumerable<T>` 인터페이스로 받으면 박싱되어 다시 할당이 생긴다). 구버전 Unity Mono에서 특히 문제였고, 지금은 많이 개선됐다. **"인터페이스로 받지 마라"가 핵심**이다.
- **Q.** 최적화는 언제 해야 하나?
  **A.** **측정 후에.** Profiler로 병목을 확인하지 않고 추측으로 고치면 가독성만 해치고 효과가 없는 경우가 많다. "Premature optimization is the root of all evil"을 인용하되, 다만 **매 프레임 도는 코드의 할당은 처음부터 피하는 게 맞다**는 균형 잡힌 답이 좋다.

## Q2-12. 인터페이스를 설명하라 `★`

**30초 답변**
> 인터페이스는 **구현 없이 "이런 멤버를 제공해야 한다"는 규약만 정의**하는 타입입니다. 클래스는 단일 상속만 가능하지만 **인터페이스는 여러 개 구현할 수 있어** 다중 상속의 이점을 안전하게 얻습니다. 상속 계층이 전혀 다른 클래스들에 같은 능력을 부여하고 싶을 때 쓰며, 구체 타입이 아니라 인터페이스에 의존하게 만들어 결합도를 낮춥니다.

**상세 설명**
```csharp
public interface IDamageable { void TakeDamage(int amount); }
public interface IHealable   { void Heal(int amount); }

public class Player : MonoBehaviour, IDamageable, IHealable {  // 다중 구현
    public void TakeDamage(int a) { hp -= a; }
    public void Heal(int a)       { hp += a; }
}
public class Barrel : MonoBehaviour, IDamageable {             // 완전히 다른 계층인데 같은 능력
    public void TakeDamage(int a) { Explode(); }
}

// 사용하는 쪽은 구체 타입을 몰라도 됨
void Hit(GameObject target) {
    if (target.TryGetComponent<IDamageable>(out var d)) d.TakeDamage(10);
}
```
- 인터페이스 멤버는 기본적으로 `public`이고 접근 지정자를 붙이지 않는다.
- 구현 클래스는 **모든 멤버를 반드시 구현**해야 한다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-10 — 인터페이스 다중 구현과 **제네릭 인터페이스** 실습.
- `unity_핵심정리.md` 5-15 — **UI 이벤트 후킹 인터페이스**(`IPointerClickHandler` 등)로 "클릭 관통" 버그를 막은 실전 사례. 인터페이스를 구현하기만 하면 Unity가 알아서 호출해주는 구조라 좋은 예시다.
- `unity_핵심정리.md` 18-8 — `IEquatable` 구현.

**꼬리질문**
- **Q.** 인터페이스에 구현을 넣을 수 있나?
  **A.** C# 8부터 **기본 인터페이스 메서드(default interface method)** 가 도입되어 가능해졌다. 기존 인터페이스에 새 멤버를 추가해도 구현체들이 깨지지 않게 하려는 목적이다. 다만 **Unity는 C# 9까지 지원하지만 이 기능은 런타임 지원이 필요해 제한적**이므로, 면접에서는 "언어 차원에선 가능하나 Unity에서는 주의가 필요하다"고 답하는 게 정확하다.
- **Q.** 인터페이스에 필드를 둘 수 있나?
  **A.** 없다. 상태(필드)를 가질 수 없고 프로퍼티/메서드/이벤트/인덱서만 선언할 수 있다. **상태를 공유하고 싶으면 추상 클래스**를 써야 한다.
- **Q.** Unity에서 인터페이스를 인스펙터에 노출할 수 있나?
  **A.** 기본 직렬화기는 인터페이스를 직렬화하지 못한다. 그래서 `ScriptableObject`나 구체 클래스로 받거나, 커스텀 `PropertyDrawer`를 만들어 우회한다. → `unity_핵심정리.md` 5-23, 12-7 참고.

## Q2-13. 추상 클래스와 인터페이스의 차이는? `★`

**30초 답변**
> 추상 클래스는 **구현된 메서드와 필드를 가질 수 있고 단일 상속만 가능**해서, 자식들이 공유할 공통 코드와 상태를 물려주는 "is-a" 관계에 씁니다. 인터페이스는 **구현 없이 규약만 정의하고 다중 구현이 가능**해서, 상속 계층이 다른 클래스들에 같은 기능을 부여하는 "can-do" 관계에 씁니다. 공유할 코드가 있으면 추상 클래스, 능력만 규정하면 인터페이스입니다.

**상세 설명**

| | 추상 클래스 | 인터페이스 |
|---|---|---|
| 다중 상속/구현 | **불가**(1개만) | **가능**(여러 개) |
| 필드(상태) | 가능 | 불가 |
| 구현된 메서드 | 가능 | C# 8+ 제한적 |
| 접근 지정자 | 자유 | 항상 public |
| 생성자 | 있음(자식이 호출) | 없음 |
| 관계 | is-a (계층) | can-do (능력) |

```csharp
public abstract class Enemy : MonoBehaviour {
    protected int hp = 100;                       // 공통 상태
    protected void Die() { Destroy(gameObject); } // 공통 구현
    public abstract void Attack();                // 자식이 반드시 구현
}
```

**내 프로젝트 연결**

**꼬리질문**
- **Q.** 둘을 같이 쓰는 경우도 있나?
  **A.** 흔하다. **인터페이스로 규약을 정의하고, 추상 클래스로 그 인터페이스의 공통 구현을 제공**하는 패턴이다. 예: `IDamageable` 인터페이스 + `DamageableBase` 추상 클래스. .NET BCL의 `IList<T>` ↔ `List<T>` 관계도 비슷하다.
- **Q.** C++엔 인터페이스 키워드가 없는데 어떻게 하나?
  **A.** 순수 가상 함수만 가진 클래스로 표현한다. C++은 다중 상속이 되므로 언어 차원의 구분이 필요 없었다. → `01_C_CPP.md` Q1-06.

## Q2-14. `delegate`와 `event`의 차이는?

**30초 답변**
> `delegate`는 **메서드를 담을 수 있는 타입**이고, `event`는 그 델리게이트를 **외부에서 안전하게만 쓰도록 감싼 것**입니다. 델리게이트 필드는 외부에서 `=`로 통째로 덮어쓰거나 직접 호출할 수 있어서 다른 구독자를 날려버릴 수 있지만, `event`로 선언하면 외부에서는 `+=`/`-=`만 가능하고 **호출은 선언한 클래스 안에서만** 할 수 있습니다. 프로퍼티가 필드를 캡슐화하듯, `event`가 델리게이트를 캡슐화합니다.

**상세 설명**
```csharp
public delegate void OnHit(int dmg);

public class A {
    public OnHit  hitDelegate;   // 위험: 외부에서 a.hitDelegate = null; 가능
    public event OnHit hitEvent; // 안전: 외부에서 += / -= 만 가능
}
// 외부에서
a.hitDelegate = null;      // 다른 구독자 전부 날림 - 컴파일됨!
a.hitDelegate(10);         // 외부에서 강제 발생 - 컴파일됨!
// a.hitEvent = null;      // 컴파일 에러
// a.hitEvent(10);         // 컴파일 에러
a.hitEvent += MyHandler;   // 이것만 가능
```
- 델리게이트는 **멀티캐스트**가 된다 — `+=`로 여러 메서드를 등록하면 순서대로 전부 호출된다.
- 표준 델리게이트: `Action`(반환 없음), `Func<T>`(반환 있음), `Predicate<T>`(bool 반환). 직접 `delegate`를 선언하는 대신 이걸 쓰는 게 요즘 관례다.

**내 프로젝트 연결**

- `unity_핵심정리.md` 15-3 — 로컬라이제이션에서 **델리게이트 이벤트로 언어 변경을 전파**한 실전 사례. 처음엔 값을 직접 전달하다가 **신호만 전달하는 방식으로 설계를 개선**한 과정까지 기록해뒀다.
- `unity_핵심정리.md` 5-14 — `List<T>` + `Predicate` 델리게이트 활용.

**꼬리질문**
- **Q.** 이벤트 구독 해제를 안 하면 어떻게 되나?
  **A.** 발행자가 구독자 참조를 계속 붙들고 있어서 **구독자가 GC에 수거되지 않는 메모리 누수**가 생긴다. Unity에서는 더 나쁜데, `Destroy`된 `MonoBehaviour`가 이벤트를 통해 호출되면 `MissingReferenceException`이 터진다. **`OnEnable`에서 구독, `OnDisable`에서 해제**가 정석이다.
- **Q.** UnityEvent와 C# event의 차이는?
  **A.** `UnityEvent`는 **인스펙터에서 시각적으로 연결**할 수 있어 기획자/디자이너가 코드 없이 배선할 수 있다. 대신 리플렉션 기반이라 C# `event`보다 **느리고 할당도 있다.** C# `event`는 빠르지만 코드로만 연결한다. 실무에선 UI/에디터 노출은 `UnityEvent`, 성능이 중요한 내부 로직은 C# `event`로 나눠 쓴다. → `unity_핵심정리.md` 10-3에서 Ground Plane 배치에 `UnityEvent` 리스너를 쓴 사례가 있다.

## Q2-15. 람다식과 익명 메서드란?

**30초 답변**
> 이름 없이 그 자리에서 정의하는 함수입니다. `delegate(int x) { return x*2; }` 형태가 익명 메서드이고, 이걸 더 간결하게 만든 `x => x * 2`가 람다식입니다. 짧은 콜백을 위해 별도 메서드를 만들 필요가 없어 코드가 간결해지지만, **외부 변수를 캡처하면 컴파일러가 숨은 클래스를 만들어 힙 할당이 발생**하므로 매 프레임 도는 코드에서는 주의해야 합니다.

**상세 설명**
```csharp
// 변천사
button.onClick.AddListener(delegate() { Debug.Log("hi"); });  // 익명 메서드 (C# 2)
button.onClick.AddListener(() => Debug.Log("hi"));            // 람다 (C# 3)

List<int> nums = new List<int> { 1, 2, 3 };
nums.RemoveAll(n => n % 2 == 0);        // Predicate<int>
```
- **캡처(closure)**: 람다가 바깥 지역 변수를 참조하면, 컴파일러가 그 변수를 담은 클래스를 만들어 힙에 올린다.
```csharp
int threshold = 10;                       // 캡처됨 -> 힙 할당 발생
list.RemoveAll(n => n > threshold);
list.RemoveAll(n => n > 10);              // 캡처 없음 -> 컴파일러가 캐싱, 할당 없음
```

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-5 — **람다식 실전 활용(사용자 입력 기반 계산기)** 실습.
- `unity_핵심정리.md` 5-2 — 델리게이트 → 익명 메서드 → 람다로 이어지는 **C# 문법 변천사**를 정리해뒀다. 이 질문에 딱 맞는 자료다.
- `unity_핵심정리.md` 5-25 — `menu.AddItem(..., () => { Debug.Log("CONTEXT MENU1"); })` 처럼 에디터 확장에서 람다를 콜백으로 사용.

**꼬리질문**
- **Q.** 람다 캡처가 왜 성능 문제인가?
  **A.** 캡처가 있으면 **매 호출마다 클로저 객체가 힙에 새로 할당**되어 GC 부담이 된다. 캡처가 없는 람다는 컴파일러가 정적 필드에 한 번만 만들어 재사용하므로 할당이 없다. 매 프레임 도는 코드에선 캡처를 피하거나 미리 델리게이트를 필드에 캐싱해둔다.
- **Q.** 클로저의 반복문 변수 캡처 함정을 아나?
  **A.** C# 5 이전에는 `for`/`foreach` 변수를 캡처하면 **모든 람다가 마지막 값 하나를 공유**하는 유명한 버그가 있었다. C# 5부터 `foreach`는 반복마다 새 변수를 만들도록 수정됐지만, `for`는 여전히 하나를 공유하므로 루프 안에서 지역 복사본을 만들어야 한다.

## Q2-16. `const`와 `readonly`의 차이는?

**30초 답변**
> `const`는 **컴파일 타임 상수**로 선언과 동시에 값이 정해져야 하고 암묵적으로 `static`이며, 사용하는 쪽 코드에 **값이 그대로 박제**됩니다. `readonly`는 **런타임 상수**로 생성자에서 값을 결정할 수 있고 인스턴스마다 다른 값을 가질 수 있습니다. 라이브러리 경계를 넘는 값은 `const`로 두면 값 변경 시 재컴파일이 필요해지므로 `static readonly`가 안전합니다.

**상세 설명**

| | `const` | `readonly` |
|---|---|---|
| 값 결정 | 컴파일 타임 | 런타임(생성자까지) |
| 허용 타입 | 기본형, `string`, `enum`, `null` | 모든 타입 |
| `static` | 암묵적으로 static | 선택 |
| 인스턴스별 값 | 불가 | 가능 |
| 사용처 코드 | 값이 인라인 박제 | 필드 참조 |

```csharp
public const int MaxHp = 100;                    // 어디서 쓰든 100이 박제됨
public static readonly Vector3 Spawn = new Vector3(0,1,0);  // const 불가(Vector3는 기본형 아님)
public readonly int id;                          // 생성자에서만 대입 가능
public MyClass(int i) { id = i; }
```
- **버전 관리 함정**: A.dll의 `const`를 B.exe가 참조하면 값이 B에 박제된다. A만 고쳐 배포해도 B는 옛 값을 쓴다. `static readonly`는 실행 시 A를 참조하므로 이 문제가 없다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-13 — **필드 캡슐화: `const` vs `static readonly` vs 프로퍼티** 비교 실습. 이 질문에 정확히 대응하는 항목이다.

**꼬리질문**
- **Q.** `Vector3`를 `const`로 못 만드는 이유는?
  **A.** `const`는 컴파일 타임에 값이 확정되어야 하는데 `Vector3`는 `struct`라서 생성자 호출이 필요하다. 컴파일러가 계산할 수 있는 건 기본형, `string`, `enum`, `null`뿐이다. 그래서 `static readonly`를 쓴다.
- **Q.** C++의 `const`와 뭐가 다른가?
  **A.** C++의 `const`는 "변경 불가"라는 의미가 포인터/멤버 함수 등 훨씬 넓은 문맥에 적용되고(→ `01_C_CPP.md` Q1-17), C#의 `const`는 좁게 "컴파일 타임 상수 필드"만 뜻한다. C++의 `constexpr`이 C# `const`에 더 가깝다.

## Q2-17. C#의 `string`은 왜 특별한가?

**30초 답변**
> `string`은 **참조 타입인데 불변(immutable)**이고 **값처럼 비교**되는 특별한 타입입니다. 한 번 만들어진 문자열은 절대 수정되지 않아서, `s += "a"` 같은 코드는 기존 객체를 고치는 게 아니라 **새 문자열 객체를 만들고 참조를 바꾸는 것**입니다. 또 `==` 연산자가 오버로딩되어 참조가 아니라 내용을 비교하고, 동일한 리터럴은 **인터닝**으로 하나의 객체를 공유합니다.

**상세 설명**
```csharp
string a = "hello";
string b = "hello";
Console.WriteLine(a == b);              // True (내용 비교 + 인터닝)
Console.WriteLine(ReferenceEquals(a,b));// True (리터럴 인터닝으로 같은 객체)

string s = "a";
s += "b";       // "a"는 버려지고 "ab"라는 새 객체가 생김 -> 가비지 발생
```
- **불변의 장점**: 스레드 안전, 해시 캐싱 가능(`Dictionary` 키로 안전), 공유 가능.
- **불변의 단점**: 조작할 때마다 새 객체 → **가비지 발생**. 그래서 `StringBuilder`가 필요하다 → Q2-18.

**꼬리질문**
- **Q.** `string`을 `Dictionary` 키로 써도 되나?
  **A.** 된다. 불변이라 해시가 변하지 않으므로 안전하고 흔하게 쓴다. 다만 문자열 해싱 자체가 `int`보다 비싸므로, 성능이 중요한 곳에선 `enum`이나 `int` ID를 쓰는 게 낫다. Unity에서 애니메이터 파라미터를 `Animator.StringToHash`로 미리 정수로 바꿔 쓰는 게 같은 이유다.
- **Q.** `string`과 `String`의 차이는?
  **A.** 없다. `string`은 `System.String`의 C# 별칭(alias)이다. 관례상 타입을 쓸 땐 `string`, 정적 메서드를 부를 땐 `String.Format`처럼 쓰기도 하지만 기능은 동일하다.
- **Q.** 문자열 비교는 `==`와 `Equals` 중 뭘 써야 하나?
  **A.** C#에서는 둘 다 내용 비교라 결과가 같다. 다만 **대소문자 무시나 문화권 설정이 필요하면 `string.Equals(a, b, StringComparison.OrdinalIgnoreCase)`** 를 명시적으로 쓰는 게 안전하고, `Ordinal` 비교가 문화권 비교보다 훨씬 빠르다.

## Q2-18. 반복문에서 문자열을 계속 더하면 왜 문제인가?

**30초 답변**
> `string`이 불변이라 `+=` 할 때마다 **새 문자열 객체를 만들고 기존 내용을 전부 복사**하기 때문입니다. n번 반복하면 할당도 n번, 복사량은 O(n²)이 되어 성능과 GC 양쪽에 치명적입니다. 대신 내부 버퍼를 재사용하는 **`StringBuilder`**를 쓰면 O(n)으로 끝납니다.

**상세 설명**
```csharp
// 나쁨 - 1000번 반복하면 1000개의 중간 문자열이 전부 가비지
string s = "";
for (int i = 0; i < 1000; i++) s += i.ToString();

// 좋음 - 내부 버퍼에 append, 필요할 때만 확장
var sb = new StringBuilder(4096);      // 예상 크기를 미리 잡으면 더 좋음
for (int i = 0; i < 1000; i++) sb.Append(i);
string result = sb.ToString();
```
- 단, **적은 횟수(2~3개)의 연결은 그냥 `+`가 낫다.** 컴파일러가 `string.Concat` 한 번 호출로 최적화하므로 `StringBuilder` 객체를 만드는 비용이 오히려 손해다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 7-7 — TempleRun의 `OnGUI`에서 **매 프레임 문자열 `Replace`가 불필요한 할당을 만든다**는 이슈를 직접 발견해 "고쳐볼 만한 부분"에 기록했다. 이 질문에 대한 실제 경험 사례로 쓸 수 있다.

**꼬리질문**
- **Q.** Unity UI에서 점수 표시는 어떻게 최적화하나?
  **A.** ① **값이 바뀔 때만 갱신**한다(매 프레임 대입 금지), ② `StringBuilder`를 필드로 재사용하고, ③ TextMeshPro의 `SetText(StringBuilder)` 오버로드를 쓰면 `ToString()` 할당까지 없앨 수 있다. ④ 자주 쓰는 숫자 문자열은 미리 배열로 캐싱하기도 한다.
- **Q.** 문자열 보간 `$"Score: {x}"` 은 어떤가?
  **A.** C# 10 이전에는 `string.Format`으로 컴파일되어 **박싱과 할당**이 있었다. C# 10부터 `DefaultInterpolatedStringHandler`로 최적화됐지만 **Unity는 C# 9까지라 이 최적화를 받지 못한다.** 그래서 Unity에선 여전히 핫패스에서 보간 문자열을 피해야 한다. — 이걸 알고 답하면 매우 좋은 인상을 준다.

## Q2-19. `char` 타입과 `string` 타입의 차이는? `★`

> 원본 엑셀에서 **답변이 비어있던 문항.**

**30초 답변**
> `char`는 **단일 유니코드 문자 하나**를 담는 16비트 값 타입이고, `string`은 **`char`의 시퀀스**를 담는 참조 타입입니다. `char`는 작은따옴표 `'A'`, `string`은 큰따옴표 `"A"`로 씁니다. `char`는 스택에 2바이트로 올라가고, `string`은 힙에 객체로 할당됩니다.

**상세 설명**
```csharp
char c = 'A';           // 값 타입, 2바이트(UTF-16 코드 유닛)
string s = "A";         // 참조 타입, 힙 객체
string t = "Hello";
char first = t[0];      // 인덱서로 char 하나 꺼내기
char[] arr = t.ToCharArray();
```
| | `char` | `string` |
|---|---|---|
| 타입 | 값 타입(`System.Char`) | 참조 타입(`System.String`) |
| 크기 | 2바이트 고정 | 가변 |
| 따옴표 | `'A'` | `"A"` |
| null | 불가(기본값 `'\0'`) | 가능 |
| 불변성 | (값이라 해당 없음) | 불변 |

- C#의 `char`는 **UTF-16 코드 유닛 1개**다. 그래서 이모지처럼 코드 포인트가 큰 문자는 `char` 2개(서로게이트 쌍)로 표현되어 `s.Length`가 사람이 세는 글자 수와 다를 수 있다. 한글은 완성형 음절이 BMP 안에 있어서 `char` 1개로 표현된다.

**꼬리질문**
- **Q.** C의 `char`와 뭐가 다른가?
  **A.** C의 `char`는 **1바이트**이고 사실상 작은 정수 타입이라 아스키 위주다. C#의 `char`는 **2바이트 유니코드**라 한글·한자를 한 글자로 담을 수 있다. 그래서 C에서 한글을 다루려면 인코딩(CP949/UTF-8)을 신경 써야 하고 바이트 단위로 잘리는 문제가 생긴다.
  > 실제로 이 문제를 겪었다 — 내 실습 코드 상당수가 **CP949로 저장되어 있어 UTF-8 도구로 읽으면 주석이 깨졌다.** `00_작업계획.md`에도 기록해둔 사항이다.
- **Q.** `string`의 길이를 셀 때 주의할 점은?
  **A.** `s.Length`는 **UTF-16 코드 유닛 개수**지 사람이 인식하는 글자 수가 아니다. 이모지, 결합 문자(한글 자모 조합 등)가 섞이면 다르다. 정확한 글자 수가 필요하면 `StringInfo`를 써야 한다.

## Q2-20. 프로퍼티(Property)란?

**30초 답변**
> 필드처럼 접근하지만 내부적으로는 **`get`/`set` 메서드로 동작**하는 멤버입니다. 필드를 `private`으로 감추고 프로퍼티로 노출하면, 값을 읽고 쓸 때 **유효성 검사나 부가 동작을 끼워 넣을 수 있고** 나중에 내부 구현을 바꿔도 사용하는 쪽 코드가 안 깨집니다. 캡슐화를 문법적으로 편하게 만든 장치입니다.

**상세 설명**
```csharp
private int hp;
public int Hp {
    get => hp;
    set => hp = Mathf.Clamp(value, 0, maxHp);   // 대입할 때 자동으로 범위 제한
}

public int Level { get; private set; }            // 자동 구현 프로퍼티 + 외부 쓰기 금지
public int MaxHp { get; } = 100;                  // 읽기 전용
```
- `value`는 `set` 안에서 대입된 값을 가리키는 예약어다.
- **Unity 주의**: 프로퍼티는 기본적으로 **인스펙터에 직렬화되지 않는다.** 필드에 `[SerializeField]`를 붙이고 프로퍼티로 감싸는 게 표준 패턴이다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-6 — 프로퍼티의 `get`/`set` 실습.
- `unity_핵심정리.md` 5-13 — 필드 캡슐화 방식 비교.
- `unity_핵심정리.md` 5-19 관련 이슈 — **`AutoMove.Instance` 프로퍼티가 게터 안에서 값을 변경하고 있던 실제 문제**를 발견해 기록해뒀다(`get { return moveSpeed = 3.0f; }`). "게터는 부작용이 없어야 한다"는 원칙의 반례라 면접 소재로 좋다.

**꼬리질문**
- **Q.** 프로퍼티와 필드 중 뭘 public으로 노출해야 하나?
  **A.** **프로퍼티**다. 필드를 public으로 열면 나중에 검증 로직을 추가할 때 시그니처가 바뀌어 호출부가 전부 깨진다. 프로퍼티로 열어두면 내부만 바꾸면 된다.
- **Q.** 게터에서 값을 바꾸면 왜 문제인가?
  **A.** "읽기만 한다"는 기대를 깨뜨린다. 디버거가 값을 표시하려고 게터를 호출하는 것만으로도 상태가 바뀌고, Unity 인스펙터가 프레임마다 게터를 호출하면 값이 계속 덮어써진다. 실제로 내 코드에서 이 문제를 발견했다(위 참조).

## Q2-21. 제네릭이란? C++ 템플릿과 뭐가 다른가?

**30초 답변**
> 타입을 매개변수로 받아 **타입에 무관하게 동작하는 코드를 한 번만 작성**하는 기능입니다. `List<T>`처럼 쓰면 타입 안전성을 유지하면서 박싱도 피할 수 있습니다. C++ 템플릿은 **컴파일 타임에 타입별 코드를 실제로 복제 생성**하지만, C# 제네릭은 **컴파일 후에도 IL에 제네릭 정보가 남고 런타임(CLR)이 처리**해서 참조 타입끼리는 코드를 공유합니다. 또 C#은 `where` 제약을 명시해야 합니다.

**상세 설명**
```csharp
public class Pool<T> where T : Component, new() {   // 제약: Component 상속 + 기본 생성자 필요
    private Stack<T> items = new Stack<T>();
    public T Get() => items.Count > 0 ? items.Pop() : new T();
}
```

| | C++ 템플릿 | C# 제네릭 |
|---|---|---|
| 처리 시점 | 컴파일 타임(코드 생성) | 컴파일 + 런타임(CLR) |
| 코드 복제 | 타입마다 전부 | 값 타입만, 참조 타입은 공유 |
| 제약 | 없음(덕 타이핑, C++20 Concepts로 해결) | **`where` 필수** |
| 에러 시점 | 사용 지점, 메시지 난해 | 선언 지점, 명확 |
| 바이너리 크기 | 커짐 | 상대적으로 작음 |

**내 프로젝트 연결**
- `unity_핵심정리.md` **5-16** — `MonoSingleton1 → 2 → 3` 진화 과정에서 **`where T : MonoSingleton3<T>` 자기 참조 제약(CRTP류 패턴)** 을 사용했다. 제네릭 제약의 고급 사례라 면접에서 설명하면 좋다.
- `unity_핵심정리.md` 5-10(제네릭 인터페이스), 5-14(`List<T>` + `Predicate`).
- `cpp_핵심정리.md` 8·17·18·19번 — C++ 템플릿 쪽 실습(스택/이중 연결 리스트 템플릿화).

**꼬리질문**
- **Q.** 제네릭 제약(`where`)의 종류는?
  **A.** `where T : class`(참조 타입), `struct`(값 타입), `new()`(기본 생성자 필요), `BaseClass`(특정 클래스 상속), `IInterface`(인터페이스 구현), `T : U`(다른 타입 매개변수 상속). 여러 개를 콤마로 조합할 수 있다.
- **Q.** `where T : new()`가 왜 필요한가?
  **A.** 제네릭 코드 안에서 `new T()`를 하려면 컴파일러가 **T에 매개변수 없는 생성자가 있다는 보장**을 받아야 한다. 이 제약이 없으면 `new T()`는 컴파일 에러다.
- **Q.** IL2CPP에서 제네릭에 문제가 있다던데?
  **A.** IL2CPP는 AOT 컴파일이라 **런타임에 새로운 제네릭 타입을 만들 수 없다.** 리플렉션으로 `List<SomeType>`을 동적으로 생성하면 "해당 코드가 생성되지 않았다"는 런타임 에러가 난다. `link.xml`이나 더미 코드로 미리 사용을 명시해야 한다. → `03_Unity.md` Q3-03.

## Q2-22. `List<T>`와 `Dictionary<K,V>`의 내부 구조는?

**30초 답변**
> `List<T>`는 **내부가 배열**입니다(이름과 달리 연결 리스트가 아님). 공간이 차면 보통 **두 배 크기의 새 배열을 만들어 전부 복사**하므로 인덱스 접근은 O(1)이지만 중간 삽입·삭제는 O(n)입니다. `Dictionary<K,V>`는 **해시 테이블**이라 평균 O(1) 조회를 제공하고, 해시 충돌은 버킷 내 체이닝으로 처리합니다.

**상세 설명**
```csharp
var list = new List<int>(100);     // Capacity를 미리 잡으면 재할당 없음
list.Add(1);                        // 평균 O(1), 재할당 시 O(n)
int x = list[0];                    // O(1)
list.Insert(0, 5);                  // O(n) - 뒤를 전부 밀어야 함

var dict = new Dictionary<string,int>();
dict["a"] = 1;                      // 평균 O(1)
```
- `List<T>` 확장: `Capacity`가 부족하면 `Capacity * 2`로 새 배열 할당 후 `Array.Copy`. **크기를 알면 생성자에 넘겨서 재할당을 없애는 게 좋은 습관**이다.
- `Dictionary` 동작: `key.GetHashCode()` → 버킷 인덱스 계산 → 충돌 시 같은 버킷 안에서 `Equals`로 선형 탐색.
- `Dictionary`는 **순서를 보장하지 않는다.** 순서가 필요하면 `SortedDictionary`(트리, O(log n))나 별도 리스트를 함께 관리한다.

**꼬리질문**
- **Q.** `List<T>`에서 요소를 자주 지우면 왜 느린가?
  **A.** `RemoveAt(i)`는 뒤의 원소를 전부 앞으로 당겨야 해서 O(n)이다. 순서가 상관없으면 **마지막 원소를 그 자리에 옮기고 마지막을 지우는(swap-remove)** 기법으로 O(1)로 만들 수 있다. 게임에서 활성 오브젝트 목록 관리에 자주 쓴다.
- **Q.** 반복하면서 삭제하면 어떻게 되나?
  **A.** `foreach` 중 컬렉션을 수정하면 `InvalidOperationException`이 난다. **뒤에서 앞으로 `for` 루프를 돌거나**, `RemoveAll(predicate)`를 쓰거나, 삭제 대상을 따로 모아 나중에 지운다.
- **Q.** `Dictionary` 조회가 O(1)이 아닐 때는?
  **A.** 해시 함수가 나빠 **충돌이 몰리면** 한 버킷에 다 들어가 O(n)이 된다. 또 `GetHashCode`를 재정의하면서 `Equals`를 안 고치면(또는 그 반대) 조회가 아예 실패한다. **`Equals`와 `GetHashCode`는 항상 함께 재정의해야 한다**는 규칙이 여기서 나온다.

## Q2-23. `IEnumerable`과 `yield return`이란?

**30초 답변**
> `IEnumerable`은 **`foreach`로 순회할 수 있다는 규약**이고, `yield return`은 그 열거자를 **컴파일러가 자동으로 만들어주는 문법**입니다. `yield return`을 쓰면 값을 하나 반환하고 그 지점의 상태를 기억한 채 **중단했다가, 다음 요소를 요청받으면 그 자리에서 재개**합니다. 전체 컬렉션을 미리 만들지 않고 필요할 때 하나씩 만드는 **지연 실행**이 핵심이고, **Unity의 코루틴이 정확히 이 문법을 활용한 것**입니다.

**상세 설명**
```csharp
IEnumerable<int> GetNumbers() {
    for (int i = 0; i < 3; i++) {
        Debug.Log("생성 " + i);
        yield return i;        // 여기서 멈추고 값을 반환, 다음 요청 시 여기서 재개
    }
}
foreach (var n in GetNumbers()) Debug.Log("소비 " + n);
// 출력: 생성0, 소비0, 생성1, 소비1, 생성2, 소비2   (미리 다 만들지 않음)
```
- 컴파일러가 **상태 기계(state machine) 클래스**를 자동 생성한다. 어디까지 실행했는지를 필드에 저장해두고 `MoveNext()` 호출 시 그 지점부터 이어간다.
- Unity 코루틴은 `IEnumerator`를 반환하고, Unity가 매 프레임 `MoveNext()`를 호출해주는 구조다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 1-4(코루틴과 `yield return`), 2-8(코루틴 자기 재귀 호출), 8-6(**코루틴 기반 우선순위 FSM**), 18-5(A* 탐색을 코루틴으로 시각화).

**꼬리질문**
- **Q.** 코루틴은 스레드인가?
  **A.** **아니다.** 코루틴은 메인 스레드에서 실행되며, Unity가 매 프레임 `MoveNext()`를 불러주는 것뿐이다. 그래서 코루틴 안에서 무거운 계산을 하면 **여전히 프레임이 멈춘다.** 진짜 병렬 처리가 필요하면 `Thread`나 `Job System`을 써야 한다. **매우 자주 나오는 함정 질문이다.** → `03_Unity.md` Q3-10.
- **Q.** `IEnumerable`과 `IEnumerator`의 차이는?
  **A.** `IEnumerable`은 "열거 가능한 대상"으로 `GetEnumerator()`를 제공하고, `IEnumerator`는 실제 순회 상태를 가진 "커서"로 `MoveNext()`/`Current`를 제공한다. Unity 코루틴 메서드의 반환 타입이 `IEnumerator`인 이유가 여기 있다.

## Q2-24. `async`/`await`와 `Task`를 설명하라

**30초 답변**
> `Task`는 **비동기 작업 하나를 나타내는 객체**이고, `async`/`await`는 그 작업이 끝날 때까지 **스레드를 붙잡지 않고 기다렸다가 이어서 실행**하게 해주는 문법입니다. `await`를 만나면 메서드가 즉시 반환되고 호출자가 계속 진행하며, 작업이 끝나면 나머지 부분이 재개됩니다. 파일 I/O나 네트워크처럼 **기다리는 시간이 대부분인 작업**에서 스레드 낭비를 없애는 게 목적입니다.

**상세 설명**
```csharp
async Task<string> LoadDataAsync(string url) {
    using var client = new HttpClient();
    string result = await client.GetStringAsync(url);  // 여기서 반환, 완료되면 재개
    return result;
}
```
- **비동기 ≠ 멀티스레드.** I/O 대기는 스레드를 쓰지 않고 OS에 맡긴다. CPU를 계속 쓰는 작업이라면 `Task.Run`으로 스레드 풀에 넘겨야 실제 병렬이 된다.
- `async void`는 **이벤트 핸들러 외에는 쓰면 안 된다** — 예외를 잡을 수 없고 완료를 기다릴 수도 없다. 반드시 `async Task`로.

**내 프로젝트 연결**
- `unity_핵심정리.md` 15-6 — `CSVReader`가 **동기/비동기 이중 지원**(코루틴 + `async`/`await`)을 하도록 만들고 `#if UNITY_2020_1_OR_NEWER`로 조건부 컴파일한 실습. 이 질문의 실제 코드 사례로 쓸 수 있다.

**꼬리질문**
- **Q.** Unity에서 코루틴과 `async`/`await` 중 뭘 써야 하나?
  **A.** 상황에 따라 다르다. **코루틴**은 `MonoBehaviour` 생명주기에 묶여 오브젝트가 파괴되면 자동으로 멈추고 프레임 단위 제어(`yield return null`)가 쉬워서 게임 연출에 적합하다. **`async`/`await`**는 반환값을 받을 수 있고 예외 처리가 되며 `MonoBehaviour` 없이도 쓸 수 있어 네트워크/파일 I/O에 적합하다. 다만 **`async`는 오브젝트가 파괴돼도 자동으로 취소되지 않아** `CancellationToken`을 직접 관리해야 하는 게 큰 함정이다. 실무에선 **UniTask** 라이브러리로 이 문제를 해결하는 경우가 많다.
- **Q.** Unity에서 `await` 후에 메인 스레드로 돌아오나?
  **A.** Unity는 `UnitySynchronizationContext`를 제공해서 기본적으로 메인 스레드로 돌아온다. 하지만 `ConfigureAwait(false)`를 쓰거나 컨텍스트가 없는 상황이면 다른 스레드에서 재개될 수 있고, 그 상태로 Unity API를 호출하면 예외가 난다. **Unity API는 메인 스레드에서만 호출 가능**하다는 원칙을 항상 기억해야 한다.

## Q2-25. 스레드와 `Task`의 차이는?

**30초 답변**
> `Thread`는 **OS 스레드를 직접 하나 만드는 것**이라 생성 비용이 크고 개수를 개발자가 관리해야 합니다. `Task`는 **"해야 할 작업 단위"**를 나타내는 상위 추상화로, 내부적으로 **스레드 풀에서 스레드를 빌려 쓰기** 때문에 생성 비용이 훨씬 싸고, 반환값·예외 전파·취소·연속 작업 같은 기능이 기본으로 제공됩니다. 요즘은 특수한 경우가 아니면 `Task`를 씁니다.

**상세 설명**

| | `Thread` | `Task` |
|---|---|---|
| 추상화 수준 | OS 스레드 직접 | 작업 단위 |
| 생성 비용 | 큼(약 1MB 스택) | 작음(풀 재사용) |
| 반환값 | 없음(별도 처리) | `Task<T>` |
| 예외 전파 | 어려움 | `await`로 자연스럽게 |
| 취소 | 수동 플래그 | `CancellationToken` |
| 용도 | 장시간 전용 스레드 | 짧은 비동기 작업 |

**내 프로젝트 연결**
- `c_핵심정리.md` 13번 — WinAPI `CreateThread`와 `CRITICAL_SECTION`으로 **스레드/임계구역을 직접** 다뤄봤다.
- `cpp_핵심정리.md` 21·22·23번 — `mutex`/`lock_guard`/`unique_lock`, 이중검사 잠금(DCLP)과 `call_once`, 세마포어.
> 이 경험 덕분에 "동기화를 직접 해본 적 있나?"는 꼬리질문에 구체적으로 답할 수 있다.

**꼬리질문**
- **Q.** Unity에서 멀티스레드를 쓸 때 주의점은?
  **A.** **Unity API는 메인 스레드에서만 호출할 수 있다.** `transform.position` 접근조차 다른 스레드에서 하면 예외가 난다. 그래서 워커 스레드에서는 순수 계산만 하고 결과를 메인 스레드로 넘겨 반영해야 한다. Unity는 이를 안전하게 하려고 **Job System + Burst 컴파일러**를 제공하며, 여기서는 관리 객체가 아닌 `NativeArray` 같은 값 타입만 다룬다.
- **Q.** 경쟁 상태(race condition)와 데드락을 설명해보라.
  **A.** 경쟁 상태는 여러 스레드가 공유 자원에 동시 접근해 **실행 순서에 따라 결과가 달라지는** 상황이고, 데드락은 서로가 상대의 락을 기다리며 **영원히 멈추는** 상황이다. 데드락은 상호 배제·점유 대기·비선점·순환 대기 네 조건이 모두 성립할 때 발생하므로, **락 획득 순서를 전역적으로 통일**하면 순환 대기를 깨서 막을 수 있다. → `06_CS기본.md` 참고.

## Q2-26. LINQ란? 게임에서 써도 되나?

**30초 답변**
> LINQ는 컬렉션을 **SQL 비슷한 문법으로 질의**하는 기능으로, `Where`, `Select`, `OrderBy` 같은 확장 메서드로 필터링·변환·정렬을 간결하게 표현합니다. 지연 실행이라 실제 순회 전까지는 계산되지 않습니다. 다만 **내부적으로 열거자 객체와 람다 클로저를 힙에 할당**하기 때문에, 게임에서는 **매 프레임 도는 코드(`Update`)에서는 쓰지 않고** 초기화나 로딩처럼 빈도가 낮은 곳에만 씁니다.

**상세 설명**
```csharp
// 읽기 좋지만 할당이 있음
var nearby = enemies.Where(e => Vector3.Distance(e.pos, p) < 10f)
                    .OrderBy(e => e.hp)
                    .ToList();

// 핫패스에서는 직접 루프
for (int i = 0; i < enemies.Count; i++) {
    if ((enemies[i].pos - p).sqrMagnitude < 100f) { ... }   // sqrMagnitude로 sqrt도 회피
}
```
- 할당이 생기는 지점: ① 각 연산자마다 **열거자 객체**, ② 외부 변수를 캡처하는 **람다 클로저**, ③ `ToList()`/`ToArray()`의 **결과 컬렉션**.

**꼬리질문**
- **Q.** 지연 실행(lazy evaluation)이 뭔가?
  **A.** `Where`를 호출한 시점에는 아무 계산도 안 하고, `foreach`나 `ToList()`로 **실제 값을 요청할 때** 비로소 실행된다. 그래서 쿼리를 만들어두고 나중에 여러 번 순회하면 **매번 다시 계산**되는 함정이 있다. 결과를 재사용하려면 `ToList()`로 확정해야 한다.
- **Q.** `First()`와 `FirstOrDefault()`의 차이는?
  **A.** `First()`는 조건에 맞는 게 없으면 **예외**를 던지고, `FirstOrDefault()`는 **기본값**(참조 타입이면 `null`, 값 타입이면 0)을 반환한다. Unity에서는 `FirstOrDefault()`가 `null`을 반환할 때 Fake Null 문제와 겹칠 수 있어 주의해야 한다.

## Q2-27. 예외 처리와 `finally`의 동작은?

**30초 답변**
> `try` 블록에서 발생한 예외를 `catch`에서 잡고, `finally`는 **예외가 발생하든 안 하든, 심지어 중간에 `return`을 해도 반드시 실행**됩니다. 그래서 파일 닫기나 락 해제처럼 꼭 수행해야 하는 정리 작업을 `finally`에 둡니다. 다만 예외 처리는 비용이 크므로 **정상적인 흐름 제어에 예외를 쓰면 안 됩니다.**

**상세 설명**
```csharp
try {
    DoSomething();
    return 1;                  // return 해도
}
catch (FileNotFoundException e) {   // 구체적인 예외부터
    Debug.LogError(e.Message);
    throw;                     // 스택 트레이스 보존 (throw e; 는 스택을 덮어씀!)
}
catch (Exception e) { }        // 포괄적인 것은 마지막
finally {
    Cleanup();                 // 반드시 실행됨
}
```
- **`throw;` vs `throw e;`** — `throw e;`는 스택 트레이스를 현재 위치로 **초기화**해버려 원인 추적이 어려워진다. 다시 던질 땐 항상 `throw;`.
- `catch` 순서는 **구체적인 것 → 포괄적인 것**. 반대로 쓰면 컴파일 에러다.

**꼬리질문**
- **Q.** 예외가 비싼 이유는?
  **A.** 예외 객체 생성, **스택 트레이스 수집**, 스택 되감기(unwinding) 과정이 모두 비싸다. 특히 스택 트레이스 수집이 큰 비용이다. 그래서 "값이 없을 수 있다" 정도는 예외 대신 `TryGetValue` 패턴이나 `null` 반환으로 처리한다.
- **Q.** Unity에서 예외 처리를 어떻게 쓰나?
  **A.** 게임 로직에서는 거의 안 쓰고, **외부 자원을 다룰 때**(파일 읽기, JSON 파싱, 네트워크 응답) 주로 쓴다. 실제로 `unity_핵심정리.md` 16-4에서 AES CBC 암호화 구현 시 **길이 검증 예외 처리**를 추가한 사례가 있다.
- **Q.** `finally`가 실행되지 않는 경우도 있나?
  **A.** 있다. `Environment.Exit()` 호출, 프로세스 강제 종료, 스택 오버플로 같은 치명적 상황에서는 실행이 보장되지 않는다.

## Q2-28. `IDisposable`과 `using` 블록이란?

**30초 답변**
> `IDisposable`은 **명시적으로 정리해야 하는 자원을 가진 타입임을 나타내는 인터페이스**로, `Dispose()` 하나를 요구합니다. `using` 블록은 그 블록을 벗어날 때 **예외가 나더라도 `Dispose()`를 반드시 호출**해줍니다. GC는 파일 핸들이나 소켓 같은 **비관리 자원의 해제 시점을 보장하지 못하기 때문에** 이 패턴이 필요하며, C++의 RAII에 대응하는 C#의 장치입니다.

**상세 설명**
```csharp
using (var request = UnityWebRequestAssetBundle.GetAssetBundle(url, ver, 0)) {
    yield return request.SendWebRequest();
    ...
}   // 블록을 벗어나면 request.Dispose() 자동 호출

// C# 8부터는 중괄호 없이도 가능 (스코프 끝에서 Dispose)
using var sr = new StreamReader(path);
```
- `using`은 컴파일러가 `try { ... } finally { x?.Dispose(); }` 로 바꾼다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-21 — AssetBundle 로드에서 `using (UnityWebRequest request = ...)` 로 감싼 실제 코드. "왜 `using`으로 감쌌는가?"가 그 항목의 꼬리질문으로 이미 정리되어 있다.
- `cpp_핵심정리.md` 21번 — C++의 `lock_guard` RAII와 개념이 동일하다.

**꼬리질문**
- **Q.** GC가 있는데 왜 `Dispose`가 필요한가?
  **A.** GC는 **관리 메모리만** 다룬다. 파일 핸들, 소켓, DB 커넥션, 네이티브 메모리 같은 **비관리 자원**은 GC가 알지 못하며, 설령 finalizer로 정리한다 해도 **언제 실행될지 알 수 없다.** 파일을 계속 붙들고 있으면 다른 프로세스가 접근 못 하는 등 실질적 문제가 생기므로 명시적 해제가 필요하다.
- **Q.** `Dispose`와 finalizer(`~ClassName`)를 함께 쓰는 패턴은?
  **A.** 표준 **Dispose 패턴**이다. `Dispose()`가 호출되면 정리 후 `GC.SuppressFinalize(this)`로 finalizer를 건너뛰게 하고, 개발자가 `Dispose`를 깜빡했을 때만 finalizer가 최후의 안전망으로 동작한다. 다만 finalizer는 GC를 두 번 거치게 만들어 비싸므로 꼭 필요할 때만 만든다. → `unity_핵심정리.md` 5-11에 "C# 소멸자를 지양하는 이유"로 정리해뒀다.

## Q2-29. 직렬화와 역직렬화란?

**30초 답변**
> 직렬화는 **메모리상의 객체를 저장하거나 전송할 수 있는 형태(바이트, JSON, XML 등)로 변환**하는 것이고, 역직렬화는 그 반대입니다. 게임에서는 세이브 데이터 저장, 네트워크 패킷 전송, 설정 파일 관리에 쓰입니다. Unity는 자체 직렬화기를 가지고 있어 인스펙터 노출과 씬 저장에도 이 메커니즘을 사용합니다.

**상세 설명**
```csharp
[System.Serializable]
public class SaveData { public int level; public float hp; public string name; }

string json = JsonUtility.ToJson(data);              // 직렬화
SaveData loaded = JsonUtility.FromJson<SaveData>(json);  // 역직렬화
```
**Unity 직렬화기의 규칙 (자주 물어봄)**
- `public` 필드 또는 `[SerializeField]`가 붙은 `private` 필드만 대상.
- `static`, `const`, **프로퍼티**는 직렬화되지 않는다.
- **다차원 배열(`int[,]`)과 `Dictionary`는 지원하지 않는다.** 1차원 배열과 `List<T>`는 된다.
- 커스텀 클래스는 `[System.Serializable]`이 필요하다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **12-7** — `[System.Serializable]`과 **다차원 배열이 인스펙터에 노출되지 않는 한계**를 직접 확인한 항목.
- `unity_핵심정리.md` **22-1** — 그 한계를 실제로 우회한 사례(다차원 격자를 `List<bool>` + `index = y*width + x`로 저장).
- `unity_핵심정리.md` 16-1 — 저장 시스템을 `BinaryWriter` → 평문 `StreamWriter` → **`JsonUtility` + 암호화**로 3단계 발전시킨 실습.
- `unity_핵심정리.md` 21-1 — SimpleJSON 파서 사용.

**꼬리질문**
- **Q.** `JsonUtility`와 `Newtonsoft.Json`의 차이는?
  **A.** `JsonUtility`는 Unity 내장이라 **빠르고 가볍지만** `Dictionary`, 다형성, `null` 처리, 최상위 배열을 지원하지 않는다. `Newtonsoft.Json`(Json.NET)은 기능이 훨씬 풍부하지만 무겁고 IL2CPP에서 리플렉션 관련 주의가 필요하다. 간단한 세이브 데이터는 `JsonUtility`, 복잡한 구조는 Json.NET을 쓴다.
- **Q.** 세이브 데이터를 그냥 JSON으로 저장하면 문제가 없나?
  **A.** 문제가 있다. 평문이라 **유저가 열어서 수정**할 수 있다. 그래서 암호화하거나 체크섬으로 변조를 감지해야 한다. 실제로 `unity_핵심정리.md` 16-5에서 **원문 → Base64 → AES 암호화** 3단계를 직접 실험했고, "Base64는 인코딩이지 암호화가 아니다"라는 구분도 정리해뒀다. 다만 16-6에 기록했듯 **키가 클라이언트에 하드코딩되어 있으면 결국 뚫린다**는 한계도 인지하고 있다.
- **Q.** `BinaryFormatter`는 왜 쓰면 안 되나?
  **A.** **보안 취약점** 때문이다. 역직렬화 과정에서 임의 코드 실행이 가능해 .NET에서 **사용 중단(deprecated)** 되었고, Unity의 CoreCLR 전환 로드맵에서도 제거 대상으로 명시되어 있다. JSON이나 커스텀 바이너리 포맷을 써야 한다.

## Q2-30. 접근 제한자 종류를 설명하라

**30초 답변**
> `public`은 어디서나, `private`은 같은 클래스 안에서만, `protected`는 같은 클래스와 상속받은 자식에서만, `internal`은 **같은 어셈블리 안에서만** 접근할 수 있습니다. `protected internal`은 둘 중 하나만 만족해도 되고(합집합), `private protected`는 둘 다 만족해야 합니다(교집합). 클래스 멤버의 기본값은 `private`입니다.

**상세 설명**

| 제한자 | 같은 클래스 | 자식 클래스 | 같은 어셈블리 | 외부 어셈블리 |
|---|---|---|---|---|
| `private` | O | X | X | X |
| `protected` | O | O | X | X |
| `internal` | O | O(같은 어셈블리) | O | X |
| `protected internal` | O | O | O | X |
| `private protected` | O | O(같은 어셈블리) | X | X |
| `public` | O | O | O | O |

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-12 — `virtual`/`override` 다형성과 함께 **`internal` 접근제한자**를 다룬 항목.
- Unity에서는 `[SerializeField] private` 조합이 가장 권장되는 패턴 — 인스펙터에는 노출하되 다른 스크립트가 함부로 못 바꾸게 한다.

**꼬리질문**
- **Q.** Unity에서 `public` 필드를 쓰면 안 되는 이유는?
  **A.** 인스펙터에 노출하려고 `public`을 쓰는 경우가 많은데, 그러면 **다른 스크립트도 마음대로 접근**할 수 있어 캡슐화가 깨진다. `[SerializeField] private`을 쓰면 인스펙터 노출은 유지하면서 외부 접근은 막을 수 있다.
- **Q.** 어셈블리가 Unity에서 뭔가?
  **A.** 컴파일 단위(DLL)다. 기본적으로 모든 스크립트가 `Assembly-CSharp.dll` 하나로 컴파일되지만, **Assembly Definition(asmdef)** 파일로 폴더 단위 어셈블리를 나누면 ① 변경 시 **해당 어셈블리만 재컴파일**되어 빌드 시간이 줄고, ② `internal`로 모듈 경계를 강제할 수 있다.
  > 관련 경험: `unity_핵심정리.md` 12-5에서 **`MonoBehaviour`를 별도 C# 클래스 라이브러리 DLL로 빌드**해본 실습이 있다. 어셈블리 분리의 극단적 형태를 직접 다뤄본 셈이다.

## Q2-31. `var`와 `dynamic`의 차이는?

**30초 답변**
> `var`는 **컴파일 타임에 타입이 확정**되는 타입 추론입니다. 단지 개발자가 타입 이름을 안 쓸 뿐이고, 컴파일된 결과는 명시적으로 쓴 것과 완전히 동일합니다. `dynamic`은 **타입 검사를 런타임으로 미루는** 것이라 컴파일러가 아무 검사도 하지 않고, 잘못된 멤버를 호출해도 실행 중에야 예외가 납니다. 성능과 안전성 모두 `var`가 낫고, `dynamic`은 특수한 상황에서만 씁니다.

**상세 설명**
```csharp
var a = 10;          // int로 확정. a = "hi"; 는 컴파일 에러
dynamic b = 10;      // 런타임 결정. b = "hi"; 도 가능
b.NoSuchMethod();    // 컴파일 통과, 실행 시 RuntimeBinderException
```
- `var`는 **초기화가 필수**다(타입을 추론할 근거가 있어야 하므로). 필드에는 못 쓰고 지역 변수에만 쓸 수 있다.
- `var`를 꼭 써야 하는 경우: **무명 형식(anonymous type)** — 이름이 없어서 다른 방법이 없다.

**내 프로젝트 연결**
- `unity_핵심정리.md` 5-17 — **`var` 타입 추론과 무명 형식** 실습.

**꼬리질문**
- **Q.** `var`를 남용하면 안 되는 이유는?
  **A.** 오른쪽에서 타입을 추론하기 어려운 경우 **가독성이 떨어진다.** `var result = GetData();` 만 보면 반환 타입을 알 수 없다. 일반적으로 `new`나 캐스팅으로 타입이 명백할 때만 쓰는 게 좋다.
- **Q.** Unity에서 `dynamic`을 쓸 수 있나?
  **A.** **IL2CPP 빌드에서는 사실상 못 쓴다.** `dynamic`은 런타임 코드 생성에 의존하는데 AOT 컴파일에서는 불가능하다. Mono 백엔드에서는 되지만 권장하지 않는다.

## Q2-32. C#이 C++보다 느린가?

**30초 답변**
> 일반적으로는 C++이 빠르지만 **차이가 항상 크지는 않고, 경우에 따라 역전되기도 합니다.** C#은 JIT 컴파일이라 첫 실행에 워밍업 비용이 있고 GC로 인한 예측 불가능한 멈춤이 있으며 메모리 레이아웃을 직접 통제하기 어렵습니다. 반면 JIT은 **실행 중인 CPU에 맞춰 최적화**할 수 있고, 힙 할당 자체는 포인터를 미는 것이라 C++의 `malloc`보다 빠를 수도 있습니다. 게임에서 문제가 되는 건 평균 속도보다 **GC로 인한 프레임 스파이크(최악 지연)**입니다.

**상세 설명**

| 관점 | C++ | C# |
|---|---|---|
| 컴파일 | AOT(네이티브) | IL → JIT (또는 IL2CPP로 AOT) |
| 메모리 제어 | 완전 통제 | GC에 위임 |
| 할당 비용 | `malloc` 탐색 | 포인터 밀기(빠름) |
| 해제 비용 | 즉시, 예측 가능 | GC 시점 불명, **스파이크** |
| 캐시 최적화 | 레이아웃 직접 설계 | 제한적 |
| 실행 시 최적화 | 불가(컴파일 시 확정) | **JIT이 런타임 정보 활용** |

- 게임에서 진짜 중요한 건 **평균 FPS가 아니라 1% low(최악 프레임)** 다. GC 스파이크 하나가 체감 품질을 크게 떨어뜨린다.
- 그래서 Unity는 성능이 중요한 부분에 **Burst 컴파일러 + Job System + DOTS**를 제공해 C# 코드를 C++급 네이티브로 컴파일한다.

**꼬리질문**
- **Q.** 그럼 왜 게임 로직을 C#으로 짜나?
  **A.** **개발 생산성** 때문이다. 메모리 버그가 줄고, 반복 작업이 빠르고, 툴 생태계가 좋다. 엔진 코어처럼 성능이 결정적인 부분은 C++로 짜고, 자주 바뀌는 게임 로직은 C#으로 짜는 **하이브리드 구조**가 Unity의 설계다.
- **Q.** IL2CPP를 쓰면 C++만큼 빨라지나?
  **A.** 아니다. IL2CPP는 IL을 C++로 변환해 AOT 컴파일하므로 **JIT 워밍업이 없고 실행 속도가 개선**되지만, **GC는 여전히 Boehm이고 메모리 모델도 그대로**다. 그래서 GC 스파이크 문제는 남는다. 진짜 C++급 성능이 필요하면 DOTS/Burst나 네이티브 플러그인으로 가야 한다.
  > 관련 경험: `unity_핵심정리.md` 12번(UnityDll)에서 **C++ 네이티브 DLL을 만들어 P/Invoke로 연동**해본 적이 있다. "성능이 필요한 부분을 네이티브로 뺀다"는 이 답변의 실전 사례로 쓸 수 있다.
