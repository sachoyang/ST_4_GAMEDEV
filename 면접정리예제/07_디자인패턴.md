## Q7-01. 디자인 패턴이란? 왜 알아야 하나?

**30초 답변**
> 소프트웨어 설계에서 **반복적으로 나타나는 문제에 대한 검증된 해결 방식**을 정리한 것입니다. 매번 처음부터 고민하지 않아도 되고, 무엇보다 **"여기는 옵저버 패턴을 썼다"** 한마디로 팀원과 구조를 공유할 수 있는 **공통 어휘**가 된다는 점이 큽니다. 다만 패턴은 목적이 아니라 도구라서, 문제에 맞지 않는데 억지로 적용하면 오히려 복잡해집니다.

**상세 설명**

| 분류 | 목적 | 예 |
|---|---|---|
| **생성 패턴** | 객체 생성 방식 | 싱글턴, 팩토리, 빌더, 프로토타입 |
| **구조 패턴** | 객체 조합 | 어댑터, 퍼사드, 데코레이터, 컴포지트 |
| **행위 패턴** | 객체 간 상호작용 | 옵저버, 전략, 상태, 커맨드 |

**게임에서 특히 자주 쓰이는 것**: 싱글턴(매니저), 옵저버(이벤트), 상태(캐릭터 AI), 오브젝트 풀(총알/이펙트), **컴포넌트(Unity의 근간)**, 커맨드(입력/리플레이), 전략(공격 방식 교체).

**꼬리질문**
- **Q.** 면접에서 패턴을 물어보는 이유는?
  **A.** 패턴 이름을 외웠는지가 아니라, **"어떤 문제 상황에서 왜 이 구조를 택했는가"** 를 설명할 수 있는지를 본다. 그래서 답할 때 반드시 **자기 프로젝트의 실제 적용 사례**를 붙이는 게 좋다.

## Q7-02. 싱글턴 패턴을 설명하라 `★★`

**30초 답변**
> **클래스의 인스턴스가 프로그램 전체에 하나만 존재하도록 보장하고 전역 접근점을 제공하는** 생성 패턴입니다. 생성자를 감추고 정적 메서드나 프로퍼티로만 인스턴스를 얻게 만듭니다. 게임의 매니저 클래스에 흔히 쓰이지만, **전역 상태를 만들어 결합도를 높이고 테스트를 어렵게 하기 때문에 남용하면 안 됩니다.**

> **실전 적용 경험(3단계 진화, 제네릭 싱글턴, Unity 특유의 함정)은 `03_Unity.md` Q3-07에 자세히 정리되어 있다.** 면접에서 "프로젝트에서 쓴 싱글턴"을 물으면 그쪽 내용으로 답한다.

**상세 설명**
```csharp
// 순수 C# - 지연 초기화 + 스레드 안전
public sealed class GameData {
    private static readonly Lazy<GameData> instance = new(() => new GameData());
    public static GameData Instance => instance.Value;
    private GameData() { }        // 외부 생성 차단
}
```
```cpp
// C++ - Meyers 싱글턴 (C++11부터 스레드 안전 보장)
class Logger {
public:
    static Logger& Instance() {
        static Logger inst;       // 최초 호출 시 1회만 초기화
        return inst;
    }
private:
    Logger() = default;
    Logger(const Logger&) = delete;              // 복사 차단
    Logger& operator=(const Logger&) = delete;
};
```

**내 프로젝트 연결**
- `cpp_핵심정리.md` **20번** — 싱글톤 두 가지 구현과 **스레드 안전성**, **22번** — 이중검사 잠금(DCLP)과 `call_once`.
- `unity_핵심정리.md` **5-8**(순수 C# vs MonoBehaviour 싱글턴), **5-16**(제네릭 싱글턴 진화, `where T : MonoSingleton3<T>`), **4-1**(정적 인스턴스 매니저), **15-1**(**싱글턴을 정적 클래스로 리팩터링** — 싱글턴이 항상 답은 아니라는 사례).

**꼬리질문**
- **Q.** 싱글턴과 정적 클래스의 차이는?
  **A.** 싱글턴은 **인스턴스라서 인터페이스를 구현하거나 상속할 수 있고 다형성이 가능**하며, 생성 시점을 제어할 수 있다. 정적 클래스는 그런 게 안 되지만 더 단순하다. **상태가 없고 유틸리티성이면 정적 클래스**가 낫다. 실제로 로컬라이제이션을 싱글턴에서 정적 클래스로 바꿔본 적이 있다(15-1).
- **Q.** 왜 안티 패턴이라고도 하나?
  **A.** ① 전역 상태라 어디서든 바뀔 수 있어 **버그 추적이 어렵고**, ② 의존성이 파라미터에 드러나지 않아 **숨겨진 결합**이 생기며, ③ **단위 테스트에서 교체(mock)가 불가능**하고, ④ 생명주기 관리가 까다롭다. 대안으로는 **의존성 주입(DI)** 이나 `ScriptableObject` 기반 참조가 있다.

## Q7-03. 옵저버 패턴을 설명하라

**30초 답변**
> **한 객체의 상태가 바뀌면 그것을 구독하고 있는 여러 객체에게 자동으로 알리는** 행위 패턴입니다. 발행자(Subject)는 구독자가 누구인지 구체적으로 몰라도 되고, 구독자는 필요할 때 등록·해제만 하면 되어 **결합도가 크게 낮아집니다.** C#에서는 `delegate`와 `event`가 이 패턴을 언어 차원에서 지원합니다.

**상세 설명**
```csharp
public class PlayerHealth : MonoBehaviour {
    public event Action<int, int> OnHealthChanged;   // 발행자
    private int hp;
    public void TakeDamage(int d) {
        hp -= d;
        OnHealthChanged?.Invoke(hp, maxHp);          // 누가 듣는지 몰라도 됨
    }
}

public class HealthBarUI : MonoBehaviour {           // 구독자
    [SerializeField] private PlayerHealth player;
    void OnEnable()  => player.OnHealthChanged += UpdateBar;
    void OnDisable() => player.OnHealthChanged -= UpdateBar;   // 반드시 해제!
    void UpdateBar(int cur, int max) => bar.fillAmount = (float)cur / max;
}
```
- **장점**: 체력이 바뀔 때 UI, 사운드, 이펙트, 업적 시스템이 각자 반응할 수 있고, 새 반응을 추가해도 `PlayerHealth`는 손대지 않는다(**OCP** 만족).
- **주의**: 구독 해제를 안 하면 **메모리 누수**와 파괴된 객체 호출로 인한 예외가 생긴다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **5-3**(`event` vs `delegate` — 캡슐화), **5-4**(구독/해제와 MonoBehaviour 생명주기).
- `unity_핵심정리.md` **15-3** — 로컬라이제이션에서 **델리게이트 이벤트로 언어 변경을 전파**한 실전 사례. 처음엔 값을 직접 전달하다가 **신호만 전달하는 방식으로 설계를 개선**한 과정까지 기록해뒀다. 이게 옵저버 패턴 설계 판단의 좋은 예시다.
- `unity_핵심정리.md` **5-15** — UI 이벤트 후킹 인터페이스(`IPointerClickHandler` 등)도 넓게 보면 같은 발상이다.

**꼬리질문**
- **Q.** 이벤트가 너무 많아지면?
  **A.** 흐름을 추적하기 어려워진다("이 함수는 누가 부르지?"). 그래서 **이벤트 버스나 중앙 이벤트 매니저**로 모으거나, 이벤트 이름과 흐름을 문서화한다. 결합도를 낮추는 대신 **추적성을 잃는 트레이드오프**가 있다는 걸 인지해야 한다.
- **Q.** `UnityEvent`와 C# `event` 중 뭘 쓰나?
  **A.** **인스펙터에서 연결해야 하면 `UnityEvent`**(기획자가 코드 없이 배선 가능), **성능이 중요한 내부 로직은 C# `event`**(리플렉션 기반이 아니라 빠름). → `02_CSharp.md` Q2-14.

## Q7-04. 상태(State) 패턴을 설명하라

**30초 답변**
> **객체의 상태를 각각 클래스로 분리하고, 상태 객체를 교체함으로써 행동이 바뀌게 하는** 패턴입니다. `if/else`나 `switch`로 상태를 분기하던 코드가 상태가 늘어날수록 감당이 안 되는 문제를 해결합니다. 새 상태를 추가할 때 **기존 코드를 건드리지 않고 클래스만 추가**하면 되어 개방-폐쇄 원칙을 만족합니다.

**상세 설명**
```csharp
// Before - 상태가 늘 때마다 이 분기문을 계속 고쳐야 함
void Update() {
    if (state == State.Idle)        { /* ... */ }
    else if (state == State.Patrol) { /* ... */ }
    else if (state == State.Chase)  { /* ... */ }
    // 상태 추가할 때마다 여기를 수정
}

// After - State 패턴
public abstract class EnemyState {
    public abstract void Enter(Enemy e);
    public abstract void Update(Enemy e);
    public abstract void Exit(Enemy e);
}
public class ChaseState : EnemyState { /* 추격 로직만 */ }

public class Enemy : MonoBehaviour {
    private EnemyState current;
    public void ChangeState(EnemyState next) {
        current?.Exit(this);
        current = next;
        current.Enter(this);
    }
    void Update() => current?.Update(this);
}
```

**내 프로젝트 연결 — 세 가지 방식을 다 구현해봤다**
- `unity_핵심정리.md` **13-1** — FSM을 **① 절차적 `if/else` → ② 순수 C# State 패턴 → ③ Unity Animator `StateMachineBehaviour`** 세 가지로 순서대로 다시 구현한 비교 사례. **"같은 문제를 여러 기법으로 풀어본" 가장 명확한 근거 자료**다.
- `unity_핵심정리.md` **13-2**(`StateMachineBehaviour`), **13-3**(Animator 파라미터로 전환 제어 — 책임 분리), **13-4**(**커스텀 Script Template으로 상태 클래스 보일러플레이트 자동 생성**).
- `unity_핵심정리.md` **8-6** — zombieStudy의 **코루틴 기반 우선순위 FSM**(또 다른 접근 방식).

**꼬리질문**
- **Q.** 세 방식 중 뭐가 제일 나았나?
  **A.** 상황에 따라 다르다는 걸 직접 해보고 알았다. **`if/else`** 는 상태가 2~3개면 오히려 단순하고 명확하다. **State 패턴**은 상태별 로직이 복잡하고 늘어날 여지가 있을 때 유리하지만 클래스가 많아진다. **Animator `StateMachineBehaviour`** 는 애니메이션과 자연스럽게 묶이고 시각적으로 보이지만, 그래프가 복잡해지면 디버깅과 버전 관리가 어렵다. 실무에서는 **애니메이션 전환은 Animator, 게임 로직 상태는 코드 FSM**으로 나누는 경우가 많다.
- **Q.** State 패턴에서 상태 객체를 매번 `new` 하면?
  **A.** 상태 전환마다 **힙 할당이 생겨 GC 부담**이 된다. 상태 객체는 보통 상태를 갖지 않으므로 **미리 만들어두고 재사용**하거나, `Dictionary<StateType, State>`에 캐싱해두는 게 좋다. → `03_Unity.md` Q3-16.

## Q7-05. 전략(Strategy) 패턴을 설명하라

**30초 답변**
> **알고리즘을 인터페이스 뒤로 캡슐화해서 런타임에 교체할 수 있게 하는** 패턴입니다. 예를 들어 공격 방식(근접/원거리/마법)을 각각 클래스로 만들고 캐릭터가 그중 하나를 참조하게 하면, 무기를 바꾸는 것만으로 공격 로직이 바뀝니다. 상태 패턴과 구조는 비슷하지만, **상태 패턴은 상태가 스스로 다음 상태를 결정하고 전략 패턴은 외부에서 골라 넣어준다**는 점이 다릅니다.

**상세 설명**
```csharp
public interface IAttackStrategy { void Attack(Transform target); }

public class MeleeAttack  : IAttackStrategy { public void Attack(Transform t) { /* 근접 */ } }
public class RangedAttack : IAttackStrategy { public void Attack(Transform t) { /* 원거리 */ } }

public class Character : MonoBehaviour {
    private IAttackStrategy strategy;
    public void EquipWeapon(IAttackStrategy s) => strategy = s;   // 런타임 교체
    public void DoAttack(Transform t) => strategy?.Attack(t);
}
```
| | 상태 패턴 | 전략 패턴 |
|---|---|---|
| 전환 주체 | **상태 자신이 결정** | **외부(클라이언트)가 지정** |
| 의도 | 상태에 따른 행동 변화 | 알고리즘 교체 |
| 상태 간 인지 | 서로를 알기도 함 | 서로 모름 |

**내 프로젝트 연결**
- `unity_핵심정리.md` **5-10**(인터페이스 다중 구현), **5-14**(`List<T>` + **`Predicate` 델리게이트** — 델리게이트로 전략을 주입하는 경량 버전).
- `cpp_핵심정리.md` **10번** — 컴포지션 기반 책임 분리 설계.

**꼬리질문**
- **Q.** C#에서는 인터페이스 대신 델리게이트로도 되지 않나?
  **A.** 맞다. 전략이 **메서드 하나뿐이면 `Action`/`Func` 델리게이트로 충분**하고 훨씬 간결하다. 전략에 여러 메서드나 상태가 필요하면 인터페이스가 낫다. `List.Sort(comparison)`이나 `RemoveAll(predicate)`가 델리게이트 방식 전략의 예다.

## Q7-06. 팩토리 패턴을 설명하라

**30초 답변**
> **객체 생성 로직을 별도의 클래스나 메서드로 분리하는** 생성 패턴입니다. 사용하는 쪽이 구체적인 클래스 이름을 몰라도 되어 결합도가 낮아지고, 생성 방식이 바뀌어도 팩토리만 고치면 됩니다. 게임에서는 적 종류에 따라 다른 프리팹을 만들거나, 아이템 타입별로 다른 클래스를 생성할 때 씁니다.

**상세 설명**
```csharp
public class EnemyFactory : MonoBehaviour {
    [SerializeField] private EnemyData[] enemyDataList;

    public Enemy Create(EnemyType type, Vector3 pos) {
        EnemyData data = enemyDataList.First(d => d.type == type);
        Enemy e = Instantiate(data.prefab, pos, Quaternion.identity);
        e.Initialize(data);                    // 생성 + 초기화를 한 곳에
        return e;
    }
}
// 사용하는 쪽은 구체 클래스를 모른다
factory.Create(EnemyType.Slime, spawnPoint);
```

## Q7-07. 오브젝트 풀 패턴을 설명하라

**30초 답변**
> 객체를 필요할 때마다 생성·파괴하는 대신 **미리 만들어두고 재사용하는** 패턴입니다. 생성·파괴 비용이 크거나 빈번한 경우에 효과적이고, 특히 **GC가 있는 환경에서는 가비지 자체를 만들지 않아 프레임 스파이크를 막는** 게 핵심 이점입니다. 총알, 이펙트, 적처럼 자주 생성되는 오브젝트에 필수적으로 씁니다.

> **Unity에서의 구현 코드와 주의점(상태 초기화, 풀이 빌 때 대응, `UnityEngine.Pool`)은 `03_Unity.md` Q3-16에 자세히 정리되어 있다.**

**상세 설명**
```
[풀]  ┌──── Get() ────▶  사용 중인 객체
      │                        │
      └──── Release() ◀────────┘
      (파괴하지 않고 비활성화 후 반납)
```
- **Unity에서 특히 중요한 이유**: Boehm GC가 힙을 압축하지 않아 할당/해제 반복이 **단편화를 누적**시키고, 세대 구분이 없어 **힙이 커질수록 GC 시간이 길어진다.** → `02_CSharp.md` Q2-09.

## Q7-08. 컴포넌트 패턴이란? Unity와 무슨 관계인가?

**30초 답변**
> **기능을 독립적인 컴포넌트로 나누고, 객체는 필요한 컴포넌트를 조합해서 갖게 하는** 패턴입니다. 상속 계층을 깊게 만드는 대신 조합으로 기능을 구성해서, "날면서 헤엄치는 적" 같은 다중 특성 문제를 깔끔하게 해결합니다. **Unity의 `GameObject` + `Component` 구조가 바로 이 패턴**이고, 이것이 Unity 아키텍처의 근간입니다.

**상세 설명**
```
상속 방식의 한계
    Enemy
   /     \
FlyingEnemy  SwimmingEnemy
        \    /
   "날면서 헤엄치는 적"?  → 다중 상속 불가 / 코드 중복

컴포넌트 방식
GameObject "적"
  + Transform
  + Rigidbody
  + Health
  + FlyMovement      ← 필요한 것만 조합
  + SwimMovement     ← 둘 다 붙이면 됨
```
- **"상속보다 컴포지션을 선호하라"** 는 원칙의 대표적 구현이다. → `01_C_CPP.md` Q1-10 꼬리질문.
- **장점**: 기능 재사용, 런타임에 `AddComponent`/`Destroy`로 능력 추가·제거, 각 컴포넌트를 독립적으로 테스트 가능.
- **단점**: 컴포넌트 간 통신이 필요할 때 `GetComponent` 의존이 생기고, 오브젝트에 붙은 컴포넌트가 많아지면 전체 동작 파악이 어려워진다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **10번** — **컴포지션 기반 책임 분리 설계**를 C++에서 직접 실습했다. Unity 컴포넌트 구조를 이해하는 기반이 된다.

**꼬리질문**
- **Q.** ECS는 컴포넌트 패턴과 뭐가 다른가?
  **A.** Unity의 기본 컴포넌트 패턴은 **컴포넌트가 데이터와 로직을 둘 다 가진다**(`MonoBehaviour`에 필드와 `Update`가 함께 있음). **ECS(Entity Component System)** 는 **컴포넌트를 순수 데이터로만** 두고 로직을 System으로 완전히 분리한다. 그러면 같은 종류의 데이터를 배열에 모아둘 수 있어 **캐시 효율이 극대화**된다. Unity DOTS가 이 방향이다. → `04_자료구조_알고리즘.md` Q4-25.
- **Q.** 컴포넌트끼리 어떻게 통신하나?
  **A.** ① `GetComponent`로 참조를 캐싱해 직접 호출(가장 일반적, `Awake`에서 캐싱), ② **이벤트/옵저버**로 느슨하게 연결, ③ `SendMessage`(문자열 기반이라 비권장 — `03_Unity.md` Q3-33), ④ 인터페이스로 추상화(`GetComponent<IDamageable>()`).

## Q7-09. 커맨드 패턴을 설명하라

**30초 답변**
> **요청(동작)을 객체로 캡슐화해서 실행을 나중으로 미루거나, 저장하거나, 되돌릴 수 있게 하는** 패턴입니다. 각 명령이 `Execute()`와 `Undo()`를 갖게 하면 실행 취소가 자연스럽게 구현되고, 명령들을 큐나 스택에 담아 리플레이나 매크로도 만들 수 있습니다. 게임에서는 입력 리매핑, 되돌리기, 리플레이 저장, 턴제 게임의 행동 큐에 씁니다.

**상세 설명**
```csharp
public interface ICommand { void Execute(); void Undo(); }

public class MoveCommand : ICommand {
    private readonly Transform t;
    private readonly Vector3 delta;
    public MoveCommand(Transform t, Vector3 d) { this.t = t; delta = d; }
    public void Execute() => t.position += delta;
    public void Undo()    => t.position -= delta;
}

public class CommandInvoker {
    private readonly Stack<ICommand> history = new();
    public void Run(ICommand c) { c.Execute(); history.Push(c); }
    public void UndoLast() { if (history.Count > 0) history.Pop().Undo(); }
}
```
- **입력 리매핑**: 키와 커맨드를 `Dictionary<KeyCode, ICommand>`로 묶으면, 키 설정 변경이 딕셔너리만 바꾸는 일이 된다.
- **리플레이**: 실행된 커맨드를 시간과 함께 기록해두고 순서대로 재생하면 리플레이가 된다. 네트워크의 **락스텝** 방식도 같은 발상이다(입력만 전송). → `06_CS기본.md` Q6-21.

**내 프로젝트 연결**
- `unity_핵심정리.md` **22-6** — 에디터 툴에서 `Undo.RecordObject`로 실행 취소를 구현했다. **Unity 에디터의 Undo 시스템이 커맨드 패턴의 실제 응용**이다.
- `04_자료구조_알고리즘.md` Q4-01 — 되돌리기에 **스택**이 쓰이는 이유가 여기 있다.

**꼬리질문**
- **Q.** `Undo`를 구현하는 두 가지 방식은?
  **A.** ① **역연산 저장** — 위 코드처럼 반대 동작을 정의(메모리 효율적이지만 모든 동작에 역연산이 정의 가능해야 함), ② **상태 스냅샷 저장(메멘토 패턴)** — 실행 전 상태를 통째로 저장(간단하지만 메모리를 많이 씀). Unity의 `Undo.RecordObject`는 스냅샷 방식이다.

## Q7-10. MVC / MVP / MVVM의 차이는?

**30초 답변**
> 셋 다 **데이터(Model)와 화면(View)을 분리해서 UI 로직이 게임 로직과 뒤섞이지 않게 하는** 아키텍처 패턴입니다. **MVC**는 Controller가 입력을 받아 Model을 바꾸고 View가 Model을 관찰하며, **MVP**는 Presenter가 View와 Model 사이를 중재해 View가 Model을 전혀 모르게 하고, **MVVM**은 ViewModel과 View를 **데이터 바인딩으로 자동 연결**합니다. Unity에서는 데이터 바인딩 지원이 제한적이라 **MVP나 그 변형을 쓰는 경우가 많습니다.**

**상세 설명**

| | 흐름 | View ↔ Model | 특징 |
|---|---|---|---|
| **MVC** | Controller → Model → View | View가 Model을 앎 | 고전적 |
| **MVP** | View ↔ **Presenter** ↔ Model | **완전 분리** | 테스트 용이 |
| **MVVM** | View ↔(바인딩)↔ ViewModel ↔ Model | 바인딩으로 자동 | 바인딩 프레임워크 필요 |

- **왜 필요한가**: UI 코드에 게임 로직을 섞으면 ① UI를 바꿀 때 로직까지 손대야 하고, ② 로직을 **UI 없이 테스트할 수 없으며**, ③ 같은 데이터를 여러 UI에서 보여주기 어렵다.
- Unity에서는 UI Toolkit이 데이터 바인딩을 지원하기 시작했지만, uGUI 기반에서는 보통 **이벤트(옵저버)로 Model 변경을 View에 전파**하는 간이 MVP 형태를 쓴다.

**내 프로젝트 연결**
- `winapi_핵심정리.md` **10번** — **엔진/윈도우 책임 분리 설계**. WinAPI 시절부터 "UI와 로직을 분리한다"는 같은 문제의식을 다뤘고, `00_작업계획.md`에도 이 연결고리를 미리 걸어뒀다(**"UI/로직 책임 분리(winapi 10번 ↔ MonoBehaviour vs 순수 C# 클래스)"**).

**꼬리질문**

  **A.** 규모에 따라 다르다. 작은 프로젝트에서 억지로 적용하면 파일만 늘어난다. 다만 **`MonoBehaviour`에 게임 로직을 다 넣지 말고 순수 C# 클래스로 로직을 빼는 것**만으로도 이점이 크다 — 테스트 가능하고, `MonoBehaviour`를 `new`로 못 만드는 제약(`03_Unity.md` Q3-08)에서도 자유롭다.

## Q7-11. 어댑터 / 퍼사드 패턴을 설명하라

**30초 답변**
> **어댑터**는 **호환되지 않는 인터페이스를 내가 원하는 형태로 변환해주는 중간 계층**입니다. 서드파티 라이브러리나 SDK를 내 코드 구조에 맞춰 감쌀 때 씁니다. **퍼사드**는 **복잡한 서브시스템 여러 개를 하나의 단순한 인터페이스로 감싸는** 것으로, 사용하는 쪽이 내부 복잡도를 몰라도 되게 만듭니다.

**상세 설명**
```csharp
// 어댑터 - 서드파티 SDK를 내 인터페이스에 맞춤
public interface IAdService { void ShowRewardAd(Action onReward); }

public class UnityAdsAdapter : IAdService {           // SDK가 바뀌어도
    public void ShowRewardAd(Action onReward) {        // 이 클래스만 고치면 됨
        Advertisement.Show("rewardedVideo", new ShowOptions { ... });
    }
}

// 퍼사드 - 복잡한 초기화를 하나로
public class GameBootstrap : MonoBehaviour {
    public void StartGame() {
        SaveSystem.Load();
        AudioManager.Initialize();
        Localization.Load();
        SceneLoader.LoadAsync("MainMenu");
    }
}
```
- **어댑터의 실질적 가치**: 서드파티 SDK를 코드 전역에서 직접 부르면 **SDK 교체 시 모든 호출부를 고쳐야 한다.** 어댑터로 감싸두면 교체 비용이 한 클래스로 국한된다.

  **A.** **직접 호출을 코드 전역에 퍼뜨리지 말고 래퍼(어댑터)를 하나 만들어** 그 뒤에 숨긴다. 그러면 ① 라이브러리 교체가 쉽고, ② 테스트 시 가짜 구현으로 바꿔치기할 수 있으며, ③ 플랫폼별 분기를 한 곳에 모을 수 있다. 실제로 여러 번 API 마이그레이션을 겪어보니 이게 왜 중요한지 체감했다.

## Q7-12. 널 오브젝트 패턴을 설명하라

**30초 답변**
> `null` 대신 **"아무것도 하지 않는" 기본 구현 객체를 반환해서 null 체크를 없애는** 패턴입니다. 호출하는 쪽이 매번 `if (x != null)`을 쓰지 않아도 되어 코드가 단순해지고 `NullReferenceException` 위험이 줄어듭니다. 다만 **진짜 오류인 상황까지 조용히 넘어가게 만들 수 있어** 남용하면 디버깅이 어려워집니다.

**상세 설명**
```csharp
public interface IWeapon { void Attack(); }
public class Sword    : IWeapon { public void Attack() { /* 베기 */ } }
public class NoWeapon : IWeapon { public void Attack() { /* 아무것도 안 함 */ } }

public class Player {
    private IWeapon weapon = new NoWeapon();      // null이 아닌 기본값
    public void DoAttack() => weapon.Attack();     // null 체크 불필요
}
```
- Unity에서 특히 의미가 있는 이유: **Unity 오브젝트의 null 체크는 오버로딩된 `==` 때문에 일반 C# 객체와 다르게 동작**한다(Fake Null). 널 오브젝트로 대체하면 이 혼란을 피할 수 있는 경우가 있다. → `03_Unity.md` Q3-25.

**꼬리질문**
- **Q.** 언제 쓰면 안 되나?
  **A.** **없다는 사실 자체가 중요한 정보일 때**다. 예를 들어 "저장 파일이 없다"를 널 오브젝트로 감추면 새 게임 시작 처리를 놓친다. 조용히 넘어가는 게 위험한 곳에서는 명시적으로 실패를 알려야 한다.

## Q7-13. 패턴을 남용하면 어떤 문제가 생기나?

**30초 답변**
> 문제 규모에 비해 **구조가 과도해져서(over-engineering) 오히려 이해와 수정이 어려워집니다.** 간단한 `if` 두 줄이면 될 것을 State 패턴으로 만들어 클래스 다섯 개로 늘리면, 코드를 읽는 사람이 흐름을 따라가기 위해 파일 여러 개를 오가야 합니다. 패턴은 **문제가 실제로 나타났을 때 적용하는 도구**이지, 처음부터 갖춰야 할 형식이 아닙니다.

**상세 설명**

| 남용 증상 | 결과 |
|---|---|
| 모든 매니저를 싱글턴으로 | 전역 상태 난립, 테스트 불가, 초기화 순서 지옥 |
| 상태 2개인데 State 패턴 | 파일만 늘고 가독성 하락 |
| 인터페이스를 무조건 추출 | 구현체가 하나뿐인 빈 껍데기 |
| 이벤트로만 통신 | 호출 흐름 추적 불가 |
| 과도한 추상화 계층 | 실제 코드를 찾기까지 여러 단계 |

**균형 잡힌 답변 방향**
> "패턴을 아는 것"보다 **"언제 쓰지 않을지 아는 것"** 이 더 중요하다. 실제로 내 FSM 프로젝트에서 세 가지 방식을 다 구현해보니, **상태가 적을 땐 `if/else`가 오히려 명확했다.** 문제가 커지는 걸 확인한 뒤 리팩터링하는 게 맞다는 걸 직접 겪었다(`unity_핵심정리` 13-1).

**꼬리질문**
- **Q.** 그럼 언제 패턴을 도입하나?
  **A.** **같은 종류의 수정이 반복될 때**다. 예를 들어 "적 상태를 추가할 때마다 `Update`의 분기문을 고치고 있다"면 State 패턴 도입 신호다. 미리 예측해서 넣기보다 **실제 통증이 나타났을 때** 리팩터링하는 게 낫다.
- **Q.** YAGNI가 뭔가?
  **A.** "You Aren't Gonna Need It" — **지금 필요하지 않은 기능은 만들지 말라**는 원칙이다. "나중에 확장할 수도 있으니까" 미리 만든 추상화는 대부분 실제로 필요한 형태와 다르게 만들어져 결국 다시 고치게 된다.
  > 관련해서 내 코드에서 실제 사례를 발견한 적이 있다 — `unity_핵심정리.md` 18-8의 **`PairNode`/`IEquatable` 실행 대기열**, 12-4의 **구현했지만 호출하지 않는 마샬링 함수**, 14-4의 **직접 만들었지만 쓰이지 않는 커스텀 라이팅 함수**. 셋 다 "만들었지만 실제로 연결되지 않은 확장 설계"라 같은 패턴으로 기록해뒀다.
