## Q6-01. 메모리 종류를 말해보라 (RAM, ROM 등) `★★`

> 원본 엑셀에서 **답변이 비어있던 문항.** 하드웨어 관점을 묻는 질문이다.

**30초 답변**
> 크게 **휘발성과 비휘발성**으로 나뉩니다. **RAM**은 전원이 꺼지면 내용이 사라지는 휘발성 메모리로 실행 중인 프로그램과 데이터가 올라가고, **ROM**은 전원이 없어도 유지되는 비휘발성으로 부팅에 필요한 펌웨어(BIOS)가 들어갑니다. 속도 순으로는 **레지스터 > 캐시(L1/L2/L3) > 주기억장치(RAM) > 보조기억장치(SSD/HDD)** 순이고, 빠를수록 용량이 작고 비쌉니다.

**상세 설명**
```
        빠름 / 작음 / 비쌈
  ┌─────────────────────┐
  │  레지스터 (CPU 내부)  │  ~1 사이클
  ├─────────────────────┤
  │  L1 / L2 / L3 캐시   │  ~4 / ~12 / ~40 사이클
  ├─────────────────────┤
  │  주기억장치 (RAM)     │  ~200+ 사이클
  ├─────────────────────┤
  │  보조기억장치 (SSD)   │  ~수만 사이클
  │              (HDD)   │  ~수백만 사이클
  └─────────────────────┘
        느림 / 큼 / 쌈
```

| 종류 | 휘발성 | 특징 |
|---|---|---|
| **레지스터** | 휘발성 | CPU 내부, 가장 빠름 |
| **캐시(SRAM)** | 휘발성 | CPU와 RAM 사이 완충 |
| **RAM (DRAM)** | **휘발성** | 주기억장치. 실행 중 프로그램 |
| **ROM** | **비휘발성** | 펌웨어/BIOS. 읽기 위주 |
| SSD / HDD | 비휘발성 | 보조기억장치 |
| 플래시 메모리 | 비휘발성 | USB, SSD의 기반 |

- **SRAM vs DRAM**: SRAM은 플립플롭으로 구성되어 빠르지만 비싸고 집적도가 낮아 **캐시**에 쓰인다. DRAM은 커패시터라 주기적 리프레시가 필요하지만 싸고 집적도가 높아 **주기억장치**에 쓰인다.
- **ROM의 종류**: PROM(1회 기록), EPROM(자외선으로 지움), **EEPROM**(전기로 지움 — 요즘 펌웨어 업데이트가 가능한 이유).

**게임 개발자 관점으로 연결하기**
> 이 계층 구조가 중요한 이유는 **캐시 지역성**이 실제 게임 성능을 좌우하기 때문이다. RAM 접근은 캐시보다 50배 이상 느려서, 데이터를 연속된 배열에 모아 순차 접근하는 것만으로 몇 배 빨라진다. Unity의 **DOTS/ECS**가 정확히 이 원리를 노린 설계다. → `04_자료구조_알고리즘.md` Q4-25.

**꼬리질문**
- **Q.** 게임에서 이 지식을 어떻게 쓰나?
  **A.** ① 자료구조 선택(배열 vs 연결 리스트), ② 구조체 크기 줄이기(패딩 최소화 → 한 캐시 라인에 더 많이), ③ 2차원 배열을 행 우선으로 순회, ④ 모바일은 RAM이 작아 텍스처 메모리 관리가 중요하다.
- **Q.** 가상 메모리는 어디에 해당하나?
  **A.** RAM이 부족할 때 **디스크 일부를 메모리처럼 쓰는** 기법이다. → Q6-09.

## Q6-02. 캐시 메모리와 L1/L2/L3란?

**30초 답변**
> CPU와 주기억장치(RAM) 사이의 **속도 차이를 메우기 위한 고속 완충 메모리**입니다. 자주 쓰는 데이터를 미리 가져다 두어 RAM 접근을 줄입니다. L1이 가장 작고 빠르며 코어마다 하나씩 있고, L2는 조금 크고 느리며, L3는 가장 크고 보통 여러 코어가 공유합니다. CPU는 L1 → L2 → L3 → RAM 순으로 찾아 내려갑니다.

**상세 설명**

| | 크기 | 지연 | 공유 |
|---|---|---|---|
| **L1** | 32~64KB | ~4 사이클 | 코어 전용(명령/데이터 분리) |
| **L2** | 256KB~1MB | ~12 사이클 | 보통 코어 전용 |
| **L3** | 8~32MB | ~40 사이클 | **여러 코어 공유** |
| RAM | GB 단위 | ~200+ 사이클 | 전체 |

- **캐시 라인**: 캐시는 바이트 단위가 아니라 보통 **64바이트 블록 단위**로 읽어온다. 그래서 `int` 하나만 읽어도 주변 16개가 함께 올라온다 — 이게 순차 접근이 빠른 이유다.
- **False Sharing**: 서로 다른 스레드가 같은 캐시 라인의 다른 변수를 수정하면, 실제로는 독립적인데도 캐시 일관성 프로토콜 때문에 계속 무효화되어 성능이 급락한다. 멀티스레드 최적화의 함정이다.

**꼬리질문**
- **Q.** 명령 캐시와 데이터 캐시를 왜 나누나?
  **A.** 명령어 읽기와 데이터 읽기가 **동시에 일어날 수 있어** 한 캐시를 두고 경쟁하면 병목이 된다. L1을 I-Cache/D-Cache로 나누면 병렬 접근이 가능하다(하버드 아키텍처 구조).

## Q6-03. 캐시 히트와 미스란?

**30초 답변**
> 필요한 데이터가 **캐시에 있으면 히트**, 없어서 하위 계층(L2, L3, RAM)까지 가져와야 하면 **미스**입니다. 미스가 나면 수십~수백 사이클을 낭비하므로 히트율이 성능을 좌우합니다. 캐시는 **시간 지역성**(최근 쓴 걸 또 쓴다)과 **공간 지역성**(근처를 곧 쓴다)을 전제로 동작하므로, 이 가정에 맞게 코드를 짜면 히트율이 올라갑니다.

**상세 설명**
```cpp
// 캐시 친화적 - 행 우선 순회 (연속 메모리)
for (int y = 0; y < H; y++)
    for (int x = 0; x < W; x++)
        sum += arr[y][x];        // 메모리 순서대로

// 캐시 비친화적 - 열 우선 순회 (매번 건너뜀)
for (int x = 0; x < W; x++)
    for (int y = 0; y < H; y++)
        sum += arr[y][x];        // 매 접근마다 캐시 미스 가능
```
**미스의 종류 (3C)**
- **Compulsory(강제)**: 처음 접근하는 데이터 — 피할 수 없음
- **Capacity(용량)**: 작업 데이터가 캐시보다 커서 밀려남
- **Conflict(충돌)**: 같은 캐시 세트로 매핑되어 서로 밀어냄

**내 프로젝트 연결**
- `cpp_핵심정리.md` **15번** — 구조체 패딩과 `sizeof`. 구조체를 작게 만들면 한 캐시 라인에 더 많이 들어간다.
- `unity_핵심정리.md` **22-1** — 2차원 격자를 1차원 `List`로 `index = y*width + x` 저장. **행 우선 연속 저장**이라 캐시에 유리하다.

**꼬리질문**
- **Q.** 게임 코드에서 캐시 미스를 줄이려면?
  **A.** ① 배열 기반 자료구조 사용, ② **SoA(Struct of Arrays)** — 자주 순회하는 필드만 모아 배열로, ③ 구조체 크기 축소, ④ 매 프레임 순회하는 컬렉션을 연속 메모리로 유지, ⑤ 가상 함수 호출을 핫패스에서 줄이기(간접 참조).

## Q6-04. 프로세스와 스레드의 차이는?

**30초 답변**
> **프로세스는 실행 중인 프로그램의 독립적인 인스턴스**로 자기만의 메모리 공간을 갖습니다. **스레드는 프로세스 안의 실행 흐름 단위**로, 같은 프로세스의 스레드끼리는 **코드·데이터·힙 영역을 공유하고 스택과 레지스터만 각자 갖습니다.** 그래서 스레드 간 통신은 빠르지만 공유 자원 동기화 문제가 생기고, 프로세스는 격리되어 안전하지만 통신 비용이 큽니다.

**상세 설명**
```
프로세스 A                        프로세스 B (완전히 격리)
┌──────────────────────┐         ┌──────────────┐
│ 코드 / 데이터 / 힙    │ ← 공유  │ 코드/데이터/힙│
│ ┌────┐ ┌────┐ ┌────┐ │         └──────────────┘
│ │스택│ │스택│ │스택│ │ ← 각자
│ │Th1 │ │Th2 │ │Th3 │ │
│ └────┘ └────┘ └────┘ │
└──────────────────────┘
```
| | 프로세스 | 스레드 |
|---|---|---|
| 메모리 | **독립** | 코드·데이터·힙 **공유** |
| 각자 갖는 것 | 전부 | **스택, 레지스터, PC** |
| 생성 비용 | 큼 | 작음 |
| 통신(IPC) | 파이프, 소켓, 공유메모리 (느림) | 그냥 변수 접근 (빠름) |
| 안정성 | 하나 죽어도 무관 | **하나 죽으면 프로세스 전체 위험** |
| 동기화 | 거의 불필요 | **필수** |

**내 프로젝트 연결**
- `c_핵심정리.md` **13번** — WinAPI `CreateThread`와 `CRITICAL_SECTION`으로 **스레드와 임계구역을 직접** 다뤄봤다.
- `cpp_핵심정리.md` **21번** — C++11 `mutex`/`lock_guard`/`unique_lock` (RAII 락), **23번** 세마포어.

**꼬리질문**
- **Q.** Unity에서 멀티스레드를 쓸 수 있나?
  **A.** 쓸 수 있지만 **Unity API는 메인 스레드에서만 호출 가능**하다. `transform.position` 접근조차 다른 스레드에서 하면 예외가 난다. 워커 스레드에서는 순수 계산만 하고 결과를 메인 스레드에서 반영해야 한다. Unity는 이를 안전하게 하려고 **Job System + Burst**를 제공하며, 여기선 관리 객체가 아닌 `NativeArray` 같은 값 타입만 다룬다. → `03_Unity.md` Q3-10.
- **Q.** 코루틴은 스레드인가?
  **A.** **아니다.** 메인 스레드에서 실행되며 Unity가 매 프레임 `MoveNext()`를 호출해주는 것뿐이다. 코루틴 안에서 무거운 계산을 하면 여전히 프레임이 멈춘다. 자주 나오는 함정 질문이다.
- **Q.** 멀티프로세스를 쓰는 경우는?
  **A.** 안정성이 중요할 때다. 크롬이 탭마다 프로세스를 분리해 하나가 죽어도 전체가 안 죽게 하는 것이 대표적이다. 게임에서는 서버가 매치마다 프로세스를 분리하기도 한다.

## Q6-05. 컨텍스트 스위칭이란?

**30초 답변**
> CPU가 실행하던 스레드를 멈추고 다른 스레드로 전환할 때, **현재 상태(레지스터, 프로그램 카운터, 스택 포인터)를 저장하고 다음 스레드의 상태를 복원하는** 과정입니다. 이 자체가 순수한 오버헤드이고, **캐시와 TLB가 무효화**되어 실제 비용은 더 큽니다. 그래서 스레드를 무작정 많이 만들면 오히려 느려집니다.

**상세 설명**
```
스레드 A 실행 → [상태 저장] → 스케줄러 → [상태 복원] → 스레드 B 실행
                     ↑ 오버헤드 ↑
              + 캐시/TLB 무효화 (숨은 비용이 더 큼)
```
- **프로세스 간 전환이 스레드 간 전환보다 비싸다** — 메모리 주소 공간까지 바꿔야 해서 TLB(주소 변환 캐시)를 통째로 비워야 한다.
- **스레드 풀을 쓰는 이유**: 스레드를 매번 만들고 없애는 비용 + 과도한 컨텍스트 스위칭을 피하려고, 적당한 개수를 미리 만들어 재사용한다. C#의 `Task`가 이 방식이다. → `02_CSharp.md` Q2-25.

**꼬리질문**
- **Q.** 스레드는 몇 개가 적당한가?
  **A.** **CPU 바운드 작업이면 코어 수만큼**이 이론적 최적이다(더 만들면 컨텍스트 스위칭만 늘어남). **I/O 바운드면 대기 시간이 많으므로 코어 수보다 많이** 둘 수 있다. 게임에서는 렌더/물리/오디오 등 엔진이 이미 코어를 쓰고 있으므로 워커를 과하게 만들면 오히려 경합이 생긴다.
- **Q.** 컨텍스트 스위칭은 언제 일어나나?
  **A.** ① 타임 슬라이스 만료(선점형 스케줄링), ② I/O 대기로 블로킹, ③ 더 높은 우선순위 스레드 등장, ④ `sleep`/`yield` 같은 자발적 양보, ⑤ 인터럽트 발생.

## Q6-06. 뮤텍스와 세마포어의 차이는?

**30초 답변**
> **뮤텍스는 한 번에 하나의 스레드만 임계 구역에 들어가게 하는 잠금**이고 **잠근 스레드만 풀 수 있습니다(소유권 개념).** **세마포어는 동시에 N개까지 허용하는 카운터**로, 소유권 개념이 없어 다른 스레드가 신호를 줄 수도 있습니다. 즉 뮤텍스는 상호 배제, 세마포어는 자원 개수 제한 또는 스레드 간 신호 전달에 씁니다.

**상세 설명**

| | 뮤텍스(Mutex) | 세마포어(Semaphore) |
|---|---|---|
| 허용 개수 | **1개** | **N개** |
| 소유권 | **있음**(잠근 스레드만 해제) | 없음 |
| 용도 | 상호 배제 | 자원 풀 제한, 신호 전달 |
| 이진 세마포어 | — | N=1이면 뮤텍스와 유사(소유권은 없음) |

```cpp
// 뮤텍스 - RAII로 안전하게
std::mutex mtx;
{
    std::lock_guard<std::mutex> lock(mtx);   // 생성 시 lock
    sharedData++;                             // 예외가 나도
}                                             // 소멸자가 반드시 unlock

// 세마포어 - 동시 3개까지 허용
std::counting_semaphore<3> sem(3);
sem.acquire();  /* 자원 사용 */  sem.release();
```
- **임계 구역(Critical Section)**: 공유 자원에 접근하는 코드 영역. 한 번에 하나의 스레드만 실행되어야 한다.
- Windows의 `CRITICAL_SECTION`은 같은 프로세스 안에서만 쓰는 가벼운 뮤텍스다(커널 진입 없이 유저 모드에서 처리되는 경우가 많아 빠름).

**내 프로젝트 연결 — 직접 다뤄봤다**
- `c_핵심정리.md` **13번** — WinAPI `CreateThread` + **`CRITICAL_SECTION`** 으로 임계구역 처리.
- `cpp_핵심정리.md` **21번** — `mutex`/`lock_guard`/`unique_lock`을 **"RAII 락"** 으로 정리.
- `cpp_핵심정리.md` **22번** — **이중검사 잠금(DCLP)과 `call_once`** — 지연 초기화의 스레드 안전성.
- `cpp_핵심정리.md` **23번** — 세마포어.
> C 스타일 수동 `Enter`/`Leave`에서 C++ RAII 락으로 넘어간 과정을 직접 겪었기 때문에, "왜 RAII가 안전한가"를 경험으로 설명할 수 있다. → `01_C_CPP.md` Q1-30.

**꼬리질문**
- **Q.** 왜 `lock_guard`를 쓰나?
  **A.** 수동으로 `lock()`/`unlock()`을 부르면 중간에 `return`하거나 **예외가 발생했을 때 unlock을 놓쳐 데드락**이 된다. `lock_guard`는 스코프를 벗어날 때 소멸자가 반드시 호출되므로 구조적으로 이 실수를 막는다.
- **Q.** 이중검사 잠금(DCLP)이 뭔가?
  **A.** 싱글턴 지연 초기화에서 매번 락을 잡으면 느리니, **락 없이 먼저 확인하고 null일 때만 락을 잡은 뒤 다시 확인**하는 기법이다. 다만 컴파일러/CPU 명령 재배치 때문에 순진하게 구현하면 깨져서, C++11에서는 `std::call_once`나 함수 내 지역 정적 변수(Meyers 싱글턴)를 쓰는 게 안전하다. 직접 실습해봤다(`cpp_핵심정리` 22번).
- **Q.** 스핀락은 뭔가?
  **A.** 락을 얻을 때까지 **대기 없이 계속 확인하며 도는** 락이다. 컨텍스트 스위칭 비용이 없어서 **대기 시간이 아주 짧을 때** 유리하지만, 오래 기다리면 CPU를 낭비한다.

## Q6-07. 데드락이란? 어떻게 막나?

**30초 답변**
> 두 개 이상의 스레드가 **서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태**입니다. 발생하려면 **상호 배제, 점유 대기, 비선점, 순환 대기** 네 조건이 모두 성립해야 하고, 하나만 깨면 막을 수 있습니다. 실무에서 가장 현실적인 방법은 **락 획득 순서를 전역적으로 통일해서 순환 대기를 없애는 것**입니다.

**상세 설명**
```
스레드 A: 락1 획득 → 락2 대기
스레드 B: 락2 획득 → 락1 대기        → 둘 다 영원히 대기
```
**데드락 발생 4조건 (모두 성립해야 함)**

| 조건 | 의미 | 깨는 방법 |
|---|---|---|
| **상호 배제** | 자원을 한 번에 하나만 | 공유 가능하게(현실적으로 어려움) |
| **점유 대기** | 가진 채로 다른 걸 기다림 | 필요한 락을 **한 번에 전부** 획득 |
| **비선점** | 뺏을 수 없음 | 타임아웃 후 포기(`try_lock`) |
| **순환 대기** | 대기가 원형으로 이어짐 | **락 순서 통일** ← 가장 실용적 |

```cpp
// 위험 - 스레드마다 순서가 다름
// A: lock(m1); lock(m2);
// B: lock(m2); lock(m1);   ← 데드락

// 안전 1 - 순서 통일 (항상 m1 먼저)
// 안전 2 - 한 번에 획득 (C++11)
std::lock(m1, m2);
std::lock_guard<std::mutex> l1(m1, std::adopt_lock);
std::lock_guard<std::mutex> l2(m2, std::adopt_lock);
```

**꼬리질문**
- **Q.** 기아 상태(Starvation)와 데드락의 차이는?
  **A.** 데드락은 **아무도 진행 못 하는** 상태, 기아는 **특정 스레드만 계속 자원을 못 얻는** 상태다. 우선순위가 낮은 스레드가 계속 밀리면 기아가 생기고, **에이징**(대기 시간에 따라 우선순위를 올림)으로 해결한다.
- **Q.** 라이브락은?
  **A.** 서로 양보하느라 계속 상태는 바뀌는데 **진행은 못 하는** 상태다. 복도에서 마주친 두 사람이 계속 같은 방향으로 비키는 상황과 같다. 무작위 대기 시간을 넣어 해결한다.
- **Q.** Unity 게임에서 데드락을 겪을 일이 있나?
  **A.** 게임 로직이 메인 스레드에서만 돌기 때문에 흔하지는 않다. 다만 ① 워커 스레드로 로딩/네트워크 처리를 할 때, ② 네이티브 플러그인에서 자체 스레드를 쓸 때 발생할 수 있다. 실제로 `unity_핵심정리.md` 12번에서 **C++ 네이티브 DLL을 P/Invoke로 연동**해봤는데, DLL이 자체 스레드를 쓴다면 이런 문제를 고려해야 한다.

## Q6-08. 경쟁 상태(Race Condition)란?

**30초 답변**
> 여러 스레드가 공유 자원에 동시에 접근할 때 **실행 순서에 따라 결과가 달라지는** 상황입니다. 예를 들어 `count++` 는 읽기·증가·쓰기 세 단계로 나뉘는데, 두 스레드가 겹치면 증가가 한 번만 반영될 수 있습니다. 해결책은 뮤텍스로 임계 구역을 보호하거나, `Interlocked` 같은 **원자적 연산**을 쓰는 것입니다.

**상세 설명**
```
count = 0 일 때, 두 스레드가 동시에 count++ 실행

스레드 A: 읽기(0) ──────── 더하기(1) ── 쓰기(1)
스레드 B: ─── 읽기(0) ── 더하기(1) ──────── 쓰기(1)
결과: 2가 아니라 1
```
```csharp
// 위험
count++;

// 안전 1 - 락
lock (lockObj) { count++; }

// 안전 2 - 원자적 연산 (락보다 빠름)
System.Threading.Interlocked.Increment(ref count);
```
- **`volatile`은 해결책이 아니다.** `volatile`은 "캐시하지 말고 매번 메모리에서 읽어라"는 뜻이라 **가시성** 문제만 다루고, `++` 같은 복합 연산의 **원자성**은 보장하지 않는다. 자주 나오는 함정이다.

**꼬리질문**
- **Q.** 원자적(atomic) 연산이 뭔가?
  **A.** **중간에 끼어들 수 없는, 나뉘지 않는 연산**이다. CPU가 하드웨어 수준으로 보장한다. C#의 `Interlocked.Increment`, C++의 `std::atomic`이 이를 제공하며, 단순 카운터라면 락보다 훨씬 빠르다.
- **Q.** 게임에서 경쟁 상태를 겪은 적 있나?
  **A.** Unity 게임 로직은 메인 스레드 단일이라 직접 겪을 일은 드물지만, C 실습에서 **`CreateThread`로 여러 스레드가 공유 변수를 건드리게 만들어 값이 깨지는 걸 직접 확인**하고 `CRITICAL_SECTION`으로 해결해봤다(`c_핵심정리` 13번). 그때 "동기화가 왜 필요한지"를 눈으로 봤다.

## Q6-09. 가상 메모리와 페이징이란?

**30초 답변**
> 가상 메모리는 **실제 물리 메모리보다 큰 주소 공간을 각 프로세스에게 제공하는** 기법입니다. 프로그램은 연속된 가상 주소를 쓰고, OS와 MMU가 이를 **페이지 단위로 물리 메모리에 매핑**합니다. 당장 필요 없는 페이지는 디스크(스왑)로 내려서 물리 메모리를 절약하고, 프로세스 간 메모리를 격리해 안정성과 보안도 확보합니다.

**상세 설명**
```
프로세스의 가상 주소 공간          물리 메모리(RAM)
┌────────────┐                    ┌──────────┐
│ 페이지 0   │────────────────────▶│ 프레임 5 │
│ 페이지 1   │──┐                  │ 프레임 2 │
│ 페이지 2   │  │  ┌───────────────│ 프레임 8 │
└────────────┘  │  │               └──────────┘
                └──┼──▶ 디스크(스왑) — 지금 안 쓰는 페이지
```
- **페이지 폴트**: 접근한 페이지가 물리 메모리에 없으면 발생. OS가 디스크에서 가져와 매핑한다. **디스크 접근이라 매우 느리다.**
- **스래싱(Thrashing)**: 페이지 폴트가 너무 잦아 실제 작업보다 페이지 교체에 시간을 다 쓰는 상태. 메모리가 부족할 때 시스템이 극단적으로 느려지는 현상이다.
- **TLB**: 가상→물리 주소 변환 결과를 캐싱하는 하드웨어. 매번 페이지 테이블을 조회하면 느리기 때문이다.
- **페이지 교체 알고리즘**: FIFO, **LRU(가장 오래 안 쓴 것)**, Optimal(이론상 최적), Clock(LRU 근사).

**꼬리질문**
- **Q.** 게임에서 가상 메모리가 문제 되는 경우는?
  **A.** **모바일에는 보통 스왑이 없다.** 메모리를 초과하면 스왑으로 버티는 게 아니라 OS가 앱을 그냥 강제 종료시킨다. 그래서 모바일 게임은 메모리 상한을 엄격히 지켜야 하고, 텍스처 해상도·에셋 언로드 관리가 중요하다. → `03_Unity.md` Q3-18, Q3-24.
- **Q.** 왜 페이지 단위로 나누나?
  **A.** 고정 크기 블록으로 나누면 **외부 단편화가 없고** 매핑 테이블 관리가 단순하다. 대신 페이지 안에 남는 공간은 **내부 단편화**가 된다. 보통 4KB를 쓴다.

## Q6-10. CPU 스케줄링 알고리즘에는 뭐가 있나?

**30초 답변**
> 어떤 프로세스에게 CPU를 줄지 정하는 정책입니다. **FCFS**는 먼저 온 순서, **SJF**는 실행 시간이 짧은 것 우선, **라운드 로빈**은 일정 시간(타임 퀀텀)씩 돌아가며, **우선순위 스케줄링**은 중요도 순으로 배정합니다. 현대 OS는 이를 조합한 **다단계 피드백 큐**를 쓰며, 선점형이라 시간이 다 되면 강제로 다른 프로세스에게 넘깁니다.

**상세 설명**

| 알고리즘 | 방식 | 특징 |
|---|---|---|
| **FCFS** | 먼저 온 순서 | 단순, **호위 효과**(긴 작업이 앞을 막음) |
| **SJF** | 짧은 것 먼저 | 평균 대기 최소, 하지만 실행 시간을 미리 알기 어려움 |
| **라운드 로빈** | 타임 퀀텀씩 순환 | 공정, **대화형 시스템에 적합** |
| **우선순위** | 중요도 순 | **기아 위험** → 에이징으로 해결 |
| 다단계 피드백 큐 | 여러 큐 + 동적 이동 | 현대 OS의 실제 방식 |

- **선점형 vs 비선점형**: 선점형은 실행 중인 프로세스를 강제로 중단시킬 수 있어 응답성이 좋다. 비선점형은 자발적으로 놓을 때까지 기다린다. 현대 범용 OS는 선점형이다.
- **실시간 OS(RTOS)** 는 데드라인 보장이 목적이라 다른 스케줄링을 쓴다.

**꼬리질문**
- **Q.** 게임 클라이언트에 스케줄링이 영향을 주나?
  **A.** 준다. OS가 게임 스레드를 언제 실행할지 보장하지 않아서 **프레임 시간이 들쭉날쭉해진다.** 그래서 게임은 `Application.targetFrameRate`나 VSync로 목표를 정하고, 델타 타임 기반 로직으로 불규칙성을 흡수한다. 또 백그라운드 앱이 CPU를 뺏으면 프레임이 튀는 것도 같은 이유다.

## Q6-11. 메모리 단편화란?

**30초 답변**
> **외부 단편화**는 할당과 해제를 반복하면서 빈 공간이 잘게 쪼개져, 전체 여유 메모리는 충분한데 **연속된 큰 블록을 잡을 수 없는** 상태입니다. **내부 단편화**는 요청보다 큰 블록을 할당해서 남는 부분이 낭비되는 것입니다. 장시간 실행되는 게임에서 특히 문제가 되어, **메모리 풀을 미리 잡아두고 재사용**하는 기법으로 대응합니다.

**상세 설명**
```
외부 단편화
[사용][ 빈 ][사용][ 빈 ][사용][ 빈 ]
       10KB       15KB       20KB     ← 합은 45KB인데
                                        30KB 연속 블록은 못 잡음
```
**대응 방법**
1. **메모리 풀** — 같은 크기 블록을 미리 잡아두고 재사용 (게임에서 가장 흔한 해법)
2. **압축(Compaction)** — 사용 중인 블록을 한쪽으로 몰아 빈 공간을 합침
3. 크기별 할당자(Slab Allocator) 사용
4. 페이징 — 고정 크기라 외부 단편화가 없음(대신 내부 단편화)

**Unity에서 특히 중요한 이유**
> **Unity의 Boehm GC는 힙을 압축하지 않는다.** 그래서 `Instantiate`/`Destroy`를 반복하면 단편화가 계속 누적되고, 한 번 커진 힙은 OS에 잘 반환되지도 않는다. 이게 **오브젝트 풀링이 Unity에서 특히 중요한 이유**다. → `02_CSharp.md` Q2-09, `03_Unity.md` Q3-16.

**꼬리질문**
- **Q.** GC가 있는데도 단편화가 생기나?
  **A.** GC 종류에 따라 다르다. **.NET의 GC는 SOH를 압축해서** 단편화가 해소되지만, **LOH(85,000바이트 이상)는 기본적으로 압축하지 않고**, **Unity의 Boehm GC는 아예 압축을 안 한다.** → `02_CSharp.md` Q2-10.

## Q6-12. 리틀 엔디언과 빅 엔디언이란?

**30초 답변**
> 여러 바이트로 이루어진 값을 메모리에 저장하는 **바이트 순서**입니다. **리틀 엔디언은 낮은 자리 바이트를 낮은 주소에** 저장하고(x86, ARM 대부분), **빅 엔디언은 높은 자리 바이트를 낮은 주소에** 저장합니다(네트워크 표준). 서로 다른 시스템끼리 이진 데이터를 주고받을 때 변환하지 않으면 값이 깨지므로, 네트워크 통신과 파일 포맷에서 반드시 신경 써야 합니다.

**상세 설명**
```
0x12345678 을 저장하면

리틀 엔디언 (x86, ARM):   [78][56][34][12]   ← 낮은 자리부터
빅 엔디언 (네트워크):      [12][34][56][78]   ← 높은 자리부터
                          낮은주소 → 높은주소
```
- **네트워크 바이트 순서 = 빅 엔디언**이 표준이다. 그래서 소켓 프로그래밍에서 `htons`/`htonl`(host to network) 같은 변환 함수를 쓴다.
- **실무 영향**: 서버와 클라이언트의 아키텍처가 다르거나, PC에서 만든 바이너리 세이브 파일을 콘솔에서 읽을 때 문제가 된다. **그래서 구조체를 그대로 전송하면 안 되고 명시적 직렬화를 해야 한다.** → `01_C_CPP.md` Q1-23.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **24번** — **Winsock TCP/UDP 소켓 프로그래밍**을 직접 해봤다. 소켓 API를 다루면 바이트 순서 변환 함수를 마주치게 된다.

**꼬리질문**
- **Q.** 어떻게 확인하나?
  **A.** `int`에 1을 넣고 첫 바이트를 확인하면 된다. 첫 바이트가 1이면 리틀 엔디언, 0이면 빅 엔디언이다.
```cpp
int x = 1;
bool isLittle = (*(char*)&x == 1);
```

## Q6-13. 커널 모드와 유저 모드란?

**30초 답변**
> CPU의 **권한 수준**입니다. **커널 모드**는 하드웨어와 모든 메모리에 직접 접근할 수 있는 최고 권한으로 OS 핵심 코드가 실행되고, **유저 모드**는 제한된 권한으로 일반 응용 프로그램이 실행됩니다. 응용 프로그램이 파일 읽기나 네트워크 통신 같은 특권 작업을 하려면 **시스템 콜**로 커널에 요청해야 하며, 이 모드 전환에는 비용이 듭니다.

**상세 설명**
```
유저 모드 (응용 프로그램)
    │  시스템 콜 (read, write, socket …)
    ▼  ← 모드 전환 비용 발생
커널 모드 (OS 핵심, 드라이버)
    │
    ▼
하드웨어
```
- **왜 나누나**: 응용 프로그램의 버그나 악성 코드가 시스템 전체를 망가뜨리지 못하게 **격리**하기 위해서다.
- **시스템 콜 비용**: 모드 전환 + 컨텍스트 저장/복원이 필요해 일반 함수 호출보다 훨씬 비싸다. 그래서 파일 I/O를 잘게 여러 번 하는 것보다 **버퍼에 모아 한 번에** 하는 게 빠르다.

**꼬리질문**
- **Q.** 게임 개발에서 이걸 알아야 하는 이유는?
  **A.** ① 파일 I/O나 네트워크 호출이 왜 비싼지 이해할 수 있고, ② 로그를 매 프레임 파일에 쓰면 왜 느린지 알 수 있으며, ③ 안티치트 솔루션이 커널 드라이버로 동작하는 이유(유저 모드에서는 다른 프로세스 메모리 보호가 어려움)를 설명할 수 있다.

## Q6-14. 컴파일과 링크 과정을 설명하라

**30초 답변**
> 소스 코드가 실행 파일이 되기까지 **전처리 → 컴파일 → 어셈블 → 링크** 네 단계를 거칩니다. 전처리기가 `#include`와 매크로를 펼치고, 컴파일러가 이를 어셈블리로, 어셈블러가 기계어 목적 파일(.obj)로 바꾼 뒤, **링커가 여러 목적 파일과 라이브러리를 묶어 심볼 참조를 실제 주소로 연결**해 실행 파일을 만듭니다.

**상세 설명**
```
main.cpp ──전처리──▶ main.i ──컴파일──▶ main.s ──어셈블──▶ main.obj ─┐
util.cpp ──────────────────────────────────────────────▶ util.obj ─┼─링크─▶ app.exe
                                              라이브러리(.lib/.dll) ─┘
```
**단계별 대표 에러**

| 단계 | 대표 에러 |
|---|---|
| 전처리 | 헤더 파일을 찾을 수 없음 |
| 컴파일 | 문법 오류, 타입 불일치, 선언되지 않은 식별자 |
| **링크** | **정의되지 않은 외부 심볼**(선언만 하고 구현 안 함), **중복 정의** |

- **선언 vs 정의**: 선언은 "이런 게 있다"고 알리는 것(컴파일러가 필요), 정의는 실제 구현(링커가 필요). 헤더에 선언, .cpp에 정의가 원칙이다.
- **정적 링크 vs 동적 링크**: 정적(.lib)은 실행 파일에 코드를 포함해 배포가 간단하지만 크기가 커지고, 동적(.dll)은 실행 시 로드해 크기가 작고 공유되지만 DLL이 없으면 실행이 안 된다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **12번**(UnityDll) — **C++ 네이티브 DLL과 C# 클래스 라이브러리 DLL을 직접 빌드**해서 Unity에 연동해봤다. `extern "C"`로 네임 맹글링을 끄고 `DllImport`로 심볼을 찾는 과정이 정확히 링크 개념의 실전 적용이다.
- `winapi_핵심정리.md` **12번** — **x64 마이그레이션 이슈**를 다뤘다. 32비트 라이브러리와 64비트 프로젝트를 섞으면 링크 에러가 난다.

**꼬리질문**
- **Q.** 헤더 가드(`#pragma once`)는 왜 필요한가?
  **A.** 같은 헤더가 여러 번 `#include`되면 **중복 정의 에러**가 난다. 헤더 가드가 두 번째 포함부터 내용을 건너뛰게 한다.
- **Q.** C#은 이 과정이 어떻게 다른가?
  **A.** C#은 **IL(중간 언어)로 컴파일**되어 어셈블리(.dll/.exe)가 되고, 실행 시 **JIT이 기계어로** 바꾼다. 링크 개념이 있긴 하지만 어셈블리 참조 방식이라 C++의 링커만큼 명시적이지 않다. Unity의 IL2CPP는 IL을 다시 C++로 바꿔 네이티브 컴파일하므로 C++ 방식으로 돌아간다. → `03_Unity.md` Q3-03.

## Q6-15. 32비트와 64비트의 차이는?

**30초 답변**
> CPU가 한 번에 처리하는 데이터 크기와 **주소 공간의 크기**가 다릅니다. 32비트는 최대 4GB(2³²)까지만 주소를 지정할 수 있어 실제로는 프로세스당 2GB 정도만 쓸 수 있지만, 64비트는 사실상 제한이 없습니다. 포인터 크기도 4바이트에서 8바이트로 커져 **구조체 크기와 메모리 사용량이 늘어납니다.**

**상세 설명**

| | 32비트 | 64비트 |
|---|---|---|
| 주소 공간 | 4GB (실제 2GB) | 사실상 무제한 |
| 포인터 크기 | 4바이트 | **8바이트** |
| 레지스터 | 적음 | 많음(성능 유리) |
| 게임 현실 | 대용량 에셋 감당 불가 | **현재 표준** |

- **모바일**: Google Play와 App Store 모두 **64비트 지원을 필수로 요구**한다. Unity에서 Android 빌드 시 ARM64를 반드시 포함해야 한다.
- **포인터가 커지면**: 포인터를 많이 가진 자료구조(연결 리스트, 트리)의 메모리 사용량이 늘고 캐시 효율도 나빠진다.

**내 프로젝트 연결**
- `winapi_핵심정리.md` **12번** — **x64 마이그레이션 이슈**를 직접 정리했다. 포인터를 `int`에 담던 코드가 64비트에서 깨지는 문제 등이 대표적이다.

**꼬리질문**
- **Q.** 32비트 코드를 64비트로 옮길 때 주의점은?
  **A.** ① 포인터를 `int`에 담으면 **잘린다** — `intptr_t`/`size_t`를 써야 한다, ② `long` 크기가 플랫폼마다 다르다(Windows는 4바이트, Linux는 8바이트), ③ 구조체 패딩이 달라져 바이너리 파일 포맷 호환성이 깨진다, ④ 32비트 DLL과 64비트 프로세스는 섞을 수 없다.

## Q6-16. TCP와 UDP의 차이는? 게임은 뭘 쓰나?

**30초 답변**
> **TCP는 연결 지향 프로토콜**로 3-way handshake로 연결을 맺고 **순서 보장, 재전송, 흐름 제어**를 제공해 신뢰성이 높지만 그만큼 지연이 있습니다. **UDP는 비연결형**으로 그냥 보내기만 해서 빠르지만 **손실·순서 뒤바뀜·중복을 애플리케이션이 직접 처리**해야 합니다. 게임에서는 실시간 위치 동기화처럼 최신 데이터가 중요하면 UDP, 아이템 거래나 채팅처럼 반드시 도달해야 하면 TCP를 씁니다.

**상세 설명**

| | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향(handshake) | 비연결형 |
| 신뢰성 | **보장**(재전송) | 없음 |
| 순서 | **보장** | 없음 |
| 속도 | 느림 | **빠름** |
| 헤더 크기 | 20바이트+ | 8바이트 |
| 흐름/혼잡 제어 | 있음 | 없음 |
| 게임 용도 | 로그인, 채팅, 거래, 로비 | **실시간 위치·입력 동기화** |

**게임에서 UDP를 선호하는 진짜 이유**
> TCP는 패킷이 하나 유실되면 **그 뒤에 도착한 패킷들까지 순서를 지키려고 대기**시킨다(Head-of-Line Blocking). FPS에서 0.5초 전 위치를 기다리느라 현재 위치를 못 받는 건 최악이다. UDP는 유실된 건 그냥 버리고 **최신 위치를 바로 적용**하면 되므로 실시간 게임에 맞다.

- 실무에서는 **UDP 위에 필요한 신뢰성만 얹은 커스텀 프로토콜**(신뢰성 있는 UDP)을 쓰는 경우가 많다. Photon, Mirror, ENet 등이 이런 방식이다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **24번** — **Winsock으로 TCP와 UDP 소켓을 직접** 구현해봤다. 엔진 없이 바닥부터 다뤄본 경험이라 이 질문에 구체적으로 답할 수 있다.
- `unity_핵심정리.md` **8번** — Photon PUN으로 멀티플레이어를 구현했다(Photon은 내부적으로 UDP 기반).
- `unity_핵심정리.md` **21-2~21-5** — `WWWForm`/HTTP로 서버 통신, PHP+MySQL 연동, 로그인 흐름.

**꼬리질문**
- **Q.** 그럼 게임은 UDP만 쓰나?
  **A.** 아니다. **둘 다 쓴다.** 로그인·매칭·상점·채팅은 TCP(또는 HTTP)로, 인게임 실시간 동기화는 UDP로 나누는 게 일반적이다. 하나의 게임 안에 두 채널이 공존한다.
- **Q.** UDP로 신뢰성을 구현하려면?
  **A.** ① 패킷마다 **시퀀스 번호**를 붙이고, ② 수신 측이 **ACK**를 보내고, ③ 일정 시간 ACK가 없으면 **재전송**하며, ④ 중복은 시퀀스 번호로 걸러낸다. 즉 TCP의 핵심 기능을 필요한 만큼만 직접 구현하는 것이다.

## Q6-17. TCP 3-way handshake를 설명하라

**30초 답변**
> TCP 연결을 맺기 위해 **세 번 패킷을 주고받는 과정**입니다. 클라이언트가 **SYN**(연결 요청)을 보내면, 서버가 **SYN+ACK**(요청 수락 + 자기 요청)로 답하고, 클라이언트가 **ACK**로 확인하면 연결이 성립합니다. 이 과정에서 양쪽이 서로의 시퀀스 번호를 교환해 이후 순서 보장과 재전송의 기준으로 삼습니다.

**상세 설명**
```
클라이언트                          서버
    │──── SYN (seq=x) ──────────────▶│   "연결하고 싶다"
    │◀─── SYN+ACK (seq=y, ack=x+1) ──│   "좋다, 나도 연결 요청"
    │──── ACK (ack=y+1) ────────────▶│   "확인"
    │◀════════ 연결 성립 ═══════════▶│
```
**연결 종료는 4-way handshake**
```
    │──── FIN ─────▶│   "보낼 거 다 보냈다"
    │◀─── ACK ──────│   "알았다"
    │◀─── FIN ──────│   "나도 다 보냈다"   ← 서버가 남은 데이터를 마저 보낼 수 있어 분리됨
    │──── ACK ─────▶│   "알았다"
```
- **왜 3번인가**: 양쪽 모두 "내가 보낼 수 있고 상대도 받을 수 있다"를 확인해야 하므로 최소 3번이 필요하다.
- **왜 종료는 4번인가**: 한쪽이 FIN을 보내도 **상대는 아직 보낼 데이터가 남아있을 수 있어서**, ACK와 FIN을 합치지 않고 나눈다.

**꼬리질문**
- **Q.** 게임에서 handshake가 문제가 되나?
  **A.** 된다. 연결 수립에 **최소 1 RTT(왕복 시간)** 가 필요해서, 지연이 큰 환경에서는 연결만으로 수백 ms가 걸린다. 그래서 실시간 게임은 연결 없는 UDP를 쓰거나, 미리 연결을 맺어두고 유지한다.
- **Q.** SYN Flood 공격이 뭔가?
  **A.** SYN만 대량으로 보내고 ACK를 안 보내서, 서버가 **반쯤 열린 연결을 계속 대기 상태로 유지하다 자원이 고갈**되는 DoS 공격이다. SYN 쿠키 방식으로 방어한다.

## Q6-18. 소켓이란?

**30초 답변**
> 네트워크 통신의 **끝점(endpoint)** 을 나타내는 추상화로, IP 주소와 포트 번호의 조합입니다. 운영체제가 제공하는 API를 통해 프로그램은 소켓을 파일처럼 읽고 쓰면서 네트워크 통신을 합니다. TCP 서버는 `socket → bind → listen → accept` 순서로, 클라이언트는 `socket → connect` 순서로 연결합니다.

**상세 설명**
```
서버                                클라이언트
socket()    소켓 생성                socket()
bind()      IP/포트 할당
listen()    연결 대기
accept()  ◀────────────────────────  connect()
recv()/send()  ◀──── 데이터 ────▶   send()/recv()
close()                              close()
```
```cpp
// TCP 서버 (Winsock)
SOCKET s = socket(AF_INET, SOCK_STREAM, 0);      // SOCK_STREAM = TCP
sockaddr_in addr = {};
addr.sin_family = AF_INET;
addr.sin_port = htons(9000);                      // 호스트 → 네트워크 바이트 순서
addr.sin_addr.s_addr = INADDR_ANY;
bind(s, (sockaddr*)&addr, sizeof(addr));
listen(s, SOMAXCONN);
SOCKET client = accept(s, nullptr, nullptr);
```
- `SOCK_STREAM` = TCP, `SOCK_DGRAM` = UDP.
- **블로킹 vs 논블로킹**: 기본은 블로킹이라 `recv`에서 데이터가 올 때까지 멈춘다. 서버는 보통 논블로킹 + `select`/`epoll`/**IOCP**(Windows)로 여러 클라이언트를 처리한다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **24번** — **Winsock TCP/UDP 소켓 프로그래밍**을 직접 실습했다. 엔진의 네트워크 기능이 결국 이 위에 올라간다는 걸 이해하고 있다는 근거가 된다.

**꼬리질문**
- **Q.** 게임 서버가 수천 명을 어떻게 처리하나?
  **A.** 클라이언트마다 스레드를 만들면 **컨텍스트 스위칭 비용으로 감당이 안 된다.** 그래서 **비동기 I/O 다중화**를 쓴다 — Windows는 **IOCP**, Linux는 **epoll**로 소수의 스레드가 수천 개 소켓을 관리한다. 이게 대규모 게임 서버 아키텍처의 핵심이다.

## Q6-19. HTTP와 HTTPS, REST API를 설명하라

**30초 답변**
> HTTP는 **요청과 응답으로 이루어진 무상태(stateless) 프로토콜**로, 클라이언트가 요청하면 서버가 응답하고 연결 상태를 기억하지 않습니다. HTTPS는 여기에 **TLS 암호화를 추가**해 통신 내용을 보호하고 서버 신원을 인증합니다. REST API는 리소스를 URL로 표현하고 **GET/POST/PUT/DELETE 같은 HTTP 메서드로 동작을 구분**하는 설계 규약입니다.

**상세 설명**

| 메서드 | 용도 | 멱등성 |
|---|---|---|
| **GET** | 조회 | O |
| **POST** | 생성 | X |
| **PUT** | 전체 수정 | O |
| PATCH | 부분 수정 | X |
| **DELETE** | 삭제 | O |

**주요 상태 코드**: 200(성공), 201(생성됨), 400(잘못된 요청), 401(인증 안 됨), 403(권한 없음), **404**(없음), 500(서버 오류)

- **무상태(stateless)** 라서 로그인 상태를 유지하려면 **토큰(JWT)이나 세션 ID**를 매 요청에 실어 보내야 한다.
- 게임에서 HTTP를 쓰는 곳: 로그인, 상점/결제, 랭킹 조회, 공지사항, 패치 노트, 에셋 다운로드.

**내 프로젝트 연결 — 실제로 해봤다**
- `unity_핵심정리.md` **21-2** `WWWForm`+`WWW`로 서버 조회, **21-3** 데이터 전송 + 서버 응답 규약(`returnCode`/`returnMsg`), **21-4** **PHP 서버 사이드 JSON 인코딩 + UTF-8/EUC-KR 문자셋 변환**, **21-5** **로그인/회원가입 흐름**(클라이언트 1차 검증 + 서버 2차 인증).
- `unity_핵심정리.md` **5-21, 8-10** — `WWW` → `UnityWebRequest` 마이그레이션.
- `unity_핵심정리.md` **15-2, 16-7** — 구글 시트를 CSV로 다운로드해 게임 데이터로 사용.

**꼬리질문**
- **Q.** 클라이언트 검증만으로 충분한가?
  **A.** 전혀 아니다. **클라이언트는 언제든 조작될 수 있으므로 보안 경계가 될 수 없다.** 클라이언트 검증은 사용자 경험을 위한 빠른 피드백일 뿐이고, 실제 인증·아이템 지급·점수 처리는 반드시 서버에서 검증해야 한다. 실제로 내 프로젝트에서 **클라이언트 1차 검증 + 서버 2차 인증** 구조로 구현했다(21-5).
- **Q.** HTTPS는 어떻게 안전한가?
  **A.** TLS handshake로 **대칭키를 안전하게 교환**한 뒤 그 키로 통신을 암호화한다. 키 교환에는 비대칭 암호(공개키/개인키)를 쓰고, 서버 인증서로 **서버가 진짜인지 검증**해 중간자 공격을 막는다.
  > 관련 경험: `unity_핵심정리.md` 16-3~16-6에서 **AES ECB → AES CBC + 매번 새 IV**로 대칭키 암호화를 직접 발전시켜봤고, **키를 클라이언트에 하드코딩하면 결국 뚫린다**는 한계도 주석으로 인지해뒀다.

## Q6-20. 게임 서버 구조에는 어떤 것들이 있나?

**30초 답변**
> 크게 세 가지입니다. **P2P**는 클라이언트끼리 직접 연결해 서버 비용이 없지만 치팅에 취약하고 NAT 문제가 있습니다. **릴레이 서버**는 패킷을 중계만 해서 구현이 간단하지만 판정 권한이 클라이언트에 있습니다. **데디케이티드(전용) 서버**는 서버가 모든 게임 로직과 판정을 담당해 치팅에 가장 강하지만 서버 비용과 개발 부담이 큽니다.

**상세 설명**

| | P2P | 릴레이 | **데디케이티드** |
|---|---|---|---|
| 서버 비용 | 없음 | 중간 | **높음** |
| 치팅 방어 | 매우 약함 | 약함 | **강함** |
| 지연 | 낮을 수 있음 | 중간 | 서버 위치 의존 |
| 호스트 이탈 | 게임 중단 | 무관 | 무관 |
| 사용 예 | 소규모 협동 | 캐주얼 모바일 | 경쟁 FPS, MMO |

- **호스트 마이그레이션**: P2P나 호스트 기반 구조에서 호스트가 나가면 다른 클라이언트가 이어받는 것.
  > 실제로 구현해봤다 — `unity_핵심정리.md` **8-4**가 **Master Client 권위 서버 패턴 + 페일오버**다. Master Client가 나가면 다른 클라이언트가 권한을 이어받는 구조를 다뤘다.
- **권한 모델 두 가지**: **소유권 기반**(각자 자기 캐릭터를 계산)과 **권위 기반**(한 쪽이 전부 계산). 내 프로젝트에서 이 둘을 비교 정리했다(`unity_핵심정리.md` **8-5**).

**꼬리질문**
- **Q.** 왜 경쟁 게임은 데디케이티드 서버를 쓰나?
  **A.** **클라이언트를 신뢰할 수 없기 때문**이다. 클라이언트가 판정하면 "내가 맞췄다", "나는 안 맞았다"를 조작할 수 있다. 서버가 모든 판정을 하고 클라이언트는 입력만 보내면 이런 치팅이 원천 차단된다.
- **Q.** 그럼 반응이 느려지지 않나?
  **A.** 느려진다. 그래서 **클라이언트 예측(prediction)** 으로 입력 즉시 화면에 반영하고, 나중에 서버 결과가 오면 **차이를 보정(reconciliation)** 한다. 다른 플레이어는 **보간(interpolation)** 으로 부드럽게 표시한다. → Q6-21.

## Q6-21. 네트워크 지연을 어떻게 보완하나?

**30초 답변**
> 네 가지 기법을 조합합니다. **클라이언트 예측**은 서버 응답을 기다리지 않고 내 입력을 즉시 화면에 반영하고, **서버 보정**은 서버 결과가 오면 차이를 부드럽게 맞춥니다. **보간**은 다른 플레이어의 위치를 수신 지점 사이로 부드럽게 이어주고, **추측 항법(dead reckoning)** 은 패킷이 늦으면 마지막 속도로 위치를 예측합니다. 여기에 **지연 보상(lag compensation)** 으로 서버가 과거 시점 기준으로 판정하기도 합니다.

**상세 설명**

| 기법 | 대상 | 목적 |
|---|---|---|
| **클라이언트 예측** | 내 캐릭터 | 입력 즉시 반응 |
| **서버 보정** | 내 캐릭터 | 예측 오차 수정 |
| **보간(Interpolation)** | 다른 플레이어 | 끊김 없는 이동 |
| **추측 항법(Dead Reckoning)** | 다른 플레이어 | 패킷 지연 시 예측 |
| **지연 보상** | 히트 판정 | 쏜 시점 기준으로 판정 |
| **락스텝(Lockstep)** | 전체 | 입력만 동기화(RTS에 사용) |

- **왜 보간이 필요한가**: 네트워크 패킷은 초당 10~20회 정도만 온다. 그대로 적용하면 다른 플레이어가 뚝뚝 끊겨 보인다. 수신한 위치 사이를 시간에 따라 이어주면 부드러워진다.
- **락스텝**: 모든 클라이언트가 **같은 입력을 받아 같은 시뮬레이션을 돌리는** 방식. 위치가 아니라 입력만 보내면 되어 대역폭이 매우 작아 RTS(유닛 수천 개)에 적합하지만, **완벽한 결정론(determinism)** 이 요구되어 부동소수점 오차 하나로도 데스싱크가 난다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **8-3** — `OnPhotonSerializeView`로 위치·상태를 커스텀 동기화. 여기서 수신값을 그대로 적용할지 보간할지의 문제를 직접 마주쳤다.
- `unity_핵심정리.md` **8-7** — 정수 상태코드를 실어보내는 애니메이션 동기화(대역폭 절약 기법).

**꼬리질문**
- **Q.** 지연 보상의 부작용은?
  **A.** 서버가 쏜 사람의 과거 시점 기준으로 판정하면, **맞은 사람 입장에서는 "이미 엄폐물 뒤에 숨었는데 맞는"** 경험을 하게 된다. 쏜 사람의 공정성과 맞은 사람의 체감이 충돌하는 구조적 트레이드오프라 완벽한 답이 없다.
- **Q.** 동기화 대역폭을 줄이려면?
  **A.** ① 필요한 값만 보내고 **정밀도를 낮춘다**(float 대신 압축된 정수), ② 변경된 값만 보내는 **델타 압축**, ③ 상태를 정수 코드로 압축(내 프로젝트 8-7 사례), ④ 거리에 따라 전송 빈도를 낮추는 **관심 영역(AoI)** 관리.

## Q6-22. 기본키와 외래키란?

**30초 답변**
> **기본키(Primary Key)** 는 테이블에서 각 행을 **유일하게 식별하는 컬럼**으로, 중복될 수 없고 `NULL`도 허용되지 않으며 테이블당 하나만 존재합니다. **외래키(Foreign Key)** 는 다른 테이블의 기본키를 참조하는 컬럼으로, 테이블 간 관계를 표현하고 **참조 무결성**을 보장합니다.

**상세 설명**
```sql
CREATE TABLE Player (
    player_id  INT PRIMARY KEY,          -- 기본키
    nickname   VARCHAR(20) UNIQUE NOT NULL
);
CREATE TABLE Inventory (
    item_id    INT PRIMARY KEY,
    player_id  INT,
    FOREIGN KEY (player_id) REFERENCES Player(player_id)   -- 외래키
);
```
**키의 종류**

| 키 | 의미 |
|---|---|
| **기본키** | 행을 유일하게 식별. 유일 + NOT NULL |
| 후보키 | 기본키가 될 수 있는 자격을 갖춘 키들 |
| 대체키 | 후보키 중 기본키로 안 뽑힌 것 |
| **외래키** | 다른 테이블의 기본키를 참조 |
| 복합키 | 여러 컬럼을 묶어 만든 키 |

- **참조 무결성**: 외래키가 가리키는 행이 존재해야 한다. 부모 행을 지우려 할 때 `CASCADE`(같이 삭제), `SET NULL`, `RESTRICT`(막음) 중 정책을 정한다.

**꼬리질문**
- **Q.** 게임 DB 설계 예를 들어보라.
  **A.** `Player`(player_id, nickname, level) ← `Inventory`(item_id, player_id, item_type_id, count) → `ItemType`(item_type_id, name, damage). 플레이어와 아이템 종류는 각각 독립 테이블이고, 인벤토리가 둘을 연결하는 구조다.

## Q6-23. 정규화란?

**30초 답변**
> 데이터 **중복을 줄이고 이상 현상(anomaly)을 방지하기 위해 테이블을 분해하는 과정**입니다. 1정규형은 모든 컬럼이 원자값을 갖게 하고, 2정규형은 기본키 일부에만 의존하는 컬럼을 분리하며, 3정규형은 키가 아닌 컬럼에 의존하는 컬럼을 분리합니다. 보통 3정규형까지 하며, 성능이 필요하면 **의도적으로 역정규화**하기도 합니다.

**상세 설명**

| 정규형 | 조건 |
|---|---|
| **1NF** | 모든 컬럼이 원자값(하나의 값)이어야 |
| **2NF** | 1NF + **부분 함수 종속 제거**(복합키 일부에만 의존하는 컬럼 분리) |
| **3NF** | 2NF + **이행 함수 종속 제거**(비키 컬럼에 의존하는 컬럼 분리) |
| BCNF | 3NF 강화 |

**이상 현상 3가지 (정규화를 하는 이유)**
- **삽입 이상**: 불필요한 데이터까지 넣어야만 삽입이 가능
- **갱신 이상**: 중복된 값 중 일부만 고쳐 데이터가 불일치
- **삭제 이상**: 한 정보를 지우면 필요한 다른 정보까지 사라짐

**꼬리질문**
- **Q.** 역정규화는 왜 하나?
  **A.** 정규화하면 테이블이 잘게 쪼개져 **조회할 때 JOIN이 많아지고 느려진다.** 읽기가 압도적으로 많은 시스템(랭킹 조회, 게임 로그 분석)에서는 일부 컬럼을 의도적으로 중복 저장해 JOIN을 줄인다. **정합성을 희생하고 성능을 얻는 트레이드오프**다.
- **Q.** 게임에서 정규화를 어디까지 하나?
  **A.** 계정·결제·아이템 소유처럼 **정합성이 중요한 데이터는 정규화**하고, 로그나 통계처럼 **조회 성능이 중요한 데이터는 역정규화**하는 게 일반적이다.

## Q6-24. 인덱스란? 왜 빨라지나?

**30초 답변**
> 테이블의 특정 컬럼에 대해 **정렬된 별도 자료구조(주로 B-트리)를 만들어 두는 것**입니다. 인덱스가 없으면 전체 행을 다 훑어야(풀 스캔) 하지만, 인덱스가 있으면 트리를 따라 **O(log n)** 에 찾을 수 있습니다. 대신 인덱스도 저장 공간을 차지하고, **삽입·수정·삭제 시 인덱스도 함께 갱신**해야 해서 쓰기 성능이 떨어집니다.

**상세 설명**
```sql
CREATE INDEX idx_player_level ON Player(level);
-- WHERE level > 50  같은 조회가 빨라짐
```
| | 인덱스 있음 | 인덱스 없음 |
|---|---|---|
| 조회 | **O(log n)** | O(n) 풀 스캔 |
| 삽입/수정/삭제 | 느림(인덱스 갱신) | **빠름** |
| 저장 공간 | 추가 소요 | 없음 |

- **B-트리(정확히는 B+트리)** 를 쓰는 이유: 디스크는 블록 단위로 읽으므로, 노드 하나에 많은 키를 담아 **트리 높이를 낮추면 디스크 접근 횟수가 줄어든다.** 이진 트리보다 훨씬 유리하다.
- **인덱스를 걸면 좋은 곳**: `WHERE`, `JOIN`, `ORDER BY`에 자주 쓰이는 컬럼. **카디널리티(값의 다양성)가 높을수록** 효과적이다(성별처럼 값이 두 개뿐이면 효과가 거의 없다).

**꼬리질문**
- **Q.** 인덱스를 많이 걸면 좋은가?
  **A.** 아니다. 쓰기가 느려지고 저장 공간도 늘어난다. **읽기와 쓰기 비율**을 보고 정해야 하며, 실제로 쿼리 실행 계획(`EXPLAIN`)을 확인해 인덱스가 쓰이는지 검증해야 한다.
- **Q.** 자료구조 지식과 연결하면?
  **A.** DB 인덱스는 **B+트리**, 메모리 캐시는 **해시 테이블**을 쓰는 게 전형적이다. 해시는 O(1)이지만 **범위 검색과 정렬이 안 되고**, 트리는 O(log n)이지만 범위 검색이 된다. DB는 `WHERE level BETWEEN 10 AND 20` 같은 범위 조회가 많아 트리가 맞다. → `04_자료구조_알고리즘.md` Q4-08.

## Q6-25. 트랜잭션과 ACID란?

**30초 답변**
> 트랜잭션은 **여러 작업을 하나의 논리적 단위로 묶어 전부 성공하거나 전부 취소되게 하는** 것입니다. ACID는 그 성질로, **원자성**(전부 되거나 전부 안 됨), **일관성**(제약 조건 유지), **격리성**(동시 트랜잭션이 서로 간섭하지 않음), **지속성**(커밋되면 장애가 나도 유지됨)을 뜻합니다. 게임에서는 아이템 거래나 결제처럼 중간에 끊기면 안 되는 처리에 필수입니다.

**상세 설명**
```sql
BEGIN TRANSACTION;
    UPDATE Player SET gold = gold - 1000 WHERE player_id = 1;   -- 구매자 지불
    UPDATE Player SET gold = gold + 1000 WHERE player_id = 2;   -- 판매자 수령
    INSERT INTO Inventory (player_id, item_id) VALUES (1, 500); -- 아이템 이전
COMMIT;    -- 하나라도 실패하면 ROLLBACK
```
| 속성 | 의미 |
|---|---|
| **A**tomicity(원자성) | 전부 성공 or 전부 롤백 |
| **C**onsistency(일관성) | 제약 조건이 항상 유지됨 |
| **I**solation(격리성) | 동시 실행되어도 순차 실행처럼 |
| **D**urability(지속성) | 커밋되면 장애에도 보존 |

- **왜 게임에 중요한가**: 아이템 거래 중간에 서버가 죽으면 **골드는 빠졌는데 아이템은 안 들어오는** 상황이 생긴다. 트랜잭션으로 묶으면 전부 롤백되어 이런 사고를 막는다. **아이템 복사 버그**도 격리성이 깨질 때 발생한다.

**꼬리질문**
- **Q.** 격리 수준(Isolation Level)이 뭔가?
  **A.** 격리를 얼마나 엄격하게 할지의 단계다. `READ UNCOMMITTED` → `READ COMMITTED` → `REPEATABLE READ` → `SERIALIZABLE` 순으로 엄격해지며, 엄격할수록 안전하지만 **동시 처리 성능이 떨어진다.** 낮은 수준에서는 더티 리드, 논리피터블 리드, 팬텀 리드 같은 문제가 생긴다.
- **Q.** 아이템 복사 버그는 왜 생기나?
  **A.** 두 요청이 **동시에 같은 아이템을 읽고 각자 처리**하면 하나가 둘이 될 수 있다. 트랜잭션과 적절한 잠금(비관적/낙관적 락)으로 막아야 한다. 이건 Q6-08의 경쟁 상태가 DB 레벨에서 나타난 것과 같다.

## Q6-26. RDB와 NoSQL의 차이는?

**30초 답변**
> **RDB(관계형 DB)** 는 정해진 스키마에 따라 테이블로 저장하고 SQL로 질의하며, **트랜잭션과 정합성이 강점**입니다. **NoSQL**은 스키마가 유연하고 **수평 확장(서버를 늘려 분산)이 쉬워** 대용량·고속 처리에 강하지만, 복잡한 조인과 강한 일관성 보장이 약합니다. 게임에서는 계정·결제는 RDB, 랭킹 캐시나 로그·세션은 NoSQL을 쓰는 식으로 나눠 씁니다.

**상세 설명**

| | RDB | NoSQL |
|---|---|---|
| 스키마 | **고정** | 유연 |
| 확장 | 수직(스케일 업) | **수평(스케일 아웃)** |
| 트랜잭션 | **강함(ACID)** | 제한적(BASE) |
| 조인 | 강력 | 약함/없음 |
| 예시 | MySQL, PostgreSQL, MSSQL | **Redis**, MongoDB, DynamoDB |

**게임에서의 실제 조합**
- **RDB**: 계정, 결제 내역, 아이템 소유권 — 정합성이 절대적으로 중요
- **Redis(인메모리 키-값)**: 랭킹 보드(Sorted Set), 세션, 매칭 대기열, 캐시 — **속도가 중요**
- **문서형/로그 DB**: 플레이 로그, 통계, 이벤트 기록 — 스키마가 자주 바뀌고 양이 많음

**내 프로젝트 연결**
- `unity_핵심정리.md` **21번**(JSON) — 강의 자료에서 **PHP + MySQL 기반 서버 연동**을 다뤘다. 클라이언트가 `WWWForm`으로 요청하면 PHP가 MySQL을 조회해 JSON으로 응답하는 구조였다.

**꼬리질문**
- **Q.** 랭킹 시스템을 만든다면?
  **A.** 실시간 조회가 많고 정렬이 필요하므로 **Redis의 Sorted Set**이 적합하다. 점수 기준 정렬과 순위 조회가 O(log n)에 되고 메모리 기반이라 매우 빠르다. 다만 영속성이 필요하므로 **주기적으로 RDB에 백업**하거나 Redis의 영속화 옵션을 쓴다.

## Q6-27. 깃으로 버전 관리를 해보았나? `★★`

> 원본 엑셀에서 **답변이 비어있던 문항.** 실제 면접에서 나온 질문이다.

**30초 답변**
> 네, 실습 코드와 정리 자료를 Git 저장소로 관리했습니다. `add`/`commit`/`push`/`pull` 같은 기본 흐름과 브랜치를 나눠 작업하고 병합하는 과정, 충돌이 났을 때 해결하는 것까지 다뤄봤습니다. Unity 프로젝트는 **`.meta` 파일과 씬 파일 충돌** 같은 특유의 주의점이 있어서 `.gitignore` 설정과 병합 전략을 신경 써야 한다는 것도 알고 있습니다.

**상세 설명 — 기본 흐름**
```bash
git init                       # 저장소 생성
git status                     # 변경 상태 확인
git add <파일>                  # 스테이징
git commit -m "메시지"          # 커밋
git log --oneline              # 히스토리 확인

git branch feature/inventory   # 브랜치 생성
git switch feature/inventory   # 브랜치 이동 (구: checkout)
git merge feature/inventory    # 병합
git push origin main
git pull origin main
```
**주요 개념**

| 개념 | 의미 |
|---|---|
| Working Directory | 실제 작업 폴더 |
| **Staging Area** | 커밋할 것을 골라두는 중간 영역 |
| Repository | 커밋 히스토리 저장소 |
| **브랜치** | 독립적인 작업 라인 |
| **HEAD** | 현재 위치한 커밋 |
| 원격(remote) | GitHub 등 서버 저장소 |

**브랜치 전략**
- **Git Flow**: `main` / `develop` / `feature` / `release` / `hotfix` — 체계적이지만 복잡
- **GitHub Flow**: `main` + `feature` 브랜치 + PR — 단순, 소규모 팀에 적합

**꼬리질문**
- **Q.** 충돌이 나면 어떻게 해결하나?
  **A.** Git이 충돌 부분을 `<<<<<<<`, `=======`, `>>>>>>>` 마커로 표시해주면, **양쪽 코드를 확인해 최종 형태로 직접 수정**하고 마커를 지운 뒤 `git add`로 해결됐음을 알리고 커밋한다. 중요한 건 **양쪽 의도를 이해하고 합치는 것**이지 한쪽을 무작정 고르는 게 아니다. 애매하면 작성자에게 물어본다.
- **Q.** 실수로 커밋한 걸 되돌리려면?
  **A.** 아직 push 안 했으면 `git reset --soft HEAD~1`(변경 내용은 유지하고 커밋만 취소). **이미 push했고 다른 사람이 받았다면 `git revert`** 로 되돌리는 커밋을 새로 만드는 게 안전하다. `reset --hard`는 작업 내용을 날리므로 신중해야 한다.
- **Q.** `.gitignore`에 뭘 넣나?
  **A.** 빌드 산출물, 임시 파일, 개인 설정, 용량이 큰 자동 생성 파일. Unity라면 `Library/`, `Temp/`, `Obj/`, `Build/`, `Logs/`, `*.csproj`, `*.sln`을 제외한다. → Q6-29.

## Q6-28. merge와 rebase의 차이는?

**30초 답변**
> **merge**는 두 브랜치를 합치는 **병합 커밋을 새로 만들어** 히스토리에 분기와 합류가 그대로 남습니다. **rebase**는 내 커밋들을 떼어내 **대상 브랜치 끝에 다시 붙여** 히스토리가 한 줄로 깔끔해집니다. rebase는 **커밋 해시가 바뀌므로 이미 공유된 브랜치에는 쓰면 안 된다**는 게 가장 중요한 원칙입니다.

**상세 설명**
```
merge                              rebase
main    A─B─────E(merge)           main    A─B─C'─D'
             \ /                              (C,D가 재작성됨)
feature       C─D                  feature 브랜치는 사라지듯 일직선
```
| | merge | rebase |
|---|---|---|
| 히스토리 | 분기가 그대로 보존 | **일직선으로 정리** |
| 커밋 해시 | 유지 | **변경됨** |
| 안전성 | **안전** | 공유 브랜치에선 위험 |
| 추적성 | 언제 합쳤는지 명확 | 원래 분기 정보 사라짐 |

- **황금 규칙**: **이미 원격에 push해서 다른 사람이 받아간 커밋은 rebase하지 않는다.** 히스토리가 갈라져 팀원들의 저장소가 꼬인다.
- 실무에서는 **로컬에서 내 작업을 정리할 때 rebase, 공유 브랜치에 합칠 때 merge**로 나눠 쓰는 경우가 많다.

**꼬리질문**
- **Q.** `squash`는 뭔가?
  **A.** 여러 커밋을 **하나로 합치는** 것이다. "오타 수정", "다시 수정" 같은 자잘한 커밋을 하나의 의미 있는 커밋으로 묶어 히스토리를 깔끔하게 만든다. GitHub PR 병합 시 "Squash and merge" 옵션이 이것이다.
- **Q.** 좋은 커밋 메시지란?
  **A.** **무엇을 왜 바꿨는지**가 드러나야 한다. "수정", "버그 픽스" 같은 건 나중에 아무 도움이 안 된다. "인벤토리 슬롯 개수가 최대치를 넘어도 추가되던 문제 수정"처럼 구체적으로 쓴다. 커밋 단위도 **하나의 논리적 변경**으로 유지하는 게 좋다.

## Q6-29. Unity 프로젝트에서 Git을 쓸 때 주의점은?

**30초 답변**
> 세 가지가 핵심입니다. 첫째, **`.meta` 파일을 반드시 커밋해야 합니다** — Unity는 파일명이 아니라 `.meta`의 guid로 참조를 관리하므로 이게 빠지면 참조가 전부 끊어집니다. 둘째, **`Library/` 같은 자동 생성 폴더는 `.gitignore`로 제외**합니다. 셋째, **씬과 프리팹은 병합 충돌 해결이 매우 어려워서** 텍스트 직렬화 설정을 켜고, 되도록 한 사람이 하나의 씬만 수정하도록 작업을 나눕니다.

**상세 설명**

**① `.gitignore` (Unity 표준)**
```
Library/
Temp/
Obj/
Build/
Builds/
Logs/
UserSettings/
*.csproj
*.sln
*.unitypackage
```
**② 필수 설정 — Project Settings → Editor**
- **Asset Serialization: Force Text** — 씬/프리팹을 YAML 텍스트로 저장해 diff와 병합이 가능해진다(바이너리면 아예 병합 불가).
- **Version Control Mode: Visible Meta Files**

**③ Git LFS** — 텍스처, 오디오, 모델 같은 대용량 바이너리는 **Git LFS**로 관리한다. 안 그러면 저장소 크기가 폭발한다.

**④ 씬 충돌 대응**
- 작업 전에 "이 씬은 내가 잡는다"고 팀에 알리는 **락 문화**
- 씬을 **Additive로 분리**해 각자 다른 씬을 편집
- 오브젝트를 프리팹으로 빼서 씬 파일 변경을 최소화
- Unity의 **Smart Merge(UnityYAMLMerge)** 도구 설정

**내 프로젝트 연결**
- `unity_핵심정리.md` **12-6, 22번 관련** — 씬 파일(`.unity`) YAML을 직접 열어 `MonoBehaviour` 블록의 **`m_Script` guid와 `.meta` 파일 guid를 대조**해서 어떤 스크립트가 실제로 붙어있는지 검증한 경험이 있다. **`.meta` guid가 참조의 근간이라는 걸 실제로 확인한 셈**이라, 이 질문에 구체적으로 답할 수 있다.

**꼬리질문**
- **Q.** `.meta` 파일을 지우면 어떻게 되나?
  **A.** Unity가 **새 guid를 발급**해서, 그 에셋을 참조하던 모든 곳(프리팹의 스크립트 연결, 씬의 재질 연결)이 **전부 끊어진다.** 인스펙터에 "Missing" 표시가 뜨고 일일이 다시 연결해야 한다.
- **Q.** 왜 `Library/`는 제외하나?
  **A.** Unity가 에셋을 임포트하며 자동 생성하는 캐시라 **용량이 매우 크고 기기마다 다르며, 지워도 재생성**된다. 커밋하면 저장소만 비대해지고 충돌도 끊임없이 난다.

**30초 답변 (뼈대 — 본인 경험으로 채울 것)**
> 저희는 **기능 단위로 담당을 나누고 Git 브랜치를 분리**해서 작업했습니다. 씬처럼 충돌이 나기 쉬운 파일은 한 사람만 수정하도록 미리 정해두고, 공통으로 쓰는 부분은 인터페이스나 매니저를 먼저 합의한 뒤 각자 구현했습니다. 진행 상황은 [사용한 도구]로 공유했고, 문제가 생기면 바로 이야기해서 오래 막히지 않도록 했습니다.

**답변 구성 요소 (이 중 실제로 해당하는 것만 골라 쓸 것)**

| 항목 | 말할 수 있는 내용 |
|---|---|
| **분업 기준** | 기능별(전투/UI/데이터) vs 레이어별(클라/서버) vs 씬별 |
| **협업 도구** | Git/GitHub, Notion, Trello, Discord, 구글 스프레드시트 |
| **충돌 방지** | 브랜치 분리, 씬 담당자 지정, 프리팹으로 분리 |
| **인터페이스 합의** | 매니저 클래스, 이벤트 규약을 먼저 정하고 병렬 작업 |
| **겪은 문제** | 씬 충돌, 서로 다른 네이밍, 진행 속도 차이 |
| **해결 방법** | 규칙 문서화, 데일리 공유, 코드 리뷰 |

**활용 가능한 실제 근거 (내 프로젝트에서)**
- **데이터를 코드에서 분리한 경험**: `ScriptableObject`(`unity_핵심정리` 5-22), **구글 스프레드시트를 CSV로 받아 게임 데이터로 사용**(15-2, 16-7). → *"기획 담당이 코드를 몰라도 데이터를 수정할 수 있게 만들어서 병목을 줄였다"* 는 분업 개선 사례로 말할 수 있다.
- **에디터 도구를 만들어 다른 담당자의 작업을 돕는 것**: 커스텀 인스펙터·`EditorWindow`·`PropertyDrawer`·Script Template(5-18~5-32, 13-4, 22번). → *"반복 작업을 툴로 만들어 팀 전체 시간을 줄이는 접근"*
- **인터페이스 기반 설계**: `IDamageable` 같은 규약을 먼저 정하면 서로 구현을 몰라도 병렬 작업이 가능하다(5-10, 5-15).
- **문자열 기반 API의 위험**(5-1, 7-4): 여러 명이 작업할 때 이름 오타가 런타임에야 드러나는 문제 → 타입 안전한 방식으로 바꾸는 게 협업에 유리하다는 논거.

**꼬리질문**
- **Q.** 팀원과 코드 스타일이 다르면?
  **A.** 개인 취향보다 **일관성이 중요**하므로, 팀 컨벤션을 정하고 그에 맞춘다. 가능하면 `.editorconfig`나 린터로 **자동화해서 사람이 신경 쓰지 않게** 만드는 게 좋다. 리뷰에서 스타일 지적으로 시간을 쓰는 건 낭비다.
- **Q.** 다른 사람 코드를 이해해야 할 때 어떻게 하나?
  **A.** 먼저 **진입점과 데이터 흐름**을 찾고, 실제로 실행하며 디버거나 로그로 따라간다. 그래도 모르면 추측하지 말고 물어본다.
  > 이건 실제로 많이 해봤다 — 22개 Unity 프로젝트를 정리하면서 **강의 자료 PDF와 실제 코드를 대조**해 "어디까지가 튜토리얼이고 어디부터가 직접 수정한 부분인지"를 판별했고(`unity_핵심정리` 7번 TempleRun 사례), 같은 이름의 스크립트가 여러 경로에 있을 때 **diff로 최종본을 판별**한 적도 있다(16번 FSM 사례).
- **Q.** 일정이 밀리면 어떻게 하나?
  **A.** **빨리 공유하는 게 가장 중요하다.** 혼자 붙들고 있다가 마감에 터뜨리는 게 최악이다. 막힌 지점을 구체적으로 설명하고, 우선순위를 조정하거나 범위를 줄이는 논의를 한다.
