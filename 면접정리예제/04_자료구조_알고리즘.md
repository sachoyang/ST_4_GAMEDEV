## Q4-01. 스택과 큐의 차이는? `★★`

**30초 답변**
> 스택은 **후입선출(LIFO)** 구조로 마지막에 넣은 것이 먼저 나오고, `push`/`pop`이 한쪽 끝(top)에서만 일어납니다. 큐는 **선입선출(FIFO)** 구조로 먼저 넣은 것이 먼저 나오며, 뒤(rear)에서 넣고 앞(front)에서 뺍니다. 스택은 함수 호출, 실행 취소, 되돌아가기에 쓰이고, 큐는 작업 대기열, 너비 우선 탐색, 이벤트 처리에 쓰입니다.

**상세 설명**
```
스택 (LIFO)              큐 (FIFO)
   push↓ ↑pop            enqueue→ [ ][ ][ ] →dequeue
  ┌───┐                            rear    front
  │ C │ ← top
  │ B │
  │ A │
  └───┘
```
| | 스택 | 큐 |
|---|---|---|
| 원칙 | LIFO | FIFO |
| 삽입/삭제 | 한쪽 끝(top) | 양쪽 끝(rear/front) |
| 주요 연산 | `push`/`pop`/`peek` | `enqueue`/`dequeue`/`front` |
| 게임 활용 | 되돌리기, 씬 스택, 재귀 대체 | 스폰 대기열, BFS, 메시지 큐 |
| 복잡도 | 모두 O(1) | 모두 O(1) |

**게임에서의 실제 활용**
- **스택**: UI 창 스택(뒤로 가기), 되돌리기, DFS 구현, 상태 스택(일시정지 위에 설정창).
- **큐**: 오브젝트 풀의 대기 목록, 네트워크 패킷 처리, BFS 길찾기, 애니메이션 재생 대기열.

**내 프로젝트 연결**
- `c_핵심정리.md` **12번** — **스택을 배열로 직접 구현 + 백트래킹(미로찾기)**. C 폴더 전체의 대표 예제다.
- `cpp_핵심정리.md` **18번** — 자료구조 직접구현의 진화: **배열 스택 → 클래스 스택 → 템플릿 스택, 그리고 원형 큐**.

**꼬리질문**
- **Q.** 스택을 실제로 구현해봤나?
  **A.** 세 단계로 해봤다. C에서는 배열과 `top` 인덱스로 직접 구현해 미로찾기 백트래킹에 썼고(`c_핵심정리` 12번), C++에서는 이걸 클래스로 캡슐화한 뒤 **템플릿으로 일반화**해서 어떤 타입이든 담을 수 있게 만들었다(`cpp_핵심정리` 18번).

  **A.** 앞에서 빼면 뒤 원소를 전부 당겨야 해서 O(n)이 된다. `front` 인덱스만 옮기면 O(1)이지만 앞쪽 공간이 낭비된다. 이를 해결한 게 **원형 큐**다 → Q4-04.

## Q4-02. 배열과 리스트의 차이는? `★`

**30초 답변**
> 배열은 **연속된 메모리에 고정 크기**로 저장되어 인덱스 접근이 O(1)이고 캐시 효율이 좋지만, 크기를 바꿀 수 없고 중간 삽입·삭제가 O(n)입니다. 연결 리스트는 **노드가 포인터로 연결된** 구조라 크기가 유연하고 위치를 알면 삽입·삭제가 O(1)이지만, 인덱스 접근이 불가능하고 노드가 흩어져 순회가 느립니다. 실무에서는 캐시 효율 때문에 **동적 배열(`vector`/`List<T>`)이 기본 선택**입니다.

**상세 설명**

| 연산 | 배열/동적 배열 | 연결 리스트 |
|---|---|---|
| 인덱스 접근 | **O(1)** | O(n) |
| 맨 앞 삽입/삭제 | O(n) | **O(1)** |
| 중간 삽입/삭제 | O(n) | **O(1)** (위치 알 때) |
| 맨 뒤 삽입 | 평균 O(1) | O(1) |
| 메모리 | 연속, 오버헤드 없음 | 노드마다 포인터 오버헤드 |
| 캐시 효율 | **매우 좋음** | 나쁨 |

- **중요한 함정**: 연결 리스트의 "중간 삽입 O(1)"은 **이미 그 위치의 노드를 알고 있을 때**만이다. 인덱스로 찾아가야 하면 탐색에 O(n)이 들어서 결국 O(n)이다.
- **C#의 `List<T>`는 연결 리스트가 아니라 내부가 배열**이다. 이름 때문에 혼동하기 쉬워 면접에서 자주 확인한다. 진짜 연결 리스트는 `LinkedList<T>`다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **13번**(STL 컨테이너 & 반복자), **19번**(이중 연결 리스트 직접 구현).
- `c_핵심정리.md` **4번**(1차원 배열), **8번**(2차원 배열).
- `unity_핵심정리.md` **12-8** — C# 배열 문법 총정리(1차원/다차원/가변길이).
- `unity_핵심정리.md` **22-1** — 2차원 격자를 **1차원 `List<bool>` + `index = y*width+x`** 로 저장한 사례.

**꼬리질문**
- **Q.** 동적 배열은 어떻게 커지나?
  **A.** 용량이 차면 보통 **1.5~2배 크기의 새 배열을 할당하고 전부 복사**한 뒤 기존 것을 버린다. 개별 삽입은 가끔 O(n)이지만 **분할 상환(amortized)하면 평균 O(1)**이다. 크기를 미리 알면 `reserve()`/`Capacity`로 잡아두는 게 좋다.
- **Q.** 그럼 연결 리스트는 언제 쓰나?
  **A.** ① 요소의 **주소가 절대 바뀌면 안 될 때**(동적 배열은 재할당 시 전부 이동), ② 중간 삽입·삭제가 압도적으로 많고 이미 위치를 알고 있을 때, ③ 리스트 병합이 빈번할 때. 게임에서는 드물고, 대부분 동적 배열이 낫다.
- **Q.** 게임에서 리스트 중간 요소를 자주 지운다면?
  **A.** 순서가 상관없으면 **마지막 원소를 그 자리로 옮기고 마지막을 제거(swap-remove)** 해서 O(1)로 만든다. 활성 적/총알 목록 관리에 흔히 쓰는 기법이다.

## Q4-03. 이중 연결 리스트를 직접 구현해보라 `★`

> 원본 엑셀에 "22.03.14 수업자료 참고"로만 되어 있던 문항. **코딩 테스트로 나올 수 있으니 직접 짤 수 있어야 한다.**

**30초 답변**
> 각 노드가 **데이터와 앞/뒤 노드 포인터 두 개**를 갖는 구조입니다. 단일 연결 리스트와 달리 양방향 순회가 가능하고, 특정 노드를 알면 그 앞뒤를 바로 알 수 있어 **삭제가 O(1)**입니다. 구현 시 head/tail 처리를 단순화하려고 **센티넬(더미) 노드**를 앞뒤에 두는 기법을 씁니다.

**상세 설명**
```cpp
template<typename T>
class DoublyLinkedList {
    struct Node {
        T data;
        Node* prev;
        Node* next;
        Node(const T& d) : data(d), prev(nullptr), next(nullptr) {}
    };
    Node* head;   // 센티넬
    Node* tail;   // 센티넬
    int   count;

public:
    DoublyLinkedList() : count(0) {
        head = new Node(T());       // 더미 노드
        tail = new Node(T());
        head->next = tail;
        tail->prev = head;          // 빈 리스트: head <-> tail
    }
    ~DoublyLinkedList() { Clear(); delete head; delete tail; }

    // pos 노드 앞에 삽입 - O(1)
    void InsertBefore(Node* pos, const T& value) {
        Node* n = new Node(value);
        n->prev = pos->prev;
        n->next = pos;
        pos->prev->next = n;        // 센티넬 덕분에 null 체크가 필요 없다
        pos->prev = n;
        count++;
    }
    void PushBack(const T& v)  { InsertBefore(tail, v); }
    void PushFront(const T& v) { InsertBefore(head->next, v); }

    // 노드 제거 - O(1)
    void Remove(Node* n) {
        if (n == head || n == tail) return;
        n->prev->next = n->next;
        n->next->prev = n->prev;
        delete n;
        count--;
    }
    void Clear() { while (head->next != tail) Remove(head->next); }
};
```
**센티넬 노드를 쓰는 이유**: 센티넬이 없으면 삽입/삭제 시 "맨 앞인가?", "맨 뒤인가?", "유일한 원소인가?"를 매번 분기해야 한다. 센티넬을 두면 **모든 경우가 동일한 코드로 처리**되어 버그가 크게 줄어든다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **19번** — **이중 연결 리스트를 센티넬 노드 패턴으로 직접 구현하고 템플릿화**한 항목. 정확히 이 질문의 답이다.

**꼬리질문**
- **Q.** 단일 연결 리스트와 비교하면?
  **A.** 이중 연결 리스트는 **역방향 순회와 O(1) 삭제**가 가능한 대신 노드마다 포인터가 하나 더 필요해 **메모리를 더 쓴다.** 단일 연결 리스트에서 특정 노드를 지우려면 이전 노드를 알아야 해서 탐색 O(n)이 필요하다.
- **Q.** 소멸자에서 뭘 주의해야 하나?
  **A.** 모든 노드를 순회하며 `delete` 해야 한다. 안 하면 **메모리 누수**다. 또 이 클래스는 포인터 멤버를 갖고 있으므로 **Rule of Three**에 따라 복사 생성자와 복사 대입 연산자도 구현하거나 `= delete`로 막아야 한다(얕은 복사 시 이중 해제). → `01_C_CPP.md` Q1-03.
- **Q.** STL의 `std::list`와 뭐가 다른가?
  **A.** `std::list`가 정확히 이중 연결 리스트다. 실무에선 직접 구현할 일이 거의 없지만, **면접에서는 포인터 조작 능력과 경계 조건 처리 능력을 보려고** 묻는다.

## Q4-04. 원형 큐와 덱(Deque)이란?

**30초 답변**
> **원형 큐**는 배열의 끝과 시작을 논리적으로 이어붙여, 앞쪽에서 빠져나간 공간을 재사용하는 큐입니다. `front`와 `rear` 인덱스를 배열 크기로 나눈 나머지(`% size`)로 순환시켜 O(1) 삽입·삭제를 유지하면서 공간 낭비를 없앱니다. **덱(Deque)** 은 양쪽 끝 모두에서 삽입·삭제가 가능한 자료구조로, 스택과 큐를 동시에 대신할 수 있습니다.

**상세 설명**
```cpp
class CircularQueue {
    int data[SIZE];
    int front = 0, rear = 0, count = 0;
public:
    bool Enqueue(int v) {
        if (count == SIZE) return false;            // 가득 참
        data[rear] = v;
        rear = (rear + 1) % SIZE;                    // 핵심: 나머지 연산으로 순환
        count++;
        return true;
    }
    bool Dequeue(int& out) {
        if (count == 0) return false;
        out = data[front];
        front = (front + 1) % SIZE;
        count--;
        return true;
    }
};
```
- **가득 참과 비어있음 구분**: `front == rear`만으로는 둘을 구분할 수 없다. 해결책은 ① `count` 변수를 따로 두거나, ② 한 칸을 비워두고 `(rear+1)%SIZE == front`를 "가득 참"으로 판단하는 것이다. **면접 단골 포인트다.**
- **덱**: C++ `std::deque`, C# `LinkedList<T>`나 `Queue`/`Stack` 조합. 게임에서 슬라이딩 윈도우, 최근 입력 버퍼 등에 쓴다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **18번** — 스택 진화 과정과 함께 **원형 큐**를 직접 구현했다.

**꼬리질문**
- **Q.** 원형 큐를 게임에서 어디에 쓰나?
  **A.** ① **입력 버퍼**(격투 게임의 커맨드 입력 기록), ② **네트워크 패킷 링 버퍼**, ③ 최근 N프레임의 성능 기록(FPS 평균 계산), ④ 오디오 스트리밍 버퍼. 크기가 고정이고 오래된 것부터 덮어써도 되는 데이터에 적합하다.

## Q4-05. 해시 테이블이란? 충돌은 어떻게 해결하나?

**30초 답변**
> 키를 **해시 함수로 정수 인덱스로 변환해 배열에 바로 접근**하는 자료구조입니다. 탐색·삽입·삭제가 평균 O(1)로 매우 빠릅니다. 서로 다른 키가 같은 인덱스로 매핑되는 **충돌**이 필연적으로 발생하는데, 해결법은 같은 버킷에 연결 리스트로 매다는 **체이닝**과 빈 자리를 찾아 넣는 **개방 주소법** 두 가지입니다.

**상세 설명**
```
키 "apple" → 해시 함수 → 42 → 42 % 16 = 10번 버킷

체이닝(Chaining)                 개방 주소법(Open Addressing)
[10] → ("apple") → ("grape")     [10] ("apple")
                                  [11] ("grape")  ← 충돌 시 다음 빈 칸
```
| | 체이닝 | 개방 주소법 |
|---|---|---|
| 충돌 처리 | 버킷에 리스트로 매달기 | 다른 빈 버킷 탐사 |
| 메모리 | 노드 오버헤드 | 배열만(캐시 유리) |
| 삭제 | 간단 | 복잡(삭제 표시 필요) |
| 적재율 | 1 초과 가능 | 1 미만 필수 |
| 사용처 | STL `unordered_map`, C# `Dictionary` | Python dict, 고성능 구현 |

- **개방 주소법의 탐사 방식**: 선형 탐사(`+1`씩), 이차 탐사(`+1, +4, +9`), 이중 해싱(다른 해시 함수로 간격 결정).
- **적재율(load factor)** 이 일정 수준(보통 0.75)을 넘으면 **재해싱** — 버킷 배열을 2배로 늘리고 전부 다시 배치한다. 이때 O(n)이 걸린다.

**꼬리질문**
- **Q.** 좋은 해시 함수의 조건은?
  **A.** ① **균등 분포** — 키가 버킷에 고르게 흩어져야 충돌이 적다, ② **빠른 계산**, ③ **결정적** — 같은 키는 항상 같은 값, ④ 비슷한 키가 전혀 다른 해시를 갖는 **눈사태 효과**.
- **Q.** 최악의 경우 시간 복잡도는?
  **A.** **O(n)** 이다. 모든 키가 같은 버킷에 몰리면 결국 선형 탐색이 된다. 그래서 해시 함수 품질이 중요하고, 실제로 이걸 악용해 서버를 마비시키는 **해시 충돌 DoS 공격**도 존재한다.
- **Q.** `Equals`와 `GetHashCode`를 함께 재정의해야 하는 이유는?
  **A.** 해시 테이블은 **해시로 버킷을 찾고 `Equals`로 최종 확인**한다. 둘의 규칙이 어긋나면(같다고 판단되는 두 객체가 다른 해시를 가지면) 분명히 넣었는데 못 찾는 버그가 생긴다. → `02_CSharp.md` Q2-22.

## Q4-06. "오픈 서치"란? `★★`

> 실제 면접에서 나온 질문인데 **용어가 모호하다.** 문맥(직전에 "스택과 큐", "메모리 종류"를 물어봄)상 자료구조·탐색 쪽 질문일 가능성이 높다. 아래 세 가지 해석을 준비해두고, **면접에서는 "어떤 맥락에서의 오픈 서치를 말씀하시는 걸까요?"라고 되묻는 것이 최선**이다. 모르면서 아는 척하는 것보다 훨씬 낫다.

**해석 ① 개방 주소법(Open Addressing) — 가장 가능성 높음**
> 해시 테이블에서 충돌이 발생했을 때 **다른 빈 버킷을 찾아 저장하는 방식**입니다. 체이닝처럼 별도 리스트를 만들지 않고 배열 안에서만 해결해서 메모리가 연속적이라 캐시 효율이 좋습니다. 선형 탐사, 이차 탐사, 이중 해싱 방식이 있고, 삭제 시에는 탐사 경로가 끊기지 않도록 **삭제 표시(tombstone)** 를 남겨야 하는 게 까다로운 점입니다. → Q4-05.

**해석 ② 개방 탐색 / 완전 탐색 계열**
> 정해진 규칙 없이 가능한 경우를 넓게 탐색하는 방식을 뜻할 수도 있습니다. 게임 AI에서는 **A\*처럼 Open List(열린 목록)를 유지하며 탐색하는 알고리즘**을 이렇게 부르기도 합니다. A*는 아직 탐색하지 않은 후보를 Open List에, 이미 확정한 노드를 Closed List에 두고 F값이 가장 작은 노드를 반복해서 꺼냅니다. → Q4-19.

**해석 ③ OpenSearch (검색 엔진)**
> Elasticsearch에서 갈라져 나온 **오픈소스 검색·분석 엔진**입니다. 대량의 로그나 문서를 색인해 빠르게 검색하는 용도로, 게임 서버 로그 분석에 쓰이기도 합니다. 클라이언트 개발 직군 면접에서 나올 가능성은 낮습니다.

**꼬리질문 대비**
- **Q.** 모르는 용어가 나오면 어떻게 하겠나?
  **A.** **솔직히 되묻는다.** "제가 아는 범위에서는 A/B 두 가지 의미로 쓰이는데 어느 쪽을 말씀하시는지 확인해도 될까요?"라고 하면, 오히려 용어를 여러 각도로 알고 있다는 인상을 준다. 아는 척했다가 꼬리질문에서 무너지는 게 최악이다.
- **Q.** 그럼 A*의 Open List는 어떻게 관리하나?
  **A.** F값이 최소인 노드를 반복해서 꺼내야 하므로 **우선순위 큐(힙)** 로 관리하는 게 표준이다. 리스트로 관리하면 매번 최소값을 O(n)으로 찾아야 한다. 내 A* 구현에서는 리스트를 순회하는 방식이었고, 힙으로 바꾸면 개선 여지가 있다는 걸 알고 있다. → Q4-09, Q4-19.

## Q4-07. 트리와 이진 탐색 트리(BST)를 설명하라

**30초 답변**
> 트리는 **부모-자식 관계로 이루어진 계층 구조**이고 사이클이 없습니다. 이진 트리는 자식이 최대 둘인 트리이며, **이진 탐색 트리(BST)** 는 여기에 "왼쪽 자식은 부모보다 작고 오른쪽 자식은 부모보다 크다"는 규칙을 더한 것입니다. 이 규칙 덕분에 탐색·삽입·삭제를 평균 O(log n)에 할 수 있습니다.

**상세 설명**
```
        8            중위 순회(왼→루트→오른) 하면
      /   \          3, 4, 6, 8, 10, 14  ← 정렬된 순서로 나온다
     3     10
    / \      \
   1   6     14
```
**순회 방식**

| 방식 | 순서 | 용도 |
|---|---|---|
| 전위(Pre-order) | 루트 → 왼 → 오 | 트리 복사, 직렬화 |
| **중위(In-order)** | 왼 → **루트** → 오 | **BST를 정렬된 순서로** |
| 후위(Post-order) | 왼 → 오 → 루트 | 트리 삭제, 계산식 평가 |
| 레벨(BFS) | 위에서 아래로 층별 | 최단 경로, 층별 처리 |

- **게임에서의 트리**: 씬 계층(Transform 부모-자식), 행동 트리(Behaviour Tree), UI 계층, 공간 분할(쿼드트리/옥트리), 스킬 트리.

**내 프로젝트 연결**
- `unity_핵심정리.md` **19-1** — 배열 기반 완전 이진 트리로 힙을 구현.
- `unity_핵심정리.md` **19-5** — **힙의 트리 구조를 GameObject로 실시간 시각화**(좌표 계산식으로 층별 배치).
- Unity의 `Transform` 계층 자체가 트리 구조다.

**꼬리질문**
- **Q.** BST의 최악의 경우는?
  **A.** 이미 **정렬된 데이터를 순서대로 삽입**하면 한쪽으로만 자라 사실상 연결 리스트가 되어 **O(n)** 이 된다. 이걸 막으려고 균형 트리를 쓴다 → Q4-08.
- **Q.** 트리의 높이와 복잡도 관계는?
  **A.** 탐색은 루트에서 리프까지 내려가므로 **높이에 비례**한다. 완전히 균형 잡힌 이진 트리의 높이는 `log₂n`이라 O(log n)이고, 한쪽으로 치우치면 높이가 n이 되어 O(n)이다.

## Q4-08. 균형 이진 트리(AVL, 레드-블랙)가 왜 필요한가?

**30초 답변**
> 일반 BST는 삽입 순서에 따라 한쪽으로 치우쳐 **최악 O(n)** 이 될 수 있기 때문입니다. 균형 트리는 삽입·삭제 때마다 **회전(rotation)** 으로 좌우 높이 차를 일정 범위로 유지해 **항상 O(log n)을 보장**합니다. AVL은 엄격하게 균형을 맞춰 탐색이 빠르고, 레드-블랙 트리는 느슨하게 맞춰 삽입·삭제가 빠릅니다.

**상세 설명**

| | AVL 트리 | 레드-블랙 트리 |
|---|---|---|
| 균형 조건 | 좌우 높이 차 ≤ 1 (엄격) | 루트-리프 경로의 검은 노드 수 동일 (느슨) |
| 탐색 | **더 빠름** | 조금 느림 |
| 삽입/삭제 | 회전 많음 | **회전 적음** |
| 실제 사용 | DB 인덱스 일부 | **STL `map`/`set`, C# `SortedDictionary`, 리눅스 커널** |

- 실무에서 마주치는 건 대부분 **레드-블랙 트리**다. C++ `std::map`, C# `SortedDictionary`가 이걸 쓴다.
- **회전(rotation)**: 부모-자식 관계를 재배치해 높이를 낮추는 O(1) 연산이다.

**꼬리질문**
- **Q.** `map`(트리) 대신 `unordered_map`(해시)을 쓰면 되지 않나?
  **A.** 단순 조회만 필요하면 해시가 더 빠르다. 하지만 트리는 **키가 정렬된 상태로 유지**되어 ① 순서대로 순회, ② **범위 검색**(`lower_bound`로 "50 이상 100 이하"), ③ 최소/최대값 즉시 조회가 가능하다. 랭킹 시스템처럼 순서가 중요한 곳에서는 트리가 맞다. → `01_C_CPP.md` Q1-29.

## Q4-09. 힙과 우선순위 큐란?

**30초 답변**
> 힙은 **부모가 자식보다 항상 크거나(최대 힙) 작은(최소 힙)** 완전 이진 트리입니다. 루트에 항상 최댓값 또는 최솟값이 있어서 **O(1)로 조회**하고 **O(log n)으로 삽입·삭제**할 수 있습니다. 이 성질을 이용해 "가장 우선순위 높은 것을 먼저 꺼내는" **우선순위 큐**를 구현합니다. 완전 이진 트리라서 포인터 없이 **배열로 표현**하는 것이 특징입니다.

**상세 설명**
```
배열 인덱스 관계 (0-based)
  부모(i)      = (i-1) / 2
  왼쪽 자식(i)  = 2i + 1
  오른쪽 자식(i) = 2i + 2

      10(0)
     /    \
   7(1)   9(2)          배열: [10, 7, 9, 3, 5]
   /  \
 3(3) 5(4)
```
**삽입(Push) — 상향 재정렬(Sift-Up)**: 맨 끝에 넣고, 부모보다 크면 부모와 교환하며 위로 올라간다. O(log n)
**삭제(Pop) — 하향 재정렬(Sift-Down)**: 루트를 꺼내고 맨 끝 원소를 루트로 옮긴 뒤, 자식 중 큰 쪽과 비교하며 내려간다. O(log n)

**내 프로젝트 연결 — 직접 구현해봤다**
- `unity_핵심정리.md` **19-1** 배열 기반 완전이진트리, **19-2** 삽입 + 상향 재정렬(Sift-Up), **19-3** 삭제 + 하향 재정렬(Sift-Down), **19-4** **Min-Heap ↔ Max-Heap 전환(비교 부등호만 다름)**, **19-5** 힙 구조 실시간 시각화, **19-6** 배열 인덱스 방식과 포인터 방식 절충 설계.
> 이 프로젝트(`우선순위HeapSort`)는 통째로 이 질문의 답변 자료다.

**꼬리질문**
- **Q.** Min-Heap과 Max-Heap을 어떻게 전환하나?
  **A.** **비교 부등호만 뒤집으면 된다.** 실제로 구현해보고 이 점을 정리해뒀다(19-4). 또는 값에 -1을 곱해 넣거나 비교자(comparer)를 주입하는 방법도 있다.
- **Q.** 힙 정렬(Heap Sort)의 복잡도는?
  **A.** 모든 원소를 넣고(n × log n) 하나씩 빼면(n × log n) **O(n log n)** 이다. 추가 메모리가 거의 필요 없는 **제자리 정렬**이라는 장점이 있지만, 캐시 효율이 나빠서 실제로는 퀵 정렬보다 느린 경우가 많다.
- **Q.** 게임에서 우선순위 큐를 어디에 쓰나?
  **A.** ① **A\* 길찾기의 Open List**(F값이 최소인 노드를 꺼냄 — 가장 대표적), ② 이벤트/타이머 스케줄러(가장 빠른 시각의 이벤트를 먼저), ③ AI 행동 우선순위, ④ 네트워크 패킷 우선순위 처리.
- **Q.** C#/C++에 내장되어 있나?
  **A.** C++는 `std::priority_queue`(기본 최대 힙), C#은 **.NET 6부터 `PriorityQueue<TElement, TPriority>`** 가 추가됐다. 다만 **Unity는 .NET Standard 2.1 기준이라 이 클래스를 쓸 수 없어서 직접 구현하거나 라이브러리를 써야 한다.** 내가 직접 구현해본 게 그래서 의미가 있다.

## Q4-10. 그래프를 표현하는 두 가지 방법은?

**30초 답변**
> **인접 행렬**은 `V×V` 2차원 배열에 연결 여부를 저장해서 두 정점의 연결을 O(1)에 확인할 수 있지만 메모리를 O(V²) 씁니다. **인접 리스트**는 각 정점마다 연결된 정점들의 리스트를 두어 메모리가 O(V+E)로 효율적이지만, 특정 연결 확인은 O(degree)가 걸립니다. **간선이 적은 희소 그래프에는 인접 리스트**, 조밀한 그래프에는 인접 행렬이 유리합니다.

**상세 설명**
```
그래프          인접 행렬              인접 리스트
0 — 1             0 1 2 3              0: [1, 2]
|   |          0 [0 1 1 0]             1: [0, 3]
2 — 3          1 [1 0 0 1]             2: [0, 3]
               2 [1 0 0 1]             3: [1, 2]
               3 [0 1 1 0]
```
| | 인접 행렬 | 인접 리스트 |
|---|---|---|
| 메모리 | O(V²) | **O(V+E)** |
| 연결 확인 | **O(1)** | O(degree) |
| 인접 정점 순회 | O(V) | **O(degree)** |
| 적합한 경우 | 조밀한 그래프 | **희소 그래프(대부분)** |

- 게임의 길찾기 그리드는 보통 **각 칸이 인접한 8칸과만 연결**된 희소 그래프라, 인접 리스트를 명시적으로 만들지 않고 **좌표 계산으로 이웃을 즉석에서 구하는** 방식을 많이 쓴다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **18번**(Astar) — 그리드 기반 길찾기를 구현했다. 그리드는 사실상 그래프이고, 이웃 노드를 좌표 오프셋으로 계산하는 방식을 썼다.

**꼬리질문**
- **Q.** 게임에서 그래프를 어디에 쓰나?
  **A.** ① **길찾기**(내비게이션 메시, 웨이포인트 그래프), ② 퀘스트/대화 분기, ③ 스킬 트리, ④ 상태 기계(FSM도 그래프다), ⑤ 던전 생성(방과 통로의 연결).

## Q4-11. 시간 복잡도와 빅오 표기법을 설명하라

**30초 답변**
> 시간 복잡도는 **입력 크기 n이 커질 때 연산 횟수가 얼마나 증가하는지**를 나타냅니다. 빅오 표기법은 그 **증가율의 상한**을 표현하며, 상수 배수와 낮은 차수 항은 무시합니다. 예를 들어 `3n² + 5n + 10`은 `O(n²)`입니다. 실제 실행 시간이 아니라 **확장성**을 비교하는 도구입니다.

**상세 설명**

| 복잡도 | 이름 | n=1,000일 때 | 예시 |
|---|---|---|---|
| O(1) | 상수 | 1 | 배열 인덱스 접근, 해시 조회 |
| O(log n) | 로그 | 약 10 | 이진 탐색, 균형 트리 |
| O(n) | 선형 | 1,000 | 배열 순회, 선형 탐색 |
| O(n log n) | 선형로그 | 약 10,000 | 퀵/병합/힙 정렬 |
| O(n²) | 이차 | 1,000,000 | 버블/선택/삽입 정렬, 이중 루프 |
| O(2ⁿ) | 지수 | 천문학적 | 부분집합 완전탐색 |

- **빅오는 최악의 경우**를 나타내는 게 관례다. 평균은 빅세타(Θ), 최선은 빅오메가(Ω)로 구분하지만 실무에선 대개 빅오만 쓴다.
- **공간 복잡도**도 같은 방식으로 표현한다. 추가로 쓰는 메모리 기준이다.

**꼬리질문**
- **Q.** O(n²)이 O(n log n)보다 항상 느린가?
  **A.** 아니다. **n이 작으면 상수 항이 지배**해서 단순한 알고리즘이 더 빠를 수 있다. 실제로 여러 표준 라이브러리의 정렬은 원소가 일정 개수(보통 16~32개) 이하면 **삽입 정렬로 전환**한다. 빅오는 어디까지나 큰 n에서의 경향이다.
- **Q.** 게임에서 시간 복잡도를 어떻게 고려하나?
  **A.** 게임은 **매 프레임 반복**되므로 O(n²) 로직이 60번/초 돌면 치명적이다. 예를 들어 모든 적끼리 거리 검사를 하면 O(n²)인데, **공간 분할(쿼드트리, 그리드)** 로 주변만 검사하면 사실상 O(n)으로 줄일 수 있다. → Q4-24.

## Q4-12. 버블 정렬을 설명하라 `★`

**30초 답변**
> 인접한 두 원소를 비교해 순서가 잘못되어 있으면 교환하는 것을 반복하는 정렬입니다. 한 번 순회할 때마다 가장 큰 값이 맨 뒤로 "거품처럼" 올라가서 붙은 이름입니다. 구현이 매우 단순하지만 시간 복잡도가 **O(n²)** 로 느려서 실무에서는 쓰지 않고, 교육용이나 원소가 극히 적을 때만 씁니다.

**상세 설명**
```cpp
void BubbleSort(int arr[], int n) {
    for (int i = 0; i < n - 1; i++) {
        bool swapped = false;                       // 최적화: 교환이 없으면 이미 정렬됨
        for (int j = 0; j < n - 1 - i; j++) {       // -i : 뒤쪽은 이미 확정
            if (arr[j] > arr[j+1]) {
                std::swap(arr[j], arr[j+1]);
                swapped = true;
            }
        }
        if (!swapped) break;                        // 이미 정렬 완료 -> 최선 O(n)
    }
}
```
| | 복잡도 |
|---|---|
| 최선(이미 정렬, 플래그 최적화 시) | **O(n)** |
| 평균/최악 | **O(n²)** |
| 공간 | **O(1)** (제자리 정렬) |
| 안정성 | **안정 정렬** |

**꼬리질문**
- **Q.** 선택 정렬, 삽입 정렬과 비교하면?
  **A.** 셋 다 O(n²)이지만 성격이 다르다. **선택 정렬**은 최솟값을 찾아 앞으로 보내며 교환 횟수가 최소(O(n))지만 항상 O(n²) 비교를 한다(불안정 정렬). **삽입 정렬**은 이미 정렬된 부분에 끼워 넣는 방식으로 **거의 정렬된 데이터에서는 O(n)에 가까워** 실전에서 유용하다. 버블 정렬은 셋 중 가장 느린 편이다.
- **Q.** 공간 복잡도가 O(1)인 이유는?
  **A.** 원본 배열 안에서 교환만 하고 추가 배열을 안 만들기 때문이다. 이를 **제자리(in-place) 정렬**이라 한다. 원본 엑셀 답변에는 "공간 복잡도 O(n)"이라고 되어 있는데, 입력 배열까지 포함하면 O(n), **추가 공간 기준으로는 O(1)** 이 정확한 표현이다. 면접에서는 "추가 공간 O(1)"이라고 말하는 게 안전하다.

## Q4-13. 퀵 정렬을 설명하라 `★`

**30초 답변**
> **피벗(기준값)을 하나 정하고, 피벗보다 작은 값은 왼쪽 큰 값은 오른쪽으로 분할한 뒤, 양쪽을 재귀적으로 다시 정렬**하는 분할 정복 알고리즘입니다. 평균 O(n log n)이고 제자리 정렬이라 추가 메모리가 거의 없으며 캐시 효율이 좋아 **실무에서 가장 널리 쓰입니다.** 다만 피벗을 잘못 고르면 최악 O(n²)이 됩니다.

**상세 설명**
```cpp
int Partition(int arr[], int low, int high) {
    int pivot = arr[high];          // 맨 뒤를 피벗으로
    int i = low - 1;
    for (int j = low; j < high; j++) {
        if (arr[j] < pivot) {
            i++;
            std::swap(arr[i], arr[j]);
        }
    }
    std::swap(arr[i+1], arr[high]);  // 피벗을 제자리로
    return i + 1;
}
void QuickSort(int arr[], int low, int high) {
    if (low < high) {
        int p = Partition(arr, low, high);
        QuickSort(arr, low, p - 1);      // 피벗 제외하고 양쪽 재귀
        QuickSort(arr, p + 1, high);
    }
}
```
| | 복잡도 |
|---|---|
| 평균 | **O(n log n)** |
| 최악(정렬된 배열 + 끝 피벗) | **O(n²)** |
| 공간 | O(log n) — 재귀 스택 |
| 안정성 | **불안정 정렬** |

**꼬리질문**
- **Q.** 최악의 경우는 언제이고 어떻게 피하나?
  **A.** **이미 정렬된 배열에서 항상 맨 앞/뒤를 피벗으로 고르면** 한쪽이 비어 분할이 안 되고 재귀 깊이가 n이 되어 O(n²)이다. 대응책은 ① **중앙값 3개 중 하나 고르기(median-of-three)**, ② **무작위 피벗**, ③ 재귀가 너무 깊어지면 힙 정렬로 전환하는 **인트로 정렬(introsort)** — C++ `std::sort`가 이 방식이다.
- **Q.** 병합 정렬 대신 퀵 정렬을 쓰는 이유는?
  **A.** 둘 다 평균 O(n log n)이지만 퀵 정렬은 ① **추가 메모리가 거의 없고**(병합 정렬은 O(n) 필요), ② **참조 지역성이 좋아 캐시 효율이 높다.** 그래서 실측 성능이 대체로 더 빠르다. 다만 최악 보장이 필요하거나 **안정 정렬**이 필요하면 병합 정렬을 쓴다.
- **Q.** 재귀 깊이가 스택 오버플로를 일으킬 수 있나?
  **A.** 가능하다. 최악의 경우 재귀 깊이가 n까지 간다. 그래서 실무 구현은 **작은 쪽을 먼저 재귀하고 큰 쪽은 반복으로 처리**해서 스택 깊이를 O(log n)으로 제한한다.
  > 관련 경험: `unity_핵심정리.md` 18-5의 A* 구현에서 **"재귀 함수 호출의 제한으로 프로그램이 강제 종료될 수 있다"**는 이유로 재귀 대신 코루틴을 택했다. 같은 문제 의식이다.

## Q4-14. 병합 정렬을 설명하라

**30초 답변**
> 배열을 **절반씩 계속 나눠 더 이상 나눌 수 없을 때까지 쪼갠 뒤, 정렬된 두 부분을 병합하며 올라오는** 분할 정복 알고리즘입니다. 어떤 입력에서도 **항상 O(n log n)을 보장**하고 **안정 정렬**이라는 장점이 있지만, 병합을 위한 **추가 배열 O(n)** 이 필요합니다.

**상세 설명**
```cpp
void Merge(int arr[], int left, int mid, int right, int temp[]) {
    int i = left, j = mid + 1, k = left;
    while (i <= mid && j <= right)
        temp[k++] = (arr[i] <= arr[j]) ? arr[i++] : arr[j++];   // <= 가 안정성의 핵심
    while (i <= mid)   temp[k++] = arr[i++];
    while (j <= right) temp[k++] = arr[j++];
    for (int x = left; x <= right; x++) arr[x] = temp[x];
}
void MergeSort(int arr[], int left, int right, int temp[]) {
    if (left >= right) return;
    int mid = (left + right) / 2;
    MergeSort(arr, left, mid, temp);
    MergeSort(arr, mid + 1, right, temp);
    Merge(arr, left, mid, right, temp);
}
```
| | 복잡도 |
|---|---|
| 최선/평균/최악 | **O(n log n) 항상 보장** |
| 공간 | **O(n)** |
| 안정성 | **안정 정렬** |

**꼬리질문**
- **Q.** 왜 `<=`가 안정성의 핵심인가?
  **A.** 같은 값일 때 **왼쪽(먼저 있던) 것을 먼저 넣기** 때문이다. `<`로 바꾸면 오른쪽 것이 먼저 들어가 원래 순서가 뒤집혀 불안정 정렬이 된다.
- **Q.** 연결 리스트 정렬에는 어느 쪽이 유리한가?
  **A.** **병합 정렬**이다. 연결 리스트는 임의 접근이 안 되어 퀵 정렬의 파티셔닝이 비효율적이지만, 병합 정렬은 순차 접근만 하면 되고 **포인터만 재연결하면 되어 추가 메모리도 O(1)** 로 줄일 수 있다. 그래서 `std::list::sort`가 병합 정렬 기반이다.

## Q4-15. 정렬 알고리즘을 비교하라 / 안정 정렬이란?

**30초 답변**
> **안정 정렬**은 **값이 같은 원소들의 원래 순서가 정렬 후에도 유지되는** 정렬입니다. 예를 들어 점수로 정렬할 때 같은 점수인 두 사람의 순서가 입력 순서 그대로 남으면 안정 정렬입니다. 다중 조건 정렬(먼저 이름순, 그다음 점수순)을 할 때 중요합니다. 병합·삽입·버블 정렬은 안정이고, 퀵·힙·선택 정렬은 불안정합니다.

**상세 설명**

| 알고리즘 | 평균 | 최악 | 공간 | 안정 | 특징 |
|---|---|---|---|---|---|
| 버블 | O(n²) | O(n²) | O(1) | **O** | 교육용 |
| 선택 | O(n²) | O(n²) | O(1) | X | 교환 횟수 최소 |
| 삽입 | O(n²) | O(n²) | O(1) | **O** | **거의 정렬된 데이터에 매우 빠름** |
| **퀵** | O(n log n) | O(n²) | O(log n) | X | **실무 표준, 캐시 효율 최고** |
| **병합** | O(n log n) | **O(n log n)** | O(n) | **O** | 최악 보장, 안정 |
| 힙 | O(n log n) | O(n log n) | O(1) | X | 제자리 + 최악 보장 |
| 카운팅/기수 | O(n+k) | O(n+k) | O(n+k) | O | 값 범위가 좁을 때만 |

- **실무 라이브러리**: C++ `std::sort`는 **인트로 정렬**(퀵 + 힙 + 삽입 하이브리드), `std::stable_sort`는 병합 기반. C#의 `Array.Sort`도 인트로 정렬이고 **`OrderBy`(LINQ)는 안정 정렬**이다.

**꼬리질문**
- **Q.** 안정성이 실제로 필요한 예는?
  **A.** 게임 랭킹에서 **"점수가 같으면 먼저 달성한 사람이 위"** 라는 규칙이 있을 때, 시간순으로 정렬된 목록을 점수로 안정 정렬하면 자동으로 이 규칙이 지켜진다. 불안정 정렬을 쓰면 동점자 순서가 뒤죽박죽이 된다.
- **Q.** 직접 정렬을 구현할 일이 있나?
  **A.** 드물다. 대부분 표준 라이브러리가 더 최적화되어 있다. 다만 **비교 함수(comparer)를 직접 정의**하는 일은 흔하고, 특수한 상황(부분 정렬만 필요, 값 범위가 좁아 카운팅 정렬이 유리)에서는 직접 짜기도 한다.

## Q4-16. 이진 탐색을 설명하라

**30초 답변**
> **정렬된 배열**에서 중간값과 비교해 탐색 범위를 절반씩 줄여가는 알고리즘으로 **O(log n)** 입니다. 찾는 값이 중간값보다 작으면 왼쪽 절반만, 크면 오른쪽 절반만 다시 탐색합니다. 반드시 **정렬되어 있어야** 쓸 수 있고 임의 접근이 가능한 자료구조여야 합니다.

**상세 설명**
```cpp
int BinarySearch(const int arr[], int n, int target) {
    int low = 0, high = n - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;     // (low+high)/2 는 오버플로 위험!
        if (arr[mid] == target) return mid;
        if (arr[mid] < target) low  = mid + 1;
        else                   high = mid - 1;
    }
    return -1;
}
```
- **`(low + high) / 2` 대신 `low + (high - low) / 2`** 를 쓰는 이유: `low`와 `high`가 매우 크면 더할 때 **정수 오버플로**가 난다. 유명한 면접 포인트다.
- 1,000,000개 원소에서 이진 탐색은 **약 20번** 만에 끝난다(2²⁰ ≈ 100만).

**꼬리질문**
- **Q.** 게임에서 이진 탐색을 어디에 쓰나?
  **A.** ① 정렬된 랭킹에서 내 순위 찾기, ② **확률 테이블에서 가중치 기반 무작위 뽑기**(누적 확률 배열에 이진 탐색), ③ 애니메이션 커브의 키프레임 찾기, ④ 최적값 찾기(파라메트릭 서치 — "이 값 이하로 가능한가?"를 이분 탐색).
- **Q.** `lower_bound`와 `upper_bound`는?
  **A.** `lower_bound`는 **target 이상인 첫 위치**, `upper_bound`는 **target 초과인 첫 위치**를 반환한다. 둘을 조합하면 같은 값이 몇 개인지, 어느 범위인지 O(log n)에 알 수 있다. 단순 존재 여부보다 실무에서 더 자주 쓴다.

## Q4-17. DFS와 BFS의 차이는?

**30초 답변**
> **DFS(깊이 우선 탐색)** 는 한 방향으로 갈 수 있는 데까지 파고든 뒤 막히면 되돌아오는 방식으로, **스택이나 재귀**로 구현합니다. **BFS(너비 우선 탐색)** 는 가까운 곳부터 층별로 넓게 퍼져나가는 방식으로 **큐**로 구현합니다. 가장 중요한 차이는 **가중치가 없는 그래프에서 BFS는 최단 경로를 보장하지만 DFS는 보장하지 않는다**는 점입니다.

**상세 설명**
```cpp
// DFS - 재귀
void DFS(int node, vector<vector<int>>& adj, vector<bool>& visited) {
    visited[node] = true;
    for (int next : adj[node])
        if (!visited[next]) DFS(next, adj, visited);
}

// BFS - 큐
void BFS(int start, vector<vector<int>>& adj, vector<bool>& visited) {
    queue<int> q;
    q.push(start); visited[start] = true;       // 넣을 때 방문 표시가 중요
    while (!q.empty()) {
        int cur = q.front(); q.pop();
        for (int next : adj[cur])
            if (!visited[next]) { visited[next] = true; q.push(next); }
    }
}
```
| | DFS | BFS |
|---|---|---|
| 자료구조 | 스택 / 재귀 | **큐** |
| 최단 경로 | **보장 X** | **보장 O**(무가중치) |
| 메모리 | O(높이) | O(너비) — 넓으면 많이 씀 |
| 용도 | 경로 존재 여부, 사이클 탐지, 백트래킹 | **최단 경로**, 레벨 탐색 |

- **BFS에서 큐에 넣을 때 방문 표시**를 해야 한다. 꺼낼 때 하면 같은 노드가 큐에 여러 번 들어가 비효율적이다. 자주 나오는 실수다.

**내 프로젝트 연결**
- `c_핵심정리.md` **12번** — 미로찾기에서 **스택을 직접 구현해 백트래킹**을 했다. 이게 DFS의 명시적 스택 구현이다.
- `unity_핵심정리.md` **18번** — A* 길찾기(BFS/다익스트라의 확장형).

**꼬리질문**
- **Q.** 게임에서 각각 어디에 쓰나?
  **A.** **BFS**는 "가장 가까운 적/아이템 찾기", 무가중치 그리드 최단 경로, 영역 채우기(flood fill — 같은 색 블록 찾기)에 쓴다. **DFS**는 미로 생성, 연결 요소 판별, 퍼즐 완전 탐색(백트래킹), 사이클 탐지에 쓴다.
- **Q.** 재귀 DFS의 위험은?
  **A.** 그래프가 크면 **재귀 깊이가 스택 오버플로**를 일으킨다. 명시적 스택을 써서 반복으로 바꾸면 힙 메모리를 쓰므로 훨씬 깊게 갈 수 있다. → Q4-20.

## Q4-18. 다익스트라 알고리즘이란?

**30초 답변**
> **가중치가 있는 그래프에서 한 시작점으로부터 모든 정점까지의 최단 거리**를 구하는 알고리즘입니다. 아직 확정되지 않은 정점 중 **현재까지 알려진 거리가 가장 짧은 것을 골라 확정**하고, 그 정점을 거쳐 가는 경로가 더 짧으면 갱신(완화, relaxation)하는 것을 반복합니다. 우선순위 큐를 쓰면 O((V+E) log V)입니다. **음수 가중치가 있으면 사용할 수 없습니다.**

**상세 설명**
```cpp
vector<int> Dijkstra(int start, vector<vector<pair<int,int>>>& adj, int V) {
    vector<int> dist(V, INT_MAX);
    priority_queue<pair<int,int>, vector<pair<int,int>>, greater<>> pq;  // 최소 힙
    dist[start] = 0;
    pq.push({0, start});
    while (!pq.empty()) {
        auto [d, cur] = pq.top(); pq.pop();
        if (d > dist[cur]) continue;                 // 이미 더 짧은 경로로 처리됨
        for (auto [next, w] : adj[cur]) {
            if (dist[cur] + w < dist[next]) {        // 완화(relaxation)
                dist[next] = dist[cur] + w;
                pq.push({dist[next], next});
            }
        }
    }
    return dist;
}
```
- **음수 가중치가 안 되는 이유**: "가장 짧은 것을 확정하면 더 짧아질 수 없다"는 그리디 전제가 깨지기 때문이다. 음수가 있으면 **벨만-포드** 알고리즘을 써야 한다(O(VE), 음수 사이클 탐지 가능).

**꼬리질문**
- **Q.** BFS와 다익스트라의 관계는?
  **A.** **모든 간선의 가중치가 1이면 BFS가 곧 다익스트라**다. BFS는 큐로 층별 탐색하는데, 가중치가 같으면 먼저 도달한 게 최단이기 때문이다. 가중치가 다르면 우선순위 큐가 필요해지고 그게 다익스트라다.
- **Q.** A*와 다익스트라의 차이는?
  **A.** 다익스트라는 **시작점으로부터의 실제 거리(G)만** 보고 사방으로 균등하게 퍼진다. A*는 여기에 **목표까지의 추정 거리(H, 휴리스틱)** 를 더한 F = G + H로 판단해서 **목표 방향으로 우선 탐색**하므로 훨씬 적은 노드만 방문한다. **휴리스틱이 0이면 A*는 정확히 다익스트라가 된다.** → Q4-19.

## Q4-19. A* 알고리즘을 설명하라

**30초 답변**
> 다익스트라에 **목표까지의 추정 거리(휴리스틱)** 를 더해 목표 방향으로 우선 탐색하는 길찾기 알고리즘입니다. 각 노드는 **G(시작점부터 실제 비용) + H(목표까지 추정 비용) = F** 값을 갖고, Open 리스트에서 **F가 가장 작은 노드**를 꺼내 탐색합니다. 휴리스틱이 실제 비용을 **과대평가하지 않으면 최단 경로를 보장**하며, 게임 길찾기의 사실상 표준입니다.

**상세 설명**
```
F = G + H
  G : 시작점 → 현재 노드까지 실제로 이동한 비용
  H : 현재 노드 → 목표까지의 추정 비용 (휴리스틱)

Open  리스트 : 탐색 후보 (우선순위 큐로 관리하는 게 최적)
Closed 리스트 : 이미 확정한 노드

반복:
  1. Open에서 F 최소인 노드를 꺼내 Closed로
  2. 목표면 종료 -> 부모 체인을 거꾸로 따라가 경로 복원(RetracePath)
  3. 이웃마다 새 G 계산, 더 좋으면 갱신하고 부모를 현재 노드로 설정
```
**휴리스틱 종류**

| 휴리스틱 | 계산 | 적합한 이동 |
|---|---|---|
| 맨해튼 거리 | `|dx| + |dy|` | 4방향(상하좌우)만 |
| **옥타일 거리** | `max + (√2-1) × min` | **8방향(대각선 포함)** |
| 유클리드 거리 | `√(dx² + dy²)` | 자유로운 각도 |

**내 프로젝트 연결 — 직접 구현했다**

**꼬리질문**
- **Q.** 휴리스틱이 최단 경로를 보장하려면?
  **A.** **허용 가능(admissible)** 해야 한다 — 실제 비용을 **절대 과대평가하지 않아야** 한다. 과대평가하면 더 짧은 경로를 건너뛸 수 있다. 반대로 과소평가가 심하면(극단적으로 H=0) 정확하지만 다익스트라처럼 느려진다. **정확성과 속도의 트레이드오프**다.
- **Q.** 왜 Open 리스트를 우선순위 큐로 관리하나?
  **A.** 매 반복마다 F 최소값을 꺼내야 하는데, 리스트를 선형 탐색하면 O(n)이고 힙을 쓰면 O(log n)이다. 노드가 수천 개인 그리드에서 차이가 크다.
  > 내 구현은 리스트 순회 방식이었고, `우선순위HeapSort` 프로젝트에서 힙을 따로 구현해봤으니 **두 개를 결합하면 개선할 수 있다**는 것도 말할 수 있다.
- **Q.** 왜 재귀가 아니라 코루틴으로 구현했나?
  **A.** 두 가지 이유다. ① 코드 주석에도 적었듯 **재귀 깊이 제한으로 강제 종료될 수 있어서**, ② **탐색 과정을 한 스텝씩 시각화**하고 싶어서다. 동기 함수로 다 계산하면 한 프레임에 끝나 과정이 안 보이는데, 코루틴으로 `yield return`을 넣으니 노드가 하나씩 탐색되는 게 화면에 보였다.
- **Q.** 실무에서는 A*를 직접 짜나?
  **A.** Unity는 **NavMesh**(내비게이션 메시)를 제공해서 대부분 그걸 쓴다. NavMesh는 이동 가능 영역을 폴리곤으로 구워두고 그 위에서 A*를 돌린다. 다만 그리드 기반 퍼즐 게임이나 커스텀 이동 규칙이 필요하면 직접 구현한다. **원리를 알아야 NavMesh가 안 될 때 대처할 수 있다.**

## Q4-20. 재귀와 반복 중 무엇을 써야 하나?

**30초 답변**
> 재귀는 **문제를 같은 형태의 작은 문제로 나눌 수 있을 때** 코드가 훨씬 간결하고 직관적입니다. 하지만 호출마다 스택 프레임이 쌓여 **깊어지면 스택 오버플로**가 나고 함수 호출 오버헤드도 있습니다. 반복은 빠르고 안전하지만 트리 순회 같은 경우 코드가 복잡해집니다. **깊이가 예측 가능하고 얕으면 재귀, 깊거나 예측 불가능하면 반복(명시적 스택)**을 씁니다.

**상세 설명**
```cpp
// 재귀 - 간결
int Fact(int n) { return n <= 1 ? 1 : n * Fact(n-1); }

// 반복 - 안전, 빠름
int FactIter(int n) { int r = 1; for (int i = 2; i <= n; i++) r *= i; return r; }
```
- **꼬리 재귀 최적화(TCO)**: 재귀 호출이 함수의 마지막 동작이면 컴파일러가 반복으로 바꿀 수 있다. **다만 C#은 이를 보장하지 않고 Unity에서도 기대하면 안 된다.**
- 재귀를 반복으로 바꾸는 일반적 방법: **명시적 스택**을 만들어 직접 관리한다. 힙을 쓰므로 콜 스택보다 훨씬 깊이 갈 수 있다.

**내 프로젝트 연결**
- `c_핵심정리.md` **2번** — 함수와 재귀호출 실습.
- `c_핵심정리.md` **12번** — 미로찾기에서 **재귀 대신 배열 스택으로 백트래킹**을 구현했다.
- `unity_핵심정리.md` **18-5** — A*에서 **"재귀 함수 호출의 제한으로 프로그램이 강제 종료될 수 있다"**고 주석에 명시하고 코루틴 방식을 택했다. 이 판단 근거를 실제 코드로 보여줄 수 있다.

**꼬리질문**
- **Q.** 재귀가 느린 이유는?
  **A.** 호출마다 ① 스택 프레임 생성(매개변수, 지역 변수, 복귀 주소 저장), ② 점프, ③ 복귀 처리가 필요하다. 또 인라인 최적화가 어렵고 **캐시 지역성도 나쁘다.** 다만 요즘 컴파일러는 단순 재귀를 잘 최적화해서 차이가 크지 않은 경우도 많다.
- **Q.** 피보나치를 재귀로 짜면 왜 느린가?
  **A.** 단순 재귀는 같은 값을 **지수적으로 중복 계산**해서 O(2ⁿ)이다. `Fib(5)`가 `Fib(3)`을 두 번 계산하는 식이다. **메모이제이션**으로 결과를 캐싱하면 O(n)이 된다 → Q4-21.

## Q4-21. 동적 계획법(DP)이란?

**30초 답변**
> **큰 문제를 작은 부분 문제로 나누되, 부분 문제의 답을 저장해두고 재사용**해서 중복 계산을 없애는 기법입니다. 적용하려면 ① 큰 문제를 작은 문제로 나눌 수 있고(최적 부분 구조), ② 같은 부분 문제가 반복해서 나와야(중복 부분 문제) 합니다. 위에서 아래로 재귀하며 캐싱하는 **메모이제이션**과 아래에서 위로 표를 채우는 **타뷸레이션** 두 방식이 있습니다.

**상세 설명**
```cpp
// 메모이제이션 (Top-Down) - 재귀 + 캐시
int memo[100] = {0};
int Fib(int n) {
    if (n <= 1) return n;
    if (memo[n]) return memo[n];            // 이미 계산했으면 재사용
    return memo[n] = Fib(n-1) + Fib(n-2);
}

// 타뷸레이션 (Bottom-Up) - 반복 + 표
int FibDP(int n) {
    int dp[100]; dp[0] = 0; dp[1] = 1;
    for (int i = 2; i <= n; i++) dp[i] = dp[i-1] + dp[i-2];
    return dp[n];
}
```
| | 메모이제이션 | 타뷸레이션 |
|---|---|---|
| 방향 | Top-Down(재귀) | Bottom-Up(반복) |
| 계산 범위 | 필요한 것만 | 전부 |
| 스택 | 재귀 깊이 위험 | 안전 |
| 구현 난이도 | 직관적 | 순서 설계 필요 |

- **분할 정복과의 차이**: 분할 정복(퀵/병합 정렬)은 부분 문제가 **겹치지 않지만**, DP는 **겹친다.** 그래서 저장이 의미가 있다.

**꼬리질문**
- **Q.** 게임에서 DP를 쓰는 예는?
  **A.** ① **최적 아이템 조합**(배낭 문제 — 무게 제한 내 최대 가치), ② 스킬 트리 최적 투자, ③ 텍스트 유사도(편집 거리), ④ 격자 경로 개수 계산, ⑤ 경제 시뮬레이션의 최적 전략. 실시간 게임 루프보다는 **툴이나 밸런싱 계산**에서 더 많이 쓴다.
- **Q.** 그리디와 DP의 차이는?
  **A.** 그리디는 **매 순간 가장 좋아 보이는 선택**을 하고 되돌아보지 않아 빠르지만 항상 최적을 보장하지 않는다. DP는 모든 부분 문제의 답을 고려해 **최적을 보장**하지만 느리고 메모리를 더 쓴다. 다익스트라는 그리디, 벨만-포드는 DP 계열이다.

## Q4-22. 문자열에서 부분 문자열을 찾는 방법은? `★★`

> 실제 면접에서 **`substring`을 활용한 코딩 테스트가 15분 제한으로 출제**되었다. TDD 방식으로 풀라는 조건도 있었다.

**30초 답변**
> 가장 단순한 방법은 **모든 위치에서 한 글자씩 비교하는 브루트 포스**로 O(n×m)입니다. 이를 개선한 것이 **KMP 알고리즘**으로, 실패했을 때 이미 비교한 정보를 활용해 되돌아가는 양을 줄여 **O(n+m)** 에 해결합니다. 실무에서는 언어가 제공하는 `IndexOf`/`Contains`/`find`를 쓰지만, 원리를 알면 성능 특성을 판단할 수 있습니다.

**상세 설명**
```csharp
// C# 기본 API
str.Substring(startIndex, length);
str.IndexOf("target");          // 없으면 -1
str.Contains("target");
str.StartsWith / EndsWith / Split / Replace / Trim
```
```cpp
// 브루트 포스 - O(n*m)
int Find(const string& text, const string& pattern) {
    int n = text.size(), m = pattern.size();
    for (int i = 0; i <= n - m; i++) {
        int j = 0;
        while (j < m && text[i+j] == pattern[j]) j++;
        if (j == m) return i;
    }
    return -1;
}
```
**KMP의 핵심 아이디어**: 패턴 자체에서 "접두사이면서 접미사인 최대 길이"를 미리 계산해두면(실패 함수), 불일치가 났을 때 처음부터 다시 시작하지 않고 **건너뛸 수 있다.**

**코딩 테스트 대비 — 자주 나오는 문자열 문제 유형**
1. 부분 문자열 찾기 / 개수 세기

## Q4-23. 쿼드트리와 옥트리란?

**30초 답변**
> **공간을 재귀적으로 분할해 저장하는 트리**입니다. 쿼드트리는 2D 공간을 4개 사분면으로, 옥트리는 3D 공간을 8개 팔분공간으로 나눕니다. 오브젝트가 일정 개수를 넘으면 다시 쪼개서, "이 영역 근처에 뭐가 있나"를 **전체를 다 보지 않고 O(log n)에 가깝게** 찾을 수 있게 합니다. 충돌 검사, 컬링, 근접 탐색 최적화에 씁니다.

**상세 설명**
```
쿼드트리 (2D)                  옥트리 (3D)
┌─────┬─────┐                  같은 원리로 8개로 분할
│     │  ┌┬┐│   오브젝트가 많은  루트 → 8자식 → 각각 8자식 …
│     │  ├┼┤│   영역만 더 잘게
├─────┼──┴┴┘│   재귀 분할
│     │     │
└─────┴─────┘
```
- **왜 필요한가**: n개 오브젝트가 서로 충돌하는지 전부 검사하면 **O(n²)** 이다. 1,000개면 50만 번이다. 공간 분할로 **가까운 것끼리만** 검사하면 사실상 O(n log n) 이하로 떨어진다.
- **비슷한 기법**: 균등 그리드(단순, 오브젝트 분포가 고르면 최고), BSP 트리, **BVH(Bounding Volume Hierarchy — 레이트레이싱/물리 엔진 표준)**.

**내 프로젝트 연결**
- `unity_핵심정리.md` **19-1** — 배열 기반 완전이진트리 구현 경험이 트리 구조 이해의 기반이 된다.
- `unity_핵심정리.md` **18번** — 그리드 기반 A*는 균등 그리드 공간 분할의 일종이다.

**꼬리질문**
- **Q.** Unity에서 직접 구현할 일이 있나?
  **A.** 물리 엔진(PhysX)과 렌더링 컬링은 Unity가 내부적으로 이미 공간 분할을 쓰고 있어서 직접 만들 일은 드물다. 다만 ① **대량의 커스텀 오브젝트 근접 탐색**(수천 마리 유닛의 시야 판정), ② 프로시저럴 지형 관리, ③ 커스텀 컬링 시스템에서는 직접 구현한다.
- **Q.** 동적 오브젝트가 많으면 어떤 문제가 생기나?
  **A.** 오브젝트가 움직일 때마다 트리에서 빼고 다시 넣어야 해서 **갱신 비용**이 든다. 그래서 정적 오브젝트는 트리에, 동적 오브젝트는 균등 그리드나 별도 구조로 관리하는 **하이브리드 방식**을 쓰기도 한다.

## Q4-24. 게임에서 충돌 검사를 어떻게 최적화하나?

**30초 답변**
> 핵심은 **모든 쌍을 검사하는 O(n²)를 피하는 것**입니다. 먼저 **브로드 페이즈**에서 공간 분할이나 AABB 같은 단순한 경계 검사로 "충돌 가능성이 있는 쌍"만 추려내고, 그 후보들만 **내로우 페이즈**에서 정밀 검사합니다. Unity에서는 **레이어 충돌 매트릭스로 검사 자체를 끄고**, 콜라이더를 단순한 도형으로 유지하며, Raycast에 LayerMask를 지정하는 게 실질적인 최적화입니다.

**상세 설명**

**① 브로드 페이즈 (후보 추리기)**
- 공간 분할: 균등 그리드, 쿼드트리/옥트리, BVH
- **Sweep and Prune**: 한 축으로 정렬해두고 겹치는 구간만 검사
- **AABB(축 정렬 경계 상자)** 로 먼저 대충 걸러내기 — 비교가 매우 싸다

**② 내로우 페이즈 (정밀 검사)**
- 실제 도형 간 교차 판정(SAT, GJK 등)

**③ Unity에서 실제로 할 수 있는 것**

| 방법 | 효과 |
|---|---|
| **Layer Collision Matrix** 끄기 | 검사 자체를 건너뜀 — **가장 효과적** |
| 기본 도형 콜라이더 사용 | Mesh Collider보다 훨씬 저렴 |
| Raycast에 **LayerMask** 지정 | 검사 대상 축소 |
| 정적 오브젝트를 Static으로 표시 | 정적 트리 최적화 |
| `RaycastNonAlloc` | 할당 제거 |
| **거리 비교 시 `sqrMagnitude`** | 제곱근 연산 회피 |

```csharp
// 나쁨 - 매번 제곱근 계산
if (Vector3.Distance(a, b) < range) { }
// 좋음 - 제곱 상태로 비교
if ((a - b).sqrMagnitude < range * range) { }
```

**내 프로젝트 연결**
- `unity_핵심정리.md` **2-1** — 태그/레이어 기반 탐색 + **물리 오버랩 판정**.
- `unity_핵심정리.md` **8-8** — Raycast 기반 터렛 자동조준에서 **최단거리 타겟팅** 구현.
- `unity_핵심정리.md` **3-2** — Raycast/Overlap 기반 상태 판정.

**꼬리질문**
- **Q.** `sqrMagnitude`를 쓰는 이유를 정확히 설명해보라.
  **A.** 제곱근(`sqrt`) 연산이 사칙연산보다 훨씬 비싸다. 거리를 **비교만** 할 거라면 양변을 제곱해도 대소 관계가 유지되므로 제곱근을 생략할 수 있다. 실제 거리 값이 필요할 때만 `magnitude`를 쓴다. 매 프레임 수백 번 도는 코드에서 유의미한 차이가 난다.

## Q4-25. 캐시 지역성이 자료구조 선택에 어떤 영향을 주나?

**30초 답변**
> CPU는 메모리를 **캐시 라인(보통 64바이트) 단위로 통째로 읽어오기** 때문에, 연속된 메모리를 순차 접근하면 한 번 읽어온 데이터를 여러 번 재사용해 매우 빠릅니다. 반대로 연결 리스트처럼 노드가 흩어져 있으면 매번 캐시 미스가 나서 메모리에서 새로 가져와야 하고, 이건 캐시 접근보다 **수십~수백 배 느립니다.** 그래서 이론상 복잡도가 같거나 불리해도 **배열 기반 구조가 실측에서 이기는 경우가 많습니다.**

**상세 설명**
```
CPU 레지스터  ~1 사이클
L1 캐시       ~4 사이클
L2 캐시       ~12 사이클
L3 캐시       ~40 사이클
메인 메모리   ~200+ 사이클     ← 캐시 미스의 대가
```
- **시간 지역성**: 최근에 접근한 데이터를 다시 접근할 확률이 높다.
- **공간 지역성**: 접근한 데이터 근처를 곧 접근할 확률이 높다. → **연속 배열이 유리한 이유**

**실전 적용**
1. **배열/`vector`를 기본으로** 선택한다(Q4-02).
2. **AoS vs SoA** — 객체 배열(Array of Structs) 대신 필드별 배열(Struct of Arrays)로 두면, 특정 필드만 순회할 때 캐시 효율이 훨씬 좋다. **Unity DOTS/ECS가 정확히 이 발상**이다.
3. **구조체 크기를 줄인다** — 패딩을 줄이면 한 캐시 라인에 더 많은 원소가 들어간다(`01_C_CPP.md` Q1-23).
4. 2차원 배열은 **행 우선으로 순회**한다(`for y { for x }`). 열 우선으로 돌면 캐시 미스가 폭증한다.

**내 프로젝트 연결**
- `cpp_핵심정리.md` **15번** — 구조체/클래스 메모리 정렬(Padding)과 `sizeof`. 원본 엑셀의 "최적화" 답변이 정확히 이 내용이었는데, **캐시 관점까지 연결하면 훨씬 설득력 있는 답변**이 된다.
- `unity_핵심정리.md` **22-1** — 2차원 격자를 1차원 `List`로 저장(`index = y*width + x`). 이게 **행 우선 연속 저장**이라 캐시 친화적이라는 점을 덧붙일 수 있다.

**꼬리질문**
- **Q.** 그럼 객체지향이 성능에 불리한가?
  **A.** 상황에 따라 그렇다. 객체마다 힙에 흩어져 있고 가상 함수 호출이 간접 참조를 유발하므로 **대량 순회 시 캐시 효율이 나쁘다.** 그래서 대량 처리에는 **데이터 지향 설계(DOD)** 가 유리하고, Unity가 DOTS/ECS를 만든 이유가 이것이다. 다만 유지보수성은 OOP가 낫기 때문에 **핫패스만 DOD로 빼는** 절충이 현실적이다. → `01_C_CPP.md` Q1-12.
- **Q.** 캐시 미스를 어떻게 측정하나?
  **A.** Unity Profiler로는 직접 안 보이고, **Intel VTune, AMD uProf** 같은 프로파일러나 플랫폼별 성능 카운터를 쓴다. 실무에서는 보통 "구조를 바꿔보고 실행 시간이 줄어드는지" 로 간접 확인한다.
