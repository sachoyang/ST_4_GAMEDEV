## 소재 창고 — 내가 실제로 가진 근거

면접에서 인성 질문에 답할 때 **추상적인 형용사("성실합니다", "꼼꼼합니다") 대신 이 목록에서 구체적 사례를 꺼내 쓴다.**

### A. 스스로 문제를 발견하고 기록한 경험 (가장 강력한 소재)
| 발견한 것 | 위치 |
|---|---|
| `Account`에 **가상 소멸자가 없는데** `Container`가 기반 포인터로 `delete` 함 | `cpp_핵심정리.md` 7번 |
| `mystring::operator=`에 **자기 대입 가드 없음** | `cpp_핵심정리.md` 하단 |
| 프로퍼티 **게터 안에서 값을 변경**하고 있던 코드(`get { return moveSpeed = 3.0f; }`) | `unity_핵심정리.md` 5-19 |
| 런타임 `MonoBehaviour`에서 **에디터 전용 `AssetDatabase`를 호출**하던 버그 | `unity_핵심정리.md` St3-D |
| `OnGUI`에서 **매 프레임 문자열 `Replace`로 불필요한 할당** 발생 | `unity_핵심정리.md` 7-7 |
| 이미지가 3개 언어를 지원하는데 **텍스트 CSV는 2개 언어뿐인 불일치** | `unity_핵심정리.md` 15-4 |
| 강의 자료 코드 자체의 버그(`PlayerPrefs.GetInt(...) == null`은 항상 false) | `unity_핵심정리.md` 20-6 |
| **구현했지만 실제로 호출되지 않는 코드** 3건(마샬링 함수 / 커스텀 라이팅 함수 / 실행 대기열) | 12-4, 14-4, 18-8 |

### B. 같은 문제를 여러 방식으로 다시 풀어본 경험
| 주제 | 진화 과정 | 위치 |
|---|---|---|
| **FSM** | 절차적 `if/else` → 순수 C# State 패턴 → Animator `StateMachineBehaviour` | 13-1 |
| **A\* 실행 방식** | 동기 → 수동 스텝 → 코루틴 시각화 | 18-5 |
| **저장 시스템** | `BinaryWriter` → 평문 → `JsonUtility`+암호화 | 16-1 |
| **암호화** | AES ECB → AES CBC + 매번 새 IV | 16-3, 16-4 |
| **싱글턴** | 정적 필드 → 중복 방지 → 제네릭 베이스 클래스 | 5-16 |
| **로컬라이제이션** | 싱글턴+리스트 인덱스 → 정적 클래스+CSV Dictionary | 15-1 |
| **자료구조** | 배열 스택 → 클래스 스택 → 템플릿 스택 | `cpp_핵심정리.md` 18번 |

### C. 스스로 판단하고 이유를 남긴 경험
- A*에서 **재귀 대신 코루틴을 택하고 그 이유를 주석에 명시**("재귀 함수 호출의 제한으로 프로그램이 강제 종료될 수 있다") — 18-5
- AES 키를 **하드코딩한 것이 한계임을 스스로 주석으로 인지** — 16-6
- 튜토리얼을 넘어선 직접 업그레이드: 레거시 `Animation` → Mecanim `Animator`, `speedForward` 값 튜닝 — 7-6
- 이전 버전 실수를 **스스로 발견해 고친 흔적**: `GetChild(0) != null` → `childCount > 0` (두 스크립트에 일관되게 반영) — 11번

### D. 검증하는 습관
- **강의 자료 PDF와 실제 코드를 대조**해서 "어디까지가 튜토리얼이고 어디부터 내가 고친 것인지" 판별 — 7번(TempleRun)
- 같은 이름의 스크립트가 여러 경로에 있을 때 **diff로 최종본 판별** (실제로 구버전을 대표 예제로 쓸 뻔한 것을 잡아냄) — 16번(FSM)
- **씬 파일 YAML의 `m_Script` guid와 `.meta` guid를 대조**해 컴포넌트 부착 여부 검증 — 12-6
- 패키지에 딸려온 PDF를 강의 자료로 오인하지 않기 위해 **매번 내용을 열어 확인** (8번 반복 확인)

### E. 규모 있는 정리 경험
- **22개 Unity 프로젝트 + C/C++/WinAPI/MFC**를 개념 단위로 재정리해 5개 문서로 만든 작업. 단순 나열이 아니라 **"핵심 개념 + 그 개념을 가장 잘 보여주는 대표 예제"** 로 압축하는 기준을 세우고 진행.
- 학생 코드가 없는 프로젝트는 **억지로 채우지 않고 제외 처리**(`3dTO2d`, `ModelURP`, `URPassets3D`), 중복 프로젝트는 **관계를 밝히고 통합**(`St5` → `zombieStudy`의 이전 스냅샷).

## Q8-01. 짧게 자기소개 해주세요 `★★`

**핵심 원칙**
> **30초~1분.** 살아온 이야기가 아니라 **"이 회사의 이 자리에 왜 내가 맞는가"** 를 압축한 것이어야 한다. 이력서에 다 적힌 내용을 읽지 말고, **면접관이 더 묻고 싶어지게 만드는 미끼**를 하나 심어두는 게 좋다.

**구성 뼈대 (3문장)**
```
① 나를 한 문장으로 규정 (직무 + 핵심 강점)
② 그 강점을 뒷받침하는 가장 구체적인 근거 1개
③ 이 회사에서 무엇을 하고 싶은지
```

**예시 (본인 이야기로 바꿔 쓸 것)**
> "국비 게임 클라이언트 과정을 수료하고 Unity로 22개 프로젝트를 진행한 OOO입니다.
> 저는 **동작하는 코드를 만드는 데서 멈추지 않고, 왜 그렇게 동작하는지 확인하고 기록하는 습관**이 강점입니다. 예를 들어 FSM을 절차적 분기, State 패턴, Animator `StateMachineBehaviour` 세 가지 방식으로 각각 구현해보고 어느 상황에 무엇이 맞는지 직접 비교해봤습니다.
> 이 습관을 살려 유지보수하기 좋은 클라이언트 코드를 쓰는 개발자가 되고 싶습니다."

**꼬리질문 대비**
- **Q.** 방금 말한 FSM 세 가지, 각각 어떻게 달랐나요?
  → `07_디자인패턴.md` Q7-04, `03_Unity.md` Q3-28로 답할 수 있어야 한다. **자기소개에 심은 미끼는 반드시 물린다고 생각하고 준비할 것.**

**하면 안 되는 것**
- 출생지·학창시절부터 시작하기
- "열정 있습니다", "성실합니다" 같은 검증 불가능한 형용사만 나열
- 2분 넘기기

## Q8-02. 우리 회사에 어떻게 지원하게 되었나요? `★★`

**핵심 원칙**
> **"어느 회사에 넣어도 통하는 답"이면 실패한 답이다.** 반드시 **그 회사만의 구체적인 것**을 하나 이상 언급해야 한다. 회사 홈페이지·채용공고·출시작·기술 블로그·개발자 인터뷰를 미리 찾아본 흔적이 보여야 한다.

**구성 뼈대**
```
① 이 회사/게임의 구체적으로 무엇에 끌렸는가 (제품을 직접 해본 경험이면 최고)
② 내가 가진 것 중 무엇이 이 자리와 맞는가
③ 그래서 무엇을 기여하고 싶은가
```

**준비 체크리스트 (지원 전에 반드시 확인)**
- [ ] 이 회사의 대표작을 **직접 플레이해봤는가?** (해봤다면 구체적 감상 1개 준비)
- [ ] 채용 공고의 **자격 요건과 우대 사항**에서 내가 해당하는 항목은?
- [ ] 이 회사가 쓰는 **엔진/기술 스택**은? (Unity인지 언리얼인지, 모바일인지 PC인지)
- [ ] 최근 **출시작·업데이트·기술 블로그** 내용
- [ ] 회사 규모와 팀 구조 (신입에게 무엇을 기대할지가 달라진다)

**예시 구조**
> "[회사 게임]을 직접 플레이하면서 [구체적 요소 — 예: 전투 연출의 타격감, 최적화된 로딩]가 인상 깊었습니다.
> 저는 [내 경험 — 예: 오브젝트 풀링과 GC 최적화를 직접 구현하며 프레임 안정성을 다뤄본 경험]이 있어서, 이 부분에 기여할 수 있다고 생각했습니다."

**꼬리질문 대비**
- **Q.** 우리 게임 해봤나요? 어디가 좋았나요? → **반드시 해보고 갈 것.** 안 해봤으면서 해본 척하는 게 최악이다.
- **Q.** 다른 회사도 지원했나요? → 솔직하게 답하되 **"이 회사가 왜 특별한지"** 를 덧붙인다.

## Q8-03. 왜 게임 클라이언트 개발자인가요?

**핵심 원칙**
> "게임을 좋아해서"만으로는 부족하다. 게임을 좋아하는 사람은 많고, **"만드는 쪽"을 선택한 이유**가 필요하다. 가능하면 **직접 만들어보면서 느낀 구체적인 순간**을 말한다.

**답변 방향 3가지 (본인에게 맞는 것 선택)**

**① 결과가 눈에 보이는 것에 대한 매력**
> "클라이언트는 내가 짠 코드의 결과가 화면에서 바로 보인다는 게 좋습니다. A* 길찾기를 구현할 때 처음엔 동기 함수로 짜서 경로만 나왔는데, 코루틴으로 바꿔 **탐색 과정을 한 노드씩 시각화**해보니 알고리즘이 실제로 어떻게 동작하는지 눈으로 확인할 수 있었습니다. 그때 클라이언트 작업의 재미를 느꼈습니다." (18-5, 18-6)

**② 최적화·구조 문제에 대한 흥미**
> "게임 클라이언트는 **매 프레임 16.6ms 안에 모든 걸 끝내야 한다**는 제약이 있는 게 흥미롭습니다. 오브젝트 풀링이나 GC 최적화를 다루면서, 같은 기능이어도 어떻게 구현하느냐에 따라 체감 품질이 달라진다는 걸 직접 확인했습니다." (4-2, 7-7)

**③ 사용자 경험을 직접 만드는 것**
> "조작감이나 연출 같은 건 결국 클라이언트에서 결정됩니다. 피격 연출 코루틴이나 무적시간 처리를 만들면서 몇 프레임 차이가 체감을 바꾼다는 걸 경험했습니다." (3-3, 13-7)

**꼬리질문 대비**
- **Q.** 서버는 관심 없나요?
  **A.** 관심 없다고 하면 안 되고, 무작정 좋다고 해도 이상하다. **"클라이언트를 주력으로 하되 서버 쪽 이해도 필요하다고 생각한다"**가 좋다 — 실제로 Winsock 소켓 실습(`cpp_핵심정리` 24번), Photon 멀티플레이어(8번), PHP+MySQL 서버 연동(21번)을 해본 경험이 있으므로 근거가 있다.

## Q8-04. 본인의 단점 3가지를 말해보세요 `★★`

**핵심 원칙**
> 이 질문은 **단점 자체가 아니라 ① 자기 객관화가 되는지, ② 개선하려는 노력이 있는지**를 본다.
> - **위장 장점 금지**: "너무 완벽주의라서 힘듭니다" 같은 답은 면접관이 가장 싫어한다.
> - **직무 치명상 금지**: "꼼꼼하지 못합니다", "책임감이 약합니다"는 개발자로서 자살골.
> - **3개를 요구했으니 3개를 준비하되, 각각에 "그래서 이렇게 하고 있다"를 붙인다.**

**구성 공식**
```
단점 (솔직하게) + 그로 인해 실제 겪은 일 + 지금 하고 있는 개선 노력
```

**후보 예시 (본인에게 실제 해당하는 것만 고를 것)**

**① 하나에 파고들면 시야가 좁아지는 편**
> "관심이 생긴 부분을 깊게 파고드는 편인데, 그러다 전체 일정 배분을 놓친 적이 있습니다. 셰이더를 공부할 때 필요한 것 이상으로 오래 붙들고 있었습니다. 지금은 작업 전에 **여기까지만 한다는 범위와 시간을 먼저 정해두고** 시작합니다."

**② 처음 보는 코드나 기술 앞에서 신중해지느라 속도가 느림**
> "확실히 이해가 되기 전엔 손을 잘 못 대는 편이라 초반 속도가 느립니다. 대신 이해한 뒤에는 실수가 적다는 장점도 있습니다. 지금은 **일단 동작하는 최소 버전을 먼저 만들고 이해를 채워가는 방식**을 의식적으로 연습하고 있습니다."

**③ 질문하기까지 시간이 오래 걸림**
> "혼자 해결하려다 시간을 많이 쓴 적이 있습니다. 실제로 프로젝트에서 [구체 사례]에 오래 막혔는데, 나중에 물어보니 금방 풀렸습니다. 그 뒤로는 **'30분 넘게 막히면 일단 물어본다'는 기준**을 스스로 정해두고 지키고 있습니다."

**꼬리질문 대비**
- **Q.** 그 단점 때문에 실제로 문제가 생긴 적 있나요? → **미리 구체적 사례를 하나씩 준비해둘 것.** 이 꼬리질문은 거의 반드시 나온다.
- **Q.** 개선됐다는 걸 어떻게 아나요? → "예전에는 이랬는데 최근 [프로젝트]에서는 이렇게 달라졌다"는 **변화의 근거**를 준비.

## Q8-05. 본인의 장점은 무엇인가요?

**핵심 원칙**
> 형용사가 아니라 **행동**으로 말한다. "꼼꼼합니다"가 아니라 "무엇을 어떻게 했다"를 말하면 꼼꼼함은 저절로 전달된다.

**추천 프레임 — 위 소재 창고 A·D를 활용**

**① "만든 것을 다시 검증하는 습관"**
> "저는 코드가 동작한다고 끝내지 않고 다시 확인하는 편입니다. 실제로 제 C++ 코드를 리뷰하다가 **기반 클래스에 가상 소멸자가 없는데 컨테이너가 기반 포인터로 `delete`하고 있는 것**을 발견해서 기록해뒀고, Unity 프로젝트에서는 **프로퍼티 게터 안에서 값을 변경하고 있던 코드**를 찾아냈습니다. 당장 티가 나지 않는 문제라도 짚어두는 게 나중을 위해 낫다고 생각합니다."

**② "같은 문제를 여러 방식으로 풀어보며 근거를 만드는 습관"**
> "FSM을 세 가지 방식으로, 저장 시스템을 세 단계로, 암호화를 두 세대로 각각 다시 구현해봤습니다. 덕분에 '이게 좋다더라'가 아니라 **직접 비교해본 근거로 선택 이유를 설명할 수 있습니다.**"

**③ "출처를 확인하는 습관"**
> "TempleRun 프로젝트를 정리할 때 강의 자료 PDF와 실제 코드를 대조해서, 카메라 추적 코드가 제가 짠 게 아니라 Standard Assets를 붙인 것이라는 걸 확인했습니다. **내가 한 것과 안 한 것을 정확히 구분하는 게 중요하다**고 생각합니다."

> ③은 면접에서 **"포트폴리오 중 직접 짠 부분이 어디냐"** 는 질문에 대비하는 역할도 한다. 이건 신입 면접에서 매우 자주 나오는 확인 질문이다.

## Q8-06. 프로젝트를 하며 가장 힘들었던 점은? `★★`

**핵심 원칙**
> **STAR 구조**로 답한다: Situation(상황) → Task(과제) → Action(내가 한 것) → Result(결과와 배운 것).
> 힘들었다는 사실보다 **어떻게 접근해서 풀었는지**가 평가 대상이다. "밤새웠다"는 답은 감점이다.

**쓸 수 있는 실제 소재**

**① 구버전과 신버전 코드가 뒤섞여 판별이 어려웠던 문제**
```
S: FSM 프로젝트에서 같은 이름의 스크립트가 Assets/ 루트와 Assets/Scripts/ 두 곳에 있었다.
T: 어느 쪽이 최종본인지 판단해야 했다.
A: 폴더 구조만 보고 정리된 쪽이 최신이라고 가정하지 않고 diff로 직접 대조했다.
R: 오히려 Assets/Scripts/ 쪽이 중간에 잘린 구버전이었다. 하마터면 구버전을 기준으로
   작업할 뻔했고, 이후로는 "구조가 정돈되어 보인다고 최신은 아니다"를 원칙으로 삼았다.
```
(`unity_핵심정리.md` 16번)

**② 코드만으로는 알 수 없던 것을 다른 근거로 확인한 문제**
```
S: 프로젝트에 카메라 추적 코드가 없는데 게임에서는 카메라가 따라가고 있었다.
T: 어디서 처리되는지 찾아야 했다.
A: 강의 자료 PDF를 코드와 대조하고, 씬 파일을 열어 실제 부착된 컴포넌트를 확인했다.
R: Standard Assets의 SmoothFollow를 그대로 붙인 것이었다. 이후 "코드만 보지 말고
   에디터에서 실제로 어떻게 세팅됐는지도 확인한다"는 절차를 추가했다.
```
(`unity_핵심정리.md` 7-1, 12-6)

**③ 재귀 구현이 한계에 부딪힌 문제**
```
S: A* 길찾기를 재귀로 구현했는데 그리드가 커지면 강제 종료 위험이 있었다.
T: 깊은 탐색에서도 안전하고, 과정도 확인할 수 있게 만들어야 했다.
A: 재귀 대신 코루틴으로 바꿔 한 스텝씩 실행되게 하고, 각 노드의 F/G/H 값을 화면에 표시했다.
R: 스택 오버플로 위험이 사라졌고, 탐색 과정이 보이니 디버깅도 훨씬 쉬워졌다.
   그 판단 이유를 코드 주석에 남겨뒀다.
```
(`unity_핵심정리.md` 18-5, 18-6)

**꼬리질문 대비**

- **Q.** 그때 도움을 요청했나요? → 협업 태도를 보는 질문. 혼자 다 했다고 강조하는 건 오히려 감점이다.

## Q8-07. 프로젝트 중 갈등이 있었을 텐데 어떻게 해결했나요? `★★`

**핵심 원칙**
> **"갈등이 없었습니다"는 최악의 답이다.** 협업 경험이 없거나 문제를 인식 못 한다는 뜻으로 들린다.
> 평가 포인트는 ① 상대를 탓하지 않는가, ② 문제를 사람이 아니라 **사안 중심**으로 다루는가, ③ 결과적으로 팀에 도움이 되었는가.

**구성 뼈대**
```
① 갈등 상황 (사람 문제가 아니라 "관점 차이"로 서술)
② 상대의 입장을 어떻게 이해했는가
③ 어떤 기준으로 합의했는가  ← 여기가 핵심
④ 결과와 이후 재발 방지
```

**답변 가능한 갈등 유형 (본인 경험에 맞춰 선택)**

| 유형 | 해결 프레임 |
|---|---|
| **기술 선택 의견 차이** | 말로 다투지 않고 **각자 방식으로 작은 프로토타입을 만들어 비교** → 데이터로 결정 |
| **코드 스타일/구조 충돌** | 개인 취향보다 **일관성**이 우선. 팀 컨벤션을 정하고 자동화(린터/`.editorconfig`) |
| **작업 범위·일정 인식 차이** | 서로 뭘 하고 있는지 몰라서 생기는 경우가 많음 → **가시화**(보드, 데일리 공유) |
| **Git 충돌·씬 파일 충돌** | 감정 문제가 아니라 **프로세스 문제** → 담당 영역 분리, 프리팹 분리 규칙 |
| **완성도 기준 차이** | "언제까지 무엇을 어느 수준으로"를 **먼저 합의**하지 않아서 생김 |

**예시 문장**
> "저희는 [기능]을 어떻게 구현할지 의견이 갈렸습니다. 저는 A 방식이 유지보수에 낫다고 생각했고, 팀원은 B 방식이 빠르다고 봤습니다.
> 말로는 결론이 안 날 것 같아서 **각자 작은 버전으로 만들어 실제로 비교해보자고 제안**했습니다. 해보니 일정 안에서는 B가 현실적이었고, 대신 나중에 바꾸기 쉽도록 인터페이스만 분리해두는 것으로 합의했습니다.
> 이후로는 의견이 갈리면 **먼저 판단 기준(일정인지 확장성인지)을 정하고 이야기하는 것**이 훨씬 빠르다는 걸 배웠습니다."

**꼬리질문 대비**
- **Q.** 본인이 틀렸던 적은? → **있다고 답하는 게 좋다.** 자기 오류를 인정할 수 있는지를 본다.
- **Q.** 상대가 끝까지 안 받아들이면? → "결정권자에게 판단을 요청하거나, 팀 결정에 따르고 나중에 데이터로 재논의한다"는 식으로 **조직 안에서 일할 줄 안다**는 걸 보여준다.

**하면 안 되는 것**
- 상대방을 무능하거나 비협조적으로 묘사하기 (그 순간 "이 사람도 남 탓하겠구나"로 읽힌다)
- "제가 옳았고 결국 제 말대로 했습니다"로 끝내기

## Q8-08. 가장 좋아하는 사람 유형과 싫어하는 사람 유형은? `★★`

**핵심 원칙**
> **조직 적응력과 협업 태도**를 보는 질문이다. "싫어하는 유형"을 너무 구체적·공격적으로 말하면 **"이 사람은 남을 잘 배척하겠다"**로 읽힌다.
> 요령: **좋아하는 유형은 구체적으로, 싫어하는 유형은 "행동" 중심으로 완만하게** 말하고 **"그래도 이렇게 맞춰가려 한다"** 로 마무리한다.

**좋아하는 유형 — 답변 예시**
> "**모르는 걸 모른다고 말하고 바로 물어보는 분**을 좋아합니다. 혼자 오래 붙들고 있다가 나중에 문제가 커지는 것보다 훨씬 낫다고 생각합니다.
> 그리고 **피드백을 사안 중심으로 주고받는 분**이 편합니다. 제 코드에 대한 지적을 저에 대한 지적으로 받지 않으려고 저도 노력하고 있습니다."

**싫어하는 유형 — 답변 예시 (완만하게)**
> "특정 성격을 싫어한다기보다는, **문제가 생겼을 때 공유가 늦는 상황**이 힘들었습니다. 일정이 밀리는 것 자체보다 늦게 알게 되는 게 대응할 시간을 뺏기 때문입니다.
> 다만 이건 성격 문제라기보다 **말하기 어려운 분위기 때문일 수 있다**고 생각해서, 저부터 제 진행 상황과 막힌 부분을 먼저 공유하려고 합니다."

**꼬리질문 대비**
- **Q.** 그런 사람과 같이 일하게 되면 어떻게 하시겠어요?
  **A.** 이게 진짜 묻고 싶은 질문이다. **"피하겠다"가 아니라 "이렇게 맞춰가겠다"** 로 답해야 한다. 위 예시처럼 "내가 먼저 공유하는 문화를 만들려 한다"는 식의 **능동적 대응**이 좋다.

**하면 안 되는 것**
- 특정 직군이나 집단을 지목하기 ("기획자들은…", "나이 많은 분들은…") — 즉시 탈락 사유
- "싫어하는 사람 없습니다" — 성의 없는 답으로 들린다

## Q8-09. 꿈이 뭔가요? (입사 후 포부) `★★`

**핵심 원칙**
> **회사에서의 성장 경로**로 답한다. "제 게임을 만들어 창업하겠다" 같은 답은 솔직하더라도 **"금방 나가겠구나"** 로 들린다.
> 좋은 구조: **단기(1년) → 중기(3년) → 장기**로 나누고, 각 단계가 **회사에 기여하는 방향**과 이어지게 한다.

**구성 뼈대**
```
① 단기(6개월~1년): 빨리 전력이 되기 위해 무엇을 할 것인가
② 중기(2~3년): 어떤 영역에서 신뢰받는 사람이 되고 싶은가
③ 장기: 어떤 개발자로 남고 싶은가 (기술적 방향)
```

**예시**
> "단기적으로는 **팀의 코드베이스와 작업 방식에 빨리 적응해서 맡은 기능을 안정적으로 완성하는 것**이 목표입니다. 저는 처음 보는 코드를 파악할 때 실제로 실행해보며 흐름을 따라가는 편이라, 그 방식으로 빠르게 익히겠습니다.
> 중기적으로는 **성능과 구조 쪽에서 신뢰받는 사람**이 되고 싶습니다. 지금까지 오브젝트 풀링이나 GC 최적화, 여러 API 마이그레이션을 직접 겪어봤는데, 이런 부분은 경험이 쌓일수록 팀에 도움이 된다고 생각합니다.
> 장기적으로는 **다른 사람이 이어받기 좋은 코드를 쓰는 개발자**가 되고 싶습니다. 22개 프로젝트를 정리하면서 '몇 달 전 내 코드도 남의 코드'라는 걸 확실히 느꼈습니다."

> 마지막 문장은 **실제 경험에서 나온 통찰**이라 설득력이 있다. 이런 한 줄이 흔한 포부 답변과 차이를 만든다.

**꼬리질문 대비**
- **Q.** 하고 싶은 파트가 있나요? (전투/UI/최적화/툴 등)
  **A.** 하나를 말하되 **"다만 신입이니 우선은 주어지는 일을 잘하는 게 먼저"** 라는 균형을 덧붙인다. 참고로 본인은 **에디터 툴 제작 경험이 많은 편**이라(`unity_핵심정리` 5-18~5-32, 13-4, 22번) 툴/파이프라인 쪽에 관심을 표현할 근거가 있다.

## Q8-10. 새로운 기술은 어떻게 학습하나요?

**핵심 원칙**
> 게임 업계는 기술 변화가 빠르므로 **자기주도 학습 능력**을 중요하게 본다. **추상적인 답("책 읽고 인강 봅니다") 말고 실제 절차**를 말한다.

**답변 예시 (실제 경험 기반)**
> "저는 **공식 문서로 기본 개념을 잡고, 가장 작은 예제를 직접 만들어 확인하는** 순서로 접근합니다.
> 예를 들어 셰이더를 배울 때 개념만 읽어서는 감이 안 와서, **Cube와 Quad를 씬에 두고 RenderQueue 값을 바꿔가며 그리기 순서가 실제로 어떻게 바뀌는지 직접 실험**했습니다. 그러면서 배운 내용을 스스로 정리한 파일도 만들어뒀습니다.
> 그리고 **버전에 따라 달라지는 부분은 반드시 공식 문서에서 확인**하는 편입니다. `WWW`에서 `UnityWebRequest`로, Input Manager에서 New Input System으로 바뀌는 걸 여러 번 겪으면서, 블로그 글만 믿으면 옛날 방식을 그대로 쓰게 된다는 걸 알게 됐습니다."

(`unity_핵심정리.md` 14-2, 14-6, 5-21, 10-5)

**꼬리질문 대비**
- **Q.** 최근에 관심 있게 본 기술이 있나요?
  **A.** 하나는 준비해 갈 것. 근거 있는 소재: **Unity의 CoreCLR 전환**(2026년 Unity 6.8에서 Mono 제거, 세대별 GC 도입 예정), **DOTS/ECS**, **URP·Shader Graph**, **Addressables**. → `03_Unity.md` Q3-35.
- **Q.** 모르는 문제를 만나면?
  **A.** ① 에러 메시지와 공식 문서 먼저, ② 최소 재현 코드로 문제 범위 좁히기, ③ 그래도 안 되면 **혼자 오래 붙들지 않고 물어본다**. Q8-04의 단점 개선 노력과 일관되게 답하면 좋다.

## Q8-11. 실패했던 경험이 있나요?

**핵심 원칙**
> 실패 자체보다 **인정 → 원인 분석 → 개선**의 사이클이 도는 사람인지를 본다. 포장하려 들면 오히려 나쁘다.

**쓸 수 있는 소재**
- **"만들었지만 실제로 쓰이지 않은 코드"를 세 번이나 발견한 것** — C++ DLL에 구조체 마샬링 함수를 구현했는데 Unity 쪽에서 호출하지 않았고(12-4), 셰이더에서 커스텀 라이팅 함수를 직접 만들었는데 실제로는 기본 함수가 쓰이고 있었고(14-4), A*에 실행 대기열 구조를 설계했는데 연결하지 않았다(18-8).
  → **"필요할 것 같아서 미리 만든 것들이 실제로는 연결되지 않았다. 지금은 실제로 필요한 시점에 만들자는 쪽으로 바뀌었다"** 는 YAGNI 교훈으로 정리 가능. (`07_디자인패턴.md` Q7-13)
- **강의 자료를 그대로 따라 하다가 문제를 뒤늦게 발견한 경험** — 튜토리얼 코드의 `isGround` 판정 로직에 허점이 있었는데 처음엔 그대로 썼다(7-3).
  → "레퍼런스라고 무조건 맞는 건 아니다"는 교훈. 실제로 강의 자료 코드 자체의 버그도 나중에 발견했다(20-6의 `PlayerPrefs.GetInt(...) == null`).

**답변 구조**
```
① 무엇을 실패했는가 (변명 없이)
② 왜 그랬는지 스스로 분석한 원인
③ 그래서 무엇을 바꿨는가 (구체적 행동 변화)
```

## Q8-12. 가장 자신 있는 프로젝트를 설명해보세요

**핵심 원칙**
> **기능 나열이 아니라 "내가 어떤 문제를 어떻게 풀었는가"** 로 말한다. 면접관은 게임 소개를 듣고 싶은 게 아니라 **기술적 판단 능력**을 보고 싶어 한다.

**구성 뼈대 (2분)**
```
① 어떤 프로젝트인가 (30초 — 장르, 규모, 내 역할)
② 기술적으로 가장 어려웠던 지점 하나 (30초)
③ 그걸 어떻게 해결했고 왜 그 방법을 택했는가 (60초)  ← 핵심
④ 지금 다시 만든다면 무엇을 바꿀 것인가
```

**추천 소재 3개 (면접 상황에 맞춰 선택)**

| 프로젝트 | 어필 포인트 | 위치 |
|---|---|---|
| **A\* 길찾기** | 알고리즘 이해 + 실행 방식 3단계 진화 + 시각화 | 18번 |
| **FSM** | 같은 문제를 3가지 방식으로 구현하고 비교 + 에디터 툴 제작 | 13번 |
| **zombieStudy(Photon)** | 네트워크 동기화, 권한 모델, 페일오버 — 가장 규모가 큼 | 8번 |
| 우선순위 힙 | 자료구조를 직접 구현 + 시각화 | 19번 |
| Crypt(저장/암호화) | 보안 개념 단계적 이해 + 한계 인지 | 16번 |

**④번 "다시 만든다면"에 쓸 수 있는 실제 답**
- A*: "**Open 리스트를 리스트 순회로 관리했는데 우선순위 큐(힙)로 바꾸면 O(n)에서 O(log n)으로 개선**됩니다. 마침 다른 프로젝트에서 이진 힙을 직접 구현해봤기 때문에 결합할 수 있습니다." (18번 + 19번 결합)
- Crypt: "암호화 키가 클라이언트에 하드코딩되어 있어서 결국 뚫립니다. 실제 서비스라면 **서버에서 키를 받거나 중요 데이터는 서버에서 검증**해야 합니다." (16-6)

> **④번 질문("다시 한다면?")은 신입 면접에서 거의 반드시 나온다.** 자기 코드의 한계를 아는지를 보는 질문이라, 미리 답을 준비해두면 큰 차이가 난다.

## Q8-13. 5년 뒤 본인의 모습은?

**핵심 원칙**
> Q8-09(포부)와 겹치지만, 이쪽은 **직업인으로서의 방향성**을 더 묻는다. 구체적 직급보다 **"어떤 역할을 하고 있을 것인가"** 로 답하는 게 자연스럽다.

**답변 방향**
> "5년이면 **한 영역에서 스스로 판단하고 책임질 수 있는 수준**은 되어야 한다고 생각합니다. 지금은 '이렇게 하면 되나요?'를 묻는 단계라면, 그때는 **'이 방법과 저 방법이 있고 이런 이유로 이걸 택하는 게 좋겠습니다'라고 근거를 들어 제안할 수 있는** 사람이 되고 싶습니다.
> 그리고 후배가 들어왔을 때 **제가 겪은 시행착오를 정리해서 전달할 수 있는** 사람이면 좋겠습니다. 지금도 배운 걸 정리해두는 습관이 있어서, 그게 팀에서도 쓸모 있는 형태가 되도록 하고 싶습니다."

## Q8-14. 마지막으로 질문 있으신가요?

**핵심 원칙**
> **"없습니다"는 최악이다.** 관심이 없다는 신호로 읽힌다. **최소 2~3개를 준비**하고, 면접 중 나온 이야기와 연결되면 더 좋다.
> 좋은 질문 = **내가 잘 적응하고 기여하고 싶어 한다는 게 드러나는 질문**.

**추천 질문**

**① 업무·성장 관련 (가장 좋음)**
- "신입이 입사하면 처음 어떤 업무를 맡게 되나요?"
- "입사 전에 미리 공부해두면 도움이 될 기술이나 영역이 있을까요?"
- "팀에서 신입에게 가장 기대하는 부분은 무엇인가요?"
- "제 이력에서 보완하면 좋을 부분이 있다면 조언 부탁드립니다." (피드백을 구하는 자세)

**② 팀·프로세스 관련**
- "클라이언트 팀은 몇 분 정도이고 어떻게 업무를 나누시나요?"
- "코드 리뷰나 기술 공유는 어떤 식으로 진행되나요?"
- "기획·아트 파트와는 주로 어떻게 협업하시나요?"

**③ 기술 관련 (면접 흐름에 맞을 때)**
- "현재 어떤 Unity 버전과 렌더 파이프라인을 쓰고 계신가요?"
- "성능 최적화는 주로 어떤 방식으로 관리하시나요?"

**하면 안 되는 질문**
- 연봉·복지·휴가를 **첫 질문**으로 (최종 면접이나 처우 협의 단계에서 물을 것)
- 홈페이지에 다 나와 있는 것 (안 찾아봤다는 증거)
- "제가 붙었나요?" 같은 부담스러운 질문

## Q8-15. 면접 전체에 적용되는 원칙

**① 모르는 건 모른다고 한다**
> 아는 척했다가 꼬리질문 두세 번이면 반드시 드러난다. **"그 부분은 정확히 알지 못합니다. 다만 제가 아는 [관련 개념]으로 미루어 보면 [추론]일 것 같은데 확인해보겠습니다."** 가 최선이다. 이건 실제로 `04_자료구조_알고리즘.md` Q4-06("오픈 서치")처럼 용어가 모호한 질문에서도 그대로 적용된다.

**② 모든 기술 답변에 "내 코드에서 어떻게 썼는지"를 붙인다**
> 개념 설명은 누구나 외워올 수 있다. **차이를 만드는 건 "제 프로젝트에서는 이렇게 썼고 이런 문제를 겪었습니다"** 다. 이 폴더의 01~07 파일이 전부 그 연결고리를 미리 만들어둔 것이다.

**③ 포트폴리오에서 "직접 짠 부분"을 정확히 구분해둔다**
> 신입 면접에서 매우 자주 확인한다. 서드파티 에셋이나 튜토리얼 코드를 자기가 짰다고 하면 즉시 신뢰를 잃는다.
> 본인은 이미 각 프로젝트에서 **학생 코드와 공식/서드파티 패키지를 구분해 기록해뒀으므로**(Standard Assets, Photon SDK, Vuforia, unity-chan 등) 이 질문에 정확히 답할 수 있다.

**④ 답변 길이는 30초~1분**
> 너무 짧으면 성의 없고, 2분 넘어가면 면접관이 흐름을 놓친다. **결론 먼저, 근거는 그다음.** 이 폴더의 "30초 답변" 형식이 정확히 그 훈련이다.

**⑤ 마지막까지 태도를 유지한다**
> 답을 못 한 질문이 있어도 표정이 무너지면 남은 질문까지 영향을 받는다. 못 한 건 넘기고 다음 질문에 집중한다.
