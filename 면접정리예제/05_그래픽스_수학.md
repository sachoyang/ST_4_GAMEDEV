## Q5-01. 렌더링 파이프라인을 설명하라 `★`

**30초 답변**
> 3D 모델의 정점 데이터가 화면의 픽셀이 되기까지의 처리 과정입니다. 크게 **① 정점을 로컬 좌표에서 월드 → 뷰 → 클립 좌표로 변환**하고, **② 시야 밖을 잘라내는 클리핑과 뒷면 제거(백페이스 컬링)** 를 거쳐, **③ 화면 좌표로 옮긴 뒤(뷰포트 변환)**, **④ 래스터라이즈로 삼각형을 픽셀 조각으로 쪼개고**, **⑤ 픽셀 셰이더가 각 픽셀 색을 계산**한 다음, **⑥ 깊이·스텐실·블렌딩 테스트를 거쳐 최종 버퍼에 씁니다.**

**상세 설명**
```
[정점 데이터]
    ↓ 로컬 → 월드 변환 (모델 행렬)      ← 오브젝트 배치 (이동/회전/크기)
    ↓ 월드 → 뷰 변환 (뷰 행렬)          ← 카메라 기준으로 재배치
    ↓ ★ 버텍스 셰이더 (프로그래머블)
    ↓ 뷰 → 클립 변환 (투영 행렬)        ← 원근 적용
    ↓ 클리핑                            ← 시야 볼륨 밖 잘라내기
    ↓ 원근 나눗셈 → NDC
    ↓ 백페이스 컬링                     ← 뒷면 삼각형 제거
    ↓ 뷰포트 변환                       ← 화면 픽셀 좌표로
    ↓ 래스터라이즈                      ← 삼각형 → 픽셀 조각(프래그먼트)
    ↓ ★ 프래그먼트(픽셀) 셰이더 (프로그래머블)
    ↓ 깊이 테스트 / 스텐실 테스트 / 블렌딩
[프레임 버퍼]
```
- **프로그래머블 단계**는 버텍스 셰이더와 프래그먼트 셰이더 두 곳이다(그 외 지오메트리/테셀레이션/컴퓨트 셰이더도 있음). 나머지는 고정 기능이며 설정으로만 제어한다.
- 원본 엑셀 답변에 백페이스 컬링이 클리핑 앞에 있었는데, 실제로는 **클리핑 → 원근 나눗셈 → 백페이스 컬링** 순서다(화면 공간에서 삼각형 정점의 감김 방향으로 판정하므로).

**내 프로젝트 연결**
- `unity_핵심정리.md` **14-1** — ShaderLab 3단 구조와 Tag를 학생 본인이 정리한 학습 노트(`StudyShader.Shader`)가 있다.
- `unity_핵심정리.md` **5-29** — **프로시저럴 메시 생성**(vertices/uv/normals/triangles를 코드로 직접 구성). 파이프라인 입력이 뭔지 직접 만들어본 경험이다.

**꼬리질문**
- **Q.** CPU와 GPU 중 어디가 병목이 되나?
  **A.** 상황에 따라 다르다. **드로우 콜이 많으면 CPU 병목**(명령 준비 비용), **픽셀 처리가 무거우면 GPU 병목**(복잡한 셰이더, 높은 해상도, 오버드로우). 프로파일러에서 `Gfx.WaitForPresent`가 크면 GPU 병목이고, 해상도를 낮췄을 때 FPS가 크게 오르면 GPU 바운드다. → `03_Unity.md` Q3-19.
- **Q.** 왜 삼각형으로 그리나?
  **A.** 세 점은 **항상 하나의 평면을 이루고 볼록**하다는 게 수학적으로 보장되어, 래스터라이즈와 보간 처리가 단순하고 빠르다. 사각형은 네 점이 한 평면에 없을 수 있다.

## Q5-02. 셰이더란? `★★`

**30초 답변**
> 셰이더는 **GPU에서 실행되어 화면에 그려질 내용을 계산하는 프로그램**입니다. 정점의 위치를 변환하는 **버텍스 셰이더**와 각 픽셀의 최종 색을 결정하는 **프래그먼트(픽셀) 셰이더**가 핵심입니다. 조명, 텍스처, 그림자, 특수 효과가 전부 셰이더에서 계산되고, GPU가 수천 개 코어로 **병렬 처리**하기 때문에 매우 빠릅니다.

**상세 설명**
- **왜 GPU인가**: 화면이 1920×1080이면 약 200만 픽셀이고, 각 픽셀 계산은 서로 독립적이다. GPU는 단순한 코어 수천 개로 이를 동시에 처리한다(CPU는 강력한 코어 몇 개로 순차 처리).
- **Unity의 셰이더 작성 방식**
  - **고정 함수(Fixed Function)** — 레거시, 코드 없이 설정만
  - **Surface Shader (CG)** — Built-in RP 전용. 조명 계산을 Unity가 대신 생성해줌
  - **HLSL (URP/HDRP)** — 현재 표준. 직접 다 작성
  - **Shader Graph** — 노드 기반 비주얼 에디터, 코드 없이 제작

**내 프로젝트 연결 — 셰이더만 다룬 프로젝트가 있다**
- `unity_핵심정리.md` **14-1** ShaderLab 3단 구조 + Tag, **14-2** RenderQueue로 그리기 순서 제어 실험, **14-3** 레거시 고정함수 파이프라인, **14-4** **Surface Shader(CG)로 Lambert 라이팅 직접 구현 + 노멀맵**, **14-5** **Built-in RP CG Surface Shader → URP HLSL 마이그레이션 실사례**, **14-6** C# 스크립트가 전혀 없는 순수 셰이더 실습이라는 점.
> `ShaderST` 프로젝트는 `.shader` 파일 5개(`Deep+`/`Deep-`/`Lambert_Old`/`Lambert`/`StudyShader`)로만 구성되어 있고, `StudyShader.Shader`는 **학생 본인이 ShaderLab 구조를 정리한 학습 노트**다.
- `unity_핵심정리.md` **17-1** — 2D 캐릭터 파츠 리깅 + `SpriteLibraryAsset` 스킨 교체.

**꼬리질문**
- **Q.** 14-4에서 발견한 게 있다던데?
  **A.** Lambert 라이팅을 직접 재구현한 **커스텀 라이팅 함수를 만들었는데 실제로는 사용되지 않고 있었다.** 선언만 하고 Surface Shader의 `#pragma surface ... Lambert` 쪽으로 기본 함수가 쓰이고 있던 것이다. 배운 개념과 실제 연결 사이의 간극을 보여주는 사례라 기록해뒀다(UnityDll 12-4와 같은 패턴).
- **Q.** 셰이더 최적화 방법은?
  **A.** ① **분기(`if`)를 줄인다** — GPU는 워프 단위로 실행해서 분기가 갈리면 양쪽을 다 실행하고 버린다, ② 복잡한 연산(`pow`, `sin`, 나눗셈)을 미리 계산하거나 룩업 텍스처로 대체, ③ 픽셀 셰이더보다 **버텍스 셰이더에서 계산**(정점 수 < 픽셀 수), ④ 텍스처 샘플링 횟수 줄이기, ⑤ 정밀도를 `half`/`fixed`로 낮추기(모바일에서 효과 큼).
- **Q.** 셰이더 변형(variant)이 뭔가?
  **A.** `#pragma multi_compile`이나 키워드에 따라 컴파일된 여러 버전이다. 조합이 많으면 **셰이더 컴파일 시간과 빌드 크기가 폭증**하고 런타임 첫 사용 시 렉이 생긴다. 그래서 불필요한 변형을 `shader_feature`로 줄이고, **셰이더 사전 워밍업(Shader Warmup)** 으로 미리 컴파일해두는 기법을 쓴다.

## Q5-03. 버텍스 셰이더와 프래그먼트(픽셀) 셰이더의 역할은?

**30초 답변**
> **버텍스 셰이더는 정점 하나당 한 번 실행**되어 정점의 위치를 로컬 좌표에서 클립 좌표로 변환하고, 법선·UV·색상 같은 데이터를 다음 단계로 넘깁니다. **프래그먼트 셰이더는 래스터라이즈로 만들어진 픽셀 조각마다 실행**되어 텍스처 샘플링과 조명 계산을 거쳐 최종 색을 결정합니다. 정점 수보다 픽셀 수가 훨씬 많으므로 **무거운 계산은 버텍스 셰이더로 옮기는 게 최적화의 기본**입니다.

**상세 설명**
```hlsl
struct Attributes { float4 positionOS : POSITION; float2 uv : TEXCOORD0; };
struct Varyings   { float4 positionCS : SV_POSITION; float2 uv : TEXCOORD0; };

Varyings vert(Attributes IN) {                    // 정점마다 1회
    Varyings OUT;
    OUT.positionCS = TransformObjectToHClip(IN.positionOS.xyz);
    OUT.uv = IN.uv;
    return OUT;
}
half4 frag(Varyings IN) : SV_Target {             // 픽셀마다 1회
    return SAMPLE_TEXTURE2D(_MainTex, sampler_MainTex, IN.uv);
}
```
- 두 셰이더 사이에서 데이터는 **보간(interpolation)** 된다. 삼각형 세 정점의 UV 값이 그 안쪽 픽셀들에 비율대로 섞여 전달되는 것이다.
- 실행 횟수 비교: 캐릭터 하나가 정점 5,000개인데 화면에서 100,000픽셀을 차지하면 **20배 차이**가 난다.

**꼬리질문**
- **Q.** 왜 프래그먼트라고 부르나?
  **A.** 아직 최종 픽셀이 확정되지 않았기 때문이다. 깊이 테스트에서 탈락하거나 블렌딩으로 합쳐질 수 있어서 **"픽셀 후보"** 라는 의미로 프래그먼트라 부른다. DirectX는 픽셀 셰이더, OpenGL은 프래그먼트 셰이더라고 부르는 용어 차이도 있다.
- **Q.** 지오메트리 셰이더와 컴퓨트 셰이더는?
  **A.** **지오메트리 셰이더**는 정점을 늘리거나 줄일 수 있지만(풀 생성 등) 성능이 나빠 모바일에서 잘 안 쓴다. **컴퓨트 셰이더**는 렌더링 파이프라인과 무관하게 GPU로 범용 병렬 연산을 하는 것으로, 파티클 시뮬레이션·이미지 처리·물리 계산에 쓴다.

## Q5-04. ShaderLab의 구조를 설명하라

**30초 답변**
> Unity 셰이더는 **Shader → SubShader → Pass** 세 단계 구조입니다. `Shader`는 최상위 이름과 `Properties`(인스펙터에 노출되는 값)를 담고, `SubShader`는 하드웨어 성능별 대안을 여러 개 둘 수 있으며 GPU가 지원하는 첫 번째 것을 씁니다. `Pass`는 실제 그리기 한 번을 의미하고, 이 안에 버텍스·프래그먼트 셰이더 코드가 들어갑니다.

**상세 설명**
```shaderlab
Shader "Custom/MyShader" {
    Properties {                                  // 인스펙터 노출
        _MainTex ("Texture", 2D) = "white" {}
        _Color   ("Color", Color) = (1,1,1,1)
    }
    SubShader {
        Tags { "RenderType"="Opaque" "Queue"="Geometry" }   // 렌더링 분류/순서
        ZWrite On
        Blend Off
        Cull Back

        Pass {                                    // 그리기 1회
            CGPROGRAM
            #pragma vertex vert
            #pragma fragment frag
            ...
            ENDCG
        }
    }
    FallBack "Diffuse"                            // 전부 실패 시 대체
}
```
**주요 Tag**

| Tag | 의미 |
|---|---|
| `Queue` | 그리기 순서 (Background 1000 / Geometry 2000 / AlphaTest 2450 / **Transparent 3000** / Overlay 4000) |
| `RenderType` | 셰이더 교체(Replacement)용 분류 |
| `IgnoreProjector` | 프로젝터 영향 무시 |

**내 프로젝트 연결**
- `unity_핵심정리.md` **14-1** — ShaderLab 3단 구조와 Tag를 직접 정리. 학생이 쓴 `StudyShader.Shader` 학습 노트에 Queue와 Pass 단계 설명이 남아있다.
- `unity_핵심정리.md` **14-2** — 씬에 Cube/Quad를 배치해 **RenderQueue 그리기 순서를 실제로 실험**해봤다.

**꼬리질문**
- **Q.** SubShader가 여러 개인 이유는?
  **A.** 하드웨어 성능이 다양하기 때문이다. 고사양용 SubShader를 먼저 두고 저사양용을 뒤에 두면, GPU가 지원하는 첫 번째 것이 선택된다. 전부 실패하면 `FallBack` 셰이더로 넘어간다.
- **Q.** Pass가 여러 개면?
  **A.** 같은 오브젝트를 **여러 번 그린다.** 외곽선(먼저 확대해서 뒷면만 검게 그리고, 그 위에 본체를 그림), 다중 광원 처리 등에 쓴다. 다만 Pass가 늘면 드로우 콜도 늘어난다.

## Q5-05. 좌표계 변환 과정을 설명하라

**30초 답변**
> 오브젝트의 정점은 **로컬(모델) → 월드 → 뷰(카메라) → 클립 → NDC → 스크린** 순서로 변환됩니다. 로컬은 모델 자체의 원점 기준, 월드는 씬 전체의 기준, 뷰는 카메라를 원점으로 재배치한 것, 클립은 투영 행렬을 적용해 원근을 넣은 것이고, 원근 나눗셈을 거쳐 -1~1 범위의 NDC가 된 뒤 화면 픽셀 좌표로 바뀝니다. 각 변환은 **4×4 행렬 곱셈**으로 이루어집니다.

**상세 설명**
```
로컬(Object/Model Space)
  ↓ × 모델 행렬 (이동·회전·크기)
월드(World Space)              ← 씬 전체의 절대 좌표
  ↓ × 뷰 행렬 (카메라의 역변환)
뷰(View/Camera Space)          ← 카메라가 원점, 정면이 -Z(또는 +Z)
  ↓ × 투영 행렬 (원근/직교)
클립(Clip Space)               ← 여기서 시야 밖 클리핑
  ↓ ÷ w (원근 나눗셈)
NDC (-1 ~ 1)                   ← 정규화 장치 좌표
  ↓ 뷰포트 변환
스크린 (픽셀 좌표)
```
- **MVP 행렬**: 모델(Model) × 뷰(View) × 투영(Projection)을 미리 곱해두고 정점마다 한 번만 곱하는 게 표준 최적화다.
- **원근 나눗셈**이 원근감의 핵심 — 멀리 있을수록 `w`가 커져서 나누면 화면 중앙 쪽으로 작아진다.

**Unity에서의 좌표 변환 API**
```csharp
transform.TransformPoint(localPos);          // 로컬 → 월드
transform.InverseTransformPoint(worldPos);   // 월드 → 로컬
Camera.main.WorldToScreenPoint(worldPos);    // 월드 → 스크린
Camera.main.ScreenToWorldPoint(screenPos);   // 스크린 → 월드
Camera.main.WorldToViewportPoint(worldPos);  // 월드 → 뷰포트(0~1)
```

  **A.** **원근(Perspective)** 은 멀리 있는 게 작아 보여 3D 게임에 쓴다. **직교(Orthographic)** 는 거리와 무관하게 크기가 같아 2D 게임, UI, 건축 도면, 쿼터뷰 게임에 쓴다. Unity Camera의 Projection 설정으로 바꾼다.

## Q5-06. DirectX의 좌표계를 설명하라 `★`

> 원본 엑셀에서 **답변이 비어있던 문항.**

**30초 답변**
> DirectX는 **왼손 좌표계**를 사용합니다. X가 오른쪽, Y가 위쪽, **Z가 화면 안쪽(멀어지는 방향)** 입니다. 반면 OpenGL은 **오른손 좌표계**로 Z가 화면 바깥쪽(내 쪽)을 향합니다. **Unity는 DirectX와 같은 왼손 좌표계**를 쓰고, Unreal도 왼손 좌표계지만 Z가 위쪽이라 축 할당이 또 다릅니다.

**상세 설명**

| 엔진/API | 좌표계 | 위쪽 축 | 앞쪽 축 |
|---|---|---|---|
| **DirectX** | 왼손 | +Y | +Z (화면 안쪽) |
| **Unity** | **왼손** | +Y | +Z |
| OpenGL | 오른손 | +Y | -Z |
| **Unreal** | 왼손 | **+Z** | +X |
| Maya / 3ds Max | 오른손 / Z-up | 다름 | 다름 |

**손 구분법**: 왼손 좌표계는 왼손 엄지(X), 검지(Y), 중지(Z)를 서로 직각으로 폈을 때의 방향이다. 다른 방법으로, **X에서 Y로 감았을 때 엄지가 Z를 가리키는 손**이 그 좌표계의 손이다.

- **실무에서 왜 중요한가**: 3D 모델을 Maya/Blender에서 Unity로 가져오면 **축이 안 맞아 캐릭터가 눕거나 좌우가 뒤집히는** 일이 흔하다. 임포트 설정이나 모델링 단계에서 축을 맞춰야 한다.
- **외적(Cross Product)의 방향도 좌표계에 따라 달라진다** → Q5-10.

**꼬리질문**
- **Q.** 왼손/오른손 좌표계 변환은 어떻게 하나?
  **A.** **한 축의 부호를 뒤집으면** 된다(보통 Z). 다만 축을 뒤집으면 **삼각형의 감김 방향(winding order)도 반대**가 되어 백페이스 컬링이 뒤집히므로, 인덱스 순서도 함께 바꿔야 한다. 회전도 방향이 반대가 된다.
- **Q.** Unity에서 축 방향 상수는?
  **A.** `Vector3.forward`가 `(0,0,1)`로 **+Z가 앞**, `Vector3.up`이 `(0,1,0)`, `Vector3.right`가 `(1,0,0)`이다. `transform.forward`는 오브젝트의 로컬 앞 방향(월드 기준 벡터)을 준다.

## Q5-07. 오일러 각과 쿼터니언의 차이는? `★★`

**30초 답변**
> **오일러 각**은 X, Y, Z 축 회전을 각도로 표현해서 사람이 직관적으로 이해하기 쉽지만, **짐벌 락** 문제가 있고 회전 순서에 따라 결과가 달라지며 두 회전 사이를 부드럽게 보간하기 어렵습니다. **쿼터니언**은 4개 성분(x, y, z, w)으로 회전을 표현해서 짐벌 락이 없고 보간이 자연스러우며 연산이 효율적입니다. Unity는 내부적으로 **모든 회전을 쿼터니언으로 저장**하고, 인스펙터에만 오일러 각으로 보여줍니다.

**상세 설명**

| | 오일러 각 | 쿼터니언 |
|---|---|---|
| 표현 | (x°, y°, z°) 3개 | (x, y, z, w) 4개 |
| 직관성 | **높음** | 낮음(사람이 못 읽음) |
| 짐벌 락 | **발생** | 없음 |
| 보간 | 부자연스러움 | **Slerp로 자연스러움** |
| 회전 순서 | 결과에 영향 | 무관 |
| 연산 비용 | 삼각함수 필요 | 곱셈 위주로 효율적 |

```csharp
transform.rotation = Quaternion.Euler(0, 90, 0);              // 오일러 → 쿼터니언
Vector3 e = transform.rotation.eulerAngles;                    // 쿼터니언 → 오일러

transform.rotation = Quaternion.LookRotation(targetDir);        // 특정 방향 바라보기
transform.rotation = Quaternion.Slerp(a, b, t);                 // 부드러운 회전 보간
transform.rotation = Quaternion.AngleAxis(45, Vector3.up);      // 축 기준 회전
transform.rotation *= Quaternion.Euler(0, 10, 0);               // 회전 누적은 곱셈
```

**중요한 함정들**
- `transform.eulerAngles.y += 1;` 은 **동작하지 않는다.** `eulerAngles`는 쿼터니언에서 매번 계산되는 값이라, 읽어온 값이 원래 설정한 것과 다를 수 있고(같은 회전을 나타내는 오일러 각이 여러 개), 누적하면 값이 튄다. **회전 누적은 쿼터니언 곱셈**으로 해야 한다.
- 쿼터니언끼리 **더하면 안 되고 곱해야** 회전이 합성된다. 곱셈은 순서가 중요하다(교환 법칙 성립 안 함).

**내 프로젝트 연결**
- `unity_핵심정리.md` **3-5** — 카메라 추적에서 `Mathf.Lerp`/`Clamp` 보간 실습.
- `unity_핵심정리.md` **8-8** — Raycast 기반 터렛 자동조준. 목표 방향으로 회전시키는 데 `Quaternion.LookRotation`류 처리가 들어간다.
- `unity_핵심정리.md` **9-4** — VR에서 시선 방향 기반 이동 + 멀미 방지 정지각(회전 각도 판정).

**꼬리질문**
- **Q.** 쿼터니언의 w는 뭘 의미하나?
  **A.** 축 `(x,y,z)` 기준으로 `θ`만큼 회전할 때, `w = cos(θ/2)` 이고 `(x,y,z) = 축 * sin(θ/2)` 다. 즉 **w는 회전량, xyz는 회전축 정보**를 담는다. 크기가 1인 **단위 쿼터니언**만 회전을 나타낸다.
- **Q.** 왜 각도를 절반(θ/2)으로 쓰나?
  **A.** 쿼터니언으로 벡터를 회전시킬 때 `q * v * q⁻¹` 형태로 **두 번 곱해지기** 때문이다. 절반씩 두 번 적용되어 전체 θ가 된다.
- **Q.** 실무에서 오일러 각을 아예 안 쓰나?
  **A.** 쓴다. **사람이 값을 입력하거나 읽어야 하는 곳**(인스펙터, 애니메이션 커브 편집, 기획 데이터)에서는 오일러가 직관적이라 유용하다. 다만 **계산과 저장은 쿼터니언으로** 하고 표시할 때만 변환하는 게 원칙이다.

## Q5-08. 짐벌 락이란?

**30초 답변**
> 오일러 각으로 회전할 때 **두 축이 정렬되어 회전 자유도 하나를 잃어버리는 현상**입니다. 예를 들어 Y축(피치)을 90도로 돌리면 X축과 Z축 회전이 같은 결과를 만들게 되어, 3차원이던 회전이 사실상 2차원으로 줄어듭니다. 비행기가 수직으로 상승할 때 롤과 요가 구분되지 않는 상황이 대표적이며, 쿼터니언을 쓰면 이 문제가 없습니다.

**상세 설명**
```
정상 상태                     짐벌 락 (가운데 축 90도)
축1 ─┐                        축1 ─┐
     축2 ─┐                        축2 ─┐
          축3                           축3   ← 축1과 축3이 같은 평면
                                              → 자유도 3 → 2로 감소
```
- 원인은 오일러 각이 **순차적으로 적용되는 회전**이라는 데 있다. 앞 축의 회전이 뒤 축의 방향까지 바꿔버리기 때문에, 특정 각도에서 두 축이 겹친다.
- **역사적 사례**: 아폴로 11호의 관성 항법 장치에서 실제로 짐벌 락이 문제가 되어, 우주비행사가 특정 자세를 피해야 했다.

**꼬리질문**
- **Q.** 짐벌 락을 실제로 겪으면 어떻게 보이나?
  **A.** 카메라를 위로 90도 올린 상태에서 좌우로 돌리면 **화면이 축을 중심으로 빙글 도는(롤)** 이상한 움직임이 나온다. 1인칭 카메라에서 피치를 ±89도로 `Clamp`하는 게 흔한 회피책이다.
- **Q.** 그럼 왜 아직도 오일러 각을 쓰나?
  **A.** 직관적이고 사람이 읽고 쓰기 쉽기 때문이다. 짐벌 락은 **회전을 누적해서 저장할 때** 문제가 되지, 한 번의 절대 회전을 지정할 때는 문제가 없다. 그래서 UI/데이터는 오일러, 내부 계산은 쿼터니언으로 분리한다.
- **Q.** 쿼터니언은 왜 짐벌 락이 없나?
  **A.** 쿼터니언은 축을 순차적으로 적용하지 않고 **회전축과 회전량을 한 번에 표현**하기 때문이다. 축이 겹칠 일 자체가 없다.

## Q5-09. 벡터의 내적(Dot)은 어디에 쓰나?

**30초 답변**
> 내적은 두 벡터의 **방향이 얼마나 비슷한지**를 알려주는 스칼라 값입니다. 정규화된 두 벡터의 내적은 `cos θ`와 같아서, **1이면 같은 방향, 0이면 수직, -1이면 반대 방향**입니다. 게임에서는 적이 내 앞에 있는지 뒤에 있는지 판정, 시야각 판정, 조명 계산, 벡터 투영에 씁니다.

**상세 설명**
```
A · B = |A||B| cos θ = Ax*Bx + Ay*By + Az*Bz

정규화된 경우:
  결과  1  → 같은 방향 (0°)
  결과  0  → 수직     (90°)
  결과 -1  → 반대 방향 (180°)
```
```csharp
// 1. 앞/뒤 판정
float d = Vector3.Dot(transform.forward, (target.position - transform.position).normalized);
if (d > 0) { /* 앞에 있음 */ }

// 2. 시야각(FOV) 판정 - 60도 시야면 cos(30°) ≈ 0.866
if (d > Mathf.Cos(30f * Mathf.Deg2Rad)) { /* 시야 안 */ }

// 3. 램버트 조명 - 표면 법선과 광원 방향의 내적
float NdotL = max(0, dot(normal, lightDir));
```

**내 프로젝트 연결**

**꼬리질문**
- **Q.** 왜 각도 대신 내적 값으로 비교하나?
  **A.** `Mathf.Acos`로 각도를 구하는 건 **삼각함수 연산이라 비싸다.** 비교만 할 거면 임계 각도의 `cos` 값을 미리 계산해두고 내적 결과와 직접 비교하는 게 훨씬 빠르다. `sqrMagnitude`로 제곱근을 피하는 것과 같은 발상이다.
- **Q.** 램버트 조명이 뭔가?
  **A.** 표면이 **광원을 정면으로 볼수록 밝고, 비스듬할수록 어둡다**는 확산 반사 모델이다. 표면 법선 N과 광원 방향 L의 내적으로 밝기를 계산한다. 가장 기본적인 조명 모델이라 셰이더 학습의 첫 단계다.

## Q5-10. 벡터의 외적(Cross)은 어디에 쓰나?

**30초 답변**
> 외적은 **두 벡터 모두에 수직인 새 벡터**를 만듭니다. 결과 벡터의 크기는 두 벡터가 이루는 평행사변형의 넓이이고, 방향은 좌표계의 손 법칙을 따릅니다. 게임에서는 **삼각형의 법선 벡터 계산**, 좌/우 판정, 회전축 구하기, 물체의 토크 계산에 씁니다.

**상세 설명**
```
A × B = 두 벡터에 수직인 벡터
      크기 = |A||B| sin θ (평행사변형 넓이)
      방향 = 왼손/오른손 법칙 (좌표계에 따라 다름!)

A × B ≠ B × A   (순서를 바꾸면 방향이 반대 - 교환법칙 성립 안 함)
```
```csharp
// 1. 삼각형의 법선 구하기 (프로시저럴 메시에서 필수)
Vector3 normal = Vector3.Cross(v2 - v1, v3 - v1).normalized;

// 2. 좌/우 판정
Vector3 c = Vector3.Cross(transform.forward, toTarget);
if (c.y > 0) { /* 오른쪽 */ } else { /* 왼쪽 */ }

// 3. 두 방향 사이를 회전시킬 축
Vector3 axis = Vector3.Cross(from, to);
```

**내 프로젝트 연결**
- `unity_핵심정리.md` **5-29** — **프로시저럴 메시 생성**에서 `vertices`/`uv`/`normals`/`triangles`를 코드로 직접 구성했다. 법선을 직접 계산해야 할 때 외적이 필요하다.
- `unity_핵심정리.md` **5-30** — 기즈모로 정점을 드래그해 **실시간으로 메시를 재구성**한 종합 예제.

**꼬리질문**
- **Q.** 내적과 외적의 결과 타입이 다른가?
  **A.** 다르다. **내적은 스칼라(숫자 하나)**, **외적은 벡터**다. 내적은 "얼마나 같은 방향인가", 외적은 "수직 방향은 어디인가 + 얼마나 벌어졌나"를 알려준다.
- **Q.** 좌/우 판정에 왜 `.y`를 보나?
  **A.** 지면이 XZ 평면인 게임에서 `forward × toTarget`의 결과가 Y축 방향으로 나오기 때문이다. Y가 양수면 한쪽, 음수면 반대쪽이다. 다만 **좌표계(왼손/오른손)에 따라 어느 쪽이 오른쪽인지 반대**가 되므로 실제로 테스트해서 확인해야 한다.
- **Q.** 법선이 뒤집히면 어떻게 되나?
  **A.** 조명 계산이 반대가 되어 **면이 까맣게 보이거나**, 백페이스 컬링에 걸려 아예 안 보인다. 프로시저럴 메시를 만들 때 삼각형 인덱스의 **감김 순서(winding order)** 를 일관되게 유지해야 하는 이유다.

## Q5-11. 행렬은 그래픽스에서 왜 쓰이나?

**30초 답변**
> 이동·회전·크기 조절 같은 여러 변환을 **하나의 행렬로 합쳐서 한 번의 곱셈으로 적용**할 수 있기 때문입니다. 특히 4×4 동차 좌표 행렬을 쓰면 **이동까지 행렬 곱셈으로 표현**할 수 있어서(3×3으로는 불가능), 모든 변환을 통일된 방식으로 다룰 수 있고 GPU가 병렬로 매우 빠르게 처리합니다.

**상세 설명**
```
4×4 변환 행렬 (동차 좌표)
┌                ┐
│ R R R  Tx │      R: 회전 + 크기 (3×3)
│ R R R  Ty │      T: 이동
│ R R R  Tz │
│ 0 0 0   1 │
└                ┘

여러 변환 합성:  M = T × R × S   (오른쪽부터 적용: 크기 → 회전 → 이동)
```
- **왜 4×4인가**: 3×3 행렬로는 회전·크기는 되지만 **이동(평행 이동)은 표현할 수 없다.** 차원을 하나 늘려 동차 좌표(w=1)를 쓰면 이동도 곱셈으로 처리된다.
- **합성 순서가 중요하다**: 행렬 곱셈은 교환 법칙이 성립하지 않는다. "회전 후 이동"과 "이동 후 회전"은 완전히 다른 결과다.
- `w = 1`이면 점(위치), `w = 0`이면 방향 벡터로 취급된다. 방향 벡터는 이동의 영향을 받으면 안 되기 때문이다.

**꼬리질문**
- **Q.** Unity에서 행렬을 직접 다룰 일이 있나?
  **A.** 대부분 `Transform`이 대신해주지만, ① **GPU 인스턴싱**에서 `Graphics.DrawMeshInstanced`에 변환 행렬 배열을 직접 넘길 때, ② 셰이더에서 커스텀 변환을 할 때, ③ `Matrix4x4.TRS()`로 변환을 직접 조합할 때 쓴다.
- **Q.** 역행렬은 어디에 쓰나?
  **A.** **뷰 행렬이 카메라 변환의 역행렬**이다. 카메라를 움직이는 대신 세상을 반대로 움직이는 것과 같기 때문이다. 또 월드 좌표를 로컬 좌표로 되돌릴 때도 역행렬을 쓴다(`InverseTransformPoint`).

## Q5-12. `Lerp`와 `Slerp`의 차이는?

**30초 답변**
> `Lerp`는 **선형 보간**으로 두 값 사이를 직선으로 이동하고, `Slerp`는 **구면 선형 보간**으로 구면을 따라 일정한 각속도로 이동합니다. 위치 보간에는 `Lerp`, **회전 보간에는 `Slerp`** 를 쓰는 게 원칙입니다. 회전에 `Lerp`를 쓰면 중간 지점에서 회전 속도가 불균등해지고 크기가 줄어드는 문제가 생깁니다.

**상세 설명**
```csharp
Vector3.Lerp(a, b, t);        // 직선 경로, t는 0~1
Vector3.Slerp(a, b, t);       // 구면 경로 - 방향 벡터 보간에 적합
Quaternion.Slerp(a, b, t);    // 회전 보간 - 일정한 각속도
Quaternion.Lerp(a, b, t);     // 더 빠르지만 각속도 불균등 (작은 각도면 무방)
Mathf.Lerp(a, b, t);          // 스칼라
```
```
Lerp:  A ────────── B   (직선, 중간에서 원점에 가까워짐)
Slerp: A ⌒⌒⌒⌒⌒⌒ B    (호를 따라, 크기 유지)
```
- **`t`를 `Time.deltaTime`으로 주는 흔한 패턴**: `transform.position = Vector3.Lerp(cur, target, speed * Time.deltaTime);` — 이건 매 프레임 남은 거리의 일정 비율만큼 가는 **지수 감쇠**라 엄밀히는 프레임률 독립적이지 않다. → `03_Unity.md` Q3-06.

**내 프로젝트 연결**
- `unity_핵심정리.md` **3-4** — 체력바 UI를 `Color.Lerp` + `localScale`로 표현.
- `unity_핵심정리.md` **3-5** — 카메라 추적을 `Mathf.Lerp` + `Mathf.Clamp`로 구현.
- `unity_핵심정리.md` **3-11** — **`AnimationCurve`로 커스텀 이징(Easing) 곡선** 구현. 선형 보간을 넘어선 연출 제어다.
- `unity_핵심정리.md` **9-6** — 거리 기반 애니메이터 블렌딩.

**꼬리질문**
- **Q.** 이징(easing)이 뭔가?
  **A.** 보간을 선형이 아니라 **가속·감속 곡선**으로 만드는 것이다. `EaseIn`(천천히 시작), `EaseOut`(천천히 끝), `EaseInOut` 등이 있고, 자연스러운 UI 애니메이션에 필수적이다. Unity에서는 `AnimationCurve`로 곡선을 직접 그려 쓸 수 있다(3-11에서 실습).
- **Q.** `Quaternion.Lerp`를 써도 되는 경우는?
  **A.** **각도 차이가 작을 때**다. 차이가 작으면 오차가 무시할 만하고 `Slerp`보다 빠르다. 매 프레임 조금씩 따라가는 카메라 회전 같은 경우엔 `Lerp`로도 충분한 경우가 많다.

## Q5-13. 포워드 렌더링과 디퍼드 렌더링의 차이는?

**30초 답변**
> **포워드 렌더링**은 오브젝트를 그릴 때마다 그 자리에서 조명을 계산하는 방식으로, 광원이 N개면 오브젝트마다 N번 계산해서 **광원이 많아지면 비용이 급증**합니다. **디퍼드 렌더링**은 먼저 위치·법선·색상 등을 G-buffer라는 여러 텍스처에 저장해두고, **조명은 나중에 화면 픽셀 단위로 한 번만** 계산해서 광원이 많아도 효율적입니다. 대신 디퍼드는 메모리 대역폭을 많이 쓰고 **반투명 오브젝트를 처리하지 못합니다.**

**상세 설명**

| | 포워드 | 디퍼드 |
|---|---|---|
| 조명 계산 | 오브젝트 × 광원 수 | **화면 픽셀당 1회** |
| 광원 수 많을 때 | 급격히 느려짐 | **유리** |
| 반투명 | **가능** | **불가**(포워드로 별도 처리) |
| MSAA | 지원 | 어려움 |
| 메모리 대역폭 | 적음 | **많음**(G-buffer) |
| 재질 다양성 | 자유 | 제한적 |
| 모바일 | **적합** | 부적합(대역폭 문제) |

- **모바일에서 디퍼드를 안 쓰는 이유**: 모바일 GPU는 메모리 대역폭이 병목인데 G-buffer 읽고 쓰기가 대역폭을 크게 잡아먹는다. 그래서 모바일 게임은 거의 포워드다.
- **Forward+ / Clustered**: 화면을 타일로 나눠 각 타일에 영향을 주는 광원만 계산하는 개선된 포워드 방식. URP도 Forward+ 모드를 제공한다.

**꼬리질문**
- **Q.** Unity에서는 어떻게 설정하나?
  **A.** URP는 Universal Render Pipeline Asset에서 Rendering Path를 Forward / Forward+ / Deferred로 선택한다. Built-in RP는 카메라 또는 Graphics 설정에서 지정한다. **모바일 타깃이면 Forward가 기본 선택**이다.
- **Q.** 반투명은 왜 디퍼드에서 안 되나?
  **A.** G-buffer는 픽셀마다 **가장 앞의 표면 정보 하나만** 저장한다. 반투명은 뒤에 있는 것도 보여야 하는데 그 정보가 없다. 그래서 디퍼드 파이프라인에서도 반투명 오브젝트는 별도의 포워드 패스로 그린다.

## Q5-14. 알파 블렌딩과 알파 테스트의 차이는?

**30초 답변**
> **알파 블렌딩**은 반투명 픽셀을 뒤 배경과 **비율대로 섞는** 것으로 유리·연기·UI에 쓰이며, 뒤에서 앞 순서로 정렬해서 그려야 하고 깊이 쓰기를 꺼야 합니다. **알파 테스트(컷아웃)** 는 알파 값이 기준치 미만이면 **아예 픽셀을 버리는** 방식으로 나뭇잎·철망처럼 완전 투명/불투명만 있는 경우에 씁니다. 알파 테스트는 정렬이 필요 없고 깊이 쓰기가 가능해 더 저렴합니다.

**상세 설명**

| | 알파 블렌딩 | 알파 테스트(컷아웃) |
|---|---|---|
| 처리 | 배경과 섞음 | 기준 미만은 `discard` |
| 반투명 표현 | **가능** | 불가(0 또는 1) |
| 깊이 쓰기 | 보통 끔(`ZWrite Off`) | **켬** |
| 정렬 필요 | **필요**(뒤→앞) | 불필요 |
| RenderQueue | Transparent(3000) | AlphaTest(2450) |
| 모바일 성능 | 오버드로우 부담 | **일부 GPU에서 early-Z 무효화** 주의 |

```shaderlab
// 알파 블렌딩
Tags { "Queue"="Transparent" }
ZWrite Off
Blend SrcAlpha OneMinusSrcAlpha

// 알파 테스트
Tags { "Queue"="AlphaTest" }
// 셰이더 코드에서
clip(albedo.a - _Cutoff);      // 또는 discard
```

**내 프로젝트 연결**
- `unity_핵심정리.md` **14-2** — RenderQueue로 그리기 순서를 제어하는 실습을 하면서 **`ZWrite Off`를 전제로** 실험했다. 이 질문과 직결된다.
- `unity_핵심정리.md` **2-9** — 2D에서 Sorting Layer로 렌더링 순서 제어.

**꼬리질문**
- **Q.** 반투명 오브젝트를 왜 정렬해야 하나?
  **A.** 블렌딩은 **이미 그려진 배경 위에 섞는** 연산이라, 뒤에 있는 것이 먼저 그려져 있어야 올바른 결과가 나온다. 순서가 틀리면 뒤 물체가 앞 물체 위에 그려지는 것처럼 보인다. 그래서 Unity는 반투명 오브젝트를 카메라로부터의 거리 순으로 정렬해 그린다.
- **Q.** 정렬해도 안 되는 경우는?
  **A.** **서로 교차하는 반투명 오브젝트**는 오브젝트 단위 정렬로 해결이 안 된다(한 오브젝트의 일부는 앞, 일부는 뒤). 이럴 땐 메시를 나누거나, OIT(Order-Independent Transparency) 같은 고급 기법이 필요하다.
- **Q.** 모바일에서 알파 테스트가 느릴 수 있다는 건 왜인가?
  **A.** `discard`가 있으면 GPU가 **픽셀 셰이더를 실행하기 전엔 깊이를 확정할 수 없어서** early-Z 최적화가 무효화된다. 타일 기반 모바일 GPU에서 특히 손해가 크다. 그래서 모바일에서는 알파 테스트도 남용하지 않는 게 좋다.

## Q5-15. RenderQueue로 그리기 순서를 어떻게 제어하나?

**30초 답변**
> 셰이더의 `Queue` 태그에 숫자를 지정하면 **값이 작은 것부터 먼저 그려집니다.** Background(1000), Geometry(2000), AlphaTest(2450), Transparent(3000), Overlay(4000)가 기본 구간이고, `"Queue"="Geometry+10"` 처럼 상대값으로 미세 조정할 수도 있습니다. 2500 이하는 불투명으로 앞→뒤 정렬, 2500 초과는 반투명으로 뒤→앞 정렬됩니다.

**상세 설명**

| Queue | 값 | 정렬 방향 | 용도 |
|---|---|---|---|
| Background | 1000 | — | 스카이박스 |
| **Geometry** | **2000** | 앞→뒤 | 일반 불투명 (기본값) |
| AlphaTest | 2450 | 앞→뒤 | 컷아웃 |
| **Transparent** | **3000** | **뒤→앞** | 반투명 |
| Overlay | 4000 | 뒤→앞 | 렌즈 플레어, UI |

- **불투명을 앞→뒤로 그리는 이유**: 앞의 것을 먼저 그려두면 뒤의 것은 깊이 테스트에서 탈락해 **픽셀 셰이더를 실행하지 않아도 된다**(early-Z). 오버드로우를 줄이는 최적화다.
- **반투명을 뒤→앞으로 그리는 이유**: 블렌딩이 배경 위에 섞는 연산이라 뒤가 먼저 있어야 한다(Q5-14).

**내 프로젝트 연결**
- `unity_핵심정리.md` **14-2** — **RenderQueue로 그리기 순서 제어를 직접 실험**했다. 씬에 Cube/Quad를 배치하고 `Deep+`/`Deep-` 두 셰이더로 순서가 실제로 바뀌는 걸 확인한 실습이다.
- `unity_핵심정리.md` **2-9** — 2D의 **Sorting Layer**로 렌더링 순서 제어(같은 개념의 2D 버전).

**꼬리질문**
- **Q.** 2D 게임에서는 어떻게 순서를 정하나?
  **A.** **Sorting Layer**와 **Order in Layer**로 정한다. `SpriteRenderer`가 이걸 참조하고, 같은 레이어 안에서는 Order 값이 큰 것이 위에 그려진다. Y좌표에 따라 자동 정렬하는 기법(캐릭터가 아래 있을수록 앞)도 흔히 쓴다.

  **A.** uGUI는 **하이어라키 순서**가 곧 그리기 순서다. 아래에 있을수록 나중에 그려져 위에 보인다. `transform.SetAsLastSibling()`으로 맨 앞으로 가져올 수 있다.

## Q5-16. Z버퍼란? Z파이팅은 왜 생기나?

**30초 답변**
> Z버퍼(깊이 버퍼)는 **각 픽셀에 그려진 물체의 깊이 값을 저장하는 버퍼**입니다. 새 픽셀을 그릴 때 기존 깊이와 비교해서 더 가까우면 그리고 멀면 버려서, 그리는 순서와 무관하게 앞뒤 관계가 올바르게 표현됩니다. **Z파이팅**은 두 표면의 깊이 값이 거의 같아서 **정밀도 한계로 어느 것이 앞인지 판정이 흔들려 지글거리는** 현상입니다.

**상세 설명**
```
Z파이팅의 원인
① 두 면이 거의 같은 위치에 겹쳐 있음
② 깊이 버퍼 정밀도 부족 (특히 먼 거리)
③ Near/Far 클리핑 평면 비율이 극단적임  ← 가장 흔한 원인
```
- **깊이 정밀도는 비선형**이다. 원근 투영 때문에 **가까운 곳에 정밀도가 집중되고 먼 곳은 성기다.** 그래서 Near를 0.01처럼 아주 작게 잡으면 먼 거리의 정밀도가 급격히 나빠진다.
- **해결책**
  1. **Near 평면을 최대한 크게** 잡는다(0.01 → 0.3). 가장 효과적이다.
  2. Far 평면을 필요한 만큼만 줄인다.
  3. 겹친 면을 물리적으로 살짝 띄운다.
  4. `Offset` 명령이나 RenderQueue로 순서를 명시한다.
  5. 32비트 깊이 버퍼를 쓴다.

**꼬리질문**
- **Q.** `ZWrite Off`는 언제 쓰나?
  **A.** **반투명 오브젝트**에 쓴다. 반투명은 뒤가 비쳐야 하는데 깊이를 쓰면 뒤 물체가 깊이 테스트에서 탈락해 사라진다. 그래서 반투명은 깊이를 **읽기만 하고 쓰지 않는다.**
- **Q.** early-Z가 뭔가?
  **A.** 픽셀 셰이더를 실행하기 **전에** 깊이 테스트를 먼저 해서, 어차피 가려질 픽셀은 셰이더를 아예 실행하지 않는 최적화다. 그래서 불투명 오브젝트를 앞→뒤로 정렬해 그리면 이득이 크다(Q5-15). 다만 셰이더에서 `discard`를 쓰거나 깊이를 직접 수정하면 이 최적화가 무효화된다.

## Q5-17. 백페이스 컬링이란?

**30초 답변**
> 삼각형의 **뒷면을 그리지 않고 버리는** 최적화입니다. 닫힌 3D 모델은 안쪽 면이 어차피 보이지 않으므로, 화면 공간에서 삼각형 정점의 **감김 방향(winding order)** 을 보고 뒤를 향한 면을 제거합니다. 이것만으로 처리할 삼각형이 대략 절반으로 줄어듭니다.

**상세 설명**
```shaderlab
Cull Back     // 기본값 - 뒷면 제거
Cull Front    // 앞면 제거 (외곽선 효과 등에 사용)
Cull Off      // 양면 다 그림 (나뭇잎, 천, 평면 오브젝트)
```
- **판정 방법**: 화면에 투영된 삼각형의 정점이 시계 방향인지 반시계 방향인지로 앞뒤를 구분한다. 그래서 **좌표계를 뒤집으면 감김 방향도 뒤집혀** 컬링이 반대로 동작한다(Q5-06).
- **`Cull Off`가 필요한 경우**: 나뭇잎이나 종이처럼 두께가 없는 평면 오브젝트는 양쪽에서 다 보여야 한다. 대신 비용이 두 배가 되고, 조명 계산 시 법선이 한쪽만 있어서 뒷면이 이상하게 보일 수 있다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **5-29, 5-30** — 프로시저럴 메시를 직접 만들 때 `triangles` 인덱스 순서를 잘못 넣으면 면이 안 보이는 걸 겪게 된다. 감김 순서의 실전 의미다.

**꼬리질문**
- **Q.** 모델이 안 보이는데 뒤에서는 보인다면?
  **A.** **법선이 뒤집혔거나 삼각형 감김 순서가 반대**다. 모델링 툴에서 노멀을 뒤집거나(Flip Normals), 임포트 시 축 변환 때문에 뒤집힌 경우 스케일에 음수가 들어갔는지 확인한다.

## Q5-18. 텍스처 압축 포맷을 왜 신경 써야 하나?

**30초 답변**
> 텍스처는 게임 메모리와 빌드 크기의 **대부분을 차지하기 때문**입니다. 압축하지 않은 RGBA32 텍스처는 1024×1024만 해도 4MB인데, 압축 포맷을 쓰면 1/4~1/8로 줄어듭니다. 중요한 건 **GPU가 압축된 상태 그대로 읽을 수 있는 포맷**(ASTC, ETC2, BC 계열)을 써야 한다는 점으로, PNG/JPG는 로드 시 압축이 풀려 메모리 이득이 없습니다.

**상세 설명**

| 플랫폼 | 권장 포맷 |
|---|---|
| **Android/iOS(현대)** | **ASTC** (품질/크기 조절 폭이 넓음) |
| Android(구형) | ETC2 (알파 지원), ETC1 (알파 없음) |
| iOS(구형) | PVRTC |
| PC/콘솔 | **BC(DXT)** 계열 — BC1/BC3/BC7 |

- **PNG/JPG는 저장 포맷이지 GPU 포맷이 아니다.** 로드하면 RGBA로 풀려서 메모리에 올라간다. 이 구분을 정확히 아는 게 포인트다.
- **밉맵을 켜면 메모리가 약 33% 증가**하지만 원거리 렌더링 품질과 성능이 좋아진다(Q5-19).
- Unity에서는 Texture Import Settings에서 **플랫폼별로 다른 포맷과 최대 해상도**를 지정할 수 있다.

**꼬리질문**
- **Q.** 텍스처 메모리를 줄이는 다른 방법은?
  **A.** ① **해상도를 낮춘다**(가장 효과적 — 절반으로 줄이면 메모리는 1/4), ② 알파가 필요 없으면 알파 없는 포맷 사용, ③ **텍스처 아틀라스**로 여러 개를 합쳐 드로우 콜과 낭비 공간 줄이기, ④ 노멀맵은 전용 압축 사용, ⑤ Read/Write Enabled를 끄면 CPU 쪽 사본이 안 생겨 메모리가 절반이 된다.
- **Q.** UI 텍스처는 어떻게 관리하나?
  **A.** **Sprite Atlas**로 묶어 드로우 콜을 줄이고, 압축은 품질 저하가 눈에 띄기 쉬워 신중하게 정한다. 아이콘처럼 작은 것들을 낱개로 두면 아틀라스 여백 낭비와 드로우 콜이 모두 늘어난다.

## Q5-19. 밉맵(Mipmap)이란?

**30초 답변**
> 원본 텍스처를 절반씩 줄인 **작은 버전들을 미리 만들어두고, 카메라에서 멀어질수록 작은 버전을 쓰는** 기법입니다. 멀리 있는 물체에 고해상도 텍스처를 쓰면 픽셀 하나에 텍셀 여러 개가 몰려 **지글거리는 앨리어싱**이 생기는데, 밉맵을 쓰면 이를 없애고 **텍스처 캐시 효율도 좋아져 오히려 빨라집니다.** 대신 메모리를 약 33% 더 씁니다.

**상세 설명**
```
레벨 0: 1024×1024  (원본)
레벨 1:  512×512
레벨 2:  256×256
...           총 메모리 = 원본 × 1.33
```
- **왜 33%인가**: 1 + 1/4 + 1/16 + 1/64 + ... = 4/3 ≈ 1.33
- **3D 오브젝트는 밉맵을 켠다**, **UI와 2D 스프라이트는 보통 끈다**(항상 같은 거리에서 보이므로 불필요하고 흐려지기만 한다).
- **밉맵 블리딩**: 밉맵 레벨 사이가 갑자기 바뀌면 경계가 보이므로, **삼선형 필터링(Trilinear)** 으로 두 레벨을 섞는다. **이방성 필터링(Anisotropic)** 은 비스듬히 보는 표면(바닥, 도로)의 선명도를 개선한다.

**꼬리질문**
- **Q.** 밉맵이 성능에 도움이 되는 이유는?
  **A.** 멀리 있는 물체에 작은 텍스처를 쓰면 **텍스처 캐시 적중률이 크게 올라간다.** 고해상도 텍스처를 띄엄띄엄 샘플링하면 캐시 미스가 잦은데, 밉맵은 필요한 만큼만 읽어서 메모리 대역폭을 아낀다.
- **Q.** 밉맵이 없으면 어떤 현상이 보이나?
  **A.** 멀리 있는 체크무늬 바닥이나 격자 텍스처가 **카메라가 움직일 때마다 지글거린다(shimmering).** 픽셀마다 어느 텍셀을 고르느냐가 계속 바뀌기 때문이다.

## Q5-20. 노멀 맵이란?

**30초 답변**
> 표면의 **법선 벡터 정보를 RGB 색상으로 저장한 텍스처**입니다. 실제 정점을 늘리지 않고도 조명 계산 시 법선을 픽셀 단위로 바꿔서 **울퉁불퉁한 디테일이 있는 것처럼 보이게** 합니다. 폴리곤 수를 크게 늘리지 않고 표면 디테일을 표현할 수 있어서 게임 그래픽의 핵심 기법입니다. 파란빛이 도는 이유는 대부분의 법선이 표면에서 바깥쪽(탄젠트 공간의 +Z)을 향하기 때문입니다.

**상세 설명**
- **탄젠트 공간(Tangent Space)** 노멀맵이 표준이다. 법선을 월드가 아니라 **표면 기준 상대 좌표**로 저장하므로, 오브젝트가 회전하거나 변형되어도 그대로 쓸 수 있고 여러 오브젝트가 같은 노멀맵을 공유할 수 있다.
- RGB → 법선 변환: `normal = tex2D(_BumpMap, uv).rgb * 2 - 1` (0~1 범위를 -1~1로)
- Unity에서는 텍스처 임포트 설정에서 **Texture Type을 "Normal map"** 으로 지정해야 올바른 압축과 처리가 적용된다.

**관련 맵 종류**

| 맵 | 역할 |
|---|---|
| **Normal Map** | 법선 방향 → 요철 표현 |
| Height/Parallax Map | 실제 깊이감(시차 효과) |
| **Metallic / Smoothness** | PBR 금속성·거칠기 |
| Ambient Occlusion | 틈새 그림자 |
| Emission | 자체 발광 |

**내 프로젝트 연결**
- `unity_핵심정리.md` **14-4** — **Surface Shader(CG)로 Lambert 라이팅 직접 구현 + 노멀맵**을 다뤘다. 노멀맵을 실제 셰이더 코드에서 샘플링해본 경험이 있다.

**꼬리질문**
- **Q.** 노멀맵으로 실루엣도 바뀌나?
  **A.** **바뀌지 않는다.** 조명 계산만 속이는 것이라 물체의 외곽선은 여전히 원래 폴리곤 형태다. 비스듬히 보면 평평하다는 게 티가 난다. 실루엣까지 바꾸려면 실제 지오메트리(테셀레이션, 디스플레이스먼트)나 시차 오클루전 매핑이 필요하다.
- **Q.** 노멀맵은 어떻게 만드나?
  **A.** ① **고폴리곤 모델을 만들고 저폴리곤에 베이크**(가장 일반적), ② 높이맵에서 변환, ③ 사진에서 생성, ④ Substance Painter 같은 툴에서 직접 페인팅.

## Q5-21. Built-in RP, URP, HDRP의 차이는?

**30초 답변**
> **Built-in RP**는 Unity의 오래된 기본 렌더 파이프라인으로 커스터마이징이 어렵고 사실상 레거시입니다. **URP(Universal RP)** 는 모바일부터 콘솔까지 폭넓은 플랫폼에서 성능과 품질의 균형을 맞춘 것으로 **현재 대부분의 프로젝트가 쓰는 표준**입니다. **HDRP(High Definition RP)** 는 고사양 PC/콘솔 전용으로 물리 기반 조명과 고급 그래픽 기능을 제공하지만 모바일에서는 쓸 수 없습니다.

**상세 설명**

| | Built-in | **URP** | HDRP |
|---|---|---|---|
| 타깃 | 전체(레거시) | **모바일~콘솔** | 고사양 PC/콘솔 |
| 커스터마이징 | 어려움 | **가능**(SRP) | 가능 |
| 셰이더 | CG Surface Shader | **HLSL / Shader Graph** | HLSL / Shader Graph |
| SRP Batcher | 없음 | **있음** | 있음 |
| 현재 위치 | 레거시 | **표준** | 고사양 전용 |

- **파이프라인 전환은 쉽지 않다.** 셰이더를 전부 다시 써야 하고, 포스트 프로세싱·조명 설정도 다르며, 서드파티 에셋이 해당 파이프라인을 지원하는지 확인해야 한다.

**내 프로젝트 연결**
- `unity_핵심정리.md` **14-5** — **Built-in RP의 CG Surface Shader를 URP HLSL로 마이그레이션한 실사례**를 직접 다뤘다. 같은 Lambert 셰이더를 두 파이프라인 버전으로 나란히 만들어 비교했다(`Lambert_Old.shader` vs `Lambert.shader`).
> 내가 겪은 여러 마이그레이션 사례 중에서도 이건 **스크립팅 API가 아니라 렌더 파이프라인 자체의 전환**이라 성격이 다르다는 점도 기록해뒀다.
- `unity_핵심정리.md` 12번(ModelURP), 15번(URPassets3D) — URP 환경에서 에셋을 임포트해 렌더링 테스트한 프로젝트들.

**꼬리질문**
- **Q.** 신규 프로젝트라면 뭘 고르겠나?
  **A.** **URP**다. Built-in은 사실상 유지보수 모드이고, HDRP는 모바일을 포기해야 하며 요구 사양이 높다. URP는 SRP Batcher, Shader Graph, Render Feature 같은 현대적 기능을 쓰면서 플랫폼 선택지를 열어둘 수 있다.
- **Q.** 파이프라인을 중간에 바꾸면 뭐가 문제인가?
  **A.** ① 커스텀 셰이더를 전부 다시 작성해야 하고, ② 재질이 분홍색으로 깨지며(셰이더 못 찾음), ③ 조명·포스트 프로세싱 설정이 초기화되고, ④ 서드파티 에셋이 호환되지 않을 수 있다. **프로젝트 초기에 결정해야 하는 사항**이다.

## Q5-22. 메시(Mesh)는 무엇으로 구성되나?

**30초 답변**
> 메시는 **정점(vertices) 배열과 그 정점들을 삼각형으로 묶는 인덱스(triangles) 배열**이 핵심입니다. 여기에 각 정점의 **법선(normals)** — 조명 계산용, **UV 좌표** — 텍스처 매핑용, **탄젠트** — 노멀맵용, 정점 색상 등이 정점 개수만큼 병렬 배열로 함께 저장됩니다. 코드로 직접 구성할 수도 있습니다.

**상세 설명**
```csharp
Mesh mesh = new Mesh();
mesh.vertices  = new Vector3[] {                 // 정점 위치
    new Vector3(0,0,0), new Vector3(1,0,0),
    new Vector3(0,1,0), new Vector3(1,1,0)
};
mesh.uv        = new Vector2[] {                 // 텍스처 좌표 (정점 수와 같아야 함)
    new Vector2(0,0), new Vector2(1,0),
    new Vector2(0,1), new Vector2(1,1)
};
mesh.triangles = new int[] { 0,2,1, 2,3,1 };     // 인덱스 3개 = 삼각형 1개
mesh.RecalculateNormals();                        // 법선 자동 계산
mesh.RecalculateBounds();                         // 컬링용 경계 갱신
GetComponent<MeshFilter>().mesh = mesh;
```
- **인덱스를 쓰는 이유**: 정점을 공유하면 중복 저장을 피할 수 있다. 사각형은 정점 4개 + 인덱스 6개면 되지만, 인덱스 없이는 정점 6개가 필요하다.
- **`triangles` 배열의 순서가 감김 방향을 결정**하고, 이게 백페이스 컬링과 법선 방향에 영향을 준다(Q5-17).

- `unity_핵심정리.md` **5-30** — **기즈모로 정점을 드래그해 실시간으로 메시를 재구성**하는 종합 예제. 에디터 확장과 메시 생성을 결합했다.

**꼬리질문**
- **Q.** UV가 뭔가?
  **A.** 텍스처 위의 좌표다. 0~1 범위로 정규화되어 있고, 각 정점이 텍스처의 어느 지점에 대응하는지를 지정한다. 3D 모델을 펼쳐서 2D 텍스처에 매핑하는 작업을 **UV 언래핑**이라 한다.
- **Q.** 왜 U, V라고 부르나?
  **A.** X, Y, Z가 이미 공간 좌표로 쓰이고 있어서, 텍스처 좌표에는 다른 문자인 U, V를 썼다. 3D 텍스처면 W까지 쓴다.
- **Q.** 정점 수와 삼각형 수의 관계는?
  **A.** `triangles` 배열 길이 ÷ 3 = 삼각형 개수다. 정점은 여러 삼각형이 공유할 수 있어서 정점 수와 삼각형 수는 비례하지 않는다. 다만 **UV나 법선이 끊기는 지점(하드 엣지, UV 이음새)에서는 위치가 같아도 정점을 분리**해야 해서 실제 정점 수가 늘어난다. "모델러가 말하는 정점 수와 엔진의 정점 수가 다른" 이유가 이것이다.
