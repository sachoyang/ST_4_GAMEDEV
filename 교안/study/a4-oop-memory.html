A-4 · 메모리와 언어 기반

객체지향의 메모리 모델

클래스를 하나 선언하면 메모리에 정확히 무엇이 놓이는가. 답은 "멤버를 적은 순서대로"가 아니다. 사이사이 빈틈이 끼고, 가상 함수를 하나라도 쓰면 소스에 없는 포인터가 맨 앞에 붙는다. 이 장은 그 실제 모양을 보고, 거기서 다형성·가상 소멸자·RAII가 어떻게 흘러나오는지를 따라간다.

이 장의 결론 먼저

객체의 메모리 모양을 결정하는 건 딱 두 가지다 — 정렬 규칙(A-3에서 본 그것)과 vptr이라는 숨은 포인터 하나. 이 둘만 알면 sizeof가 왜 그 값인지 전부 설명된다.

그리고 그 포인터 하나가 객체지향의 값과 비용을 동시에 만든다. 다형성이 되는 것도, 가상 소멸자가 필요한 것도, 가상 호출이 인라인되지 않는 것도, 요즘 엔진이 ECS로 가는 것도 전부 이 포인터 하나에서 출발한다.

1. 클래스는 메모리에서 어떤 모양인가

C++은 멤버를 선언한 순서대로 놓는다(접근 지정자가 같은 구간 안에서). 그런데 순서대로 놓기만 하는 게 아니라, 각 멤버가 자기 정렬 요구를 만족하는 주소에 놓이도록 사이에 빈 바이트를 끼워 넣는다. 이 빈 바이트를 패딩(padding)이라 한다.

배치 규칙 — 이 세 줄이 전부다
  1. 다음 멤버의 시작 위치를 그 멤버의 정렬 배수로 올린다. 올린 만큼이 패딩이 된다.
  2. 구조체 전체의 정렬 = 멤버들 정렬 요구의 최댓값.
  3. sizeof는 그 구조체 정렬의 배수로 올림한다. 그래서 맨 뒤에도 패딩이 붙을 수 있다.

3번이 왜 필요한지는 배열을 생각하면 바로 이해된다. 객체를 배열로 늘어놓았을 때 두 번째 원소도 정렬을 지켜야 하는데, 그러려면 한 원소의 크기 자체가 정렬의 배수여야 한다.

말로만 보면 안 와닿는다. 직접 순서를 바꿔보자.

실제로 재본 값

위 위젯의 기본 예제가 실제 컴파일러에서 어떻게 나오는지 확인해봤다.

struct Pad   { char c; int i; char d; double e; };   // sizeof = 24
struct Tight { double e; int i; char c; char d; };   // sizeof = 16

// 실제 멤버 위치 (MSVC x64, offsetof로 확인)
Pad   : c@0  i@4  d@8  e@16      → 10바이트가 패딩
Tight : e@0  i@8  c@12 d@13      →  2바이트가 패딩

(MSVC x64로 직접 컴파일해 측정. 위젯의 계산 결과와 정확히 일치한다.)

같은 멤버, 같은 개수인데 크기가 24와 16이다. 순서만 바꿨는데 3분의 2로 줄었다. 객체 10만 개면 2.4MB와 1.6MB의 차이고, 더 중요하게는 캐시에 들어가는 개수가 1.5배 차이난다.

왜 컴파일러가 알아서 재배치해주지 않는가

C++ 표준이 선언 순서를 지키라고 못박았기 때문이다. 순서를 보장해야 하는 이유가 있다 — 파일이나 네트워크로 구조체를 통째로 주고받거나, C 라이브러리·하드웨어 레지스터와 메모리 배치를 맞춰야 하는 코드가 세상에 아주 많다. 컴파일러가 마음대로 순서를 바꾸면 그런 코드가 전부 깨진다. 대신 C#은 다른 선택을 했다 — 7절에서 다룬다.

정렬(alignment)이 왜 존재하는지, CPU가 왜 그걸 요구하는지는 A-3의 4절에서 다뤘다. 이 장에서는 그 규칙을 쓰기만 한다.

2. 소스에 없는 멤버 — vptr

이제 클래스에 virtual을 하나 붙여보자. 크기가 갑자기 8바이트 늘어난다.

클래스sizeof왜
class Empty {};1멤버가 없어도 0이 아니다 — 서로 다른 객체는 주소가 달라야 하니까
class A { virtual ~A(); };8멤버가 하나도 없는데 8. 이게 vptr이다
class Base { int a; virtual void f(); };16vptr 8 + int 4 + 뒤쪽 패딩 4

(전부 MSVC x64 실측)

virtual이 하나라도 있으면 컴파일러는 객체 맨 앞에 포인터를 하나 몰래 넣는다. 이걸 vptr(virtual pointer)이라 하고, 이 포인터가 가리키는 곳이 vtable(virtual table) — 그 타입의 가상 함수 주소들이 순서대로 적힌 표다.

이 그림 하나로 설명되는 것들
  • 다형성 — 기반 클래스 포인터로 불러도 객체가 들고 있는 vptr이 자기 타입의 표를 가리키므로 올바른 함수가 불린다.
  • 가상 함수 호출 비용 — 표를 두 번 거쳐야 한다 (3절).
  • 가상 소멸자 — 소멸자도 표의 한 칸일 뿐이다. 표에 없으면 못 찾는다 (4절).
  • 객체 크기 — 가상 함수가 100개여도 객체는 8바이트만 늘어난다. 개수와 무관하다.

3. 가상 함수 호출은 얼마나 비싼가

일반 함수 호출은 컴파일 시점에 주소가 정해진다. 기계어에 "여기로 가라"가 박힌다. 가상 함수는 실행 시점에 주소를 찾아야 한다.

일반 호출가상 호출
주소 결정컴파일 시점실행 시점
하는 일바로 점프vptr 읽기 → vtable에서 함수 주소 읽기 → 그 주소로 점프
대략적 비용거의 0 (인라인되면 진짜 0)예측 성공 시 3~10 사이클, 실패 시 15~20 사이클
인라인가능불가능 — 무엇을 부를지 모르니까
진짜 비용은 사이클 수가 아니다

인라인이 막히는 것이 훨씬 크다. float GetX() { return X; } 같은 한 줄짜리 함수는 인라인되면 호출이라는 개념 자체가 사라져서 그냥 값을 읽는 명령 하나가 된다. 가상으로 만드는 순간 그게 불가능해지고, 호출 준비·복귀 비용이 함수 본체보다 커진다.

거기에 인라인이 막히면 그 뒤의 최적화도 연쇄적으로 막힌다 — 상수 전파, 루프 밖으로 빼기, 벡터화가 전부 "이 함수가 무슨 짓을 할지 모른다"는 이유로 포기된다. 그래서 "가상 함수는 느리다"가 아니라 "작은 함수를 수만 번 가상 호출하면 느리다"가 정확한 표현이다.

분기 예측이 실패하는 조건

CPU는 "다음에 어디로 점프할지"를 미리 추측해서 앞서 일을 시작해둔다. 가상 호출은 목적지가 여러 개일 수 있는 점프라 추측이 어렵다. 같은 타입만 계속 나오면 CPU가 금방 학습해서 거의 공짜가 되지만, 매 반복마다 다른 타입이 섞여 나오면 계속 틀린다.

게임 루프가 정확히 그 상황이다 — 한 리스트에 함선·적·탄이 섞여 있고 매 프레임 전부 순회한다. C-2의 8절에서 말한 "다형성의 대가"가 이것이다.

컴파일러의 반격 — 탈가상화(devirtualization)

컴파일러도 손 놓고 있지 않다. 실제 타입을 확정할 수 있으면 가상 호출을 일반 호출로 바꿔버린다. 그걸 돕는 게 final 키워드다.

class CBullet final : public CMover {     // "더 이상 상속되지 않는다"
    void Move() override;                  // → 컴파일러가 호출 대상을 확정할 수 있다
};

final은 설계 의도를 밝히는 동시에 최적화 힌트가 된다. 더 이상 상속할 계획이 없는 클래스에는 붙여두는 게 요즘 관례다.

4. 가상 소멸자 — 없으면 실제로 무슨 일이 나는가

소멸자도 vtable의 한 칸일 뿐이다. 그래서 규칙이 단순하다 — 기반 클래스 포인터로 delete할 생각이라면, 소멸자가 표에 있어야 한다.

CMover* m = new CBullet(...);
delete m;          // 소멸자가 virtual이 아니면 → CMover의 소멸자만 불린다

교과서는 여기서 "파생 클래스 소멸자가 호출되지 않아 자원이 샙니다"라고 끝낸다. 그런데 실제로는 그것보다 나쁜 일이 일어난다.

우리가 이미 본 실제 사례

C-2의 오브젝트 풀을 떠올려보자. 각 클래스가 operator delete를 재정의해서 자기 전용 풀로 메모리를 되돌리게 해뒀다. 그런데 delete가 어느 operator delete를 부를지는 소멸자가 확정한 타입을 따라간다.

소멸자가 가상이 아니면 → 기반 클래스의 operator delete가 불린다 → 탄이 탄 풀로 돌아가지 못한다. 몇 초 만에 풀이 고갈되고 탄이 안 나가기 시작한다. 누수가 아니라 게임이 멈추는 버그다. 그리고 원인이 소멸자에 있다는 걸 알아채기가 매우 어렵다.

그럼 소멸자는 항상 virtual로?

아니다. vptr 8바이트가 붙기 때문이다. 작은 값 타입(Vector3 같은 것)에 쓸데없이 가상 소멸자를 달면 크기가 두 배가 될 수도 있다. 기준은 이렇다.

이 클래스는…해야 할 것
기반 포인터로 delete될 수 있다virtual ~Base();
상속은 되지만 다형적으로 삭제되진 않는다소멸자를 protected로 (기반 포인터 삭제를 막는다)
상속할 생각이 없다final을 붙인다. 가상 소멸자는 넣지 않는다
내 실습 코드에서 이 문제를 실제로 발견한 사례가 있다 — cpp_핵심정리.md 7번 항목(Account 상속 계층을 Container<Account*>가 기반 포인터로 delete하는데 가상 소멸자가 없었다).

5. 상속의 메모리 모델 — 그리고 그 한계

단일 상속 — 기반이 앞, 파생이 뒤

파생 클래스는 기반 클래스를 통째로 앞에 품고 자기 멤버를 뒤에 붙인다. 그래서 Derived*를 Base*로 바꾸는 건 주소를 그대로 쓰면 된다 — 비용이 0이다. C-2에서 static_cast가 공짜였던 이유가 이것이다.

다중 상속과 가상 상속 — 값이 급격히 커진다

구조sizeof무슨 일이
Base { int a; virtual f(); }16vptr + int + 패딩
Derived : Base { int b; }24기반의 뒤쪽 패딩을 재활용하지 않는다 (MSVC 기준, 아래 참고)
Multi : B1, B2 { int z; }40vptr이 두 개. 기반이 둘이니 표도 둘
VD1 : virtual VBase { int a; }24가상 상속은 포인터를 또 하나 추가한다

(MSVC x64 실측. VBase 자체는 4바이트짜리 클래스다.)

주의 — 이 숫자는 컴파일러마다 다르다

Derived가 24인 것은 MSVC가 기반 클래스의 뒤쪽 패딩을 재활용하지 않기 때문이다. GCC/Clang이 쓰는 Itanium ABI는 그 패딩 자리에 파생 멤버를 넣어서 16이 나온다. 객체 레이아웃은 표준이 정한 게 아니라 ABI(플랫폼 규약)가 정한다 — 그래서 구조체를 파일에 통째로 쓰거나 네트워크로 보내는 코드는 위험하다. "이 크기가 정확히 얼마인가"는 내 환경에서 재봐야만 알 수 있다.

여기서 나오는 설계 교훈

다중 상속에서 Multi*를 B2*로 바꾸면 주소가 달라진다(두 번째 기반이 뒤쪽에 있으니까). 포인터를 정수처럼 비교하던 코드가 조용히 깨지는 지점이다. 상속이 깊고 넓어질수록 객체는 커지고, 캐스팅은 복잡해지고, 레이아웃은 예측하기 어려워진다.

"상속보다 컴포지션"이라는 조언은 흔히 유연성 이야기로만 설명되지만, 메모리 관점에서도 근거가 있다는 게 이 절의 요점이다.

상속 트리가 실제로 무너지는 지점과 컴포넌트 조합으로 넘어가는 이야기는 C-3 컴포넌트 구조와 업데이트 순서에서 다룬다.

6. RAII — 수명을 타입에 새긴다

여기까지가 "객체가 메모리에서 어떤 모양인가"였다. 이제 객체의 수명으로 넘어간다.

C++의 결정적인 특성은 객체가 범위를 벗어나는 순간 소멸자가 반드시 불린다는 것이다. 반드시, 예외가 던져지는 도중에도, 컴파일러가 보장한다. 이 보장 위에 세운 관용구가 RAII다.

RAII를 정확히 말하면

이름은 "자원 획득이 곧 초기화"지만, 실제 내용은 이렇다 — "되돌려야 하는 무언가를 객체의 수명에 묶어서, 되돌리는 일을 언어가 강제하게 만든다." 묶는 대상은 메모리일 수도, 파일 핸들일 수도, 락일 수도, 리스트 멤버십일 수도 있다.

마지막 예가 낯설다면 C-2의 6절을 보자 — 생성자가 활성 리스트에 자기를 등록하고 소멸자가 빠지게 해서, "객체가 살아있다"와 "리스트에 들어있다"를 같은 뜻으로 만든 실제 코드다.

추상화 비용이 정말 0인가 — 재본 결과

타입sizeof의미
생 포인터 int*8기준선
std::unique_ptr<int>8생 포인터와 똑같다. 안전을 공짜로 얻는다
std::shared_ptr<int>16참조 카운트 블록 포인터가 하나 더. 공짜가 아니다
std::vector<int>24시작·끝·용량 세 포인터
std::string32짧은 문자열은 힙에 안 가고 이 안에 들어간다(SSO)

(MSVC x64 실측)

unique_ptr이 8바이트라는 건 "안전하게 만들었더니 크기도 속도도 그대로"라는 뜻이다. C++이 말하는 zero-overhead abstraction의 가장 깔끔한 실물이다. 반대로 shared_ptr은 두 배다 — 공유 소유권은 공짜가 아니라는 것도 같이 기억해두면 좋다.

7. 요즘은 어떻게 하는가 — 업계 표준과 Unity

C++ 진영

  • 상속은 얕게, 인터페이스는 좁게. 깊은 상속 트리는 5절의 이유로 비용이 실재한다.
  • 더 상속할 생각 없으면 final — 의도 표현 + 탈가상화 힌트.
  • 가상 함수 대신 정적 다형성 — 템플릿, CRTP, std::variant + std::visit. 타입이 컴파일 시점에 정해지므로 vptr도 간접 호출도 없다. 대신 유연성을 잃는다.

AoS vs SoA — 이 장의 내용이 성능으로 바뀌는 지점

객체를 배열로 늘어놓는 방식(AoS, Array of Structs)은 자연스럽지만, "모든 적의 X좌표만 훑는" 코드에서는 필요 없는 멤버까지 캐시에 끌려온다. 64바이트짜리 객체에서 4바이트만 쓰면 캐시 라인의 94%가 낭비다.

반대로 X만 모은 배열, Y만 모은 배열로 쪼개면(SoA, Struct of Arrays) 캐시 라인이 전부 쓸모 있는 데이터로 채워진다. ECS가 하는 일이 결국 이것이고, Unity DOTS도 같다. 객체지향의 "관련 데이터를 한 덩어리로 묶는다"는 직관이 하드웨어 입장에서는 반대로 작동하는 대표적인 경우다.

C# / Unity에서는

① 객체 하나에 붙는 고정 비용이 있다

C#의 class는 무조건 힙에 놓이고, 앞에 객체 헤더가 붙는다 — x64에서 16바이트(타입 정보 포인터 + 동기화용 워드)다. C++의 vptr 8바이트에 해당하는 것이 여기서는 두 배이고, 가상 함수가 없어도 무조건 붙는다.

그래서 int 하나 담은 클래스도 실제로는 24바이트쯤 먹는다. 작은 객체를 수만 개 만드는 설계가 C#에서 특히 손해인 이유다.

② C#은 C++과 반대 선택을 했다

기본 레이아웃 규칙 — 자주 헷갈리는 부분
기본 레이아웃뜻
class (참조 타입)LayoutKind.Auto 런타임이 필드 순서를 마음대로 바꾼다. 패딩을 알아서 줄여준다
struct (값 타입)LayoutKind.Sequential 선언 순서를 지킨다. 즉 패딩은 내 책임 — 이 장의 1절이 그대로 적용된다

즉 C#에서도 struct를 쓸 때는 멤버 순서를 신경 써야 한다. 그리고 P/Invoke로 C++ 쪽에 구조체를 넘길 때는 [StructLayout(LayoutKind.Sequential)]을 명시해야 한다 — 양쪽 레이아웃이 어긋나면 값이 엉뚱하게 읽힌다.

③ 클래스 배열은 값이 나란히 있는 게 아니다

C#에서 Enemy[](클래스)를 만들면 배열에 나란히 놓이는 건 주소 100개다. 실제 객체는 힙 여기저기에 흩어져 있다. 순회할 때마다 포인터를 따라 점프한다.

반면 EnemyData[](struct)는 값 자체가 나란히 놓인다. 같은 코드처럼 보이는데 캐시 관점에서는 완전히 다른 물건이다. Unity의 Job System과 Burst가 struct와 Native Collections만 허용하는 이유가 이것이다 — 이 장에서 말한 원칙을 아예 언어 차원에서 강제하는 것이다.

④ 상속은 피할 수 없다 — MonoBehaviour

Unity에서 컴포넌트를 만들려면 MonoBehaviour를 상속해야 하고, 그 위로도 상속 계층이 길게 있다. 5절에서 말한 "상속 대신 컴포지션"을 클래스 수준에서는 못 하는 셈이다. 대신 Unity는 게임 오브젝트 수준에서 컴포지션을 한다 — 하나의 GameObject에 여러 컴포넌트를 조합해 붙이는 그 구조가 바로 컴포지션이다.

이 이야기 — 상속 트리 대신 컴포넌트 조합으로 가는 흐름과 MonoBehaviour 생명주기의 원리는 C-3에서 이어진다.

언제 이걸 신경 쓰지 않아도 되는가

  • 객체가 몇 개뿐일 때 — 매니저 클래스 하나에서 8바이트 아끼는 건 의미가 없다.
  • 매 프레임 순회하지 않을 때 — 캐시 이야기는 "많이, 자주 훑을 때"만 유효하다.
  • 가독성과 맞바꿔야 할 때 — 멤버 순서를 정렬 기준으로만 배치하면 논리적으로 관련 있는 것끼리 떨어져 읽기 나빠진다. 수만 개짜리 구조체가 아니면 가독성이 이긴다.
면접에서의 차이

"가상 소멸자는 왜 필요한가요"에 "파생 클래스 소멸자가 호출되지 않아서요"는 평균 답변이다. 여기에 "소멸자도 vtable의 한 칸이라서, 없으면 어느 타입인지 확정을 못 하고, 그러면 operator delete도 기반 클래스 것이 불립니다. 커스텀 할당자를 쓰는 코드에서는 메모리가 원래 풀로 돌아가지 못해서 누수가 아니라 기능이 멈추는 버그가 됩니다"까지 가면 원리를 아는 사람과 외운 사람이 갈린다.

8. 정리 — 이 장을 한 문단으로

30초로 말한다면

객체는 멤버를 선언 순서대로 놓되, 각 멤버가 정렬을 지키도록 사이에 패딩을 끼워 배치됩니다. 그래서 같은 멤버라도 순서만 바꾸면 크기가 달라지고, 실제로 24바이트가 16바이트가 되기도 합니다. 가상 함수가 하나라도 있으면 맨 앞에 vptr이라는 숨은 포인터가 붙어서 타입별 함수 표를 가리키는데, 다형성도, 가상 소멸자가 필요한 이유도, 가상 호출이 인라인 안 되는 것도 전부 여기서 나옵니다. 비용은 객체당 8바이트와 호출 시 간접 참조 두 번인데, 실제로 더 큰 손해는 인라인이 막히는 것입니다. C#은 class는 런타임이 필드를 재배치해주지만 struct는 선언 순서를 지키므로, Unity에서 Job이나 Burst를 쓸 때는 이 장의 규칙이 그대로 적용됩니다.

  • C-3 컴포넌트 구조와 업데이트 순서 — 상속 대신 조합

확인한 출처

  • 이 장의 sizeof·offsetof 수치는 전부 MSVC x64로 직접 컴파일해 측정한 값이다 — 패딩 예제(24↔16), Empty=1, vptr 유무(1→8), 단일/다중/가상 상속(16·24·40·24), unique_ptr=8 / shared_ptr=16 / vector=24 / string=32. 레이아웃은 ABI가 정하므로 컴파일러가 다르면 값도 달라진다(본문 5절 경고 참고).
  • Microsoft Learn — StructLayoutAttribute · .NET 메모리 레이아웃 정리 — C#에서 struct는 기본 Sequential, class는 기본 Auto(런타임 재배치 허용)
  • Managed object internals — object header layout — x64에서 객체 헤더 16바이트
  • 가상 호출 비용(예측 성공 3~10 사이클 / 실패 15~20 사이클)은 여러 자료에서 공통으로 제시되는 자릿수 감각이며, CPU 세대와 코드 형태에 따라 달라진다. 절대값보다 인라인이 막힌다는 사실이 중요하다.

직접 해보면 좋을 것

  1. 위 위젯에서 char, double, char, int를 만들어 크기를 보고, 「최적 순서로」를 눌러 비교한다.
