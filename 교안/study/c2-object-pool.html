C-2 · 게임 런타임 구조

오브젝트 관리와 메모리 풀

화면에 탄이 5000발 떠 있는 게임을 만든다고 하자. 탄은 계속 태어나고 계속 죽는다. 이걸 new와 delete로 그대로 옮기면 게임은 느려지는 게 아니라 불규칙하게 끊긴다. 이 장은 그 이유와, 게임이 30년째 쓰고 있는 해법인 오브젝트 풀의 원리를 다룬다.

이 장의 결론 먼저

오브젝트 풀은 "메모리를 아끼는 기법"이 아니다. 메모리 할당이라는 예측 불가능한 작업을 게임 루프 밖으로 몰아내는 기법이다. 아끼는 건 부수 효과고, 진짜 목적은 프레임 시간의 일정함이다.

그래서 풀의 핵심 질문은 "얼마나 아끼나"가 아니라 세 가지다 — ① 메모리를 언제 잡아둘 것인가 ② 빈 자리를 어떻게 O(1)에 찾을 것인가 ③ 다 찼을 때 무엇을 포기할 것인가.

1. 문제 — 매 프레임 수천 번의 new

수치로 보기

탄막 슈팅에서 동시에 살아있는 탄을 5000발로 잡고, 탄 하나의 평균 수명을 1초라고 하자. 그러면 1초에 5000번 생성 + 5000번 소멸이 일어난다. 60프레임으로 나누면 프레임당 약 167번의 new와 167번의 delete다. 적, 이펙트, 파편까지 더하면 실제로는 이보다 훨씬 많다.

167번이 많은 숫자인가? 그 자체로는 아니다. 문제는 167번이 항상 167번어치 시간이 걸리지 않는다는 것이다.

new가 실제로 하는 일

new 한 줄은 다음 세 가지를 순서대로 한다.

  1. 메모리 확보 — 힙 할당자에게 "N바이트짜리 빈 자리를 달라"고 요청한다.
  2. 생성자 호출 — 그 자리에 객체를 만든다.
  3. (실패 시 예외 처리)

비용이 튀는 건 1번이다. 힙 할당자는 자유 블록 목록을 뒤져서 요청 크기에 맞는 자리를 찾는데, 이 탐색 시간이 힙의 현재 상태에 따라 달라진다. 운이 좋으면 즉시 끝나고, 운이 나쁘면 목록을 한참 걷는다. 심지어 맞는 자리가 없으면 OS에게 페이지를 더 달라고 요청하고, 이건 시스템 콜이라 수 마이크로초 단위로 뛴다.

new/malloc이 내부에서 하는 일, 힙 단편화, 정렬(alignment)의 자세한 원리는 A-3 동적 할당의 진짜 비용에서 다룬다. 이 장에서는 결과만 쓴다.

진짜 문제는 평균이 아니라 최악값

게임은 매 프레임 16.6ms 안에 모든 일을 끝내야 한다(60fps 기준). 평균 5ms에 끝나던 프레임이 어쩌다 한 번 20ms가 걸리면, 그 한 프레임이 눈에 보이는 끊김(hitch)이 된다. 사람 눈은 평균 프레임률보다 튀는 프레임에 훨씬 민감하다.

왜 게임만 유별난가

웹 서버는 요청 하나가 10ms 늦어도 아무도 모른다. 게임은 프레임 하나가 늦으면 화면이 멈춘 것처럼 보인다. 게임은 처리량(throughput)이 아니라 지연 시간의 일정함(latency consistency)을 목표로 하는 소프트웨어다. 이 한 문장이 게임 프로그래밍의 거의 모든 "이상한" 관행을 설명한다 — 풀링, 고정 타임스텝, GC 회피, 미리 로딩, 전부 같은 이유다.

비용의 네 갈래

비용무엇이왜 게임에서 치명적인가
할당 시간자유 블록 탐색, 락, 최악의 경우 시스템 콜실행 시간이 힙 상태에 좌우돼 예측 불가
단편화크기가 다른 객체가 뒤섞여 생기는 구멍오래 켜둘수록 악화. 총 여유 메모리는 충분한데 할당이 실패
캐시 미스객체들이 메모리 여기저기 흩어짐매 프레임 전부 순회하는데 순회 자체가 느려짐
GC 압력(C#/Unity) 죽은 객체가 쌓여 수집기를 깨움수집이 도는 프레임만 통째로 튐
캐시 미스가 왜 그렇게 큰가는 B-1 배열 vs 연결 리스트, GC 압력은 D-2 가비지 컬렉션에서 다룬다.

2. 해법의 원리 — 만들지 말고 빌려 쓴다

오브젝트 풀의 발상은 한 문장이다.

오브젝트 풀

필요한 만큼의 객체 자리를 미리 한 번에 확보해두고, 런타임에는 만들고 지우는 대신 빌려주고 돌려받는다. 객체는 죽지 않는다 — 다만 "지금 쓰이는 중"과 "지금 노는 중" 사이를 오갈 뿐이다.

그러면 앞의 네 가지 비용이 이렇게 바뀐다.

  • 할당 시간 → 목록에서 하나 떼어내는 포인터 조작 몇 줄. 항상 같은 시간.
  • 단편화 → 슬롯 크기가 전부 같으므로 구멍이 생기지 않는다. 반납한 자리는 정확히 다음 대여자가 쓴다.
  • 캐시 미스 → 한 덩어리 버퍼에 몰아넣으면 순회가 연속 메모리 접근이 된다.
  • GC 압력 → 쓰레기가 아예 안 생긴다.

이 기법이 성립하는 전제

풀은 공짜가 아니다. 성립하려면 동시에 존재할 수 있는 개수의 상한을 미리 알아야 한다. 그런데 게임에서는 이게 대체로 알 수 있다 — 아니, 알아야만 한다. "탄이 무한히 늘어날 수 있는 게임"은 언젠가 반드시 프레임이 무너지기 때문에, 상한을 정하는 것 자체가 이미 올바른 게임 설계다.

게임 설계와 맞물리는 지점

풀 크기는 기술적 결정처럼 보이지만 실제로는 기획 수치다. "동시 탄 5000발"은 곧 "이 게임에서 화면에 나올 수 있는 최대 탄 수"라는 게임 규칙이다. 풀이 다 찼을 때 무엇을 할지(발사 무시 / 가장 오래된 탄 재활용 / 풀 증설)도 마찬가지로 기획 결정에 가깝다.

3. 풀 설계의 세 가지 축

세상의 모든 오브젝트 풀은 아래 세 축의 조합으로 설명된다. 구현을 외울 필요는 없고, "이 풀은 어느 조합인가"를 읽어낼 수 있으면 된다.

축 1 — 저장소: 한 덩어리인가, 흩어져 있는가

연속 버퍼 방식개별 할당 방식
구조큰 배열 하나를 슬롯 크기로 자름객체를 미리 new해서 목록에 담아둠
순회 성능좋음 — 연속 접근, 캐시 친화적나쁨 — 주소가 흩어짐
슬롯 크기가장 큰 타입에 맞춰 고정 → 낭비 발생타입별 실제 크기
구현 난이도높음 — 정렬, 생성/소멸 시점을 직접 관리낮음
대표 사례C++ 엔진의 커스텀 할당자, 아래 TTTUnity에서 흔히 쓰는 Queue<GameObject> 풀

축 2 — 가용 목록: 빈 자리를 어떻게 O(1)에 찾는가

가장 흔한 세 가지다.

  • 프리 리스트(free list) — 노는 슬롯들을 서로 연결해 사슬로 만든다. 핵심 트릭: 노는 슬롯의 내용은 어차피 쓸모없으므로, 그 공간 자체를 다음 슬롯을 가리키는 포인터로 재사용한다. 별도 관리용 메모리가 0바이트로 끝난다.
  • 인덱스 스택 — 비어 있는 슬롯 번호를 스택에 쌓아둔다. 이해하기 쉽고 디버깅이 편하다.
  • 비트맵 — 슬롯마다 1비트로 사용 여부를 표시. 메모리는 가장 적지만 빈 자리 찾기가 O(n/64)이라 대여가 잦으면 불리하다.

축 3 — "지금 살아있는 것들"의 순회

풀에서 놓치기 쉬운 축이다. 대여는 빨라졌는데 "살아있는 것만 골라 매 프레임 갱신"이 느리면 아무 의미가 없다. 방법은 둘로 갈린다.

  • 전체 순회 + 플래그 검사 — 슬롯 전부를 돌면서 if (!alive) continue;. 단순하지만 5000개 중 10개만 살아있어도 5000번 돈다. 대신 접근이 완전히 연속적이라 의외로 빠를 때가 많다.
  • 활성 목록 유지 — 살아있는 것만 따로 연결 리스트로 묶는다. 순회량은 정확히 살아있는 수만큼이지만, 포인터를 따라가므로 캐시 지역성은 포기한다.

아래에서 볼 TTT는 연속 버퍼 + 프리 리스트 + 활성 리스트, 즉 각 축에서 "고전적인 C++ 방식"을 하나씩 고른 조합이다.

4. 실물 해부 — TTT 프레임워크의 구조

이 코드의 출처

바탕화면 TTT/에 있는 탄막 슈팅 게임의 오브젝트 관리 뼈대다. 소스 타임스탬프는 2024-03이고, 빌드 산출물에 남은 원본 경로가 c:\users\dnvmf\onedrive\project\wooprogameproject\...(다른 사용자 계정, VS2019 툴셋)라 외부에서 받은 예제로 보인다. 이후 C:\Study\TTT에서 VS2022 툴셋으로 다시 빌드한 흔적이 있다.

코드 곳곳에 std::cout << "New", "테스크 생성" 같은 추적 출력이 박혀 있는데, 게임에 필요한 코드가 아니라 "이 함수가 언제 불리는지 눈으로 확인하려고" 넣은 학습 흔적이다. 실제로 이 프레임워크는 호출 순서가 헷갈리기 쉬운 구조라, 이렇게 찍어보는 접근 자체는 정확한 판단이었다.

여기서 읽어야 할 설계 판단이 네 가지다.

판단 1 — 슬롯을 객체가 아니라 바이트 덩어리로 잡는다

버퍼는 char 배열이다. 즉 프로그램 시작 시점에 만들어지는 것은 객체가 아니라 "객체가 들어갈 크기의 빈 공간"뿐이다. 생성자는 실제로 빌려 갈 때 비로소 돌고, 소멸자는 반납할 때 돈다.

이건 "객체를 미리 다 만들어두고 껐다 켠다"는 흔한 방식(Unity의 SetActive 풀)과 결정적으로 다른 선택이다. 미리 만들어두는 방식은 구현이 쉽지만, 객체가 죽은 상태로도 계속 살아있어서 이전 사용자의 값이 남는 문제가 생긴다. 바이트 덩어리 방식은 매번 생성자가 돌기 때문에 항상 깨끗한 초기 상태로 시작한다.

판단 2 — 리스트를 두 개로 나눈다

활성 리스트는 매 프레임 순회 대상이라 앞뒤로 오갈 수 있어야 하고(삭제할 때 이전 노드가 필요하다), 프리 리스트는 "아무거나 하나 꺼내고 아무 데나 도로 넣는" 용도라 한 방향이면 충분하다. 그래서 활성은 이중 연결, 프리는 단방향이다. 필요한 만큼만 자료구조를 쓴 것이다.

판단 3 — Prev == NULL을 "지금 노는 중" 표식으로 겸용한다

슬롯마다 "사용 중/노는 중" 플래그를 따로 두지 않는다. 프리 리스트에 들어간 노드는 Prev를 쓸 일이 없으므로, 그 자리를 NULL로 두고 그 자체를 상태 표식으로 재사용한다. 실제로 반납 함수에 이런 검사가 있다.

void CTaskList::Delete(void* p) {
    CTask* task = (CTask*)p;
    assert(task->Prev != NULL);   // Prev가 NULL이면 이미 반납된 것 → 이중 반납 탐지
    task->Prev = NULL;            // 반납 표시
    task->Next = FreeTask->Next;  // 프리 리스트 맨 앞에 끼움
    FreeTask->Next = task;
}

메모리 한 바이트도 더 쓰지 않고 이중 반납(double free)이라는 대표적 버그를 잡아내는 장치가 생겼다. "이미 있는 필드의 의미 없는 상태를 표식으로 쓴다"는 건 저수준 코드에서 자주 보는 관용구다.

판단 4 — 센티넬 노드로 경계 분기를 없앤다

슬롯 0과 1은 실제 데이터가 아니라 머리 역할만 하는 가짜 노드다. 덕분에 "리스트가 비어 있는가", "맨 앞인가", "맨 뒤인가" 같은 특수 케이스가 코드에서 사라진다. 삽입은 언제나 "어떤 노드 앞에 끼운다", 삭제는 언제나 "앞뒤를 이어준다"로 통일된다.

센티넬 패턴 자체의 원리와 없을 때 코드가 어떻게 복잡해지는지는 B-1 배열 vs 연결 리스트에서 다룬다. 내 실습 코드의 다른 사례는 cpp_핵심정리.md 19번(cDouble_LinkedList)에도 있다.

대여와 반납의 실제 비용

void* CTaskList::New(size_t size) {
    assert(size <= TaskSize);
    if (FreeTask->Next == FreeTask) return NULL;  // 다 찼다
    CTask* task = FreeTask->Next;
    FreeTask->Next = task->Next;                  // 사슬에서 떼어냄
    return task;
}

비교 한 번, 대입 두 번. 힙 탐색도, 시스템 콜도, 락도 없다. 어떤 상황에서 호출해도 걸리는 시간이 같다 — 1절에서 말한 "예측 불가능성"이 사라졌다는 뜻이고, 이게 풀을 쓰는 진짜 이유다.

5. 할당 경로 바꿔치기 — operator new 오버로딩

풀을 만들었으면 이제 CBullet이 풀에서 태어나게 해야 한다. 방법은 둘이다.

  1. 팩토리 함수를 만들어 BulletPool.Create(...)처럼 부른다 — 명시적이지만 호출부 코드가 전부 바뀐다.
  2. new CBullet(...)이라는 문법은 그대로 두고, 그 안에서 메모리를 어디서 가져올지만 바꿔치기한다.

C++은 2번을 언어 차원에서 지원한다. 이게 클래스별 operator new 오버로딩이다.

먼저: new라는 키워드는 사실 두 가지 일이다

여기서 operator new는 "메모리를 어디서 가져올까"만 담당하는 함수다. 객체 생성과는 아무 상관이 없다. 그래서 이걸 클래스마다 다시 정의하면 "이 클래스는 이 풀에서 태어난다"를 선언할 수 있다.

class CBullet : public CMover {
public:
    void* operator new(size_t n);      // 이 클래스 전용 메모리 공급처
    void  operator delete(void* p);
};

void* CBullet::operator new(size_t n) { return BulletList->New(n); }
void  CBullet::operator delete(void* p) {        BulletList->Delete(p); }

이제 게임 코드 어디서든 그냥 new CBullet(...)이라고 쓰면 되고, 호출부는 풀의 존재를 전혀 몰라도 된다. 나중에 할당 전략을 바꿔도 호출부는 그대로다.

꼭 알아야 할 규칙 네 가지
  • 클래스 안에 쓴 operator new/delete는 static을 안 붙여도 자동으로 정적 멤버다. 객체가 아직 없는 시점(또는 이미 사라진 시점)에 불리므로 당연히 그래야 한다.
  • 파생 클래스가 상속받는다. 재정의하지 않으면 부모 것이 쓰인다 — 이건 편리하면서 동시에 부모 풀에 자식이 들어가버리는 버그의 원인이 된다.
  • 인자 size_t n은 컴파일러가 실제 생성할 타입의 크기를 넣어준다. 부모 것을 상속받아 쓰면 자식 크기가 들어온다.
  • 배열 new[] / delete[]는 완전히 별개의 함수다. 풀 방식에서는 보통 쓰지 않는다.

기반 클래스의 operator new를 막아두는 이유

TTT의 CTask는 operator new를 private으로 선언해뒀다. 얼핏 이상해 보이지만 의도가 분명하다 — "CTask나 CMover를 직접 new하지 마라. 어느 풀에 넣을지 정해지지 않았으니까."라는 봉인이다. 실제로 풀은 CMyShip·CEnemy·CBullet 세 개로 나뉘어 있고, 어느 것에도 속하지 않는 중간 클래스를 직접 만드는 건 말이 안 된다.

다만 봉인하는 방법이 낡았다. 지금이라면 이렇게 쓴다.

// TTT의 방식 — 본문이 비어 있어 값을 반환하지 않는다 (호출되면 정의되지 않은 동작)
void* operator new(size_t n) {}

// C++11 이후의 정석 — 호출 자체를 컴파일 에러로 만든다
void* operator new(size_t) = delete;

TTT 코드가 지금까지 문제없이 돌아간 건 그 함수가 한 번도 호출되지 않았기 때문이다. 호출되지 않으면 컴파일러가 코드를 생성하지 않고, 그래서 "값을 반환하지 않음" 경고조차 뜨지 않는다. "경고가 없다 = 안전하다"가 아니라는 좋은 예다.

빠져 있는 조각 — placement new

풀 방식에는 원래 짝이 되는 문법이 하나 더 있다. 이미 확보된 메모리 위에 객체만 생성하는 placement new다.

void* mem = pool.Allocate();     // 자리만 얻고
CBullet* b = new (mem) CBullet(...);   // 그 자리에 생성자만 돌린다
b->~CBullet();                    // 반납 전엔 소멸자를 직접 부른다
pool.Free(mem);

TTT는 operator new 오버로딩으로 같은 효과를 냈기 때문에 본체 객체에는 필요 없다. 문제는 센티넬 노드다. 센티넬은 버퍼의 원시 바이트를 CTask*로 캐스팅해서 멤버에 바로 접근하는데, 그 자리에서는 생성자가 한 번도 돌지 않았다. 언어 규칙상 아직 객체가 존재하지 않는 메모리를 객체처럼 다루는 셈이라 형식적으로는 미정의 동작이고, CTask가 가상 함수를 가진 클래스라 가상 함수 테이블 포인터가 초기화되지 않은 채로 남는다. 지금은 센티넬에 대해 가상 함수를 부르지 않아서 드러나지 않을 뿐이다.

6. 등록과 해제를 언어에 맡기기 — 생성자와 소멸자

객체를 만들었으면 활성 리스트에 넣어야 하고, 없앨 땐 빼야 한다. 이걸 호출부가 직접 하면 반드시 언젠가 빠뜨린다. TTT는 이 일을 기반 클래스의 생성자와 소멸자에 넣었다.

CTask::CTask(CTaskList* list) {          // 태어나면 자동으로 활성 리스트에 등록
    Prev = list->ActiveTask->Prev;
    Next = list->ActiveTask;
    Prev->Next = Next->Prev = this;
}
CTask::~CTask() {                        // 죽으면 자동으로 빠짐
    Prev->Next = Next;
    Next->Prev = Prev;
}
여기서 얻는 보장

"객체가 살아있다"와 "리스트에 들어있다"가 같은 뜻이 된다. 둘이 어긋날 방법이 없다 — 생성자를 건너뛰고 객체를 만들 수는 없기 때문이다. 등록을 깜빡하는 버그, 해제를 깜빡하는 버그가 존재할 수 없는 구조가 된다.

이게 C++의 RAII(Resource Acquisition Is Initialization) 사고방식이다. 흔히 "메모리·파일·락을 자동으로 해제하는 기법"으로만 소개되지만, 본질은 더 넓다 — "어떤 상태를 객체의 수명에 묶어서, 언어가 강제하게 만든다"이다. 여기서 묶은 자원은 메모리가 아니라 리스트 멤버십이다.

RAII의 일반 원리와 소멸자 호출 시점(스택 풀림 포함)은 A-4 객체지향의 메모리 모델에서 다룬다.
Unity에서는 이 자리에 무엇이 오는가

C#에는 결정적 소멸자가 없어서 같은 방식을 못 쓴다. 대신 Unity는 OnEnable/OnDisable이 그 역할을 한다 — 오브젝트를 켤 때 매니저에 등록하고 끌 때 해제하는 패턴이 Unity 풀링 코드의 표준 관용구인 이유가 이것이다. 다만 C++의 소멸자와 달리 "반드시 불린다"는 보장이 약하다 (씬 전환, 애플리케이션 종료 순서 등). 자세한 차이는 C-3에서 다룬다.

7. 순회 도중의 삭제 — 게임 루프의 고질적 문제

게임 루프의 뼈대는 늘 같다.

살아있는 것 전부에 대해:
    갱신한다
    죽었으면 목록에서 뺀다

문제는 "목록을 순회하는 도중에 목록이 바뀐다"는 것이다. 그것도 남이 바꾸는 게 아니라 순회 중인 그 코드 자신이 바꾼다. 탄이 적을 맞히면 탄과 적이 동시에 죽고, 적이 죽으면서 폭발 이펙트를 새로 만들기도 한다.

왜 위험한가 — 반복자 무효화

지금 가리키고 있는 노드를 지워버리면, 다음으로 넘어갈 때 참조할 Next가 이미 해제된 메모리가 된다. 배열이었다면 원소를 지운 순간 뒤의 것들이 앞으로 밀려 한 개를 건너뛰고 지나가는 조용한 버그가 생긴다. 이걸 반복자 무효화(iterator invalidation)라 한다.

언어마다 대처가 다르다.

  • C++ STL — erase()가 다음 유효한 반복자를 반환한다. 받아쓰지 않으면 그대로 터진다.
  • C# — foreach 도중 컬렉션을 수정하면 InvalidOperationException을 던져 알려준다.
  • 직접 만든 리스트 — 아무도 안 알려준다. 알아서 설계해야 한다.

TTT의 해법 — 커서를 한 칸 물리고 지운다

void CTaskIter::Remove() {
    Task = Task->Prev;      // 커서를 이전 노드로 되돌리고
    delete Task->Next;      // 방금까지 보고 있던 노드를 지운다
}

이 두 줄이 성립하는 건 앞의 설계 판단들이 전부 맞물려 있기 때문이다 — 센티넬이 있어서 A가 첫 노드여도 Prev가 항상 유효하고, 소멸자가 알아서 앞뒤를 이어주며, 가상 소멸자라서 delete가 실제 타입(CBullet 등)의 소멸자와 그 타입의 operator delete를 정확히 호출해 올바른 풀로 되돌린다.

여기서 가상 소멸자가 없다면

CTask*로 delete했을 때 CBullet의 소멸자가 불리지 않고, operator delete도 CTask의 것(비어 있는 그 함수)이 불려서 탄이 영원히 프리 리스트로 돌아오지 못한다. 몇 초 만에 풀이 고갈되고 탄이 안 나가기 시작한다. "가상 소멸자를 왜 쓰나"라는 면접 질문에, 교과서적인 "파생 클래스 소멸자가 안 불려서요" 대신 이 시나리오를 말할 수 있으면 완전히 다른 답변이 된다.

다른 해법들 — 실무에서 더 흔한 것들

방식동작장단점
죽음 플래그 + 사후 정리 순회 중엔 alive=false만 찍고, 루프가 끝난 뒤 한 번에 정리 가장 안전하고 가장 흔하다. 삭제가 프레임 경계로 미뤄져 동작이 예측 가능해진다
뒤에서 앞으로 순회 배열을 for (i = n-1; i >= 0; --i)로 돈다 배열에서 밀림 문제가 사라진다. 순서가 중요하면 못 쓴다
지연 삭제 큐 삭제 요청을 큐에 넣고 안전한 시점에 비운다 여러 시스템이 서로를 죽이는 복잡한 경우의 정석
커서 후퇴 (TTT) 즉시 삭제하되 반복자가 스스로 보정 즉시성이 필요할 때 우아하다. 다만 "남을 죽이는" 경우는 못 막는다

마지막 줄이 중요하다. TTT 방식은 자기 자신을 지우는 것은 안전하게 처리하지만, 순회 중인 객체가 리스트의 다른 객체를 지우는 경우는 여전히 커서를 무효화할 수 있다. 탄이 적을 맞히는 순간이 정확히 그 상황이다. 그래서 실무에서는 위의 "죽음 플래그 + 사후 정리"가 기본값이다.

8. 다형성으로 루프를 단순하게, 그리고 그 대가

TTT의 상속 계층은 CTask → CMover → { CMyShip, CEnemy, CBullet }이다. CTask는 풀에 들어갈 수 있음을, CMover는 화면에서 움직임(위치·각도·크기·색)을 담당한다. 덕분에 게임 루프가 이렇게 짧아진다.

for (CTaskIter i(list); i.HasNext(); ) {
    CMover* m = static_cast<CMover*>(i.Next());
    m->Move();                  // 실제로 뭐가 움직이는지 루프는 모른다
    if (!m->Alive) i.Remove();
}

루프는 자기가 다루는 게 함선인지 적인지 탄인지 모르고, 알 필요도 없다. 새 적 타입을 추가해도 이 루프는 한 글자도 바뀌지 않는다. 이것이 다형성이 실제로 값을 하는 자리다 — 교과서의 Animal→Dog/Cat 예제보다 이 게임 루프가 훨씬 정직한 예시다.

대가 세 가지

  • 간접 호출 — Move()가 어느 함수인지 실행 시점에 표(vtable)를 뒤져서 결정한다. 포인터를 한 번 더 따라간다.
  • 인라인 불가 — 컴파일러가 호출 대상을 모르니 함수 본문을 펼쳐 넣을 수 없다. 짧은 함수일수록 손해가 크다.
  • 분기 예측 실패 — 매 반복마다 다른 타입이 섞여 나오면 CPU가 다음에 실행할 코드를 못 맞힌다. 이게 셋 중 제일 비싸다.
vtable이 실제로 어떻게 놓이고 호출 비용이 왜 발생하는지는 A-4 객체지향의 메모리 모델에서 다룬다.
그래서 요즘 엔진들은 왜 ECS로 가는가

위 세 가지 대가는 객체 하나에 데이터와 동작이 붙어 있고, 서로 다른 타입이 한 리스트에 섞여 있다는 구조에서 나온다. 대안은 발상을 뒤집는 것이다 — 타입별로 모으고, 데이터만 배열로 늘어놓고, 그 배열 전체를 한 함수가 처리한다.

그러면 가상 호출이 사라지고, 메모리 접근이 완전히 연속적이 되고, 분기 예측이 항상 맞는다. 이것이 데이터 지향 설계(DOD)이고 Unity DOTS/ECS가 하는 일이다. "객체지향이 틀렸다"가 아니라, 수만 개를 매 프레임 도는 상황에서는 하드웨어 사정이 설계를 바꾼다는 이야기다. TTT 정도의 규모(수천 개)에서는 가상 함수 방식이 여전히 합리적이다.

static_cast가 여기서 안전한 이유

리스트에서 꺼낸 CTask*를 CMover*로 검사 없이 내리꽂는다. 안전한 유일한 근거는 "이 리스트에는 CMover 계열만 들어간다"는 규약뿐이다. 언어가 보장해주는 게 아니라 사람이 지키기로 한 약속이다. 누군가 CMover를 상속하지 않은 태스크를 같은 리스트에 넣는 순간, 조용히 깨진다.

더 안전하게 가려면 dynamic_cast(실행 시간 검사, 비용 있음)를 쓰거나, 애초에 리스트를 타입으로 묶는다(CTaskList<CMover> 같은 템플릿). 템플릿 방식이 비용 0에 컴파일 타임 보장까지 얻는 정석이고, TTT가 개선될 수 있는 지점이다.

9. 요즘은 어떻게 하는가 — 업계 표준과 Unity

지금까지 본 TTT는 2000년대 C++ 게임 코드의 전형이다. 원리를 이해하는 데는 이만한 교재가 없지만, 지금 실무에서 이걸 손으로 다시 짜는 일은 거의 없다. 같은 문제를 오늘날에는 어떻게 푸는지를 알아야 "옛날 방식을 이해했다"가 아니라 "왜 지금 방식이 그렇게 생겼는지 안다"가 된다.

C++ 진영 — 손으로 짜던 것이 표준으로 들어왔다

TTT가 손으로 만든 "미리 잡아둔 버퍼에서 잘라 쓰기"는 C++17에서 <memory_resource> (줄여서 PMR)라는 이름으로 표준에 들어왔다.

char buffer[1 << 20];                                   // 1MB를 미리 잡아두고
std::pmr::monotonic_buffer_resource arena{buffer, sizeof(buffer)};
std::pmr::vector<Bullet> bullets{&arena};              // 표준 컨테이너가 이 버퍼에서 할당받는다
// ... 한 프레임 동안 마음껏 쓰고
arena.release();                                       // 프레임 끝에 통째로 되돌린다 — 개별 해제 없음

핵심은 monotonic_buffer_resource가 개별 해제를 아예 하지 않는다는 점이다. 할당은 포인터를 앞으로 밀기만 하고(그래서 범프 할당자라 부른다), 되돌릴 때는 통째로 되돌린다. 게임의 "이번 프레임에만 쓸 임시 데이터"에 정확히 맞는 모양이라 프레임 할당자(frame allocator) 또는 아레나(arena)라는 이름으로 거의 모든 상용 엔진이 갖고 있다.

수명이 제각각인 객체에는 std::pmr::unsynchronized_pool_resource가 크기별 풀을 만들어준다 (이름의 unsynchronized는 "락을 안 건다 = 한 스레드 전용"이라는 뜻이다). 어느 쪽이든 표준 컨테이너를 그대로 쓰면서 할당처만 바꾼다 — 5절에서 본 operator new 바꿔치기와 목적이 같고, 방식이 더 안전하다.

그다음 단계 — 풀링을 넘어 배치로

8절에서 말한 데이터 지향 설계가 여기서 이어진다. 풀은 "객체 하나하나를 재사용"하는 데서 멈추지만, ECS는 "같은 종류를 배열로 모아 통째로 처리"한다. C++ 쪽에서는 EnTT·flecs(둘 다 스파스 셋 기반), Unity 쪽에서는 DOTS/ECS가 같은 방향이다. 풀링이 할당 비용을 없앤 기법이라면, ECS는 거기에 더해 캐시 미스와 가상 호출까지 없앤다. 순서가 이렇다는 걸 알면 "왜 ECS가 나왔나"에 답할 수 있다.

Unity — 엔진이 이미 만들어서 준다

먼저 Unity에서 왜 더 절실한가부터. Instantiate() 한 번은 C++ 쪽 네이티브 객체 생성, C# 래퍼 객체 생성, 컴포넌트 초기화, 씬 등록을 전부 한다. Destroy()는 그 자리에서 지우지도 않는다 — 현재 프레임이 끝난 뒤에 처리되고, 남은 C# 쓰레기는 나중에 GC가 치운다. 그 GC가 도는 프레임이 통째로 튄다. 1절의 "예측 불가능한 최악값" 문제가 C++보다 더 심하게 나타난다.

Unity의 GC가 왜 특히 나쁜 방식(비세대별·비압축)인지는 D-2 가비지 컬렉션에서 다룬다.

1세대 — 직접 만드는 SetActive 풀

오랫동안 표준이었던 방식이다. 미리 Instantiate해서 전부 꺼두고, 필요하면 켜고, 다 쓰면 끈다. 4절의 "판단 1"에서 말한 "객체를 미리 다 만들어두는 방식"이 이것이다.

2세대 — UnityEngine.Pool.ObjectPool<T> (Unity 2021 LTS 이후 내장)

직접 짤 필요가 없어졌다. 콜백 네 개만 주면 된다.

_pool = new ObjectPool<Bullet>(
    createFunc:      () => Instantiate(prefab),     // 풀이 비었을 때 새로 만드는 법
    actionOnGet:     b  => b.Activate(),            // 빌려줄 때
    actionOnRelease: b  => b.Deactivate(),          // 돌려받을 때
    actionOnDestroy: b  => Destroy(b.gameObject),   // 풀이 꽉 차서 버릴 때
    collectionCheck: true,
    defaultCapacity: 100,
    maxSize:         1000);

var bullet = _pool.Get();     // 대여
_pool.Release(bullet);        // 반납
공식 문서에서 확인해야 할 네 가지
  • maxSize를 넘겨 반납하면 그 객체는 파괴된다. 풀이 무한히 커지지 않게 하는 안전장치다 (2절 "다 찼을 때의 정책" 중 거절에 해당).
  • collectionCheck는 에디터에서만 동작한다. 이미 풀에 있는 객체를 또 반납하면 예외를 던져 알려주는데, 플레이어 빌드에서는 이 검사가 아예 없다. 4절의 assert(Prev != NULL)와 똑같은 이중 반납 탐지이고, 똑같이 개발 중에만 켜지는 장치다.
  • 스레드 안전하지 않다. 메인 스레드에서만 호출해야 한다.
  • 컬렉션 전용 풀도 있다 — ListPool<T>, HashSetPool<T>, DictionaryPool<K,V>. 매 프레임 임시 List를 새로 만드는 코드가 만드는 쓰레기를 없애는 용도라 실전에서 의외로 이쪽이 더 자주 쓰인다.

Unity 풀링의 진짜 함정 — 더러운 상태

표의 세 번째 줄이 실무에서 사고가 나는 지점이다. C++ 방식은 대여할 때마다 생성자가 돌아서 항상 깨끗한 상태로 시작한다. Unity 방식은 같은 객체를 계속 재사용하므로 이전 사용자가 남긴 값이 그대로 남아 있다.

실제로 자주 남는 것들: Rigidbody의 속도·각속도, 돌던 코루틴, TrailRenderer/ParticleSystem의 잔상, Animator의 현재 상태, 구독해둔 이벤트, 바뀐 부모·스케일, 진행 중이던 타이머.

그래서 actionOnGet에 "켜기"만 쓰면 안 되고 "되돌리기"를 써야 한다. 6절에서 본 "상태를 객체 수명에 묶어 언어가 강제하게 만든다"는 보장이 C#에는 없기 때문에, 그 책임이 사람에게 넘어온 것이다. 이 한 문장이 C++ 풀과 Unity 풀의 차이 전부다.

업계에서 통하는 판단 기준 — 언제 풀링을 하지 않는가

풀링은 공짜가 아니다. 코드가 복잡해지고, 상태 리셋이라는 새로운 버그 종류가 생기고, 메모리를 미리 붙잡는다. Unity 공식 문서도 생성이 드물거나 가벼우면 쓰지 말라고 명시한다.

  • 쓴다 — 탄·적·이펙트·데미지 텍스트·발소리처럼 짧게 살고 자주 태어나는 것
  • 안 쓴다 — 스테이지에 한 번 놓이는 오브젝트, 생성 비용이 미미한 것, 개수 상한을 못 정하는 것
  • 먼저 잰다 — 프로파일러로 Instantiate/GC가 실제 병목인지 확인하고 나서 넣는다. "풀링은 무조건 좋다"는 태도 자체가 신입 티가 나는 지점이다
면접에서의 차이

"오브젝트 풀링 아세요?"에 "Instantiate가 비싸서 미리 만들어두고 SetActive로 껐다 켭니다"라고 답하면 딱 평균이다. 여기에 "재사용이라 이전 상태가 남는 게 실제 문제라서 Get 시점에 리셋을 명시적으로 합니다. 2021부터는 UnityEngine.Pool이 내장돼 있어서 직접 안 짜고, collectionCheck는 에디터에서만 도는 점을 알고 씁니다"까지 붙으면 완전히 다른 답변이 된다.

10. 이 코드에서 실제로 발견한 결함

공부용 예제라도 결함을 짚어내는 연습이 중요하다. 아래는 실제 소스를 읽고 확인한 것들이며, 위쪽일수록 심각하다.

① 슬롯 크기 100이 정렬을 깨뜨린다 — 가장 심각

세 리스트 모두 슬롯 크기를 100바이트로 잡았다. 그런데 실제로 재보면 이렇다.

클래스실제 크기정렬 요구슬롯 100 대비
CTask24 B8—
CMover / CEnemy56 B844 B 낭비 (44%)
CMyShip64 B836 B 낭비 (36%)
CBullet72 B828 B 낭비 (28%)

(MSVC x64, 실제 컴파일해서 측정)

낭비도 문제지만 진짜 문제는 100이 8의 배수가 아니라는 것이다. 슬롯 i의 주소는 버퍼 + 100 × i이므로, 홀수 번째 슬롯은 전부 4바이트만큼 어긋난다. 그 자리에 8바이트 정렬을 요구하는 포인터와 가상 함수 테이블 포인터가 놓인다.

x64에서는 어긋난 접근도 동작은 하지만(느릴 뿐) 언어 규칙상 미정의 동작이고, SIMD 타입(DirectX::XMVECTOR 등, 16바이트 정렬 필요)을 멤버로 추가하는 순간 즉시 크래시한다. 게임 수학 타입은 거의 다 그렇다.

// 고치는 법 — 슬롯 크기를 타입에서 뽑고, 정렬 배수로 올림한다
CTaskList(size_t count) : TaskSize(AlignUp(sizeof(T), alignof(T))), ...

덧붙여, 세 리스트를 타입별로 나눠놓고도 크기는 셋 다 100으로 똑같이 준 것은 분리의 이점을 절반 버린 셈이다. BulletList는 5000개 × 100B = 약 489KB인데, 72B로 맞췄다면 352KB로 줄고 정렬 문제도 같이 사라진다.

② 아무것도 죽지 않는다

게임 루프에는 if (!mover->Alive) i.Remove();가 있는데, 소스 전체에서 Alive를 false로 만드는 코드가 없다. 생성자에서 true로 켜고 끝이다. 즉 이 프레임워크는 죽음 처리를 위한 자리는 다 만들어놨지만 아직 아무도 죽지 않는 미완성 상태다.

③ 적과 탄은 만들어만 놓고 쓰지 않는다

EnemyList와 BulletList는 생성만 되고 게임 루프가 손대지 않는다. CBulletGame::Move()는 MyShipList 하나만 돈다. CBullet::Move()와 CMover::Move()의 본문도 비어 있다.

④ 풀이 다 찼을 때 조용히 널을 반환한다

CTaskList::New는 자리가 없으면 NULL을 반환한다. 그런데 C++ 규약상 noexcept가 붙지 않은 operator new는 널을 반환하면 안 된다 — std::bad_alloc을 던져야 한다. 널을 돌려주는 건 std::nothrow_t 버전의 몫이다.

그럼 실제로 무슨 일이 일어나는가? 컴파일러마다 다르다는 게 정확한 답이다. MSVC는 옛날 코드를 배려해 기본적으로 생성자 호출 전에 널 검사를 넣어준다 (/Zc:throwingNew-가 기본값). 그래서 이 코드는 크래시하지 않고 new CMyShip(5)가 생성자를 건너뛴 채 nullptr을 반환한다. 그런데 TTT의 호출부는 그 반환값을 받지도 검사하지도 않는다 — 탄이 조용히 안 나가고, 아무도 이유를 모른다.

/Zc:throwingNew를 켜서 최적화하거나(그러면 널 검사가 사라져 진짜로 널 위에서 생성자가 돈다), 표준을 그대로 지키는 다른 컴파일러로 옮기면 같은 코드가 크래시로 바뀐다. "내 환경에서 잘 돌아간다"가 안전을 뜻하지 않는 전형적인 예다.

고치는 방향은 둘이다. 규약대로 예외를 던지거나(throw std::bad_alloc{}), 아예 operator new를 쓰지 않고 실패를 반환값으로 표현하는 팩토리로 바꾸는 것. 게임에서는 후자가 대체로 낫다 — 탄 하나 못 쏘는 걸 예외로 처리할 이유가 없다. 2절의 "다 찼을 때의 정책"이 결국 여기서 코드로 결정된다.

교차검증으로 바로잡은 서술

이 항목은 처음에 "컴파일러가 널 검사를 넣어주지 않으므로 즉시 크래시한다"고 적었다가, Microsoft 공식 문서를 확인해 고쳤다. MSVC의 기본값은 정반대다 — "컴파일러는 이 코드가 규약을 지키지 않는 할당자와 링크될지 알 수 없기 때문에, 기본적으로 생성자 호출 전에 널 검사를 생성한다"고 명시되어 있다. 실패 양상이 '크래시'가 아니라 '조용한 무동작'이라는 건 완전히 다른 이야기라 그대로 뒀다면 잘못 외울 뻔했다.

⑤ 리스트 소멸 시 살아있는 객체의 소멸자가 불리지 않는다

CTaskList::~CTaskList() { delete[] Buffer; }   // 버퍼만 반납

지금은 모든 태스크가 단순한 값 멤버만 가져서 문제가 안 되지만, 파생 클래스가 std::string이나 별도 힙 자원을 들고 있게 되는 순간 그대로 누수다. 활성 리스트를 한 바퀴 돌며 delete한 뒤 버퍼를 반납해야 한다.

⑥ 봉인용 operator new가 값을 반환하지 않는다

5절에서 다룬 그 문제다. = delete로 바꾸면 컴파일 타임에 막힌다.

⑦ 센티넬이 생성되지 않은 메모리다

5절 마지막에서 다룬 문제. vtable 포인터가 초기화되지 않는다. placement new로 센티넬을 제대로 생성하거나, 연결 고리만 담은 가벼운 노드 구조체를 따로 두고 CTask가 그것을 포함하도록 바꾸는 게 정석이다.

⑧ main의 반환 타입이 void

실제 빌드 로그에 경고가 찍혀 있다 — warning C4326: 'main'의 반환 형식이 'int'이어야 하는데 'void'입니다. 표준 위반이며, 컴파일러에 따라 아예 에러다.

⑨ CMyShipCrash는 인스턴스를 만들 수 없다

CMyShip을 상속받아 피격 시 회전 연출을 담당하려던 클래스인데, 부모에 기본 생성자가 없고 자신도 생성자를 정의하지 않아 만들 방법이 없다. 설계 의도만 남고 미완성이다. (덧붙여 이런 "피격 상태"는 상속으로 표현하기보다 상태 값이나 컴포넌트로 두는 편이 낫다 — C-3 참고.)

⑩ 전역 MyShip 포인터가 정리되지 않는다

CMyShip 생성자가 전역 MyShip = this로 자기를 등록하는데, 소멸자에서 되돌리지 않는다. 함선이 파괴되면 해제된 메모리를 가리키는 전역 포인터가 남는다. 6절의 RAII 원칙을 여기에도 적용해야 했다.

이 목록을 면접에서 쓰는 법

"공부한 코드에서 문제를 찾아본 적 있나요"는 자주 나오는 질문이다. 이때 ⑧ 같은 문법 실수를 말하면 인상이 약하다. ①번(정렬)을 말해야 한다 — "슬롯 크기가 8의 배수가 아니라서 홀수 슬롯의 포인터 정렬이 깨져 있었고, 지금은 x64라 동작하지만 SIMD 타입을 쓰는 순간 크래시한다"는 설명은 메모리 레이아웃을 실제로 이해하고 있다는 증거가 된다.

11. 정리 — 이 장을 한 문단으로

30초로 말한다면

게임은 매 프레임 정해진 시간 안에 끝나야 하는데, new/delete는 힙 상태에 따라 걸리는 시간이 달라져서 프레임을 튀게 만듭니다. 그래서 필요한 만큼의 메모리를 시작할 때 한 덩어리로 잡아두고, 런타임에는 목록에서 떼었다 붙였다 하는 포인터 조작만으로 객체를 빌려주고 돌려받습니다. 이걸 오브젝트 풀이라고 하고, 할당 시간이 항상 일정해지는 게 핵심입니다. C++에서는 클래스별로 operator new를 재정의해서 호출부 코드를 바꾸지 않고 할당처만 풀로 바꿀 수 있고, 등록·해제는 생성자와 소멸자에 넣어 언어가 강제하게 만듭니다.

  • C-3 컴포넌트 구조와 업데이트 순서 — 상속 대신 조합, Unity 생명주기
